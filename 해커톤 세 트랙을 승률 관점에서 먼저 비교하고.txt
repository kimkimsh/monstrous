해커톤 세 트랙을 승률 관점에서 먼저 비교하고, 각각의 구체적 솔루션을 드릴게요.

트랙 선택 전략

승률은 본인 강점 × 1/(예상 참가팀 수) × 루브릭 달성 가능성으로 봐야 합니다.

트랙 2(Upstage)는 참가팀이 가장 많을 겁니다. 노코드 플랫폼이라 진입장벽이 낮고, 문제 예시(장학금·계약서·영수증 정산)까지 친절하게 주어져 있어서 비슷한 아이디어가 쏟아집니다. 기술 점수 30%는 다들 비슷하게 받을 테니 아이디어·기획 50%에서 갈리는데, 이건 운 요소가 큽니다.

트랙 3(에이전트 스쿼드)은 참가팀이 가장 적을 겁니다. Backend.AI + RNGD 환경 세팅 자체가 부담이고 벤치마크 성능이 안 나오면 그대로 망하니까요. 대신 시각화 25%가 무주공산입니다. 엔지니어링 팀 대부분이 이걸 마지막 1시간에 대충 만듭니다.

트랙 1(경북 공공데이터)이 지금 가장 유리해 보입니다. 지금까지 하신 작업 — 지저분한 실데이터 정규화, 강건성 처리, 배치 파이프라인, JSON 리포트, README 품질 — 이 인프라 루트 루브릭과 정확히 일치합니다. 게다가 대부분의 팀은 앱(루트 2)을 만들지 MCP 서버(루트 1)를 만들지 않습니다.

트랙 1 솔루션: 경북 재난 대응 MCP 서버

핵심 인사이트: "AI가 바로 쓸 수 있는 형태"는 API 래핑이 아닙니다. 한국 공공데이터의 진짜 문제는 행정동/법정동 코드 불일치, EUC-KR 인코딩, 기관마다 다른 날짜 포맷, 페이지네이션 제각각, 그리고 API가 수시로 죽는다는 것입니다. 여기를 정면으로 다루면 기술 완성도와 지속가능성을 동시에 먹습니다.

주제 추천: 산불. 2025년 3월 의성 발화 → 안동·청송·영양·영덕으로 번진 역대 최대 산불이 있었고, 경북은 고령화율과 소멸위험지역 비율이 전국 최고입니다. "대피 취약성"이라는 문제가 데이터로 명확히 잡힙니다.

MCP 도구 구성 예시:

get_fire_risk(지역) — 산림청 산불위험예보 + 기상청 풍속·습도
get_vulnerable_population(읍면동) — 고령자·1인가구 비율
find_shelters(좌표) — 행안부 대피소 + 접근 거리
assess_evacuation_gap(지역) — 위 셋을 합성한 취약 지점 산출

시연: "의성군 단밀면 오늘 산불 위험도와 고령자 대피 취약 지점은?"에 LLM이 근거 데이터와 함께 답하는 모습.

차별화 포인트 세 가지: ① 행정구역 코드 리졸버(같은 지명이 기관마다 다른 코드) ② 스냅샷 캐시 + 폴백 — 상류 API가 죽어도 도구가 동작 ③ 도구 설명(description)에 스키마·단위·갱신주기·한계를 명시해서 LLM이 오용하지 않게 하는 시맨틱 레이어. 세 번째는 실제로 MCP 품질을 가르는 부분인데 대부분 놓칩니다.

README만으로 실행되어야 한다는 조건이 명시되어 있으니, docker compose up 한 줄로 끝나게 만들고 API 키 없이도 캐시 데이터로 데모가 돌아가게 하세요. 프로토타입 보너스 10%도 여기서 확보됩니다.

트랙 2 솔루션: Upstage Document Agent

피해야 할 것: 영수증 정산, 장학금 서류. 문제 설명에 예시로 적혀 있으면 그건 이미 레드오션입니다.

추천 주제: 소상공인 정책자금 신청 자동화. 사업자등록증, 부가세과세표준증명, 임대차계약서, 4대보험 가입자명부를 한 번에 던지면 → 지원사업 자격 자동 판정 → 신청서 자동 작성까지. 서류가 스캔·도장·표가 섞인 실물이라 Parse가 반드시 필요하고, "이해를 넘어 실제 업무 처리"라는 요구를 정확히 충족합니다.

대안: 청년 전세사기 방지. 계약서 파싱 → 독소조항 탐지 → 등기부등본 대조 → 전세보증보험 가입 가능 여부 판정 → 확정일자·전입신고 체크리스트 생성. 사회적 임팩트 스토리가 강합니다.

기술 점수 30% 확보법: 네 에이전트(Parse/Classify/Extract/Instruct)를 필연적으로 다 쓰는 체인을 짜고, 반드시 webhook이나 REST로 외부 시스템(알림톡, 시트, 실제 서식 PDF 자동 채움)까지 연결하세요. 그리고 신뢰도 낮은 추출은 사람에게 확인 요청하는 분기를 넣으면 기획 완성도 점수까지 올라갑니다. 심사위원은 "이 서류가 깨끗한 PDF였으면 Upstage 안 써도 됐는데?"를 반드시 물어봅니다. 손글씨·도장·스캔 왜곡이 있는 실물 샘플로 데모하세요.

트랙 3 솔루션: 에이전트 스쿼드

스쿼드 설계: Localizer(파일 특정) → Analyzer(원인 추론) → Patcher(수정) → Verifier(테스트 실행) → Critic(리뷰), 그리고 Arbiter(포기 판정관). 문제 설명에 "언제 포기할지 결정하는 역할"이 명시되어 있다는 건 출제자가 이걸 중요하게 본다는 뜻입니다. 여기를 핵심 차별점으로 잡으세요.

효율 25% 확보법: 작은 모델로 1차 시도 → 실패 시에만 큰 모델로 에스컬레이션하는 라우팅, 시도별 예산 관리자, 실패 이력 캐시(같은 실수 반복 방지). 그리고 문제당 토큰·시간 비용을 측정해서 "해결당 비용"으로 리포트하세요. 성능만 보고하는 팀들 사이에서 확실히 눈에 띕니다.

시각화 25% — 여기가 진짜 승부처: 스포츠 중계 리플레이 메타포를 추천합니다. 에이전트를 선수로 보고 핸드오프를 패스맵으로, 타임라인은 스윔레인으로, 실패 지점은 히트맵으로. 실시간 스트리밍 + 종료 후 리플레이가 되면 심사위원이 직접 조작해볼 수 있어 압도적입니다. 최소 6시간은 여기에 배정하세요.

공통 우승 전략

루브릭을 문자 그대로 읽고, 각 항목에 대응하는 화면을 데모에 하나씩 배치하세요. 심사위원은 채점표를 보면서 듣습니다. "지속가능성"이 항목이면 라이선스·문서·유지보수 계획 슬라이드가 있어야 하고, "효율성"이 항목이면 비용 그래프가 있어야 합니다.

발표는 아키텍처가 아니라 문제 → 30초 데모 → 기술 순서로. 그리고 라이브 데모는 반드시 백업 영상을 준비하세요. 공공데이터 API는 발표 중에 잘 죽습니다.

추천을 하나로 좁히면 트랙 1의 인프라 루트입니다. 지금 하고 계신 작업과 스킬셋이 가장 잘 맞고, 경쟁 밀도가 낮으며, "우수 프로젝트는 경북도청 저장소로 이관"이라는 조건은 곧 심사위원이 실제로 운영 가능한 코드 품질을 본다는 뜻이라 강점이 그대로 점수가 됩니다.

다만 팀 구성에 따라 답이 달라집니다. 프론트엔드나 디자인이 강한 팀원이 있다면 트랙 3의 시각화 25%가 오히려 더 쉬운 먹잇감이고, 기획·발표가 강한 팀이라면 트랙 2도 해볼 만합니다. 팀 인원과 각자 강점을 알려주시면 트랙을 확정하고 시간대별 실행 계획까지 짜드릴게요.
