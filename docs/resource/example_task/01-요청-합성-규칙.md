# 01. judge가 요청을 만드는 규칙과 답을 읽는 규칙

이 문서의 내용은 전부 **121문항 실측으로 검증됐다.** 추측이 아니다.
포털이 문항마다 요청 바이트와 SHA-256을 같이 공개하므로 규칙을 재현해서 대조할 수 있고,
`tools/compose.py --verify`가 121개 전부에 대해 그 대조를 통과한다.

---

## 1. 요청 합성 규칙

포털 `/practice-sets/requests` 페이지 원문:

> For each item the judge takes your one-shot prompt for that track and:
> - replaces **every** occurrence of `{{TASK}}` with the item content shown on the item's page —
>   write the placeholder twice and you get the item twice;
> - normalises line endings, so `\r\n` and a lone `\r` become `\n` throughout;
> - strips trailing whitespace from the result;
> - appends a blank line, then the track's REQUIRED OUTPUT block verbatim, then a final newline.

식으로 쓰면 이렇다.

```
request = rstrip( normalise(prompt).replace("{{TASK}}", normalise(item_content)) )
        + "\n\n"
        + REQUIRED_OUTPUT_BLOCK
        + "\n"
```

### 실측 검증

121문항 전부에 대해 `task_content + "\n\n" + REQUIRED_OUTPUT + "\n"`이
서버가 배포하는 `request.txt`와 **바이트 단위로 일치**했다.
REQUIRED OUTPUT 블록은 **트랙당 정확히 하나**이고 문항마다 달라지지 않는다.

| 트랙 | REQUIRED OUTPUT 블록 크기 | 적용 문항 |
|---|---|---|
| coding | 819 바이트 | 20 |
| generic | 289 바이트 | 42 |
| math | 257 바이트 | 59 |

블록 원본은 `<track>/required_output.txt`에 바이트 그대로 들어 있다.

### 여기서 나오는 실무 규칙 셋

1. **`{{TASK}}`를 두 번 쓰면 문항이 두 번 들어간다.** coding 트랙에서 이 실수는 입력 토큰을 2배로 만든다.
2. **REQUIRED OUTPUT 블록은 어차피 뒤에 붙는다.** 프롬프트에서 형식을 다시 설명하는 건 토큰을 두 번 쓰는 것이다.
   보강하려면 짧게 한 줄로 족하고, 블록 전문을 복사해 넣을 이유는 없다.
3. **`{{TASK}}`는 프롬프트 맨 뒤에 둔다.** 앞쪽 지시문이 문항마다 같은 안정 프리픽스가 되어야
   prefix cache가 걸린다. 포털도 "긴 안정 프리픽스를 변하는 부분 앞에 두면 진짜 여유가 생긴다"고 안내한다.
   이 폴더의 `prompts/*.txt`가 전부 그 배치다.

## 2. 트랙별 REQUIRED OUTPUT

### math (257바이트)

```
=== REQUIRED OUTPUT ===
End your answer with a line of exactly this form:

FINAL ANSWER: \boxed{<answer>}

Put the final answer, and nothing else, inside \boxed{}.
If more than one appears, the last one is used.
Anything before it is ignored, not penalised.
```

### generic (289바이트)

```
=== REQUIRED OUTPUT ===
End your answer with a line of exactly this form:

ANSWER: <letter>

Replace <letter> with the single letter of the option you choose, and write nothing else
on that line.
If more than one appears, the last one is used.
Anything before it is ignored, not penalised.
```

### coding (819바이트)

```
=== REQUIRED OUTPUT ===
Your answer must contain a patch, written as SEARCH/REPLACE edit blocks between the two
patch markers:

*** PATCH START ***
path/to/file.py
<<<<<<< SEARCH
<the exact lines currently in the file>
=======
<the lines that replace them>
>>>>>>> REPLACE
*** PATCH END ***

Rules: one path line before every <<<<<<< SEARCH; repeat the three-marker block once per
edit; paths are relative to the repository root; SEARCH must be whole lines copied from
the file; an empty SEARCH section creates a new file.

Only what lies between *** PATCH START *** and *** PATCH END *** is graded.
If more than one appears, the last one is used.
Anything before it is ignored, not penalised.
```

**coding은 unified diff가 아니라 SEARCH/REPLACE 블록이다.** 여기를 틀리면 정답을 알아도 0점이다.
`git diff` 형식을 내놓는 스쿼드는 전 문항 `extraction_failed`가 된다.

### 세 트랙에 공통인 두 문장

> If more than one appears, the last one is used.
> Anything before it is ignored, not penalised.

**마지막 것만 채점되고, 그 앞은 아예 읽지 않는다.**
그래서 답 블록 앞의 본문은 채점상 공짜다 — 정확도를 깎지 않는다.
다만 **토큰은 그대로 든다.** 토큰 효율 30점과 동점 처리 기준에는 전부 계산된다.
"채점에 안 걸리니 길게 써도 된다"는 결론은 절반만 맞다.

## 3. judge가 답을 읽어가는 규칙 ★ 여기가 함정이다

문항 페이지 원문:

> How the judge reads an answer back out of that text — **aggregated result first, task outputs
> from the last wave backwards, and the status summary refused as an answer** —
> is `docs/contracts/answer-extraction.md` §1.

그리고 바로 앞 문단이 그 이유를 설명한다.

> When the run finishes, the app shows `**Execution complete** — N task(s) processed in M wave(s).`
> followed by a ticked line per task. **That is a deterministic status summary the runtime composes,
> not your squad's output**: the task titles in it are built out of your own prompt, so reading
> conclusions out of it tells you about your prompt rather than about the run.

### 실제 AI:GO 실행 기록으로 확인한 것

`squad/test/logs/history.json`의 `finalResult` 필드가 실제로 이렇게 생겼다.

```
**Execution complete** — 5 task(s) processed in 2 wave(s).

1. ✅ **Design Slot Machine API Spec**
   Agent: `Backend Developer`
2. ❌ **Implement Slot Machine Backend**
   Agent: `Backend Developer`
...
```

**스쿼드가 만든 텍스트가 한 글자도 없다.** 태스크 제목은 planner가 우리 프롬프트에서 만든 것이다.
`squad:execution-completed` 이벤트의 `result` 필드도 같은 문자열이다.

judge는 이걸 답으로 인정하지 않고 **마지막 웨이브부터 거꾸로** 태스크 출력을 훑는다.
그러니 스쿼드 설계에서 지켜야 하는 것은 하나다.

> **마지막 웨이브의 태스크 출력이 답 블록으로 끝나야 한다.**

마지막 웨이브가 리뷰나 요약을 하고 답 블록을 다시 안 실으면, 그 앞 웨이브가 정답을 냈어도
judge가 마지막 웨이브에서 먼저 읽어간다. `prompts/*.txt`가 "the last thing any agent in this
squad emits"라고 쓰는 이유가 이것이다.

### 데스크톱에서 볼 때

> The Execution Progress panel and the judge read the same field, so what you see there is what is graded.

- **Execution Progress 패널의 각 태스크 줄 아래 본문** = judge가 읽는 것
- 태스크 상세 서랍의 **Result 탭은 비어 보일 수 있다** — 평가가 고정한 버전에서
  스쿼드 executor가 쓰는 것과 다른 태스크 타입에서 채워지기 때문이다. 이건 우리 버그가 아니다.

`tools/extract.py`가 이 규칙을 그대로 구현한다. 상태 요약을 거부하고,
`squad:plan-ready` 이벤트에 기록된 웨이브 순서로 마지막 웨이브부터 거슬러 올라간다.

## 4. 이 폴더가 규칙을 지키는 방법

```
prompts/<track>.txt          우리가 고치는 것. {{TASK}}를 정확히 한 번 포함
<track>/tasks/<id>.txt       {{TASK}} 자리에 들어가는 문항 본문 (judge가 렌더링한 그대로)
                             coding만 <id>.<kind>.txt — swebench / livecodebench
<track>/required_output.txt  뒤에 붙는 블록 (바이트 그대로)
<track>/requests/<id>.txt    프롬프트가 {{TASK}} 한 줄일 때의 완성 요청 = 서버 배포 바이트
                             coding만 <id>.<kind>.txt
raw/request-digests.json     문항별 공개 SHA-256과 로컬 실측값
```

```bash
# 규칙 재현이 맞는지 121문항 전부 대조
bash tools/verify.sh

# 내 프롬프트로 합성한 요청 보기
python3 tools/compose.py coding-visible-0001 --prompt prompts/coding.txt | less
```

`compose.py`는 `{{TASK}}`가 없는 프롬프트를 거부한다. 문항이 통째로 빠진 요청을 만들어
전 문항 오답을 내는 사고를 막기 위해서다.
