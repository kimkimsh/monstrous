## 1. 무엇을 내야 하는가

산출물이 둘이고, 제출물이 둘이다. 헷갈리면 안 된다.

**산출물 A — 문제 해결형 에이전트 스쿼드.**
수학·코딩을 포함한 여러 범주의 문제를 푸는 스쿼드를 설계하고 튜닝한다.
누가 코드를 읽고, 누가 고치고, 누가 검증하고, **누가 포기 시점을 판단하는지**를 전부 직접 정한다.
마지막 항목이 토큰 효율 점수와 직결된다.
**문제 해결 과정의 결정적 부분은 반드시 AI:GO의 agent squad 기능 위에 올라가야 한다.** 요구사항이지 권고가 아니다.

**산출물 B — 인터랙티브 시각화.**
스쿼드의 문제 해결 과정(Trace, 로그 텍스트)을 시각화한다. 매체는 자유.

**제출물 — Squad Template JSON 하나 + 트랙별 one-shot 프롬프트 셋.**
포털 Submit 탭에 "One Squad Template JSON, plus one one-shot prompt for each track"이라고 적혀 있다.
즉 이 폴더의 `prompts/coding.txt` `prompts/math.txt` `prompts/generic.txt`가 제출물의 절반이다.

## 2. 점수 100점의 분해

| 축 | 배점 | 무엇으로 결정되나 |
|---|---|---|
| Benchmark score | 40 | 최종 벤치마크 결과의 팀 순위 |
| Visualization | 30 | Trace 시각화 품질 — observability, interpretability, traceability, explainability, clarity, insightfulness |
| Token efficiency | 30 | 정규화된 총 사용 비용. 낮을수록 높은 점수 |

### 벤치마크 40점의 내부

```
overall = 0.5 × accuracy(coding) + 0.25 × accuracy(generic) + 0.25 × accuracy(math)
```

**가중치는 문항 수 비율이 아니라 정확도에 곱하는 계수다.** `set.manifest.json`이 직접 그렇게 못 박는다.

> Weights are score weights over per-track accuracies. They are not item-count shares:
> a track's weight says how much its accuracy counts, not how many items it runs.

hidden 세트의 문항 수는 오히려 generic이 압도적이다.

| 트랙 | hidden 문항 수 | 가중치 | 문항 하나의 점수 기여 |
|---|---|---|---|
| coding | 140 ~ 240 | **0.5** | **크다** |
| generic | 448 ~ 698 | 0.25 | 작다 |
| math | 60 ~ 66 (× 2회 반복) | 0.25 | 중간 |

**coding 문항 하나가 generic 문항 하나보다 대략 10배 넘게 무겁다.**
그런데 coding 문항 하나의 입력이 60,000자다. 여기서 예산 배분의 방향이 정해진다 —
generic에 self-consistency 같은 n배 샘플링을 붓는 건 대개 손해고, 그 예산은 coding으로 가야 한다.

### 토큰 효율 30점의 과금 규칙

```
정규화 비용 = Σ (모델별 토큰수 × 모델별 USD/Mtok 기준 단가 × 실행 계수)

실행 계수:  AI:GO test run → 1/5      submission run → 1 (전액)
```

- **제출 버튼을 누르는 횟수가 곧 비용이다.** PDF 원문: 한 번 돌리면 한 번, 100번 돌리면 100번 전부 과금.
- Check(검증)는 무료·무제한. Submit to the queue를 눌러야 큐에 들어가고 과금된다.
- **토큰은 30점짜리 축이면서 동시에 40점짜리 축의 동점 처리 기준이다.** 이중으로 먹힌다.

## 3. 채점은 전부 프로그램이다

> Who decides right and wrong — **Programs, always.** Every verdict is deterministic — tests
> that pass or fail, an answer that matches or does not — and no model is ever asked to judge
> another model.

LLM-as-a-judge가 없다. 그럴듯하게 써서 점수를 얻을 여지가 0이다.

| 트랙 / 데이터셋 | grader | 방식 |
|---|---|---|
| coding / swebench | `swebench_docker` | Docker 안에서 test_patch 적용 후 pytest. fail_to_pass 통과 + pass_to_pass 유지 |
| coding / livecodebench | `livecodebench_tests` | 공개 테스트 케이스로 stdin/stdout 대조 |
| math (integer) | `integer_exact` + `math_verify` | 정수 정확 일치, 그리고 수식 동치 |
| math (expression) | `math_verify` | 수식 동치 (LaTeX 정규화 포함) |
| generic | `letter_match` | 보기 문자 대조, 대소문자 무시 |

### 결과 분류 — 시각화에 이 어휘를 그대로 쓰면 심사위원에게 바로 읽힌다

`Outcome`: `graded` / `extraction_failed` / `capped` / `grader_error` / `infrastructure_failed`
`ItemStatus`: `ok` / `capped_tokens` / `capped_wallclock` / `error`
`FailureKind`: `infrastructure` / `upstream_error` / `token_cap` / `wallclock_cap` / `runner`
`FailureOwner`: `team` / `policy` / `configuration` / `organizer`

**`grader_error`와 `infrastructure_failed`는 주최 책임이고 순위 분모에서 빠진다.**
반대로 `extraction_failed`와 `capped`는 팀 책임이다.

포털의 경고 원문을 그대로 옮긴다 — 이건 실전에서 물린다.

> The evaluation endpoint is intermittently unavailable — five independent outages were
> observed in one afternoon. Without this field an outage is indistinguishable from a squad
> that answered badly, and **AI:GO's failure-as-context semantics turn an unretried connect
> timeout into "execution completed, all tasks failed"**, which grading would read as a team's zero.

우리 러너도 같은 함정에 빠진다. `tools/run_batch.py`가 실패를 재시도하지 않고 status를 그대로 기록하는 이유가 이것이다.
**네트워크 오류와 모델이 못 푼 것을 섞으면 정확도 숫자가 거짓말을 시작한다.**

## 4. 상한(caps)

리더보드 Comparability 절 전문 중 핵심:

> every run on this page executed under a **per-item wall-clock cap** and a **per-run token
> cap**, identical for every team. … **Two of the three evaluation models are reasoning models
> — one was measured spending 97% of its output budget on reasoning tokens before it answered
> — so a token cap bites roughly an order of magnitude harder on a squad built from reasoning
> models than on one built from an instruct model.**

1. 문항당 wall-clock 상한, 실행당 토큰 상한. 구체적 숫자는 미공개이고 실행 기록(`PublishedCaps`)에 남는다.
2. 평가에 쓸 수 있는 모델은 3개. **그중 2개가 reasoning 모델**이고, 하나는 출력 예산의 97%를 사고 토큰에 쓴다.
3. 따라서 **토큰 상한이 reasoning 스쿼드에 약 10배 세게 물린다.**

→ 실무 결론: **instruct 모델을 기본으로 쓰고, reasoning 모델은 정말 필요한 지점에만 국소 투입**한다.
AI:GO CLI에서 그 레버는 `--no-think`, `--thinking-budget N`, `--reasoning-effort none`이다.
확인된 모델 이름은 `Qwen3-30B-A3B-Instruct-2507-FP8` 하나뿐이고 나머지 2개는 아직 미확인이다.

## 5. 평가 실행 중 스쿼드가 할 수 없는 것

포털 practice-sets 페이지 원문:

> your squad has no tools during a run and never browses a repository

AI:GO 공식 문서도 같은 방향으로 잠근다:

> Tools that operate on arbitrary host paths (`list_directory`, `search_files`,
> `execute_python`, etc.) are **blocked for all squad agents regardless of the tool configuration.**

**SWE-bench 문항의 저장소 코드는 judge가 검색해서 요청 본문에 넣어준다.**
이 폴더 `coding/requests/*.txt`의 60KB가 바로 그것이고, 평가 때 오는 것과 바이트가 같다.

그래서 coding 트랙의 실력은 "코드를 잘 찾는 능력"이 아니라
**"주어진 60KB 발췌만 보고 적용되는 패치를 쓰는 능력"** 이다.
검색·탐색 에이전트를 설계하는 것은 헛수고다. 필요한 건 읽기 → 가설 → 패치 작성 → 형식 자가검증이다.

## 6. 연습 세트 실측 (2026-08-22 서버 기준)

**서버가 visible 세트를 364 → 121문항으로 줄였다.** `set.manifest.json`의 `trim` 블록:

> the visible practice set was reduced to roughly one third; **the hidden set is unchanged**,
> and a subset of the original draw cannot overlap it

`../track_resource/lableup/practice-sets/`의 364문항 사본은 이제 옛날 것이다. 이 폴더가 최신이다.

### coding — 20문항, 요청 872,683바이트

| 항목 | 값 |
|---|---|
| 구성 | swebench-lite 13 + livecodebench-v6 7 |
| 요청 크기 | 최소 1,999 / 중앙값 63,812 / 최대 70,310 바이트 |
| 컨텍스트 번들 | 13문항 전부 보유, 중앙값 59,966자 (상한 60,000자를 거의 채움) |
| 저장소 | django 2, matplotlib 2, 나머지 9개 프로젝트 각 1 |
| LiveCodeBench | stdin 4 / functional 3, easy 4 / medium 3 |

중앙값 63,812바이트는 대략 **16,000~20,000 입력 토큰**이다. 에이전트 한 명이 한 번 읽는 값이고,
**여러 에이전트가 각자 다시 읽으면 그 배수로 든다.** 컨텍스트 중복 전달을 줄이는 것이 1번 최적화 과제다.

hidden의 SWE-bench가 150문항이면 입력 토큰만 250만~300만이 기본으로 깔린다. 에이전트 4명이면 1,000만이다.
`per_run_token_cap`이 존재하는 이유가 이것이다.

### math — 59문항, 요청 32,253바이트

| 항목 | 값 |
|---|---|
| 구성 | math-500-level5 48 + aime-2024 11 |
| 답 형식 | integer 35 / expression 24 |
| 요청 크기 | 최소 334 / 중앙값 491 / 최대 1,570 바이트 |
| 실행 반복 | **`run_repeats: 2`** — 같은 문제를 2회 돌려 평균 |

지문이 매우 짧다. **math의 토큰 비용은 거의 전부 출력 토큰이다.**
여기에 reasoning 모델을 붙이면 비용이 폭발하고, 문항 수가 2배로 계산된다.

### generic — 42문항, 요청 45,220바이트

| 항목 | 값 |
|---|---|
| 구성 | MMLU-Pro 14과목 × 3문항 |
| 요청 크기 | 최소 474 / 중앙값 918 / 최대 2,926 바이트 |
| 보기 개수 | 10개가 36문항, 나머지는 3·4·7·8·9개가 각각 섞임 |

**보기 개수가 문항마다 다르다.** "A부터 J 중에 고르라"고 하드코딩하면 보기가 3개인 문항에서
존재하지 않는 보기를 고른다. 요청 본문의 Options 블록에 실제 문자가 이미 나열돼 있으니 거기서만 고르게 해야 한다.

채점은 `letter_match`이고 추론 과정은 아예 읽지 않는다.
**가장 짧게 답만 뽑는 것이 정확도 손해 없이 토큰을 아끼는 지점이다.**

## 7. 제출 운영

| 항목 | 값 |
|---|---|
| Waiting submissions | 최대 3개 |
| Runs in flight | 1개 (팀당 동시 평가 1건) |
| Check(검증) | 무료·무제한 |
| 리더보드 한 줄 | 팀이 아니라 **실행 하나**. 여러 번 돌리면 여러 줄이 뜨고 감출 수 없다 |
| 동점 처리 | ① 총 토큰 적은 쪽 ② wall-clock 짧은 쪽 |

검증 실패한 제출은 큐 상태를 건드리지 않는다. 이미 처리된 폼의 재전송은 거부된다.

## 8. 아직 확인 못 한 것

온보딩 세션에서 물어야 하는 항목이다. 값을 모르면 예산 설계가 추측이 된다.

1. 평가 모델 3종의 정확한 이름과 USD/Mtok 단가 (확인된 건 `Qwen3-30B-A3B-Instruct-2507-FP8` 하나뿐)
2. `per_run_token_cap`과 `per_item_wallclock_seconds`의 실제 숫자
3. Squad Template JSON의 정확한 스키마 — AI:GO 템플릿 스키마 그대로인가, 제출 서버 전용 변형이 있는가
4. 트랙별 one-shot 프롬프트가 스쿼드의 어디로 주입되는가 — planner에게만인가, 전체 에이전트에게인가
5. "test run"의 정의 — PDF의 1/5 과금과 포털의 Development usage가 같은 것인가 다른 것인가
6. Trace 로그 확보 경로 — 포털 `/runs/{run_id}/details`인가, 로컬 AI:GO 실행 로그인가, 둘 다인가

포털이 언급하는 `docs/contracts/composition-rule.md`, `docs/contracts/patch-format.md`,
`docs/contracts/answer-extraction.md`는 **서버에 그 경로로 공개돼 있지 않다** (전부 404).
현재 확보된 것은 각 문항 페이지가 렌더링해 보여주는 요약본뿐이고, 그 내용은
`01-요청-합성-규칙.md`에 실측으로 검증해서 정리했다.
