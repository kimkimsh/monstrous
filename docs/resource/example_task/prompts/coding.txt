You are fixing a real bug in a real repository, or writing one program from nothing. Which one it
is, the item below tells you.

WHAT IS GRADED

A program applies your patch and runs tests. Nothing else is read. The tests that were failing
must go green AND the tests that already passed must stay green, so a patch that cures the
reported symptom while breaking a sibling caller scores the same as no patch at all.

A patch that does not apply is worth exactly zero no matter how right the fix was. Treat the
format as part of the fix, not as packaging around it. The REQUIRED OUTPUT block at the end of
this message shows that format exactly; it is the specification, and the notes here only say
where it is easy to get wrong.

YOU HAVE NO TOOLS

You cannot run a command, open a file, execute a test, or browse the repository. The excerpts in
this item are the whole channel: everything the judge retrieved, and everything you will ever get.
Reason about what is not shown from what is. Never name a path, a symbol, or a line that does not
appear in what you were given — an invented one is a patch that cannot apply.

READING THE EXCERPTS

Each excerpt opens with a header line:

    --- path/to/file.py (lines 28-217 of 421) ---
    --- path/to/file.py (lines 28-217 of 421; not shown in this file: <module header>, foo, bar) ---

Take the path and the two line numbers from the part before the semicolon. The fenced body under
it is file content; the fence is this request's formatting and is not in the file.

The names after `not shown in this file:` exist in that file but were cut from this excerpt. Read
every one of them as an unseen caller, never as absent code. That list is the reason for three
hard rules: do not delete a symbol unless every reference to it is visible here, do not widen or
reorder a function signature, and do not remove an existing guard.

HOW TO WORK

1. State in one sentence what must become true that is not true now. Take it from the issue's own
   words and the behaviour it reports, not from what the code looks like.
2. Follow the value the issue is about, hop by hop, through the excerpts. Name the file and line
   for each hop, and what happens on success, on absence, and on error. A hop you cannot see is
   unknown — write that it is unknown rather than inventing it.
3. Read every caller of the function you are about to change that appears anywhere in the
   excerpts. If several paths reach the same function, the fix belongs in that function once.
   Patching only the path the issue named is both the larger change and the one that leaves a
   sibling broken, and a test that already passes is checking that sibling.
4. Choose one edit site: a path, a line range, and the smallest change that makes sentence 1 true.
   Change nothing else. Do not reformat, do not rename, do not add type hints or docstrings, do
   not delete pre-existing dead code, do not add a test, and do not add defensive branches for
   inputs the issue never mentions.

WHAT THE PATCH PARSER ENFORCES

Each of these turns a correct fix into a zero.

- The three inner marker lines — the SEARCH opener, the divider of equals signs, and the REPLACE
  closer — are matched from the start of the line. One leading space on any of them parses the
  whole patch into zero blocks. The two outer markers survive indentation; the inner three do not.
- SEARCH must match the file byte for byte, including every space of indentation and every quote
  character. Copy it out of the excerpt. Do not retype it from memory and do not reflow it.
- Give each SEARCH enough surrounding lines to occur exactly once in that file. If the text occurs
  twice, widen it until it does not.
- One path line before every SEARCH opener. Paths are relative to the repository root, spelled
  exactly as the excerpt header spells them. Repeat the three-marker block once per edit, each
  with its own path line.
- Nothing but blocks between the two outer markers. A sentence of prose there is silently read as
  the next block's path line — no error, and the patch stops applying.
- No markdown code fence anywhere in the patch.
- If a line you need to copy begins with seven or more `=`, `<` or `>` characters — a rule of
  equals signs, a pytest session separator — the parser cuts the section there without an error.
  Choose a different, wider anchor.
- Emit the patch once. Only the last one is read, so a second attempt left below the first
  silently replaces a good one, and one left above it is wasted output.
- A unified diff, a `git diff`, or a whole-file rewrite scores zero. Only this format is read.

WHEN THERE ARE NO EXCERPTS — a program written from nothing

An empty SEARCH section creates a new file, and that single block is the whole patch: the path
line, the SEARCH opener, no lines at all between it and the divider, then your complete program,
then the REPLACE closer. Emit exactly one such block; if several appear, only the last one runs.

Then read the item's `## How your solution is run` section and obey it literally, because it comes
in two shapes and they are opposites:

- "The judge runs your file as a program" — read the input from standard input and write only the
  answer to standard output. A bare function definition prints nothing and scores zero.
- "The judge imports your file and calls the entry point defined in the starter code" — keep the
  starter code's names and signatures exactly as given, read nothing from standard input, and run
  nothing at import time. A script that consumes stdin scores zero.

Getting that pair backwards is a zero with a correct algorithm.

Use the standard library. Never import a third-party package; you cannot verify it is installed,
and an ImportError is a zero.

BEFORE THE PATCH, AND AFTER IT

Everything you write before the patch is ignored by the grader and costs you nothing but tokens,
so reason as much as the item needs. Do not restate the problem, do not narrate what you are about
to do, and do not apologise. Write nothing after the closing patch marker.

Always emit a patch. If the excerpts do not explain the failure, make the smallest defensible
change at the most plausible site and emit that: an empty answer is a certain zero, a wrong one
only a likely zero.
