# 02. 실험 운영 — 무엇을 재고 무엇을 고치나

프롬프트와 스쿼드 구조를 반복해서 깎을 때 쓰는 절차다.
연습 세트로 돌리는 실행은 test run 취급이므로 **기준 단가의 1/5**만 과금된다 (PDF 25페이지).
그러니 여기서 최대한 돌리고, 제출은 아껴야 한다.

---

## 1. 순환 한 바퀴

```bash
cd docs/resource/example_task

# ① 스쿼드 ID 확인 (CLI는 앱 번들 안에 있고 PATH에 없다)
AIGO="/Applications/Backend.AI GO.app/Contents/MacOS/aigo-cli"
"$AIGO" squad list

# ② 예산을 먼저 조인다. 포기 장치가 없으면 한 문항이 예산을 다 먹는다
"$AIGO" squad budget show <SQUAD_ID>

# ③ 싸고 빠른 트랙부터 — math 10문항이면 한 바퀴가 몇 분이다
python3 tools/run_batch.py <SQUAD_ID> <WORKSPACE_DIR> \
        --tracks math --limit 10 --out runs/math-01.jsonl

# ④ 채점
python3 tools/grade.py runs/math-01.jsonl --report runs/math-01.report.jsonl

# ⑤ prompts/math.txt 를 고치고 ③으로
```

**트랙 순서는 math → generic → coding.**
math와 generic은 문항당 수백 바이트라 한 바퀴가 싸다. coding은 문항당 60KB라 비싸다.
형식 문제·추출 실패 같은 구조적 결함은 싼 트랙에서 먼저 다 잡고, coding은 그게 끝난 뒤에 돌린다.

---

## 2. 무엇을 먼저 보나 — 순서가 정해져 있다

`grade.py`의 출력에서 이 순서로 읽는다. 앞의 것을 안 고치고 뒤로 가면 측정이 거짓말을 한다.

### ① `extraction_failed` 개수

정확도보다 먼저다. 답을 못 뽑으면 모델이 잘 풀었는지 아닌지 알 수가 없다.
포털도 이걸 오답과 별도로 분류한다 — 원문: *"a silent zero hides a harness defect behind a team's score."*

원인은 대개 셋 중 하나다.

- 답 블록을 아예 안 냈다 → 프롬프트가 형식을 충분히 강제하지 못함
- 마지막 웨이브가 답 블록 없이 끝났다 → **스쿼드 구조 문제.** `01-요청-합성-규칙.md` 3절
- coding에서 unified diff를 냈다 → SEARCH/REPLACE가 아니면 전부 0점

### ② `extracted_from` 필드

`run_batch.py`가 행마다 기록한다. 값이 셋이다.

| 값 | 뜻 |
|---|---|
| `aggregated_result` | 집계 결과에서 답이 나왔다. 가장 안정적 |
| `task_output(wave=N, ...)` | N번 웨이브 태스크 출력에서 나왔다. **N이 마지막 웨이브인지 확인할 것** |
| `nothing_extractable` | 상태 요약밖에 없었다. 실행은 성공했는데 답이 없는 상태 |

`nothing_extractable`이 나오면 정확도를 볼 이유가 없다. 구조부터 고친다.

### ③ 트랙별 정확도와 가중 점수

`grade.py`가 마지막에 `0.5 × coding + 0.25 × generic + 0.25 × math`로 찍는다.
일부 트랙만 돌렸으면 그 트랙들만의 가중합이라는 것도 같이 찍는다.

### ④ 토큰

`prompt_tokens` / `completion_tokens`가 행마다 있다.
정확도가 같으면 토큰이 적은 쪽이 이긴다 — 30점짜리 축이면서 동시에 벤치마크 40점의 동점 처리 기준이다.

---

## 3. 토큰을 깎는 레버 — 효과 큰 순서

### coding: 컨텍스트 중복 전달 (가장 큼)

문항 하나의 요청이 중앙값 63,812바이트, 대략 16,000~20,000 입력 토큰이다.
**에이전트 3명이 각자 전체를 다시 읽으면 그대로 3배**가 된다.
읽는 에이전트를 하나로 좁히고 나머지는 그 요약만 받는 구조가, 다른 어떤 최적화보다 크게 먹힌다.

### 사고 토큰

평가 모델 3개 중 2개가 reasoning 모델이고, 하나는 출력 예산의 97%를 사고에 쓴다.
AI:GO의 레버는 셋이다.

```bash
aigo-cli chat --no-think ...                 # <think> 블록 자체를 끔
aigo-cli chat --thinking-budget 64 ...       # 사고 토큰 하드 캡
aigo-cli chat --reasoning-effort none ...    # 하이브리드 모델의 추론 강도
```

instruct 모델을 기본으로 두고, reasoning은 정말 필요한 지점에만 국소 투입한다.

### prefix cache

지시문을 앞에, `{{TASK}}`를 뒤에. `prompts/*.txt`가 이미 그 배치다.
포털이 `cached_input_share`를 API로 노출하므로 실제로 걸리는지 측정할 수 있다.

### generic의 출력 길이

`letter_match`는 추론 과정을 아예 읽지 않는다. 문항 수는 hidden에서 448~698개로 가장 많은데
가중치는 0.25다. **여기에 self-consistency 같은 n배 샘플링을 붓는 건 대부분 손해다.**
그 예산은 가중치 0.5짜리 coding으로 가야 한다.

### 포기 장치

PDF가 스쿼드 설계 요구사항으로 "어떤 에이전트가 포기 시점을 판단할 것인가"를 직접 물었다.
AI:GO Budget Config의 `Max agent turns`, `Max tokens per task`가 그 장치다.
한 문항이 예산을 다 먹는 사고를 막는 건 프롬프트가 아니라 이 설정이다.

## 4. 측정을 망치는 것들

### 실패를 재시도로 덮지 말 것

포털 경고 원문:

> **AI:GO's failure-as-context semantics turn an unretried connect timeout into
> "execution completed, all tasks failed"**, which grading would read as a team's zero.

네트워크 오류와 모델이 못 푼 것이 같은 모양으로 보인다.
`run_batch.py`가 자동 재시도를 하지 않고 `status`를 그대로 기록하는 이유가 이것이다.
**재시도가 필요하면 재시도한 것으로 기록하고 다시 돌린다.** 조용히 덮으면 정확도 숫자가 거짓말을 시작한다.

### `gold/`를 프롬프트에 넣지 말 것

실제 평가에서 스쿼드는 `payload`만 본다. `tasks/`와 `requests/`에는 정답이 들어 있지 않고,
`gold/`는 채점기만 읽는다. 이 분리를 깨면 연습 점수가 아무 의미도 갖지 않는다.

### SWE-bench 로컬 채점의 한계를 알고 쓸 것

`grade.py`는 SWE-bench 문항에 `format_ok`만 찍고 정답 여부를 판정하지 않는다.
진짜 채점은 `swebench_docker` — 저장소와 test_patch와 컨테이너가 필요하다.
여기서 확인되는 건 **"패치가 파싱되고 SEARCH 구간을 찾을 수 있는가"** 뿐이다.
그게 값어치가 없다는 뜻이 아니다. 맞는 수정을 0점으로 만드는 실패 모드가 정확히 그것이다.

코딩 능력의 대리 지표가 필요하면 **LiveCodeBench 7문항**을 쓴다. 공개 테스트 케이스가 있어서
`grade.py`가 실제로 실행하고 정답을 판정한다.

### 연습 세트 크기를 정확도의 신뢰구간으로 환산할 것

math 59 / generic 42 / coding 20문항이다.
generic 42문항에서 1문항 차이는 2.4%p다. **프롬프트 두 개의 정확도가 1문항 차이면 그건 같은 것이다.**
차이를 주장하려면 더 많은 문항이나 반복이 필요하고, 그건 토큰을 쓴다.
싸고 결정적인 지표(추출 실패 수, 형식 오류 수, 토큰 수)를 먼저 최적화하는 게 순서인 이유다.

## 5. 결과 파일 관리

```
runs/
  math-01.jsonl          run_batch.py 출력 — item_id, output, tokens, status
  math-01.report.jsonl   grade.py 출력 — item_id, outcome, correct, detail
  prompts/math-01.txt    그때 쓴 프롬프트 사본
```

프롬프트를 고칠 때마다 사본을 같이 남긴다. `prompts/variants/`가 그 자리다.
어떤 프롬프트가 어떤 점수를 냈는지 나중에 되짚을 수 없으면, 돌린 토큰이 전부 낭비다.

`run_batch.py`가 `request_chars`도 같이 기록하므로,
프롬프트를 길게 고쳤을 때 입력이 얼마나 늘었는지 정확도 변화와 나란히 볼 수 있다.
