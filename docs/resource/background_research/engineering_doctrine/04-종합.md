# 04. 종합 — Architect와 Reviewer 계약

세 레포를 우리 조건(원샷 · 도구 0개 · SEARCH/REPLACE)으로 접은 결과다. 인용 출처는 `01`~`03` 문서에 있다.

---

## 1. 셋이 같은 말을 하는 곳 — 여기가 지지 구조다

세 레포는 서로를 인용하지 않는다(karpathy 레포는 다른 둘을 아예 모른다). 그런데도 겹치는 지점이 있고, 독립적으로 도달한 결론이므로 가중치를 높게 둔다.

| 합의 | ponytail | mark-pattern | karpathy |
|---|---|---|---|
| **요청되지 않은 추상을 만들지 마라** | "no interface with one implementation, no factory for one product" | "no call site ever receives more than one concrete implementation" | "No abstractions for single-use code" |
| **바꾼 줄마다 이유가 있어야 한다** | "Fewest files possible" | "Scope stays surgical … do not silently fold it in" | "Every changed line should trace directly to the user's request" |
| **인접 코드를 개선하지 마라** | "Deletion over addition"(단서 필요) | "If you spot something adjacent and real, report it; do not silently fold it in" | "Don't 'improve' adjacent code, comments, or formatting" |
| **패턴 이름은 근거가 아니다** | "no factory for one product" | "A pattern name is never a justification" | "Strategy pattern for single discount calculation" = 안티패턴 |
| **고치기 전에 이해하라** | "The ladder shortens the solution, never the reading" | "A name is a hypothesis; grep tells you where to look and tells you nothing about what you found" | "Don't assume. Don't hide confusion." |
| **테스트가 통과한다고 안전한 것이 아니다** | (안전 바닥) | "Tests encode what someone thought to assert" | (없음 — 오히려 테스트를 쓰라고 함) |

## 2. 셋이 어긋나는 곳 — 승자를 정한다

| 쟁점 | 주장 | 판정 |
|---|---|---|
| **"한 줄로 만들어라"** | ponytail 사다리 6번 | **폐기.** ponytail **자신의 측정**이 반대 증거다 — `safe-path`에서 줄 수가 가장 적은 arm이 4회 중 1회 경로 탈출을 허용했고, ponytail이 남긴 3줄이 바로 그 가드였다. 그리고 우리는 LOC로 채점받지 않는다. karpathy의 "minimum code that solves the problem"이 이긴다 |
| **"삭제가 추가보다 낫다"** | ponytail | **뒤집는다.** karpathy가 이긴다 — *"Don't remove pre-existing dead code unless asked."* 그린필드에서 삭제는 "안 짓는 것"이지만 패치에서 삭제는 **통과하던 테스트가 의존하는 코드를 없애는 것**이다 |
| **고아 정리** | karpathy `:40` "네 변경이 만든 미사용 import/변수를 제거하라" | **조건을 붙인다.** mark-pattern의 도달 가능성 증명이 이긴다 — 발췌 밖 호출자를 못 보는데 재수출·`__all__`·이름 기반 DI를 어떻게 아나. **모든 참조가 발췌 안에 보일 때만** 제거한다 |
| **"불가능한 시나리오에 에러 처리 금지"** | karpathy `:24` | **약화한다.** 불가능을 증명할 수단이 없다. 그리고 SWE-bench 정답의 상당수가 정확히 `None`/빈 값/범위 가드다. **"리포트가 말하지 않고 발췌가 닿지 않는 경우에 대한 처리를 추가하지 말고, 있는 처리를 지우지도 마라"**로 바꾼다 |
| **재현 테스트를 먼저 써라** | karpathy §4 전체 | **폐기.** 산출물이 틀렸다. 채점기가 테스트를 준다. 살릴 알맹이 하나 — **"실패 테스트가 곧 재현이다. 그것을 명세로 읽어라."** |
| **"린터가 잡는 것은 다시 보고하지 마라"** | mark-pattern | **Reviewer에게는 뒤집는다.** 우리에겐 린터가 없고 **형식 검증이 Reviewer의 존재 이유**다. 그대로 넣으면 리뷰어가 자기 직무를 억제한다 |
| **추천에 "makes ___ worse" 두 칸을 붙여라** | mark-pattern Move 1 | **예외 조항을 필수로 승격.** mark-pattern 자신이 적어 둔 예외(*"It does not apply to a bug fix that restores obviously-correct behavior"*)가 우리 문항 대부분에 해당한다. 두 칸은 **Architect가 구조 변경을 제안할 때만** 붙는다 |
| **묻고 멈춰라** | karpathy `:15`, mark-pattern `:196`, ponytail(반대) | **ponytail이 이긴다** — *"Never stall on an answer you can default."* 나머지 둘의 "물어라"는 원샷에서 **0점짜리 출력**이다 |

## 3. Architect 계약

**받는 것**: 이슈 본문 + 앵커 2~3개(각 앵커는 경로·줄 범위·원문 hunk).
**내는 것**: 변경 설계 한 덩어리. 어디를 왜 고치는지, 무엇을 건드리면 안 되는지, 확신도.
**절대 안 하는 것**: 패치 작성. 발췌 밖 코드 언급. 질문.

### 3-1. 순서 — 이 순서가 규율이다

```
1. 실패가 요구하는 것을 한 문장으로 다시 쓴다        ← 명세 고정
2. 앵커 안에서 그 값이 지나는 경로를 홉으로 따라간다   ← mark-pattern Move 3
3. 내가 바꿀 함수의 호출자를 발췌 안에서 전부 훑는다    ← ponytail 근본 원인 (효과 1/6→6/6)
4. 공유 지점 하나를 고르거나, 못 고르면 그렇게 말한다   ← 확신도
5. 건드리면 안 되는 것을 이름으로 적는다              ← pass-to-pass 방어
```

3번이 이 계약의 핵심이다. SWE-bench 채점이 `fail_to_pass` + `pass_to_pass`이고, ponytail의 재현 과제가 정확히 그 구조다 — 리포트는 `transfer`를 말하는데 채점기는 `withdraw`를 실행한다. **리포트가 말한 경로만 고치면 형제 호출자가 깨진 채로 남는다.**

그리고 문구가 절차여야 한다는 대조군을 기억한다. "흐름을 끝까지 따라가라"는 산문은 Opus에서 **0/3**이었고, "호출자를 전부 훑어라"는 조작적 지시가 **6/6**이었다.

### 3-2. 발췌 경계 규칙 — 환각 방지

mark-pattern의 Move 3은 *"open every file it passes through"*라고 쓴다. **우리에겐 열 파일이 없다.** 이 단서를 안 붙이면 프롬프트 안에서 가장 큰 환각 원천이 된다.

> 경로는 발췌 경계에서 멈춘다. 발췌에 없는 홉은 **모른다**고 표시하고 추측하지 않는다. 발췌 밖 경로는 근거가 아니라 가정이다.

같은 규칙이 세 곳에 더 걸린다 — 고아 제거(모든 참조가 보일 때만), "계산했는데 안 읽음"(모든 읽기 지점이 보일 때만), 삭제 제안(모든 참조가 보일 때만).

### 3-3. 실패 경로 체크리스트 — 발췌만 보고 판단 가능한 것

mark-pattern의 카탈로그에서 **도구 없이 확인 가능한 것만** 남겼다.

| # | 찾는 것 | 왜 |
|---|---|---|
| 1 | `if x:` 에 `else`가 없다 | 부재가 무엇을 뜻하는지 아무도 정하지 않았다. 파서가 정했다 |
| 2 | 한 함수에서 falsy 반환이 두 번, 뜻이 반대인 경로에서 | "확인했고 아니다"와 "확인할 수 없었다"가 같은 값이다 |
| 3 | URL·경로·셸 문자열 안 `${...}` | 미설정 변수가 `"undefined"`로 문자열화돼 **진짜 장애와 같은 catch에 떨어진다** |
| 4 | 여는 연산과 닫는 연산의 개수가 다르다 | 새는 쪽은 거의 항상 에러 경로다 |
| 5 | retry가 붙어 있다 | 멱등성을 몰래 주장한 것이다. "첫 시도는 성공했고 ack만 유실됐다면?" |
| 6 | 벽시계로 구간을 잰다 | 시계가 뒤로 점프하면 음수가 된다 |
| 7 | 술어를 계산하는데 읽는 곳이 로깅·직렬화뿐이다 | 그 검사는 존재하지 않는 것이다 *(모든 읽기 지점이 발췌에 있을 때만)* |
| 8 | 파생 클래스가 base와 같은 이름의 필드를 선언한다 | 오버라이드가 아니라 섀도잉이다. 같은 객체가 두 값을 가진 것처럼 보인다 |

### 3-4. 실패 방향은 유도한다

부재 분기를 새로 쓸 때 무엇을 할지 — 집 스타일로 정하지 않는다.

|  | 반경 좁음 | 반경 넓음 |
|---|---|---|
| **되돌릴 수 있음** | 낮춰서 계속 | 낮춰서 계속, 알린다 |
| **되돌릴 수 없음** | 거부, 이유를 호출자에게 | 거부, 알린다 |

**연산마다 새로 유도한다. 직전 답을 물려받지 않는다.**

### 3-5. 구조를 더하는 라이선스

mark-pattern Move 2b를 우리 조건으로:

> 새 구조는 **발췌 안에 오늘 존재하는 두 번째 변이점**이 허가한다. 계획이 아니라, 가능성이 아니라, 지금. 두 인스턴스를 발췌 안 줄 번호로 인용하지 못하면 **직접 코드를 쓴다.**

발췌에 변이점 둘이 들어 있는 경우는 거의 없다. **그래서 이 라이선스는 사실상 추상 추가를 전부 거절한다 — 그게 목적이다.**

### 3-6. 확신도와 컷오프

Architect는 **끊을 수 있는 첫 자리**다.

```
confident   앵커 안에서 실패를 설명하는 단일 지점을 찾았다        → Editor에게 그 지점을 준다
partial     후보가 여럿이고 하나를 못 고르겠다                  → 가장 지지되는 하나 + 차점을 한 줄로
none        발췌에 고칠 자리가 없다 (정답 파일이 안 왔을 수 있다) → Editor에게 최소 변경만 시도하라고 한다
```

`none`이 진짜로 일어난다. 연습 문항 `coding-visible-0001`은 `test_rst.py`가 추가되는데 **발췌 11개 중 `rst.py`가 없다.** 그 문항은 무엇을 해도 못 푼다. 그때 정교한 오답을 쓰는 것보다 **최소 변경 + 낮은 확신도 표시**가 낫다. 뒤의 Reviewer가 그 신호를 받는다.

## 4. Reviewer 계약

**받는 것**: 앞 태스크의 출력 전문(패치 또는 답) + 같은 앵커.
**내는 것**: ledger 줄 → 최종 답 블록. 마지막 웨이브이므로 **답을 다시 실어야 한다.**
**절대 안 하는 것**: 새 추상 제안. 스타일 지적. 맞는 답을 지어낸 답으로 덮기.

### 4-1. 두 층으로 본다 — 사용자가 요구한 것

**층 1 — 내용.** 이 패치가 실패를 실제로 고치나, 그리고 통과하던 것을 깨지 않나.

- 바꾼 줄이 실패가 요구하는 것에 **하나씩 대응**하는가 (karpathy `:43`)
- 리포트가 말한 경로만 고치고 **형제 호출자를 남겨 두지** 않았는가 (ponytail 근본 원인)
- 발췌 밖 심볼을 만들어 내지 않았는가
- 시그니처를 넓히지 않았는가 — 보이지 않는 호출자가 있다
- 있던 가드를 지우지 않았는가 (안전 바닥)

**층 2 — 형식.** 채점기 정규식에 걸리나.

- 세 내부 마커가 0열에서 시작하는가
- 모든 SEARCH 앞에 path 줄이 있는가
- SEARCH가 발췌에 글자 그대로 있는가
- `ANSWER:` 줄이 줄 전체인가 / `FINAL ANSWER:` 와 `\boxed{` 사이에 공백만 있는가

### 4-2. 승인 허가 — 이게 없으면 리뷰어가 정답을 반려한다

mark-pattern의 기준선을 그대로 가져온다.

> 발견은 **그것이 진짜이고 읽는 사람의 시간을 쓸 값이 있다는 확신이 ≥80%**일 때만 낸다. **"고칠 것 없음"은 정당하고 기대되는 결과다** — 열 번째 항목을 지어내지 말고 그렇게 말하라.

그리고 헤지 금지 — *"consider", "you might want to", "it could be argued"로 표현되는 것은 기준을 못 넘은 것이다. 잘라라."*

### 4-3. 리뷰어가 하지 말아야 할 것 — mark-pattern 거짓 양성 목록

스타일·명명·주석 밀도·매직 넘버·**함수 길이**·"테스트를 추가하세요"·이름만 보고 추론한 문제. 전부 보고하지 않는다. 그리고:

> 리뷰 중에는 새 추상을 제안하지 않는다. **factory를 들고 나타난 에이전트는 상황을 잘못 읽은 것이다.**

### 4-4. 아첨 방지 — 앞 에이전트가 자신 있게 틀렸을 때

> "agreement that arrives immediately after a user's detailed argument is the single most measurable failure mode in this whole skill. Before conceding, state the strongest case against the new position. If it survives that, concede."

Reviewer가 받는 것은 **자신 있게 쓰인 패치**다. 그 확신에 동조하지 않게 만드는 유일한 절차가 이것이다.

### 4-5. 컷오프 — Reviewer가 진짜로 끊는 자리

```
승인      형식이 맞고 내용이 맞다              → 글자 그대로 재출력
형식 수리 값은 맞고 형태가 틀렸다              → 형태만 고친다. 값은 안 건드린다
내용 수리 명백히 틀렸고 앵커 안에 답이 보인다   → 고친다. 한 번만
중단      고칠 수 없다                       → 지금 가진 것 중 형식이 유효한 최선을 내고 끝낸다
```

**"중단"이 지문의 *which ones determine when it is time to give up*에 대한 절반의 답이다.** 나머지 절반은 Architect의 `none` 확신도, 그리고 예산 산수다.

## 5. 세 레포에서 가져오지 않은 것 — 이유와 함께

| 버린 것 | 출처 | 이유 |
|---|---|---|
| `git log` 기반 판단 전부 | mark-pattern, ponytail | 히스토리가 없다. 넣으면 지어낸 커밋 주장을 만든다 |
| churn × complexity 타깃 선정 | mark-pattern `refactor.md` | 레포 전체를 못 본다 |
| 결정 기록 템플릿 | mark-pattern `decisions.md` | 파일을 쓸 수 없고, 써도 채점되지 않는다 |
| `ponytail:` 천장 주석 | ponytail | 주석 한 줄이 diff 표면을 늘리고 SEARCH 정확 일치를 깰 수 있다 |
| ONE runnable check | ponytail | 채점기가 테스트를 준다. 우리가 더하면 테스트 수집을 깬다 |
| 재현 테스트 먼저 쓰기 | karpathy §4 | 같은 이유 |
| 강도 lite/full/ultra | ponytail | 한 턴에 강도는 하나다 |
| 출력 렌더링 규칙 전부 | mark-pattern, ponytail | 우리 답 형식은 채점기가 정한다 |
| 하드웨어 보정 조항 | ponytail | 해당 도메인이 없다 |
| 디렉터리 이름 패스 | mark-pattern `review-passes.md` 패스 1 | 트리를 못 본다 |

## 6. 방법론에 대한 메모 — 프롬프트를 어떻게 쓸 것인가

mark-pattern이 자기 설계 근거로 적어 둔 두 문장이 우리 프롬프트 전체에 적용된다.

> "**Prohibitions backfire.** In head-to-head tests, a "don't do X" instruction produced *more* of the unwanted output than a positive recipe — and trended worse than no guidance at all. Agents negotiate with "don't". A recipe leaves nothing to negotiate."

> "**Shouting does not help.** Current models follow the system prompt more literally, so `CRITICAL: YOU MUST` now causes *over*triggering rather than compliance."

그리고 ponytail의 대조군이 같은 방향을 가리킨다 — 산문 지시 0/3, 절차 지시 6/6.

**결론: 금지 목록이 아니라 채울 칸으로 쓴다. 대문자 강조를 쓰지 않는다. 지시는 절차로 쓴다.**

우리 기존 프롬프트가 이 기준으로 보면 금지문이 많다. 다만 채점기 형식 규칙은 성격이 다르다 — 그것은 협상 대상이 아니라 파서의 사실이고, 사실은 사실로 적는다.
