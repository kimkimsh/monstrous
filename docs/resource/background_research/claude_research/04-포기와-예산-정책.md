# 04. 포기와 예산 정책 — 판단이 아니라 산수여야 하는 이유

> Q4: **포기 판단을 누가 하는가 — 에이전트인가 산수인가?**
>
> 결론 먼저: **산수다.** "토큰 N개 안에 끝내라"는 프롬프트 지시는 지켜지지 않는다는 것이 s1 논문의 실측이고, 모델의 자기 확신도는 정확도를 추적하지 못한다는 것이 캘리브레이션 문헌의 일치된 결론이다. 작동하는 것은 **디코딩/설정 레벨의 하드 캡**과 **러너 레벨의 잔액 산수**뿐이다.
>
> 이 트랙에서 이 문제는 특히 크다 — 문제 지문이 *"which ones determine when it is time to give up"* 을 명시적으로 물었고, 토큰 효율은 30점이면서 동시에 40점의 동점 처리 기준이다.

## 1. 프롬프트로 예산을 부탁하면 안 지켜진다

### s1: Simple test-time scaling

[arXiv 2501.19393](https://arxiv.org/abs/2501.19393) · [코드](https://github.com/simplescaling/s1)

논문의 기여 중 이번 트랙에 직결되는 것이 **budget forcing** 이다:

> we develop **budget forcing** to control test-time compute by **forcefully terminating** the model's thinking process or lengthening it by appending "Wait" multiple times to the model's generation when it tries to end.

핵심은 "forcefully" 다. 즉 **디코딩 개입**이지 프롬프트 지시가 아니다. 구현도 그렇게 되어 있다:

```python
# github.com/simplescaling/s1 — vLLM with budget forcing (발췌)
MAX_TOKENS_THINKING = 32000
sampling_params = SamplingParams(
    max_tokens=MAX_TOKENS_THINKING,   # ← 하드 캡
    min_tokens=0,
    stop_token_ids=stop_token_ids,
)
# 사고를 늘릴 때: end-of-thinking 토큰을 무시하고 "Wait"를 이어붙임
```

[alphaXiv 요약](https://www.alphaxiv.org/abs/2501.19393): *"**Maximum Token Forcing**: When the model exceeds a desired thinking budget, generation is terminated by **forcefully inserting an end-of-thinking token**."*

**함의**: 모델은 자기 토큰을 세지 못한다. 예산은 요청 파라미터(`max_tokens`)와 오케스트레이터 설정에서 강제해야 한다.

### AI:GO에서 이 레버가 어디에 있는가

`../../track_resource/lableup/03-AIGO-Squad-완전가이드.md` 7절 기준:

| 층위 | 수단 | LLM 관여 |
|---|---|---|
| **1** | 요청 파라미터 `max_tokens` (AI:GO CLI `--max-tokens`) | 0 |
| **2** | AI:GO Budget Config — `Max agent turns`, `Max tokens per task`, `Max tokens per agent`, `Max total tokens`, `Max tasks per plan`, `Max plan iterations`, `Task timeout` | 0 |
| **3** | 러너 산수 — 잔액 < 다음 시도 견적이면 다음 호출을 하지 않음 | 0 |
| (4) | reasoning 모델 대상: `--no-think` / `--thinking-budget N` / `--reasoning-effort none` | 0 |

층위 4에 주의. **`Qwen3-30B-A3B-Instruct-2507`은 non-thinking 전용 모델이라 이 레버가 무의미하다**([모델 카드](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507): *"This model supports only non-thinking mode and does not generate `<think>` blocks... specifying `enable_thinking=False` is no longer required."*). 층위 4는 **나머지 두 reasoning 모델을 쓰기로 한 경우에만** 의미가 있다.

AI:GO 공식 경고도 예산 설계에 반영해야 한다: *"Token counting is **approximate** and may slightly exceed configured limits before the system detects the overage."* → 한도는 캡보다 여유를 두고 잡을 것.

### AI:GO 안전 이벤트 — 시각화에 그대로 쓸 수 있는 어휘

| 이벤트 | 발생 조건 | 동작 |
|---|---|---|
| `squad:budget-warning` | 경고 임계값 도달 (기본 80%) | 예산 미터 강조 |
| `squad:budget-exceeded` | 어떤 한도든 도달 | 실행 자동 일시정지, 새 태스크 시작 안 함 |
| `squad:emergency-stopped` | 급격한 토큰 소비 | 전 에이전트 즉시 중지, 상태 **failed** |

## 2. "확신도로 판단"은 왜 위험한가 — 캘리브레이션 문헌

우리 초안은 "무료 신호 두 개가 엇갈릴 때만 승급"을 제안했다. 여기서 쓰이는 신호가 **모델의 자기 확신도**라면 문제가 있다.

### 언어화된 확신도는 과신한다

| 출처 | 발견 |
|---|---|
| [Wired for Overconfidence (arXiv 2604.01457)](https://arxiv.org/html/2604.01457v2) (프리프린트) | *"LLMs are often **not just wrong, but confidently wrong**."* 확신도 인플레이션은 중후반 레이어의 소수 MLP/attention head가 만들며, **정답 여부와 거의 무관하게** 작동한다 (*"largely answer-independent"*) |
| [Reasoning about Uncertainty: Do Reasoning Models Know When They Don't Know? (EACL 2026 Findings)](https://aclanthology.org/2026.findings-eacl.178/) | reasoning 모델은 (i) 대체로 **과신**하고, (ii) **깊게 추론할수록 더 과신**한다 |
| [Thinking Out Loud (EMNLP 2025)](https://aclanthology.org/2025.emnlp-main.73/) | reasoning 모델은 자기 지식 경계 인식이 **약해진다** — 사실성 벤치마크에서 "모르겠다" 응답률이 유의하게 낮다. 저자들은 이를 *"reasoning tax"* 라고 부른다. 그리고 **짧거나 덜 정교한 추론을 낼 때 오히려 확신도를 높게 표현**한다 |
| [Reasoning Models Better Express Their Confidence (NeurIPS 2025)](https://proceedings.neurips.cc/paper_files/paper/2025/file/95ee7181fe256439dca74ec794b33bb6-Paper-Conference.pdf) | **반대 방향의 결과.** reasoning 모델이 non-reasoning 대비 36개 설정 중 **33개**에서 더 나은 캘리브레이션. 원인은 slow thinking(대안 탐색·백트래킹) |

**문헌이 갈린다.** 하지만 우리 조건에서는 갈리지 않는다:

- 마지막 논문의 이득은 **slow thinking에서 나온다**. 우리 주력 모델은 non-thinking 전용이고, 토큰 캡 때문에 긴 사고를 살 수도 없다.
- `03`에서 본 GPQA 실험: 다수결 일치율 게이트와 토큰 엔트로피 게이트 **둘 다** 정확도를 개선하지 못했다(차이 0.002 미만).

> **결론: 모델의 확신도(언어화된 것이든 일치율이든)를 포기·승급의 유일한 근거로 삼지 마라.** 결정론적 신호(형식 검사 통과 여부)를 1순위로, 확신도는 참고 지표로만.

한 가지 예외 — [Strategies for Eliciting Calibrated Confidence Scores (2023)](https://openreview.net/forum?id=g3faCfrwm7)는 RLHF 모델에서 **언어화된 확신도가 조건부 확률보다 낫다**(ECE 상대 50% 감소)고 보고한다. 즉 확신도를 쓴다면 logprob이 아니라 **모델이 말로 뱉게 하는 쪽**이 낫다. 다만 그것도 과신 편향은 남는다.

## 3. 조기 종료 — 이건 실제로 돈이 된다

### Adaptive Consistency

[Diminishing Returns 논문](https://arxiv.org/html/2511.00751v2)이 인용하는 선행 연구:

> Adaptive-Consistency [Aggarwal et al.] dynamically halts sampling once answers converge, reducing [sample count] up to **7.9×** while dropping accuracy by **less than 0.1%**. Criteria-based early stopping cuts sample usage by roughly **70%** with similarly negligible accuracy loss.

**샘플을 쓸 거라면 고정 n이 아니라 수렴 시 중단.** 다만 `03`에서 본 대로 어려운 문항에서는 일치가 곧 정답을 뜻하지 않으므로, 조기 중단은 **비용 절감 장치이지 정확도 장치가 아니다**.

### 트랙별 프로그램 규칙 (LLM 호출 0회)

| 트랙 | 조기 종료 규칙 | 근거 |
|---|---|---|
| **generic** | 답 문자가 유효 `option_letters` 안에 있으면 **즉시 종료**. 검증 웨이브 없음 | 채점이 `letter_match`. 추가 웨이브의 기대 이득 < 비용 |
| **math** | `\boxed{}`가 `answer_format`에 부합하면 종료. `integer`인데 수식이면 **1회 재시도** | 채점이 `integer_exact` + `math_verify` |
| **coding / livecodebench** | (로컬 실험 시) `public_test_cases`로 실행 검증. 통과 시 즉시 종료 | 로컬에서만 가능 — 평가 중엔 도구 없음 |
| **coding / swebench** | Preflight 8개 검사 전부 통과 시 종료. 실패 시 **구체 신호 + 1회 재시도** 후 포기 | `03` 참고 |

### 잔액 산수 (층위 3)

```
if (남은 토큰 예산) < (다음 시도의 보수적 견적):
    다음 호출을 하지 않는다
```

견적은 연습 세트 실측으로 채운다. 이 규칙 하나가 **캡 초과로 인한 `capped`(팀 책임)** 를 구조적으로 막는다.

## 4. 모델 cascade — 싼 것부터, 필요할 때만 비싼 것

이번 트랙에서 모델은 3개(instruct 1 + reasoning 2)이고 단가가 다르다. 그러면 cascade가 성립한다.

### FrugalGPT

[arXiv 2305.05176](https://doi.org/10.48550/arxiv.2305.05176) · TMLR 게재본 · [코드](https://github.com/stanford-futuredata/FrugalGPT)

세 가지 비용 절감 전략:
1. **prompt adaptation** — 더 짧은 프롬프트
2. **LLM approximation** — 캐시·파인튜닝으로 비싼 모델 대체
3. **LLM cascade** — 싼 모델부터 순차 호출, 신뢰도가 충분하면 거기서 종료

구성 요소 둘: **generation scoring function** `g(q,a) → [0,1]` 와 **router**(어떤 모델을 어떤 순서로).

결과: 최고 개별 모델(GPT-4)의 성능을 **최대 98% 비용 절감**으로 재현하거나, 같은 비용에서 정확도 **+4%**. 데이터셋별 절감폭 **50~98%**.

> **우리 트랙 적용**: instruct 모델을 1차로 쓰고, **형식 검사에 걸린 문항에만** reasoning 모델을 2차로 쓰는 cascade가 가능하다. 단 두 가지 주의:
> 1. reasoning 모델은 토큰 캡을 **10배 세게** 맞는다(리더보드 경고). 승급 대상 문항 수를 엄격히 제한해야 한다.
> 2. FrugalGPT의 scoring function은 별도 학습 모델(DistilBERT)이었다. 우리는 **Preflight 통과 여부**라는 이진 신호를 scoring function으로 쓴다 — 학습이 필요 없고 결정론적이다. 이게 오히려 더 나은 선택이다.

관련: [Nadir](https://getnadir.com/blog/frugalgpt-cascade-routing-implementation-tutorial)(상용, 프리프린트 아님)의 설계 논지가 우리와 같다 — *"Other routers predict a model from the prompt alone and ship whatever that model produces... **Nadir reads the cheap-model answer before shipping**, so routing mistakes are recoverable rather than absorbed."* **프롬프트만 보고 라우팅하지 말고, 싼 모델의 답을 보고 승급을 결정하라.**

## 5. 종료 조건을 명시하지 않으면 실패한다 — MAST 근거

MAST 14개 실패 모드 중 종료·검증 관련:

- **FM-1.5 Unaware of termination conditions** — 태스크 완료를 인지하지 못함 (FC1, 41.77% 범주)
- **FM-3.1 Premature termination** — 목표 달성 전 종료 (FC3, 21.30% 범주)
- **FM-1.3 Step repetition** — 완료된 단계를 불필요하게 반복

**조기 종료와 늦은 종료가 둘 다 실패 모드로 등재되어 있다.** 즉 "언제 멈추는가"는 튜닝 파라미터 하나가 아니라 **명시적으로 설계해야 하는 계약**이다.

Anthropic의 evaluator-optimizer 경고도 같은 말을 한다:

> **Set clear stopping criteria before you start iterating.** Define maximum iteration counts and specific quality thresholds. Without these guardrails, you can end up in expensive loops where the evaluator keeps finding minor issues and the generator keeps tweaking, but **quality plateaus well before you stop iterating**.

## 6. 예산 초기값 제안 — 리서치 반영본

`../../track_resource/lableup/09-스쿼드-설계-전략.md`의 초안을 이 문서의 근거로 조정했다. **전부 가설이며 연습 세트로 스윕해야 한다.**

| 설정 | AI:GO 기본 | 초안 | **리서치 반영 제안** | 변경 이유 |
|---|---|---|---|---|
| Max total tokens | 100,000 | coding 80k / math 8k / generic 3k | coding 80k / math 8k / **generic 6k** | generic에 CoT가 필요하다(→ `07`). 3k는 너무 빡빡할 수 있음 |
| Max tokens per agent | 30,000 | coding 30k / 그 외 3k | 동일 | |
| Max tokens per task | 10,000 | coding 20k / math 2k / generic 800 | coding 20k / math 2k / **generic 1,500** | 위와 같음 |
| Max concurrent agents | 3 | 2 | **2** | 웨이브가 직렬 |
| Max tasks per plan | 20 | 6 | **6** | |
| Max plan iterations | 3 | 1 | **1** | 재계획은 통째로 비쌈 |
| Max agent turns | 20 | coding 6 / math 3 / generic 1 | coding **4~6** / math 3 / **generic 2** | s1: 하드 캡이 유일하게 작동하는 레버. coding은 스윕 필수 |
| Execution timeout | 1,800s | 캡 아래 | 캡 아래 | |
| Task timeout | 300s | 120s | **120s** | |
| Warning threshold | 80% | 70% | **70%** | 근사 카운팅 여유 |

`max_tokens` (요청 레벨 하드 캡) 제안:

| 트랙 | 초안 | **리서치 반영** | 이유 |
|---|---|---|---|
| generic | 4 | **512~1,024** | MMLU-Pro는 CoT가 필요. 답만 4토큰으로 뽑으면 **정확도가 크게 떨어진다**(→ `07`). 짧은 CoT(Chain-of-Draft 스타일) + 마지막 문자 |
| math | 32~64 | **1,024~2,048** | `\boxed{}`만 32토큰으로 제한하면 풀이 자체가 불가능. AIME는 특히 |
| coding / swebench | 1,000~2,000 | **2,048~4,096 + 꼬리 예산** | 잘림 = `extraction_failed`(팀 책임) |

> **초안 대비 가장 큰 수정이 여기 있다.** `max_tokens: 4` 같은 극단적 절약은 `extraction_failed`와 정확도 붕괴를 동시에 부른다. 절약은 **불필요한 서두·설명을 없애는 프롬프트**로 하고, `max_tokens`는 안전 상한으로만 쓴다. 근거: `07`의 MMLU-Pro CoT 효과, `05`의 Chain-of-Draft.

## 7. 이 문서의 결론

1. **프롬프트로 토큰 예산을 부탁하는 것은 작동하지 않는다.** s1이 실측했고, 작동한 것은 강제 종료(하드 캡)뿐이다.
2. **모델의 확신도를 포기 근거로 쓰지 마라.** 언어화 확신도는 정답 여부와 거의 무관하게 인플레이션되고, 다수결 일치율 게이트는 GPQA에서 실패했다.
3. **작동하는 3층 구조**: `max_tokens` 하드 캡 → AI:GO Budget Config → 러너 잔액 산수. **전부 LLM 호출 0회.**
4. **조기 종료는 비용 장치다.** 수렴 시 중단은 샘플 수를 7.9배까지 줄이면서 정확도 손실 0.1% 미만.
5. **cascade는 성립한다.** 단 scoring function은 학습 모델이 아니라 **Preflight 통과 여부**로. 그리고 reasoning 모델 승급 문항 수를 엄격히 제한.
6. **종료 조건은 명시적 계약이어야 한다.** MAST에서 조기 종료와 종료 인지 실패가 둘 다 별도 실패 모드다.
7. **초안의 `max_tokens: 4` 류 극단 절약은 철회 권장.** → `07`, `10`
