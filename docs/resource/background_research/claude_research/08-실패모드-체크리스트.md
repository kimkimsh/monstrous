# 08. 실패 모드 체크리스트 — MAST 14개를 우리 스쿼드에 1:1 대응

> 설계 리뷰용 문서. **MAST(Multi-Agent System Failure Taxonomy)의 14개 실패 모드를 우리 스쿼드 구성에 하나씩 대입**하고, 각각에 대한 방어 수단과 미비점을 적었다.
>
> 출처: [Why Do Multi-Agent LLM Systems Fail? (arXiv 2503.13657, NeurIPS 2025)](https://arxiv.org/abs/2503.13657) — 7개 MAS 프레임워크 × 1,642개 실행 트레이스 주석, inter-annotator Cohen's κ = 0.88.

---

## 0. MAST를 왜 쓰는가

세 가지 이유다.

1. **경험적으로 만들어진 유일한 MAS 실패 분류 체계다.** 저자들이 grounded theory로 200개 이상 트레이스에서 귀납했고, 개발에 쓰지 않은 별도 세트로 검증했다.
2. **논문의 핵심 주장이 우리 상황과 정확히 겹친다** — *"many MAS failures arise from the challenges in **organizational design and agent coordination** rather than the limitations of individual agents"*, 그리고 *"improvements in the base model capabilities will be insufficient."* 우리는 모델을 못 바꾸고 구조만 바꿀 수 있다.
3. **시각화 30점에 바로 쓸 수 있는 어휘다.** 주최 측 `FailureKind`/`FailureOwner` 열거형과 병기하면 "우리 실패 분류는 학계 표준 + 주최 표준 두 축"이라는 서사가 된다.

범주별 비중: **FC1 Specification 41.77% / FC2 Inter-Agent Misalignment 36.94% / FC3 Task Verification 21.30%**.

개선 실험 결과도 기억해 둘 것 — ChatDev에 다단계 검증 추가 **+15.6%p**, 역할 명세 개선 **+9.4%p**. 하지만 저자 결론은 *"simple fixes are still insufficient"*.

---

## 1. FC1 — Specification Issues (41.77%)

### FM-1.1 Disobey task specification (태스크 명세 불이행)

**정의**: 태스크 제약을 지키지 않음.

| 우리 스쿼드에서 어떻게 나타나나 | 방어 | 상태 |
|---|---|---|
| Editor가 SEARCH/REPLACE 대신 unified diff를 출력 | Preflight C2 (3마커 검사) | ✅ |
| Solver가 보기 문자 대신 문장으로 답 | Preflight G1/G2 | ✅ |
| math integer 문항에 수식 출력 | Preflight M2 | ✅ |
| 응답에 마크다운 펜스가 섞여 파싱 실패 | 출력 계약에 명시 + Preflight | ⚠️ 펜스 검사 항목 추가 필요 |

**이번 트랙에서 이 실패의 이름은 `extraction_failed`이고 팀 책임이다.** MAST에서 가장 큰 범주에 속한다는 사실이 Preflight의 존재 이유를 뒷받침한다.

### FM-1.2 Disobey role specification (역할 명세 불이행)

**정의**: 배정된 책임을 따르지 않음.

| 나타남 | 방어 | 상태 |
|---|---|---|
| Architect가 앵커만 내야 하는데 패치까지 써버림 | 출력 계약 + 러너에서 형식 파싱 (JSON 아니면 반려) | ⚠️ |
| Router가 라우팅만 해야 하는데 문제를 풀기 시작 | `max_tokens` 소량 하드 캡 | ✅ |
| Editor가 앵커 밖 파일을 수정 | Preflight C3 (path ∈ 컨텍스트 발췌 집합) | ✅ |

> **주의**: `02`에서 본 persona 연구는 역할을 **말로** 강조해도 지켜지지 않는다고 했다. 역할 준수는 **프롬프트가 아니라 파서와 캡으로** 강제해야 한다.

### FM-1.3 Step repetition (단계 반복)

**정의**: 완료된 단계를 불필요하게 반복.

| 나타남 | 방어 | 상태 |
|---|---|---|
| Editor가 같은 실패를 반복 시도 | 재시도 1회 하드 제한 + 실패 신호에 이전 시도 요약 첨부 | ✅ |
| Router가 재계획을 반복 | `Max plan iterations = 1` | ✅ |
| 같은 SEARCH 블록을 여러 번 출력 | Preflight (중복 블록 검사) | ⚠️ 항목 추가 필요 |

### FM-1.4 Loss of conversation history (대화 이력 소실)

**정의**: 예기치 않은 컨텍스트 절단.

| 나타남 | 방어 | 상태 |
|---|---|---|
| 토큰 캡에 걸려 컨텍스트가 잘림 | 잔액 산수(층위 3) + 꼬리 예산 예약 | ✅ |
| Editor에게 넘긴 발췌가 축약되어 SEARCH 원문이 사라짐 | **packet은 요약이 아니라 원문 hunk를 나른다** | ✅ 설계에 반영됨 |
| 컨텍스트가 길어져 앞부분 정보를 못 씀 (context rot) | 앵커로 읽는 양 축소 (→ `05`) | ✅ |

### FM-1.5 Unaware of termination conditions (종료 조건 인지 실패)

**정의**: 태스크 완료를 인식하지 못함.

| 나타남 | 방어 | 상태 |
|---|---|---|
| 정답을 냈는데 계속 검토 | 프로그램 조기 종료 규칙 (→ `04`) | ✅ |
| GiveUp 판단을 LLM에게 맡김 | **산수로 대체** (s1 근거) | ✅ |

## 2. FC2 — Inter-Agent Misalignment (36.94%)

이 범주가 우리에게 가장 위험하다. `01`·`02`에서 본 Anthropic의 "telephone game"이 정확히 이 범주다.

### FM-2.1 Conversation reset (대화 초기화)

**정의**: 근거 없이 대화를 다시 시작.

| 나타남 | 방어 | 상태 |
|---|---|---|
| 재시도 시 이전 시도 맥락을 버리고 처음부터 | 재시도 프롬프트에 이전 시도 + 실패 사유 첨부 | ✅ (그리고 이게 캐시 프리픽스도 늘린다) |

### FM-2.2 Fail to ask for clarification (명확화 요청 실패)

**정의**: 필요한 정보를 요청하지 못함.

| 나타남 | 방어 | 상태 |
|---|---|---|
| Editor가 앵커가 불충분한데도 추측으로 SEARCH를 씀 → **코드를 기억으로 지어냄** | Preflight C4(글자 일치 검사)가 사후에 잡음. 사전 방어는 없음 | ⚠️ **미비.** Architect가 앵커 신뢰도를 함께 내고, 낮으면 발췌를 넓히는 규칙 검토 |

**이것이 우리 설계의 가장 큰 구멍이다.** 평가 중 도구가 없어 "더 물어볼" 대상이 없다. 유일한 완화책은 앵커를 복수(상위 2~3개)로 내고 발췌 범위를 넉넉히 잡는 것.

### FM-2.3 Task derailment (태스크 이탈)

**정의**: 의도한 목표에서 벗어남.

| 나타남 | 방어 | 상태 |
|---|---|---|
| coding 문항인데 Solver 경로로 감 | Router의 `payload.kind` 분기 + 러너 검증 | ✅ |
| 이슈와 무관한 리팩터링 패치 | Preflight C3/C5 (path·유일성) 부분 방어 | ⚠️ 의미적 이탈은 못 잡음 |

### FM-2.4 Information withholding (정보 은닉)

**정의**: 중요한 통찰을 공유하지 않음.

| 나타남 | 방어 | 상태 |
|---|---|---|
| Architect가 앵커는 냈지만 "왜"를 안 남겨 Editor가 오판 | 앵커에 `why` 필드 필수 (RGFL 근거, → `06`) | ✅ |
| 실패 사유가 "실패"로만 전달됨 | Preflight가 **블록 번호 + 안 맞는 줄 + 가장 가까운 후보**를 반환 | ✅ |

### FM-2.5 Ignored other agent's input (타 에이전트 입력 무시)

**정의**: 다른 에이전트의 입력·권고를 무시.

| 나타남 | 방어 | 상태 |
|---|---|---|
| Editor가 앵커를 무시하고 다른 위치를 고침 | Preflight C3 (path 검사) + 앵커 밖 줄 범위 검사 | ⚠️ 줄 범위 검사 항목 추가 권장 |
| 재시도 시 실패 신호를 반영하지 않음 | 두 번째 실패는 즉시 give_up (반복 방지) | ✅ |

### FM-2.6 Reasoning-action mismatch (추론-행동 불일치)

**정의**: 논리와 실행의 불일치.

| 나타남 | 방어 | 상태 |
|---|---|---|
| "이 줄을 고쳐야 한다"고 써 놓고 다른 줄을 SEARCH에 넣음 | Preflight C4/C5 | ✅ |
| 장부(ledger)에 적은 것과 실제 출력이 다름 | **장부가 응답 본문 안에 있으므로 구조적으로 어긋날 수 없다** | ✅ 우리 설계의 강점 |

## 3. FC3 — Task Verification (21.30%)

### FM-3.1 Premature termination (조기 종료)

**정의**: 목표 달성 전에 종료.

| 나타남 | 방어 | 상태 |
|---|---|---|
| `max_tokens` 부족으로 마지막 PATCH 블록이 잘림 | 꼬리 예산 예약 + Preflight C8 | ✅ |
| 재시도 1회 제한 때문에 풀 수 있는 문항을 포기 | **의도된 트레이드오프.** 재시도 상한을 연습 세트로 스윕 | ⚠️ 측정 필요 |
| generic에서 CoT를 못 쓰게 해 정답을 놓침 | → `07`에서 정책 변경 | ✅ 수정됨 |

### FM-3.2 No or incomplete verification (검증 없음/불완전)

**정의**: 출력 검사가 불충분.

| 나타남 | 방어 | 상태 |
|---|---|---|
| 형식만 보고 의미를 안 봄 | 인정. **평가 중 테스트 실행이 불가능하므로 의미 검증은 원리적으로 불가** | ⚠️ 한계로 명시 |
| SEARCH 블록 유일성 미검사 | Preflight C5 (SWE-Edit 근거로 추가됨) | ✅ |

MAST 논문의 관련 지적: *"sole reliance on final-stage, low-level checks is inadequate."* 우리는 그 "final-stage, low-level check"에 크게 의존한다. **다만 도구 없는 조건에서 그것이 가능한 최선이라는 점을 시각화에서 정직하게 표시**하는 것이 낫다.

### FM-3.3 Incorrect verification (잘못된 검증)

**정의**: 부적절한 검증.

| 나타남 | 방어 | 상태 |
|---|---|---|
| LLM 검증자가 맞는 답을 틀렸다고 반려 | **LLM 검증자를 쓰지 않는다** (→ `03`) | ✅ |
| Preflight 자체의 버그로 정상 출력을 반려 | 연습 세트 121문항으로 Preflight 회귀 테스트 | ⚠️ **반드시 해야 함** |

> **Preflight가 우리 시스템의 단일 실패점이다.** 결정론적이라는 것은 "틀리면 항상 틀린다"는 뜻이기도 하다. 연습 세트로 false-positive/false-negative 비율을 실측하고, 특히 **정상 출력을 반려하는 경우**를 0에 가깝게 만들어야 한다.

## 4. MAST 밖의 실패 — 이번 트랙 고유

MAST는 일반 MAS를 다루므로 이번 트랙의 인프라·정책 실패는 다루지 않는다. 주최 측 열거형으로 보완한다.

| 실패 | 주최 분류 | 우리 방어 |
|---|---|---|
| 평가 엔드포인트 간헐적 장애 (한 오후 5회 관측) | `infrastructure_failed` / owner `organizer` | 러너가 네트워크 오류를 **모델 실패와 분리 기록** |
| AI:GO failure-as-context — 재시도 안 된 connect timeout이 "실행 완료, 전 태스크 실패"로 보고 | 위와 같으나 **잘못 분류되면 팀 0점** | 러너 레벨에서 명시적 재시도 + 별도 status |
| 토큰 캡 초과 | `capped_tokens` / owner `team` | 잔액 산수 (→ `04`) |
| wall-clock 캡 초과 | `capped_wallclock` / owner `team` | Task timeout 120초, 웨이브 최소화 |
| 채점기 오류 | `grader_error` / owner `organizer` | 분모에서 제외됨. 우리가 할 일 없음 |

`../../example_task/00-트랙-정리.md`의 경고 원문:

> Without this field an outage is indistinguishable from a squad that answered badly, and AI:GO's failure-as-context semantics turn an unretried connect timeout into "execution completed, all tasks failed", which grading would read as a team's zero.

> **시각화에서 이 구분을 보여주면 그 자체가 점수다** (→ `09`). 실패 소유권 Sankey 다이어그램이 이 어휘 위에 서 있다.

## 5. 설계 리뷰 체크리스트 — 이 표만 보고 점검

| # | 항목 | MAST 대응 | 확인 |
|---|---|---|---|
| 1 | 모든 에이전트 출력에 **파서가 있고** 파싱 실패 시 반려하는가 | FM-1.1, FM-1.2 | ☐ |
| 2 | 역할 준수를 프롬프트가 아니라 **캡·파서로** 강제하는가 | FM-1.2 | ☐ |
| 3 | 재시도 상한이 **하드 코딩**되어 있는가 | FM-1.3 | ☐ |
| 4 | 핸드오프가 요약이 아니라 **원문 hunk**를 나르는가 | FM-1.4, FM-2.4 | ☐ |
| 5 | 마지막 출력 블록의 **꼬리 예산**이 예약되어 있는가 | FM-3.1 | ☐ |
| 6 | 종료 조건이 **프로그램 규칙**으로 명시되어 있는가 | FM-1.5 | ☐ |
| 7 | 재시도 프롬프트에 **구체적 실패 사유**가 붙는가 | FM-2.1, FM-2.4 | ☐ |
| 8 | 앵커가 **복수**이고 `why`가 붙는가 | FM-2.2, FM-2.4 | ☐ |
| 9 | Editor 출력의 path·줄범위가 **앵커 안**인지 검사하는가 | FM-2.5 | ☐ |
| 10 | SEARCH 블록 **유일성**을 검사하는가 | FM-3.2 | ☐ |
| 11 | **LLM 검증자를 쓰지 않는가** | FM-3.3 | ☐ |
| 12 | Preflight의 **false-positive 비율**을 연습 세트로 측정했는가 | FM-3.3 | ☐ |
| 13 | 네트워크 오류와 모델 실패를 **분리 기록**하는가 | 트랙 고유 | ☐ |
| 14 | 잔액 산수가 **다음 호출 전에** 돌아가는가 | 트랙 고유 (`capped`) | ☐ |

## 6. 이 문서에서 나온 설계 변경 요청 다섯

리뷰 결과 초안에 없던 항목이다.

1. **Preflight에 SEARCH 블록 유일성 검사 추가** (C5) — SWE-Edit Editor 프롬프트 규칙 4.
2. **Preflight에 중복 SEARCH 블록 검사 추가** — FM-1.3.
3. **Preflight에 마크다운 펜스 검사 추가** — FM-1.1.
4. **Editor 출력의 줄 범위가 앵커 안인지 검사 추가** — FM-2.5.
5. **Preflight 자체의 회귀 테스트를 연습 세트 121문항으로 구축** — FM-3.3. Preflight가 단일 실패점이므로 필수.
