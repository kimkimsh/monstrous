## 2. 설계를 **금지**하는 제약 여섯

리서치를 시작하기 전에 이걸 먼저 못 박아야 한다. 논문에서 좋다고 나온 기법의 절반이 여기서 걸러진다.

### 금지 1 — 평가 중 도구가 없다

> "your squad has no tools during a run and never browses a repository" (제출 포털 practice-sets 페이지)

AI:GO 공식 문서도 같은 방향으로 잠근다: 임의 호스트 경로를 다루는 도구(`list_directory`, `search_files`, `execute_python` 등)는 **도구 설정과 무관하게 모든 squad 에이전트에게 차단**된다.

**걸러지는 기법**: ReAct 류 도구 루프, 저장소 탐색 에이전트, 테스트 실행 기반 self-repair(SWE-agent, OpenHands 방식), RAG, 웹 검색, 코드 실행 검증.

**살아남는 기법**: 주어진 컨텍스트 안에서의 localization, 형식 검증, 샘플링·투표, 프롬프트 구조 최적화.

### 금지 2 — 템플릿은 하나다

Squad Template JSON **1개**가 세 트랙을 전부 처리해야 한다. 트랙 분기는 Planner의 시스템 프롬프트와 트랙별 one-shot 프롬프트 안에서만 일어날 수 있다.

**걸러지는 기법**: 트랙별 전용 스쿼드, 트랙별 다른 에이전트 수.
**살아남는 기법**: 하나의 그래프 안에서 `payload.kind`로 분기하는 라우팅(→ `01`의 Routing 워크플로).

### 금지 3 — Planner는 정확히 한 명

AI:GO 스펙이 강제한다. "여러 planner가 협의한다" 류 구조는 만들 수 없다.

### 금지 4 — 상한이 있다

문항당 **wall-clock 캡**, 실행당 **토큰 캡**. 실제 숫자는 미공개이며 실행 기록(`PublishedCaps`)에만 남는다. 그리고 리더보드가 직접 경고한다:

> Two of the three evaluation models are reasoning models — one was measured spending **97% of its output budget on reasoning tokens** before it answered — so a token cap bites roughly **an order of magnitude harder** on a squad built from reasoning models.

**걸러지는 기법**: 긴 CoT를 전제로 한 test-time scaling, tree-of-thought, 대규모 self-consistency(n≥16).

### 금지 5 — 제출 자체가 비용이다

제출 실행은 전액 과금, AI:GO test run은 1/5. 대기 3개 / 동시 1개. Check는 무료·무제한.

**걸러지는 기법**: "일단 넣고 리더보드 보면서 튜닝".

### 금지 6 — 출력 형식이 곧 점수다

coding 트랙의 출력은 unified diff가 **아니라** `*** PATCH START ***` + `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` 블록이다. 형식이 틀리면 정답을 알아도 0점이고, 그것도 `extraction_failed`라는 **팀 책임** 분류로 기록된다.

세 트랙 공통 규칙 한 줄이 중요하다:

> If more than one appears, **the last one is used. Anything before it is ignored, not penalised.**

→ 응답 본문의 앞부분은 **감점 없는 자유 공간**이다. (우리 LEDGER 설계가 이 규칙 위에 서 있다.)

## 3. 설계를 **강제**하는 사실 넷

### 강제 1 — coding이 점수의 절반인데 문항은 가장 적다

| 트랙 | hidden 문항 수 (추정) | 가중치 | 문항 하나의 점수 기여 |
|---|---|---|---|
| coding | 140 ~ 240 | **0.50** | **크다** |
| generic | 448 ~ 698 | 0.25 | 작다 |
| math | 60 ~ 66 (× 2회 반복) | 0.25 | 중간 |

coding 문항 하나가 generic 문항 하나보다 대략 10배 넘게 무겁다. 그런데 coding 문항 하나의 입력이 **60,000자(≈16,000~20,000 토큰)** 다.

→ **예산 배분의 방향이 여기서 결정된다.** generic에 n배 샘플링을 붓는 것은 대개 손해고, 그 예산은 coding으로 가야 한다.

### 강제 2 — math는 2회 반복 실행된다

`run_repeats: 2`. 같은 문제를 2회 돌려 평균. **math의 토큰 비용은 문항 수 대비 2배**로 계산해야 한다. 그리고 지문이 매우 짧으므로(중앙값 491바이트) math 비용은 거의 전부 **출력 토큰**이다.

### 강제 3 — 컨텍스트는 judge가 잘라서 준다

SWE-bench 문항의 저장소 코드는 judge가 검색해 문항당 **60,000자**로 잘라 요청 본문에 넣어준다. 중앙값 59,966자, 발췌 10개, 후보 696개.

→ coding 트랙의 실력은 "코드를 잘 찾는 능력"이 아니라 **"주어진 60KB 발췌만 보고 적용되는 패치를 쓰는 능력"** 이다. 그런데 60KB는 context rot이 확실히 작동하는 길이다(→ `05`).

### 강제 4 — 실패 원인 분류 어휘가 이미 정해져 있다

`Outcome`: `graded` / `extraction_failed` / `capped` / `grader_error` / `infrastructure_failed`
`ItemStatus`: `ok` / `capped_tokens` / `capped_wallclock` / `error`
`FailureKind`: `infrastructure` / `upstream_error` / `token_cap` / `wallclock_cap` / `runner`
`FailureOwner`: `team` / `policy` / `configuration` / `organizer`

`grader_error`와 `infrastructure_failed`는 주최 책임이며 순위 분모에서 빠진다. `extraction_failed`와 `capped`는 팀 책임이다.

→ 시각화는 이 어휘를 **그대로** 쓰는 것이 유리하다(심사위원 학습 비용 0). 그리고 러너는 네트워크 실패와 모델 실패를 반드시 구분 기록해야 한다 — AI:GO의 failure-as-context 의미론 때문에 재시도되지 않은 connect timeout이 "실행 완료, 전 태스크 실패"로 보고되기 때문이다.

## 4. 모델 — 우리가 아는 것

확인된 instruct 모델은 하나다: **`Qwen3-30B-A3B-Instruct-2507-FP8`**. 나머지 2개는 reasoning 모델이며 이름 미확인.

공식 모델 카드([Hugging Face](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507))의 성적표에서 이번 트랙에 직접 대응하는 항목만 뽑으면:

| 벤치마크 | 점수 | 이번 트랙에서의 의미 |
|---|---|---|
| **MMLU-Pro** | **78.4** | generic 트랙 = MMLU-Pro. 이게 사실상 우리 상한선 |
| **AIME25** | **61.3** | math 트랙의 AIME 부분 |
| **LiveCodeBench v6 (25.02-25.05)** | **43.2** | coding 트랙의 LiveCodeBench 부분 |
| **Aider-Polyglot** | **35.6** | **코드 편집 형식 준수 능력. 여기가 이 모델의 약점** |
| IFEval | 84.7 | 지시 준수 |

**Aider-Polyglot 35.6이 이번 트랙에서 가장 중요한 숫자다.** 같은 표에서 Qwen3-235B-A22B Non-Thinking은 59.6, DeepSeek-V3-0324는 55.1이다. LiveCodeBench(순수 코드 생성) 43.2와 Aider-Polyglot(편집 형식 준수) 35.6의 격차는, **이 모델이 "못 고치는" 것이 아니라 "편집 형식을 못 낸다"**는 뜻이다. 그리고 이번 트랙 coding 출력이 정확히 그 능력을 요구한다. → `06`

모델 카드가 권장하는 설정도 그대로 쓸 수 있다:
- 샘플링: `Temperature=0.7`, `TopP=0.8`, `TopK=20`, `MinP=0`
- 출력 길이: 대부분의 질의에 16,384 토큰 권장
- 수학: 프롬프트에 `"Please reason step by step, and put your final answer within \boxed{}."` 포함
- 객관식: `"Please show your choice in the answer field with only the choice letter, e.g., "answer": "C"."`
- **이 모델은 non-thinking 전용이다.** `<think>` 블록을 생성하지 않으며 `enable_thinking=False`를 줄 필요가 없다.

마지막 항목이 중요하다. 우리 초안이 강조한 `--no-think` 레버는 **이 모델에는 애초에 해당이 없고**, 나머지 두 reasoning 모델에만 의미가 있다.

RULER 장문 성능도 참고할 것 (Full Attention 기준): 4k 98.0 / 32k 97.2 / 64k 93.4 / 128k 89.1. **60,000자(≈16~20k 토큰)는 아직 안전 구간**이지만, 여러 에이전트의 대화 이력이 누적되면 급격히 나빠진다.

## 5. 그래서 리서치가 답해야 할 질문 여섯

위 제약을 통과한 뒤 남는 실제 설계 질문이다. 각 질문에 대응하는 문서를 표시했다.

| # | 질문 | 문서 |
|---|---|---|
| Q1 | 도구도 없고 예산도 빡빡한데 **에이전트를 여러 명 두는 것이 정말 이득인가?** | `01` |
| Q2 | 둔다면 **몇 명**이고, **역할을 어떻게 자르는가?** | `02` |
| Q3 | 검증자를 **LLM으로 둘 것인가 프로그램으로 둘 것인가?** | `03` |
| Q4 | 포기 판단을 **누가** 하는가 — 에이전트인가 산수인가? | `04` |
| Q5 | 60,000자 컨텍스트를 **어떻게 배치**해야 캐시가 걸리고 정확도가 안 떨어지는가? | `05` |
| Q6 | 트랙마다 **얼마나 다르게** 대해야 하는가? | `06`, `07` |

## 6. 아직 확인 못 한 값 (온보딩·포털에서 확인 필요)

리서치로는 알 수 없고 주최 측만 아는 값들이다. 이 값이 없으면 아래 문서들의 계산이 **상대 비교로만** 유효하다.

1. 평가 모델 3종의 정확한 이름과 **USD/Mtok 단가**
2. `per_run_token_cap`, `per_item_wallclock_seconds`의 실제 숫자
3. 공유 서빙 스택이 **prefix cache를 실제로 켜두었는가**, 그리고 캐시된 입력의 과금 배율 (포털은 "cached input을 더 싸게 계량한다"고만 말한다)
4. one-shot 프롬프트가 스쿼드의 **어디로** 주입되는가 (planner에게만인가 전원인가)
5. 평가 실행 중 **러너 레벨 후처리(형식 검사·재시도)가 허용되는가** ← 우리 Preflight의 존폐가 걸림
6. Trace 로그 확보 경로
