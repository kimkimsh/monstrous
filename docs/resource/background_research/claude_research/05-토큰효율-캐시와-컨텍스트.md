# 05. 토큰 효율 — prefix cache와 컨텍스트 엔지니어링

> Q5: **60,000자 컨텍스트를 어떻게 배치해야 캐시가 걸리고 정확도가 안 떨어지는가?**
>
> 결론 먼저: **캐시는 순서가 전부다.** 프리픽스가 토큰 하나라도 달라지면 그 지점 이후는 전부 새로 계산된다. 그리고 캐시로 비용을 흡수한다고 해서 정확도까지 공짜가 되지는 않는다 — 길이 자체가 정확도를 깎는다(context rot). 두 힘이 반대 방향이라 **"컨텍스트를 앞에 두어 캐시를 먹되, 각 에이전트가 실제로 읽는 양은 줄인다"** 가 유일한 해법이다.

---

## 1. prefix cache는 정확히 어떻게 동작하는가

### 메커니즘 — 왜 "prefix"인가

[vLLM Automatic Prefix Caching 설계 문서](https://docs.vllm.ai/en/stable/design/prefix_caching/):

> we cache the kv-cache blocks of processed requests, and **reuse these blocks when a new request comes in with the same prefix** as previous requests. Since prefix caching is almost a free lunch and won't change model outputs, it has been widely used by many public endpoints (e.g., OpenAI, Anthropic, etc.) and most open source LLM inference frameworks (e.g., SGLang).

이유는 causal attention이다. [실무 해설](https://sankalp.bearblog.dev/how-prompt-caching-works/):

> Token 50's KV tensors depend on tokens 0-49. This means **KV values are only valid if the entire prefix is identical**. You can't reuse block 3's KV tensors if blocks 0, 1, or 2 are different.

vLLM은 **블록 단위 해시 체인**(부모 해시 포함)을 쓰고, **꽉 찬 블록만 캐시**한다. 문서의 예: 요청 1의 앞 10토큰이 요청 0과 같아도, 3번째 블록이 4토큰 중 2토큰만 일치하면 **앞 2블록(8토큰)만 캐시 히트**한다.

SGLang은 **RadixAttention**(radix tree)을 써서 부분 겹침과 대화 분기를 더 유연하게 처리한다([SGLang 블로그](https://lmsys.org/blog/2024-01-17-sglang/), [비교](https://medium.com/byte-sized-ai/prefix-caching-sglang-vs-vllm-token-level-radix-tree-vs-block-level-hashing-b99ece9977a1)). 멀티 에이전트에 특히 유리하다:

> For multi-agent systems sharing extensive system prompts, RadixAttention provides massive VRAM savings... Because both branches share the same root (the system prompt), RadixAttention only stores the KV cache for the system prompt **once**.
> — [RadixAttention 해설](https://rajatpandit.com/ai-engineering/radixattention-vs-pagedattention/)

> **미확인 사항**: 주최 측 공유 서빙 스택이 vLLM인지 SGLang인지 continuum-router 뒤의 무엇인지 우리는 모른다. 다만 포털이 `cached_input_share`를 노출하므로 **prefix cache가 켜져 있다는 것은 확실**하다. 어느 엔진이든 "긴 안정 프리픽스를 앞에" 원칙은 동일하다.

### 가격 — 캐시 히트는 대략 정가의 10%

주요 상용 API의 2026년 기준([TokenCost](https://tokencost.app/blog/prompt-caching-pricing-2026), [AI//COST](https://aicost.tools/blog/prompt-caching-llm-cost-math/), [Anthropic 공식 문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)):

| 항목 | 값 |
|---|---|
| 캐시 읽기 | 기본 입력가의 **약 10%** (Anthropic·OpenAI·Google 모두 수렴) |
| 캐시 쓰기 | Anthropic 5분 TTL **1.25×**, 1시간 TTL **2×** / OpenAI GPT-5.6부터 1.25× |
| 손익분기 | 무료 쓰기면 **2번째 호출**부터, 1.25× 쓰기면 약 **1.3회 재사용**, 2× 쓰기면 약 **2.1회** |
| 최소 토큰 | OpenAI 1,024 / Anthropic 512~4,096 (모델별) / Gemini 2,048~4,096 |
| TTL | 5~10분 유휴 (Anthropic 1시간 옵션) |

**두 가지 함정이 명시되어 있다.**

1. **최소 토큰 미달**: *"If your reused prefix is a 400-token system prompt, OpenAI, Anthropic, and Gemini all decline to cache it, and you pay full price on every call **while assuming caching has you covered**."* 대응책도 나와 있다 — *"make the cached block bigger on purpose, folding tool definitions and few-shot examples into the stable prefix so it clears the bar."*
2. **TTL 만료**: 요청 간격이 TTL보다 길면 매번 새로 쓴다.

> **우리 트랙 적용**: 시스템 프롬프트 + 출력 계약 + few-shot을 합쳐 **최소 1,024토큰 이상**으로 만드는 것이 오히려 유리할 수 있다. 짧게 만들려는 본능과 반대 방향이라 반직관적이지만, 최소 토큰 미달이면 캐시가 아예 안 걸린다.

### 병렬 요청 주의

Anthropic 문서:

> For concurrent requests, note that a cache entry **only becomes available after the first response begins**. If you need cache hits for parallel requests, wait for the first response before sending subsequent requests.

→ **같은 문항의 여러 에이전트를 병렬로 띄우면 캐시를 못 먹는다.** AI:GO의 `Max concurrent agents`를 낮게(2) 잡는 것이 캐시 관점에서도 옳다. 첫 에이전트가 프리픽스를 캐시에 쓰고, 나머지가 읽는 구조.

## 2. 그래서 프롬프트를 어떻게 배치하는가

포털이 사실상 답을 알려줬다:

> **Cached input** is the part of your prompt the stack served from its prefix cache. Your tier meters cached input more cheaply than fresh input, so **a prompt structure that keeps a long stable prefix in front of the varying part buys you real headroom.**

### 3층 배치 (우리 초안이 맞다)

```
┌─ Layer 1: 전 요청 동일 ─────────────────────────────┐
│  대회 컨텍스트 / 출력 계약 / 공통 금칙 / few-shot    │  ← 전 문항 캐시 히트
│  (최소 1,024토큰 이상이 되도록 의도적으로 채운다)     │
└─────────────────────────────────────────────────────┘
┌─ Layer 2: 이 문항 안에서 동일 ──────────────────────┐
│  item payload + 60,000자 컨텍스트 발췌               │  ← 문항 내 에이전트 간 캐시 히트
└─────────────────────────────────────────────────────┘
──────────────────────────── 캐시 경계 ────────────────
┌─ Layer 3: 에이전트마다 다름 ────────────────────────┐
│  이 에이전트의 역할·이번 태스크 지시 (짧게)          │  ← 여기만 새로 계산
└─────────────────────────────────────────────────────┘
```

**Layer 3이 Layer 1이나 2 앞으로 가면 캐시가 전부 깨진다.** AI:GO의 `systemPrompt`는 에이전트별 필드이므로, **Layer 1을 모든 에이전트의 systemPrompt에 동일 문자열로 복제**하고 그 뒤에 에이전트별 지시를 붙이는 형태가 된다.

### 기대 효과 — 그리고 그 한계

coding 문항 하나를 3~4개 에이전트가 본다면:
- 잘못된 배치: 60,000자 × 4 = 240,000자 전부 fresh input
- 올바른 배치: 첫 에이전트만 fresh, 나머지 3명은 캐시 읽기(≈10% 가격)
- 이론상 입력 비용 ≈ `1 + 3×0.1 = 1.3` → **원래의 약 1/3**

**단, 이건 상한이다.** 실제로는:
- 캐시 쓰기 프리미엄이 있으면 첫 호출이 1.25배
- 문항 간에는 컨텍스트가 거의 재사용되지 않는다 (`../../example_task/` 실측: django 2.7%, 나머지 0%) — 즉 **Layer 2 캐시는 한 문항 안에서만 유효**
- 병렬 실행 시 캐시 미스

측정: `GET /api/teams/me/dev-usage`의 `cached_input_tokens`, `cached_input_share`.

## 3. 반대 방향의 힘 — context rot

캐시로 비용을 흡수해도 **정확도는 흡수되지 않는다.**

### Chroma의 Context Rot 보고서

[Context Rot: How Increasing Input Tokens Impacts LLM Performance](https://www.trychroma.com/research/context-rot) (2025-07)

- 18개 모델, 8개 입력 길이 × 11개 needle 위치, 총 **194,480회 LLM 호출**.
- 설계 핵심: **태스크 복잡도를 고정하고 입력 길이만 변화**시켰다. 그래서 "길어서 나빠진 것"과 "어려워서 나빠진 것"을 분리할 수 있다.
- 결과: *"Across all experiments, **model performance consistently degrades with increasing input length**"* — 단순한 태스크에서도.
- **distractor의 효과**: 정답과 의미상 비슷한 오답 정보가 섞여 있으면 길이가 늘수록 정확도가 급격히 떨어진다.
- **위치 효과**: Chroma 실험에서는 lost-in-the-middle의 U자 곡선이 **재현되지 않았다**. *"they did not observe this U-shaped pattern... While putting important information at the start or end is a common piece of advice, this research suggests **it may not be a reliable solution** for mitigating context rot."* ([Hamel Husain 정리](https://hamel.dev/notes/llm/rag/p6-context_rot.html))
- 이상 실패 모드: 긴 입력에서 Claude는 저작권 우려로 생성을 거부하고, Gemini는 완전히 무작위 출력을 내는 경우가 관측됐다.

### 우리 조건에 대입하면

coding 문항의 컨텍스트: **60,000자 ≈ 16,000~20,000 토큰**, 후보 696개에서 뽑은 발췌 10개.

- 발췌 10개 중 실제로 고쳐야 할 곳은 보통 1~2개. **나머지 8~9개가 distractor다.** Chroma가 가장 나쁘다고 보고한 조건이다.
- Qwen3-30B-A3B-Instruct-2507의 RULER 성적([모델 카드](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507)): 4k 98.0 / 16k 96.9 / 32k 97.2 / 64k 93.4 / 128k 89.1. **16~20k 구간은 아직 좋다.**
- 하지만 여러 에이전트의 대화 이력이 누적되면 32k, 64k로 밀려간다. 그때부터 곡선이 꺾인다.

> **결론: 컨텍스트 자체는 20k 구간이라 안전하지만, 누적을 막아야 한다.** 그리고 각 에이전트가 "읽어야 하는" 양을 줄이는 것(앵커 → 발췌 축소)은 비용뿐 아니라 **정확도**를 위해서도 옳다. `06`의 localization 수치가 이걸 뒷받침한다.

## 4. 출력 토큰 줄이기 — Chain of Draft

입력은 캐시로 흡수되지만 **출력 토큰은 캐시가 없다.** 그리고 math 트랙 비용은 거의 전부 출력이다.

### Chain of Draft (CoD)

[arXiv 2502.18600](https://arxiv.org/html/2502.18600) · [코드](https://github.com/sileix/chain-of-draft)

방법: CoT 프롬프트를 그대로 두되 **"각 추론 단계를 최대 다섯 단어로 제한"** 하는 지시를 추가하고, few-shot 예시도 그 형식으로 쓴다.

| 태스크 / 모델 | Standard | CoT | **CoD** |
|---|---|---|---|
| GSM8K, GPT-4o | 53.3% | 95%+ / ~200토큰 | **91% / ~40토큰** |
| GSM8K, Claude 3.5 Sonnet | 64.6% | 95%+ / ~200토큰 | **91% / ~40토큰** |
| Date, GPT-4o | 90.0% / 1.0 | 95.9% / 28.7 | **98.3% / 15.0** |
| Sports, Claude 3.5 Sonnet | 90.6% / 1.0 | 93.2% / **189.4** | **97.3% / 14.3** (−92.4%) |
| Symbolic (coin flip) | 73.2 / 85.2% | 100% | **100%**, 토큰 −68~86% |

논문 요약: *"CoD matches or surpasses CoT in accuracy while using as little as only **7.6% of the tokens**."*

AWS Bedrock 재현([블로그](https://aws.amazon.com/blogs/machine-learning/move-beyond-chain-of-thought-with-chain-of-draft-on-amazon-bedrock/)): 총 토큰 39~76% 감소, 지연 52~79% 감소.

> **이것이 이번 트랙에서 가장 실용적인 출력 절감 기법이다.** 특히 generic 트랙에서 결정적이다 — `07`에서 볼 대로 MMLU-Pro는 CoT를 켜야 하지만, **CoT를 길게 쓸 필요는 없다.** "각 단계 최대 다섯 단어" + 마지막에 답 문자 = 정확도는 CoT 수준, 비용은 direct에 가깝게.
>
> 그리고 CoD는 few-shot 예시도 짧아지므로 **입력 토큰도 함께 줄인다** — Layer 1이 짧아지면 캐시 최소 토큰(1,024)에 못 미칠 수 있으니 균형을 볼 것.

## 5. 컨텍스트 관리 도구 — 우리가 쓸 수 있는 것과 없는 것

[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (Anthropic, 2025-09)의 원칙:

> Given that LLMs are constrained by a **finite attention budget**, good context engineering means finding the **smallest possible set of high-signal tokens** that maximize the likelihood of some desired outcome.

제시된 기법 세 가지와 우리 적용 가능성:

| 기법 | 설명 | 우리 트랙 |
|---|---|---|
| **Compaction** | 컨텍스트가 한계에 가까워지면 요약해 새 창으로 재시작 | ❌ 문항당 실행이 짧아 해당 없음. 그리고 요약 호출 자체가 비용 |
| **Structured note-taking** | 컨텍스트 밖 파일에 노트 기록 후 재로드 | ❌ 평가 중 파일 도구 없음 |
| **Sub-agent architectures** | 서브에이전트가 수만 토큰을 탐색하고 **1,000~2,000토큰 요약만 반환** | ⚠️ **부분 적용.** 우리 Architect가 이 형태. 단 요약이 아니라 앵커여야 함 |

AI:GO의 메모리 기능(`memoryEnabled`)에 대한 판단도 여기서 나온다:
- 켜면 태스크 시작마다 메모리 파일이 컨텍스트에 로드되고, `trigger_interval` 턴마다 **추가 LLM 추출 호출**이 발생한다.
- 벤치마크는 문항마다 독립적인 일회성 작업이라 누적 이득이 작다.
- **반대 논리**: 고정된 메모리 블록이 앞에 오면 캐시 프리픽스를 늘려 최소 토큰 문턱을 넘길 수 있다.
- **권고**: 기본 off. Planner에만 켜서 `cached_input_share`와 정확도를 함께 A/B.

## 6. 실무 체크리스트

- [ ] Layer 1(고정 프리픽스)을 **1,024토큰 이상**으로 만든다 — 캐시 최소 문턱 확보
- [ ] Layer 1을 **모든 에이전트의 systemPrompt에 바이트 단위로 동일하게** 복제한다 (한 글자만 달라도 캐시 깨짐)
- [ ] Layer 2(문항 컨텍스트)를 Layer 3(에이전트 지시)보다 **앞**에 둔다
- [ ] 같은 문항의 에이전트를 **병렬로 띄우지 않는다** (첫 응답이 시작돼야 캐시 엔트리가 생김)
- [ ] `Max concurrent agents = 2` 이하 유지
- [ ] 프롬프트를 수정할 때마다 `cached_input_share`를 기록한다 — 개선 곡선 자체가 시각화 재료
- [ ] 출력에 **Chain-of-Draft 스타일 제약**("각 단계 최대 N단어")을 건다
- [ ] 에이전트 간 핸드오프에서 **원문 hunk와 좌표만** 넘긴다 (요약 금지 — SEARCH 원문이 깨짐)
- [ ] 문항 간 컨텍스트 재사용을 기대하지 않는다 (실측 django 2.7%, 나머지 0%)
- [ ] 메모리는 기본 off, Planner만 A/B

## 7. 이 문서의 결론

1. **캐시는 순서가 전부다.** 프리픽스 한 토큰이 달라지면 그 뒤 전부 재계산. Layer 1 → Layer 2 → Layer 3 순서를 사수한다.
2. **캐시 읽기는 정가의 약 10%.** 문항 내 4에이전트 공유 시 이론상 입력 비용 1/3.
3. **최소 토큰(≈1,024) 미달이면 캐시가 아예 안 걸린다.** 고정 프리픽스를 일부러 키우는 것이 유리할 수 있다.
4. **병렬 실행은 캐시를 깨뜨린다.** 첫 응답이 시작된 뒤에 후속을 보내야 한다.
5. **비용과 정확도는 반대 방향이다.** 캐시가 비용을 흡수해도 길이는 정확도를 깎는다(context rot, distractor 조건에서 특히). 20k 구간은 아직 안전하지만 누적을 막아야 한다.
6. **출력은 캐시가 없다.** Chain-of-Draft가 유일하게 실측된 무손실 절감 기법 — 토큰 68~92% 감소, 정확도 유지 또는 향상.
