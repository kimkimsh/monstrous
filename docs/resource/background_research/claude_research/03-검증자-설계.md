# 03. 검증자 설계 — 프로그램으로 할 것과 LLM에게 시킬 것

> Q3: **검증자를 LLM으로 둘 것인가 프로그램으로 둘 것인가?**
>
> 결론 먼저: **프로그램으로 되는 것은 전부 프로그램으로.** LLM 자기검증(self-correction)은 외부 신호 없이는 성능을 **떨어뜨린다**는 것이 반복 확인됐고, 별도 LLM 검증자(GenRM)는 단순 다수결을 따라잡는 데만 최대 8배 연산을 쓴다. 트랙 문제 지문의 *"which ones verify the results"* 에 대한 우리 답은 **"검증자는 LLM이 아니어도 된다"** 여야 한다.

---

## 1. 외부 신호 없는 자기검증은 성능을 깎는다

### Huang et al., ICLR 2024 — 가장 결정적인 반증

[Large Language Models Cannot Self-Correct Reasoning Yet (arXiv 2310.01798)](https://arxiv.org/abs/2310.01798) · [OpenReview](https://openreview.net/forum?id=IkmD3fKBPQ)

**intrinsic self-correction** = 외부 피드백 없이 모델이 자기 답을 검토·수정하는 것. 논문의 결과:

- GSM8K, GPT-4: **95.5% → 91.5%** (1라운드) → **89.0%** (2라운드)
- GPT-3.5: 75.9% → 74.7%
- CommonSenseQA, GPT-3.5: **75.8% → 38.1%** (1라운드) → 41.8% (2라운드)

논문의 진단: *"a fundamental issue is that **LLMs cannot properly judge the correctness of their reasoning**."* 모델은 맞은 답을 틀린 답으로 "고칠" 확률이 실제 오류를 잡을 확률보다 높다.

그리고 우리에게 직접 걸리는 문장:

> The **CommonGen** experiment shows that **when the prompt is already precise and explicit, self-correction degrades performance.**

우리 출력 계약은 매우 정밀하고 명시적이다. 즉 이 조건에 정확히 해당한다.

또 하나: *"its efficacy is **no better than self-consistency** when considering an equivalent number of responses."* — 같은 예산이면 자기수정보다 독립 샘플링이 낫다.

**예외 조건도 명확하다.** 논문은 *"without the crutch of external feedback"* 를 조건으로 못 박았다. 즉 **외부 결정론적 신호가 있으면 이야기가 다르다.** 그 신호가 우리의 Preflight다.

(후속 연구 [SCoRe (arXiv 2409.12917, ICLR 2025)](https://arxiv.org/abs/2409.12917)는 RL로 자기수정을 학습시키면 MATH +15.6%, HumanEval +9.1%를 얻는다고 보고한다. 하지만 이건 **모델을 학습시킨 경우**이고, 우리는 프롬프트만 쓴다. 해당 없음.)

## 2. 별도 LLM 검증자(GenRM)는 예산 대비 손해다

[When To Solve, When To Verify: Compute-Optimal Problem Solving and Generative Verification for LLM Reasoning (arXiv 2504.01005)](https://arxiv.org/abs/2504.01005)

- 비교 대상: **Self-Consistency(SC, 다수결)** vs **Generative Reward Model(GenRM, 생성형 검증자)**.
- 결과: *"SC is more compute-efficient than GenRM for **most practical inference budgets** across diverse models and datasets. For instance, **GenRM first matches SC after consuming up to 8x the inference compute**, and requires significantly more compute to outperform it."*
- 그리고 스케일링 법칙: *"compute-optimal inference favors **scaling solution generation more aggressively than scaling the number of verifications**."*

**한 문장 요약: 고정 예산이면 "검증자를 더 부르는 것"보다 "답을 하나 더 만드는 것"이 낫다.**

관련 결과 하나 더 — [Incentivizing LLMs to Self-Verify Their Answers (arXiv 2506.01369)](https://arxiv.org/html/2506.01369v1): 외부 reward model 기반 best-of-N, beam search, DVTS가 **단순 self-consistency보다 못했다**. 원인은 분포 이동 — 외부 검증자가 학습한 데이터와 생성 모델의 출력 분포가 어긋난다.

> 우리 트랙에서는 이게 더 극단적이다. **우리는 검증자를 학습시킬 수 없고, 같은 모델을 프롬프트만 바꿔 검증자로 쓴다.** 그건 GenRM보다도 약한 신호다.

## 3. 그럼 무엇이 작동하는가 — 결정론적 형식 검증

### 실측 근거: SWE-Edit의 edit success rate

[SWE-Edit (arXiv 2604.26102)](https://arxiv.org/pdf/2604.26102v2) (프리프린트)에서 정의한 지표:

> **Edit Success Rate** — percentage of edit operations **without formatting errors**

SWE-bench Verified 500문항:

| 구성 | Edit 성공률 | Resolve율 |
|---|---|---|
| Baseline | 93.4% | 69.9% |
| + Editor 서브에이전트 | 96.1% | 71.3% |
| SWE-Edit | 96.9% | 72.0% |

세 개의 다른 모델로 반복: baseline 75.6~82.0% → 93.9~95.9%.

논문이 지적하는 것: *"the cost of a single mis-formatted edit (**a wasted reasoning trajectory**) is hidden inside the resolve rate."*

**형식 오류 한 번 = 추론 궤적 하나를 통째로 버리는 것.** 이번 트랙에서는 그게 `extraction_failed`(팀 책임)로 기록된다.

### find-replace가 정확히 무엇 때문에 깨지는가

같은 논문:

> The dominant find-replace format requires **exact string matching**; a **single whitespace mismatch** causes the edit to fail.

그리고 SWE-Edit의 Editor 시스템 프롬프트가 명시하는 규칙 네 개 — 이건 우리 Preflight가 검사해야 할 항목 목록 그 자체다:

1. SEARCH 블록은 원본 파일 내용과 **정확히** 일치해야 한다 (공백·들여쓰기 포함).
2. 여러 편집은 여러 search-replace 블록으로.
3. SEARCH 블록이 비어 있으면 파일 전체 재작성을 뜻한다.
4. **각 SEARCH 블록은 파일 안에서 유일해야 한다** — 여러 곳에 매치되면 컨텍스트를 더 넣어라.

4번은 우리 초안 Preflight 목록에 없던 검사다. **추가해야 한다.**

### Aider가 이 문제를 어떻게 다루는가

[Aider edit formats](https://aider.chat/docs/more/edit-formats.html) — `whole` / `diff`(SEARCH/REPLACE) / `diff-fenced` / `udiff` / `editor-diff` / `editor-whole`.

Aider 리더보드는 **"Percent using correct edit format"** 을 정확도와 **별도 컬럼**으로 낸다([code editing leaderboard](https://aider.chat/docs/leaderboards/edit.html)). 그 표에서 읽히는 규칙성:

- 작은/오픈 모델은 거의 전부 `whole` 포맷을 쓰고 형식 준수율 100%를 찍는다 (Qwen2.5-Coder-32B 72.9% 정확도 / 100% 형식, Qwen2.5-Coder-14B 69.2% / 100%).
- `diff`·`udiff`를 쓰는 모델은 형식 준수율이 92~98%로 떨어진다.
- Aider 문서의 직설적 요약: *"The 'whole' format is the easiest for an LLM to use, but it uses a lot of tokens."*

그리고 Aider의 실전 재시도 루프 설계도 참고 가치가 있다 — [search-replace-py](https://pypi.org/project/search-replace-py/)(Aider editblock 엔진 추출본)는 세 단계 매칭 전략을 쓴다:
1. exact match
2. **leading-whitespace-tolerant match** (선행 공백 허용)
3. dotdotdot(`...`) 분절 치환

그리고 `dry_run=True`로 **디스크에 쓰기 전에 전 블록을 검증**하고, 실패 시 `ApplyError` 메시지를 **LLM에게 그대로 되먹인다**.

> **우리에게 주는 설계 지침**: Preflight는 "실패"만 반환하면 안 되고 **어느 블록의 몇 번째 줄이 왜 안 맞는지 + 가장 가까운 후보 줄**을 반환해야 한다. 그게 재시도가 실제로 효과를 내는 조건이다.

## 4. 형식 강제 자체가 추론을 깎는다 — 반대 방향의 경고

[Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models (arXiv 2408.02442)](https://doi.org/10.48550/arxiv.2408.02442)

> we observe a **significant decline in LLMs' reasoning abilities under format restrictions**. Furthermore, we find that **stricter format constraints generally lead to greater performance degradation** in reasoning tasks.

세 단계의 제약 강도를 비교했다:
1. **Constrained Decoding (JSON-mode)** — 디코딩 단계에서 토큰 공간을 강제. 가장 강함.
2. **Format-Restricting Instructions (FRI)** — 프롬프트로 형식 지시.
3. 자유 형식.

**함의가 양날이다.**

- 나쁜 쪽: 우리 출력 계약(`\boxed{}`만, 보기 문자만, SEARCH 블록만)이 추론 능력을 깎을 수 있다.
- 좋은 쪽: 우리는 **constrained decoding을 쓰지 않는다.** 프롬프트 지시(FRI) 수준이며, 그것도 **응답 본문 앞부분이 자유 공간**이라는 트랙 규칙 덕에 "생각은 자유롭게 하고 마지막에 형식을 맞춰라"가 가능하다.

> **이 조합이 우리 LEDGER 설계의 숨은 강점이다.** 트랙 규칙 *"If more than one appears, the last one is used. Anything before it is ignored, not penalised."* 덕분에 **형식 제약과 자유 추론을 동시에** 가질 수 있다. 형식은 마지막 블록에만 걸고, 그 앞은 자유롭게 쓴다. 형식 제약으로 인한 추론 저하를 구조적으로 회피하는 것이다.

## 5. 검증 대신 다수결 — 그런데 그것도 조건부다

`02`에서 본 대로 self-consistency는 GenRM보다 예산 효율이 좋지만 한계가 뚜렷하다.

### 모달 천장(modal ceiling)

[When More Sampling Hurts: The Modal Ceiling and Correlation Ceiling of Test-Time Scaling](https://export.arxiv.org/pdf/2606.28661) (프리프린트)

- **coverage**(n개 중 하나라도 맞나)와 **selection**(투표로 맞는 걸 고르나)은 서로 다른 곡선이다.
- coverage는 계속 오르지만, selection은 **모델의 최빈 답(mode)** 으로 수렴하므로 *"self-consistency accuracy converges to the **modal-hit rate**"* — 최빈 답이 틀린 문항에서는 샘플을 늘릴수록 **오답이 더 확실히 이긴다**(anti-scaling).
- 실측 예: GSM8K, Llama-3-8B-Instruct — coverage 1.00, self-consistency 0.87에서 정체. 약 1/8의 문항은 정답이 풀에 있는데 투표가 못 꺼낸다(usable-signal gap).
- 실용 결론: *"self-consistency has captured almost all it will **within a few dozen samples**"*, 그리고 **verifier가 있으면** coverage 쪽 이득이 계속 남는다.

### 작은 모델 + 어려운 문항에서는 다수결이 해롭다

[When Self-Consistency Backfires (arXiv 2608.11403)](https://arxiv.org/html/2608.11403v1) (프리프린트) — GPQA Diamond 198문항:
- Qwen2.5-7B: 문항의 **56.6%** 에서 다수결이 정확도를 낮춤
- Llama-3-8B: **65.7%**
- 최고 일치도 구간(highest-agreement bin)에서도 최빈 답이 맞을 확률이 **약 절반**. Llama에서는 최고 일치 구간이 최저 일치 구간보다 **덜 정확**했다.
- 그리고 다수결 일치율 게이트, 토큰 엔트로피 게이트 **둘 다 실패**했다 (N=64 고정 예산 대비 정확도 차이 0.002 미만).

> **이 발견이 "확신도로 승급 여부를 정한다"는 우리 초안의 아이디어를 직접 위협한다.** 자세한 것은 `04`의 캘리브레이션 절.

## 6. 무료 신호 두 개를 어떻게 결합할 것인가

우리 초안은 "무료 신호 둘(형식 검사, 2회 샘플 일치)이 엇갈릴 때만 Auditor 승급"을 제안했다. 리서치 기준으로 재평가하면:

| 신호 | 비용 | 신뢰성 근거 | 판정 |
|---|---|---|---|
| **형식 검사 (Preflight)** | LLM 호출 0 | SWE-Edit 실측 — 형식 오류가 실제로 resolve율을 갉아먹음 (93.4% → 96.9%가 +2.1%p resolve) | ✅ **강함.** 무조건 쓴다 |
| **2회 샘플 일치** | 샘플 1회 추가 | 일치율 게이트는 GPQA에서 실패(위). 다만 GPQA는 극단적으로 어려운 세트고, MMLU-Pro·MATH-500은 그보다 쉽다 | ⚠️ **조건부.** math에서만, generic에서는 위험 |
| **LLM Auditor 승급** | 호출 1회 | GenRM은 SC를 따라잡는 데만 8배. 자기검증은 성능 저하 | ❌ **약함.** 형식 실패 시 "재시도"로 대체 권장 |

**대안 설계** — 승급 대신 **재시도 + 구체적 실패 신호**:

```
Editor 출력 → Preflight 검사
  ├─ 통과 → 종료
  └─ 실패 → 실패 사유(블록 번호 + 안 맞는 줄 + 가장 가까운 후보)를 붙여 Editor 재호출 (최대 1회)
             → 다시 실패하면 give_up (Auditor 호출 없음)
```

이것은 Huang et al.이 배제한 "intrinsic self-correction"이 **아니다** — 외부 결정론적 피드백이 있기 때문이다. 그리고 GenRM보다 훨씬 싸다. Aider의 실전 루프도 정확히 이 형태다.

## 8. 이 문서의 결론

1. **LLM 자기검증은 쓰지 않는다.** 외부 신호 없는 self-correction은 정확도를 떨어뜨린다(GSM8K 95.5→89.0, CommonSenseQA 75.8→38.1).
2. **별도 LLM 검증자도 예산 대비 손해다.** GenRM은 SC를 따라잡는 데만 최대 8배 연산.
3. **결정론적 형식 검증은 실측 효과가 있다.** SWE-Edit: 편집 성공률 +2.7~18.3%p, resolve +1.4~2.1%p, 비용 −17.9%.
4. **재시도는 "구체적 실패 신호"가 붙었을 때만 의미가 있다.** Aider의 `ApplyError` 되먹임이 표준 패턴.
5. **형식 강제는 추론을 깎지만**, 트랙의 "마지막 블록만 채점" 규칙이 이 손해를 구조적으로 피하게 해 준다.
6. **다수결은 만능이 아니다.** 작은 모델 + 어려운 문항에서는 절반 이상의 문항에서 해롭다. modal ceiling 때문에 몇십 샘플 이후 이득이 없다.
7. → **Auditor(LLM 검증자)를 "Editor 재시도 + Preflight 되먹임"으로 대체하는 안을 강하게 검토할 것.** `10`에서 최종 판정.
