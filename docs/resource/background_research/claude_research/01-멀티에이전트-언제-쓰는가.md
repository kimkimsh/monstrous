# 01. 멀티 에이전트를 언제 쓰는가 — 비용과 이득의 실측

> Q1: **도구도 없고 예산도 빡빡한데 에이전트를 여러 명 두는 것이 정말 이득인가?**
>
> 결론 먼저: **대부분의 경우 아니다.** 다만 이번 트랙은 "squad formation"이 요구사항이므로 단일 에이전트로 갈 수는 없다. 그래서 진짜 질문은 "쓸까 말까"가 아니라 **"근거가 있는 지점에만 쓰는 법"** 이다. 근거가 있는 지점은 세 개뿐이고, 그중 우리에게 해당하는 것은 **한 개 반**이다.

---

## 1. 멀티 에이전트의 가격표

### Anthropic 측정치 (프로덕션 시스템)

[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) (2025):

- 에이전트는 채팅 대비 **약 4배** 토큰을 쓴다.
- 멀티 에이전트 시스템은 채팅 대비 **약 15배** 토큰을 쓴다.
- **토큰 사용량 하나가 성능 분산의 80%를 설명한다.**
- 멀티 에이전트(Opus 4 리드 + Sonnet 4 서브)가 단일 Opus 4를 내부 리서치 평가에서 **90.2%** 앞섰다.
- 명시된 한계: *"domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today."*

마지막 문장이 이번 트랙에 정면으로 걸린다. **우리 coding 경로의 모든 에이전트는 같은 60,000자 컨텍스트를 공유해야 하고, 단계 간 의존성이 강하다.** Anthropic이 "적합하지 않다"고 명시한 바로 그 조건이다.

### Anthropic 후속 글 — 더 구체적인 배율

[When to use multi-agent systems (and when not to)](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) (2026-01):

> In our testing, multi-agent implementations typically use **3-10x more tokens** than single-agent approaches for equivalent tasks. This overhead stems from duplicating context across agents, coordination messages between agents, and summarizing results for handoffs.

오버헤드의 출처 세 가지가 명시되어 있다 — ① **에이전트 간 컨텍스트 중복**, ② 조율 메시지, ③ 핸드오프용 요약. 세 가지 다 우리 설계에서 직접 통제할 수 있는 항목이다(→ `05`).

그리고 결정적인 한 문장:

> In one experiment with agents specialized by software development role (planner, implementer, tester, reviewer), the subagents **spent more tokens on coordination than on actual work.**

**우리 초안의 5인 구성이 정확히 이 형태다.** 이 문장은 `02`에서 다시 다룬다.

## 2. 예산을 맞추면 결과가 뒤집힌다

멀티 에이전트 우위를 보고한 논문 대부분은 **단일 그리디 CoT 한 번**과 비교했다. 같은 토큰 예산을 단일 에이전트에게 주면 결과가 달라진다.

### Budget-Aware Evaluation (EMNLP 2024)

[Reasoning in Token Economies: Budget-Aware Evaluation of LLM Reasoning Strategies](https://aclanthology.org/2024.emnlp-main.1112/) · [arXiv 2406.06461](https://doi.org/10.48550/arxiv.2406.06461)

- 문항당 최대 20 질의 또는 10k 토큰으로 예산을 맞추고 7개 전략을 비교.
- **CoT + self-consistency(SC)** 라는 단순 베이스라인이 Multi-Agent Debate(MAD), Reflexion, Plan-and-Solve, Least-to-Most, Progressive-Hint를 대부분 이겼다.
- 더 나쁜 소식: *"unlike self-consistency, certain strategies such as multi-agent debate or Reflexion **can become worse if more compute budget is utilized**."*
- 원인 분석: MAD는 이전 라운드 답에 조건부로 샘플링하므로 **응답 다양성(엔트로피)이 라운드마다 감소**하고, 틀린 답으로 수렴(tunnel)할 확률이 커진다. SC는 독립 샘플링이라 이런 현상이 없다.
- 저자들의 기준 제시: *"a proposed reasoning strategy should be considered effective only if its performance is better compared to a baseline of equivalent budget."*

### 정보이론 관점 — 동일 thinking-token 예산 비교 (프리프린트)

[Single-Agent LLMs Outperform Multi-Agent Systems on Multi-Hop Reasoning Under Equal Thinking Token Budgets](https://arxiv.org/abs/2604.02460v1)

- Qwen3, DeepSeek-R1-Distill-Llama, Gemini 2.5 세 계열 × MAS 5종(Sequential, Debate, Ensemble, Parallel-roles, Subtask-parallel)을 **동일 thinking-token 예산**으로 비교.
- 결과: 가장 낮은 예산(100토큰, 애초에 추론이 안 되는 구간)을 빼면 **모든 예산에서 단일 에이전트(SAS)가 최고이거나 최고와 통계적으로 구분되지 않았다.** SAS는 토큰도 훨씬 적게 썼다.
- Data Processing Inequality에 기반한 설명: 멀티 에이전트 분해는 **커뮤니케이션 병목**을 추가하므로 정보 손실이 발생한다.
- **MAS가 유리해지는 조건도 명시했다** — 단일 에이전트의 *effective context utilization*이 충분히 나빠졌을 때. 논문의 degradation 실험: 컨텍스트를 심하게 훼손(삭제·distractor 주입)하면 SAS 우위가 줄고 MAS가 경쟁력을 갖는다.

> **우리에게 주는 함의**: 60,000자 컨텍스트 + distractor(696개 후보에서 뽑은 10개 발췌) 조건은 이 논문이 말하는 "degraded context utilization" 구간에 **가깝다**. 즉 coding 경로에서만큼은 멀티 에이전트(정확히는 localization 단계 분리)가 정당화될 수 있다. 그 정당화는 `06`에서 실제 수치로 확인된다.

### 멀티 에이전트 토론(MAD)은 특히 나쁘다

| 출처 | 발견 |
|---|---|
| [Should we be going MAD? (ICML 2024)](https://proceedings.mlr.press/v235/smit24a.html) | MAD는 self-consistency·앙상블을 **안정적으로 이기지 못한다**. 하이퍼파라미터에 매우 민감 |
| [Stop Overvaluing Multi-Agent Debate (arXiv 2502.08788)](https://arxiv.org/html/2502.08788v3) | 5개 MAD 기법 × 9개 벤치마크 × 4개 모델 — **CoT·SC 같은 단순 단일 에이전트 베이스라인을 자주 못 이긴다**, 훨씬 많은 연산을 쓰고도. 모델 이질성(heterogeneity)이 유일한 보편적 해독제 |
| [The Cost of Consensus (2026)](https://doi.org/10.1145/3786335.3813137) | **7~8B 급 모델** 10개 팀 × 3라운드, GSM-Hard/MMLU-Hard. 토론은 isolated self-correction 대비 **2.1~3.4배 토큰**을 쓰고 정확도는 같거나 낮음. sycophantic conformity 최대 85.5%, oracle gap 최대 32.3%p (정답을 생성해 놓고 다수결로 버림). **단일 에이전트에게 출력 예산 10배를 주면 토론과 대등하거나 더 낫다** |

마지막 행이 특히 중요하다. **7~8B 급에서 측정된 결과**이고, 우리 모델은 30B-A3B(활성 3.3B)다. 활성 파라미터 기준으로는 그 급에 가깝다.

## 3. 그럼에도 멀티가 이기는 세 가지 상황

Anthropic이 정리한 세 가지다([출처](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them)). 우리 트랙 적용 여부를 옆에 붙였다.

| # | 상황 | 설명 | 우리 트랙 |
|---|---|---|---|
| 1 | **컨텍스트 오염** | 서브태스크가 1,000토큰 이상의 컨텍스트를 만들지만 대부분이 본 태스크와 무관할 때. 서브에이전트가 격리된 컨텍스트에서 처리하고 요약만 반환 | **부분 적용.** coding의 60,000자 → 앵커 인덱스 축약이 정확히 이 형태 |
| 2 | **병렬화 가능** | 독립적인 탐색 경로가 여러 개일 때. *"주된 이득은 속도가 아니라 철저함(thoroughness)"* | **미적용.** 문항 하나에 병렬 탐색할 독립 경로가 없다. 문항 간 병렬은 러너 레벨이지 스쿼드 구조가 아니다 |
| 3 | **전문화가 도구 선택/집중을 개선** | 서로 다른 도구 집합을 쓸 때 | **미적용.** 평가 중 도구가 없다 |

**세 개 중 1개 부분 적용.** 이것이 "우리 스쿼드는 작아야 한다"는 결론의 1차 근거다.

### 그리고 예외적으로 안전한 분리 지점 하나 — 블랙박스 검증

같은 글:

> Verification subagents succeed because they **sidestep the telephone game problem**. Verification requires minimal context transfer by nature, so a verifier can blackbox-test a system without needing the full history of how it was built.

좋은 분해 경계로 명시된 것: 독립 리서치 경로 / 깨끗한 인터페이스로 나뉜 별개 컴포넌트 / **블랙박스 검증**.
나쁜 분해 경계로 명시된 것: **같은 작업의 순차 단계(계획→구현→테스트)** / 강결합 컴포넌트 / 공유 상태가 필요한 작업.

> 우리 초안의 웨이브 구조(Router → Architect → Editor → Preflight → Auditor)는 **명시적으로 "나쁜 경계"에 해당하는 순차 단계 분할**이다. 다만 Preflight가 LLM이 아니라 프로그램이라는 점, Architect가 컨텍스트 축약(상황 1)을 담당한다는 점에서 부분적으로 방어된다. → `10`

## 4. 컨텍스트 중심 분해 — 이 리서치의 핵심 원리

Anthropic이 가장 강하게 밀고 있는 설계 원칙이다.

> The key insight is to adopt a **context-centric view rather than a problem-centric view** when decomposing work.
>
> **Problem-centric decomposition (often counterproductive).** Dividing by type of work (one agent writes features, another writes tests, a third reviews code) creates constant coordination overhead. Each handoff loses context.
>
> **Context-centric decomposition (usually effective).** Dividing by context boundaries means an agent handling a feature should also handle its tests, because it already possesses the necessary context. **Work should only be split when context can be truly isolated.**

번역하면 — **"무슨 일인가"로 나누지 말고 "어떤 컨텍스트가 필요한가"로 나눠라.** 같은 컨텍스트를 보는 두 작업은 한 에이전트가 해야 한다.

### 우리 경로에 적용해 보면

```
coding 경로에서 "같은 컨텍스트"를 공유하는 작업:
  60,000자를 읽는다 → 어디를 고칠지 정한다 → SEARCH 블록을 쓴다
  ↑ 전부 같은 컨텍스트가 필요하다. 컨텍스트 중심으로는 하나여야 한다.

정말로 컨텍스트가 격리되는 작업:
  "이 SEARCH 문자열이 발췌 안에 글자 그대로 있는가?" ← 원문과 후보 문자열만 있으면 된다
  ↑ 이건 격리 가능하다. 그리고 LLM이 필요 없다.
```

**그런데** `06`에서 볼 SWE-Edit 논문은 정반대 방향의 실측을 내놓는다 — reasoning과 편집 형식 생성은 "인지적으로 별개 능력"이라 분리하면 편집 성공률이 +12.8~18.3%p 오른다. 두 근거가 충돌한다. 이 충돌의 해소는 `10`에서 다룬다.

## 5. 워크플로 패턴 카탈로그 — 우리가 고를 수 있는 것

[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) (Anthropic, 2024-12)의 다섯 패턴을 트랙 적용 가능성과 함께 정리한다.

| 패턴 | 무엇인가 | 이번 트랙 적용 |
|---|---|---|
| **Prompt chaining** | 태스크를 고정 단계로 분해, 각 단계가 이전 출력을 처리. 중간에 프로그램 gate를 넣을 수 있음 | ✅ **우리 웨이브 구조가 이것.** "gate"가 우리 Preflight |
| **Routing** | 입력을 분류해 전문화된 후속 태스크로 보냄. *"한 입력 종류에 최적화하면 다른 입력이 나빠지는 것"*을 막음 | ✅ **필수.** 템플릿 1개로 3트랙을 처리해야 하므로 Router는 선택이 아님 |
| **Parallelization (sectioning / voting)** | 독립 서브태스크 병렬 / 같은 태스크 반복 후 투표 | ⚠️ voting만 부분적. 예산이 허락하는 지점에만 (→ `03`, `07`) |
| **Orchestrator-workers** | 중앙 LLM이 서브태스크를 **동적으로** 쪼개고 위임 | ❌ 동적 분해는 plan iteration 비용을 부른다. AI:GO의 `Max plan iterations`를 1로 낮추는 것과 상충 |
| **Evaluator-optimizer** | 한 LLM이 생성, 다른 LLM이 평가·피드백, 루프 | ⚠️ **평가 기준이 프로그램으로 표현 가능하면 프로그램으로 하라**는 것이 이 패턴의 명시적 단서. → `03` |

Evaluator-optimizer에 붙은 Anthropic의 경고를 그대로 옮긴다:

> When to avoid: ... **If deterministic tools exist (like linters for code style), use those instead.**
>
> Pro tip: Set clear stopping criteria before you start iterating. Define maximum iteration counts and specific quality thresholds. Without these guardrails, you can end up in expensive loops where the evaluator keeps finding minor issues and the generator keeps tweaking, but quality plateaus well before you stop iterating.

두 문장이 각각 `03`(프로그램 검증)과 `04`(하드 캡)의 근거가 된다.

그리고 전체를 관통하는 문장:

> When building applications with LLMs, we recommend finding the **simplest solution possible**, and only increasing complexity when needed. ... **you should consider adding complexity only when it demonstrably improves outcomes.**

## 6. 이 문서의 결론

1. **멀티 에이전트는 3~10배 비싸다.** 이번 트랙은 토큰 효율이 30점이고 동점 처리 기준이므로, 이 배율은 그대로 점수 손실이다.
2. **예산을 맞추면 단일 에이전트가 이긴다**는 것이 여러 독립 연구의 일치된 결론이다. 우리가 이기는 유일한 길은 "에이전트를 늘려서"가 아니라 **"에이전트를 늘리지 않고 요구사항을 만족시켜서"** 다.
3. 정당화되는 분리는 **두 가지뿐**이다:
   - **컨텍스트 축약** (60,000자 → 앵커): 상황 1에 해당하고, `06`에서 정량 근거가 나온다.
   - **블랙박스 검증**: 컨텍스트 전달이 최소라 telephone game이 없다. 단, 프로그램으로 되는 것은 프로그램이 해야 한다(`03`).
4. **순차 단계 분할(계획→구현→검증)은 명시된 안티패턴**이다. 우리 설계가 여기에 걸린다는 사실을 인정하고, 각 단계가 왜 필요한지 개별로 방어해야 한다. → `02`, `10`
