# 09. 트레이스와 시각화 표준 — 30점 축의 리서치 근거

> 이 문서는 시각화 디자인 가이드가 아니다(그건 `../../track_resource/lableup/06-시각화-설계-가이드.md`). 여기서는 **"업계 표준이 실제로 무엇이고, 표준 도구들이 무엇을 못 해서 심사위원에게 차별점이 되는가"** 를 리서치로 확인한다.
>
> 결론 먼저: **OpenTelemetry GenAI semantic conventions가 사실상의 표준이고, 그 어휘를 그대로 쓰는 것이 가장 싼 신뢰 확보 수단이다.** 그리고 기존 관측 도구들의 공통 약점이 명확히 문서화되어 있다 — **타임라인은 "언제"를 기록할 뿐 "왜"를 기록하지 않는다.** 그 빈틈이 우리 차별점이다.

---

## 1. 채점 기준 여섯 축을 다시 읽기

트랙 원문(PDF 24p):

> Scores will be awarded based on how effectively the **Trace, represented as log (text) data**, is visualized with consideration for **observability, interpretability, traceability, explainability, clarity, and insightfulness**.

| 축 | 요구 | 표준 도구가 이미 하는가 |
|---|---|---|
| observability | 지금 무슨 일이 벌어지는가 | ✅ 전부 함 |
| interpretability | 그게 무슨 뜻인가 | ⚠️ 부분 |
| traceability | 결과 → 원인 역추적 | ⚠️ **여기가 빈틈** |
| explainability | 왜 그렇게 했는가 | ❌ **여기가 빈틈** |
| clarity | 한눈에 들어오는가 | ✅ 도구별 차이 |
| insightfulness | 보고 나면 몰랐던 것을 알게 되는가 | ❌ **여기가 승부처** |

아래 3절에서 이 판정의 근거를 제시한다.

## 2. OpenTelemetry GenAI Semantic Conventions — 실제 속성명

[open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai) — GenAI 전용 semconv가 별도 저장소로 분리되어 관리되고 있다.

### 스팬 종류

| operation | 스팬 이름 규칙 | 용도 |
|---|---|---|
| `chat` | `{gen_ai.operation.name} {gen_ai.request.model}` | 모델 호출 |
| `invoke_agent` | `invoke_agent {gen_ai.agent.name}` | 에이전트 호출 |
| `create_agent` | `create_agent {gen_ai.agent.name}` | 에이전트 생성 |
| `execute_tool` | — | 도구 실행 |
| `embeddings` / `retrieval` | — | 임베딩 / 검색 |

### 필수·주요 속성

| 속성 | 요구 수준 | 예시 |
|---|---|---|
| `gen_ai.operation.name` | Required | `chat`, `invoke_agent`, `execute_tool` |
| `gen_ai.provider.name` | Required | `openai`, `gcp.gen_ai` (우리는 커스텀 값) |
| `gen_ai.request.model` | Conditionally Required | 모델명 |
| `gen_ai.agent.name` | Conditionally Required | `Architect`, `Editor` |
| `gen_ai.agent.id` / `gen_ai.agent.description` / `gen_ai.agent.version` | Conditional | |
| `gen_ai.output.type` | Conditional | `text`, `json` |
| `gen_ai.response.finish_reasons` | — | `stop`, `tool_calls`, `length` |
| `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` | — | **토큰 효율 축의 핵심** |
| `gen_ai.input.messages` / `gen_ai.output.messages` / `gen_ai.system_instructions` | Opt-In | 내용 캡처 |
| `gen_ai.tool.definitions` | Opt-In | |

메트릭 두 개:
- `gen_ai.client.operation.duration` — 지연 히스토그램
- `gen_ai.client.token.usage` — 토큰 히스토그램 (`gen_ai.token.type`으로 input/output 분리)

### 설계 규칙 — 우리가 따라야 할 것

저장소 `AGENTS.md`가 명시하는 원칙 중 두 개가 우리에게 직접 적용된다:

> **Use this repo's terminology.** Reuse the established vocabulary — *operation*, *span*, *attribute*, *signal*, *inference*, *embeddings*, *execute tool*, *invoke agent* (client vs internal), *plan*, *memory*, *retrieval*, *workflow* — and existing `gen_ai.*` attribute names.
>
> **No attribute without a signal.** Every attribute added must be referenced by a span, metric, or event that defines when and how it is recorded. **No orphan attributes.**

그리고 기본값이 프라이버시 우선이라는 점([OTel 블로그](https://opentelemetry.io/blog/2026/genai-observability/)):

> By default, **no prompt content or tool arguments are captured** with GenAI telemetry... Only metadata like model names, token counts, and durations are included.

> **우리 확장 규칙**: 표준 속성을 그대로 쓰고, 트랙 고유 속성만 `jxc.*` 네임스페이스로 얹는다. 예:
> - `jxc.track` = `coding` / `math` / `generic`
> - `jxc.outcome` = `graded` / `extraction_failed` / `capped` / `grader_error` / `infrastructure_failed` ← **주최 열거형 그대로**
> - `jxc.failure_owner` = `team` / `policy` / `configuration` / `organizer`
> - `jxc.preflight.check` = `C4` 등, `jxc.preflight.result` = `pass` / `fail`
> - `jxc.anchor.hit` = 앵커가 실제 수정 위치를 포함했는가 (bool)
> - `jxc.attempt` = 시도 번호, `jxc.graded` = 이 블록이 채점 대상인가 (bool)
>
> "표준 어휘 + 주최 어휘"라는 두 축을 쓰면 심사위원의 학습 비용이 0에 수렴한다.

## 3. 기존 관측 도구가 못 하는 것 — 우리의 차별점

### 도구 지형 (2026 기준)

| 도구 | 라이선스 | 성격 | 강점 |
|---|---|---|---|
| **Langfuse** | MIT, self-host (Postgres + ClickHouse) | tracing-first, OTel 네이티브 | 트레이스 데이터 소유권, 프레임워크 무관, **agent graph 뷰** |
| **LangSmith** | 독점 (managed) | LangGraph 네이티브 | LangGraph 노드별 상태 시각화, 인간 주석 워크플로 |
| **Arize Phoenix** | Apache-2.0 | eval-first, OpenInference(OTel 확장) | 내장 LLM-as-judge 평가기, UMAP 임베딩 드리프트 |
| **Helicone** | Apache-2.0 | 프록시 | 설치 5분, 비용 추적 |

셋 다 **OpenTelemetry로 수렴**했다는 것이 2026년의 상태다([정리 글](https://dreaming.press/posts/langfuse-vs-langsmith-vs-phoenix-observability.html)).

### 공통 약점 — 인용할 가치가 있는 비판

[I tested 5 Agent Observability Tools and they all Failed the Causality Test](https://www.binarybox.org/p/i-tested-5-agent-observability-tools) (2026-05):

같은 시나리오·같은 질문("어떤 컨텍스트가 이 결정에 영향을 줬는가")으로 5개 도구를 테스트한 결과:

| 도구 | 단일 트레이스 근본원인 규명 시간 | 판정 |
|---|---|---|
| LangSmith | **60~90분** (수동 JSON 발굴) | 타임라인 도구 ❌ |
| Arize Phoenix | 60분 | 평면 span ❌ |
| Langfuse | 60~90분 | ❌ |
| LangGraph Studio | 단일 실행에는 좋음, 규모에서 질의 불가 | △ |
| GraphEvals + Neo4j | 통과 | ✅ |

핵심 진단:

> These tools model execution as **spans** — records of things that happened at specific times. They show you a waterfall of boxes stacked vertically. **Causality is buried in JSON metadata. Data flow is not a first-class relationship.**
>
> They record the **"when," not the "why."**
>
> The divide: **Timeline architecture (records "when") vs Graph architecture (records "what caused what").**

그리고 [Langfuse vs LangSmith vs Phoenix 정리](https://dreaming.press/posts/langfuse-vs-langsmith-vs-phoenix-observability.html)의 문제 제기:

> Logging answers "what the model said." Observability for agents has to answer **"why the agent took that path** through six tool calls, two retries, and a sub-agent that quietly hallucinated a customer ID."

> **이것이 우리 시각화의 논지가 되어야 한다.** 심사 6축 중 `traceability`·`explainability`·`insightfulness` 세 개가 정확히 "왜"에 해당하고, **업계 표준 도구가 그걸 못 한다는 것이 문서화되어 있다.** 우리가 그걸 하면 차별점이고, 그 차별점에 인용할 근거까지 있다.

### 참고할 만한 설계 — Langfuse의 Agent Graph 이중 뷰

[Langfuse Agent Graphs 문서](https://langfuse.com/docs/observability/features/agent-graphs)가 제공하는 두 가지 뷰는 우리가 그대로 차용할 가치가 있다:

| | **Aggregated** (기본) | **Expanded** ("as it ran") |
|---|---|---|
| 노드 하나 = | 고유한 **단계 이름** | 개별 **호출** |
| 반복 호출 | 카운터가 붙은 단일 노드로 병합 (`retrieve_docs (3/3)`) | 별도 노드로 분리 |
| 루프 | **사이클**로 그림 | 실행 순서대로 **DAG로 펼침** |
| 읽히는 것 | 에이전트의 전체 **모양** | 정확한 **실행 과정** |
| 적합 | 구조·복잡도 파악 | 특정 실행 디버깅 |

문서의 판단: *"Neither is 'correct' — they answer different questions."*

> **우리 적용**: Level 0(전체 실행 요약) ↔ Level 3(문항 하나 재생)의 줌 단계에 이 이중 뷰를 매핑할 수 있다. 그리고 우리는 **문항마다 경로가 다르다**(coding 3~4단, math 2단, generic 1단)는 점이 있으므로, Aggregated 뷰가 "우리 스쿼드는 문항 종류에 따라 다른 깊이로 돈다"를 한 화면에 보여주는 좋은 수단이 된다.

## 4. 우리 트레이스가 표준 도구보다 나은 지점 — 근거 정리

### 4-1. 바이트 동일성 (byte-identity)

우리 LEDGER 설계는 장부를 **채점되는 응답 본문 안에** 쓴다. 표준 도구는 요청/응답을 **옆에서 수집**한다.

| | 표준 도구 (Langfuse/Phoenix/LangSmith) | LEDGER |
|---|---|---|
| 수집 위치 | 요청 경로 밖 (SDK 래핑 / OTel exporter / 프록시) | **응답 본문 안** |
| 계측 비용 | 별도 span 생성·전송 (토큰 비용은 없지만 인프라 비용) | **0** |
| 채점된 것과의 일치 | 보장 없음 — 수집 시점·필터·샘플링에 따라 어긋날 수 있음 | **구조적으로 동일** |
| 검증 가능성 | 심사위원이 확인할 방법 없음 | `request.txt` 원문 ↔ 응답 원문 대조로 확인 가능 |

OTel 문서가 기본값으로 **내용을 캡처하지 않는다**고 명시한 것도 이 대비를 강화한다 — 표준 경로는 원래 "메타데이터만" 보도록 설계됐다.

### 4-2. 무료 반사실 재생

표준 도구의 재실행 기능([Phoenix의 replay-against-a-new-model](https://dreaming.press/posts/langfuse-vs-langsmith-vs-phoenix-observability.html))은 **실제로 모델을 다시 호출한다**. 우리는 각 중간 시도를 미리 로컬 채점기에 통과시켜 점수를 붙여 두므로, "n번째에서 멈췄다면 몇 점이었나"가 **재실행 없이 조회**된다.

이 아이디어의 정직한 한계도 리서치로 뒷받침된다 — 시도 2가 시도 1의 실패 신호를 보고 쓰였다면, 시도 1을 지운 세계에서 시도 2가 그대로 나온다는 보장이 없다. **화면에 명시할 것.** `08`의 MAST 정신(실패를 정직하게 분류)과도 맞다.

### 4-3. 실패 소유권 Sankey

주최 열거형(`Outcome` × `FailureKind` × `FailureOwner`)을 그대로 쓰는 Sankey는 다음을 한 화면에 보여준다:

```
전체 문항
 ├─ graded ──────────────┬─ 정답
 │                       └─ 오답
 ├─ extraction_failed ───── owner: team      ← 우리가 고칠 수 있는 것
 ├─ capped_tokens ───────── owner: team      ← 우리가 고칠 수 있는 것
 ├─ grader_error ────────── owner: organizer ← 분모에서 제외됨
 └─ infrastructure_failed ─ owner: organizer ← 분모에서 제외됨
```

포털 원문이 이 구분의 존재 이유를 직접 설명한다:

> `EXTRACTION_FAILED` is distinct from a graded-wrong answer **on purpose: a silent zero hides a harness defect behind a team's score.**

**이 문장을 화면에 인용하면 심사위원은 "이 팀은 채점 스펙을 읽었다"를 즉시 안다.**

## 5. 데이터 소스 — 무엇을 어디서 얻는가

| 소스 | 무엇이 있나 | 확보 방법 |
|---|---|---|
| **응답 본문 자체** | 장부 줄 + 시도별 블록 | 러너가 저장 (가장 신뢰도 높음) |
| AI:GO 워크스페이스 `logs/` | 실행 로그 | 로컬 파일 |
| AI:GO Discussion export (JSON) | *"JSON은 디스크 상의 룸 파일과 바이트 동일"* | `aigo squad discussion export <ID> --format json` |
| AI:GO Activity Feed | 세션 시작/중지, 태스크 배정·완료·실패, 예산 경고 (최근 200개) | 대시보드 / API |
| AI:GO 안전 이벤트 | `squad:budget-warning`, `squad:budget-exceeded`, `squad:emergency-stopped` | 이벤트 스트림 |
| AI:GO 세션 이벤트 SSE | `GET /api/v1/sessions/events` (CLI 명령 없음, 직접 구독) | REST |
| 제출 포털 | `/runs/{run_id}/details`, `BreakdownRow`, `PublishedCaps` | REST |
| dev-usage API | `cached_input_tokens`, `cached_input_share` | `GET /api/teams/me/dev-usage` |

`aigo squad discussion analytics <ID>`는 에이전트별 턴 수·토큰(prompt + completion)·**합성 토큰(대화록 총계와 분리)**·지속 시간·전략 변경 이력을 준다.

## 6. 시각화 30점 — 리서치가 지지하는 화면 목록

`../../track_resource/lableup/06-시각화-설계-가이드.md`의 화면 제안 중, **이 리서치가 근거를 대 줄 수 있는 것**만 골라 근거를 붙였다.

| 화면 | 대응 심사축 | 리서치 근거 |
|---|---|---|
| **장부 대조 뷰** (좌: request.txt 원문 / 우: 우리 응답, 마지막 블록에 `GRADED` 도장) | traceability | 표준 도구는 "채점된 바이트"를 보장 못 함 (4-1) |
| **무료 반사실 슬라이더** (최대 시도·승급 문턱·에이전트 제거 ablation) | insightfulness | 표준 도구의 replay는 실제 재호출 (4-2) |
| **낭비 사분면** (x=문항당 토큰, y=정답 여부) | insightfulness | 트랙 채점 구조(정확도 × 비용) 자체의 시각화 |
| **포기 최적 곡선** | insightfulness | s1의 budget forcing (→ `04`) |
| **캐시 히트 곡선** (`cached_input_share` 시계열) | insightfulness | prefix cache 실측 가능 (→ `05`) |
| **앵커 정확도 띠** (앵커가 실제 수정 위치를 포함했나) | explainability | localization이 최대 레버 (→ `06`) |
| **패치 해부도** (SEARCH 불일치를 글자 단위로) | explainability | SWE-Edit: 단일 공백 불일치 (→ `06`) |
| **실패 소유권 Sankey** | interpretability | 주최 열거형 + MAST (→ `08`) |
| **인과 그래프 뷰** (span이 아니라 "무엇이 무엇을 유발했나") | traceability, explainability | **표준 도구 전부가 실패한 지점** (3절) |
| Aggregated / Expanded 이중 뷰 | clarity | Langfuse agent graph 설계 |

마지막에서 두 번째 항목이 특히 값이 있다. **"타임라인은 언제를 기록할 뿐 왜를 기록하지 않는다"는 비판이 공개 문서로 존재하고, 우리가 그 빈틈을 메운다**는 서사는 심사위원에게 즉시 읽힌다.

### 하지 말아야 할 것 하나

AI:GO 모니터링 대시보드의 **Execution Timeline(가로 스윔레인, 색상: 초록=running, 빨강=error, 노랑=created, 파랑=completed, 회색=idle)** 을 그대로 다시 만드는 것.

> 심사위원(Lablup)은 이 화면을 매일 본다. 같은 것을 다시 만들면 30점 중 상위권을 못 받는다.

## 7. 이 문서의 결론

1. **OpenTelemetry GenAI semconv가 사실상 표준이고 별도 저장소로 관리된다.** `gen_ai.*` 속성명을 그대로 쓰고 트랙 고유는 `jxc.*`로 얹는다.
2. **표준 도구 셋(Langfuse/LangSmith/Phoenix)은 전부 OTel로 수렴했다.** 즉 표준 어휘를 쓰는 것이 곧 "업계 표준 준수"로 읽힌다.
3. **그 도구들의 공통 약점이 공개 비판으로 문서화되어 있다** — 타임라인은 "언제"만 기록하고 "왜"를 기록하지 않는다. 근본원인 규명에 60~90분.
4. **심사 6축 중 우리가 이겨야 할 셋(traceability, explainability, insightfulness)이 정확히 그 빈틈이다.**
5. **바이트 동일성이 우리 고유 자산이다.** 표준 도구는 요청 경로 밖에서 수집하므로 채점된 것과의 일치를 보장하지 못하고, OTel은 기본적으로 내용을 캡처하지도 않는다.
6. **AI:GO 기본 대시보드를 재현하지 마라.**
