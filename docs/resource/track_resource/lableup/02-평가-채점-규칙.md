## 2. 벤치마크의 실체 — 3개 트랙

리더보드 페이지가 트랙을 직접 설명한다. 원문과 해석을 같이 싣는다.

### coding

> Real bugs in real open-source repositories. The squad edits the source of the project itself, and the edit counts only when the tests that were failing go green and the tests that were already passing stay green.

실제 오픈소스 저장소의 실제 버그. 스쿼드가 프로젝트 소스를 직접 수정하며, **실패하던 테스트가 통과로 바뀌고(fail-to-pass) 이미 통과하던 테스트가 계속 통과할 때(pass-to-pass)만** 정답으로 인정된다. — SWE-bench의 표준 채점 방식이다.

### math

> Competition mathematics. Only the final answer is graded, checked exactly rather than read, so a right answer reached badly still counts and a good attempt that lands on the wrong number does not.

경시 수학. **최종 답만 채점**하며, 읽어서 판단하는 게 아니라 정확히 대조한다. 과정이 엉망이어도 답이 맞으면 인정되고, 과정이 훌륭해도 숫자가 틀리면 0점이다.

### generic

> Hard multiple-choice questions drawn from across the academic subjects. What is graded is the option the squad settled on, not the reasoning it printed.

여러 학문 분야에 걸친 어려운 객관식. **스쿼드가 최종적으로 고른 보기**만 채점하며, 출력한 추론 과정은 채점하지 않는다.

## 3. 트랙 가중치 — 코딩이 절반이다

`set.manifest.json`에 명시된 값이다.

```json
"weights": { "coding": 0.5, "generic": 0.25, "math": 0.25 }
```

> Weights are score weights over per-track accuracies. **They are not item-count shares**: a track's weight says how much its accuracy counts, not how many items it runs.

**가중치는 문항 수 비율이 아니라 정확도에 곱해지는 계수다.** 즉 최종 점수는

```
overall = 0.5 × accuracy(coding) + 0.25 × accuracy(generic) + 0.25 × accuracy(math)
```

문항 수는 오히려 generic이 압도적으로 많다(아래 4절). **문항이 적은 coding이 점수의 절반을 가진다** — 여기가 승부처다.

## 6. 채점자는 항상 프로그램이다

> Who decides right and wrong — **Programs, always.** Every verdict is deterministic — tests that pass or fail, an answer that matches or does not — and **no model is ever asked to judge another model.**

**LLM-as-a-judge가 없다.** 그러니 "그럴듯하게 쓰면 점수를 받는" 여지가 0이다.

트랙별 grader (매니페스트에 명시):

| 트랙 / 데이터셋 | grader | 방식 |
|---|---|---|
| coding / swebench | `swebench_docker` | Docker 안에서 test_patch를 적용해 pytest 실행 |
| coding / livecodebench | `livecodebench_tests` | 공개 테스트 케이스로 stdin/stdout 대조 |
| math (integer) | `integer_exact` + `math_verify` | 정수 정확 일치, 그리고 수식 동치 검증 |
| math (expression) | `math_verify` | 수식 동치 검증 (LaTeX 정규화 포함) |
| generic | `letter_match` | 보기 문자(A~J) 대조, 대소문자 무시 |

**시사점** — 정답 추출(answer extraction)이 실패하면 그냥 0점이 아니라 `extraction_failed`로 별도 분류된다(7절). 답을 지정된 형식으로 확실히 뽑아내는 것이 정답률만큼 중요하다.

## 7. 채점 결과 분류 체계 (Outcome / ItemStatus / FailureKind)

OpenAPI 스키마에서 그대로 가져온 값이다. 시각화 산출물이 이 어휘를 그대로 쓰면 심사위원에게 바로 읽힌다.

### `Outcome` — 왜 그 점수가 나왔는가

| 값 | 뜻 | 책임 주체 |
|---|---|---|
| `graded` | 정상 채점됨 | 팀 |
| `extraction_failed` | 답을 뽑아내지 못함 | 팀 |
| `capped` | 상한(cap)에 걸림 | 팀 |
| `grader_error` | 채점기 오류 | **주최** |
| `infrastructure_failed` | 인프라 실패 | **주최** |

> `EXTRACTION_FAILED` is distinct from a graded-wrong answer on purpose: a silent zero hides a harness defect behind a team's score.
> Two of the five are judge-owned: `GRADER_ERROR` and `INFRASTRUCTURE_FAILED`. Nothing a squad's output can do causes either one, so **neither is priced into a ranked denominator.**

주최 책임 실패는 순위 계산의 분모에서 제외된다. 반대로 `extraction_failed`와 `capped`는 **팀 책임**이다.

### `ItemStatus` — 한 문항의 실행 상태

`ok` / `capped_tokens` / `capped_wallclock` / `error`

### `FailureKind` — 실패 원인

`infrastructure` / `upstream_error` / `token_cap` / `wallclock_cap` / `runner`

> The evaluation endpoint is intermittently unavailable — five independent outages were observed in one afternoon. Without this field an outage is indistinguishable from a squad that answered badly, and **AI:GO's failure-as-context semantics turn an unretried connect timeout into "execution completed, all tasks failed"**, which grading would read as a team's zero.

**중요한 실전 경고다.** AI:GO는 실패를 컨텍스트로 넘기는 의미론(failure-as-context)을 쓰기 때문에, 재시도되지 않은 connect timeout이 "실행은 완료됐고 모든 태스크가 실패함"으로 보고된다. 우리 쪽에서도 **네트워크 오류와 모델이 못 푼 것을 반드시 구분해서 기록**해야 한다. 시각화에서 이 구분을 보여주면 그 자체로 점수다.

### `FailureOwner` — 누구 책임인가

`team` / `policy` / `configuration` / `organizer`

### `RunState` / `RunStatus`

- `RunState` (제출 서버 관점): `queued` → `awaiting_runner` → `running` → `finished` / `failed` / `ended`
- `RunStatus` (실행 기록 관점): `completed` / `capped` / `failed`

## 8. 상한(caps) — 모든 팀에게 동일

리더보드 페이지의 Comparability 절 전문:

> Comparability: every run on this page executed under a **per-item wall-clock cap** and a **per-run token cap**, identical for every team. Runs that executed under different caps are not directly comparable, and the difference is not a small correction. **Two of the three evaluation models are reasoning models — one was measured spending 97% of its output budget on reasoning tokens before it answered — so a token cap bites roughly an order of magnitude harder on a squad built from reasoning models than on one built from an instruct model.** Read the caps column before comparing two rows.

이 문단은 전략적으로 가장 중요한 정보 중 하나다. 정리하면:

1. **문항당 wall-clock 상한**과 **실행당 토큰 상한**이 있다. 구체적 숫자는 공개되지 않았고, 실행 기록(`PublishedCaps`)에 실제 적용값이 기록된다.
2. **평가에 쓸 수 있는 모델은 3개다.**
3. **그중 2개는 reasoning model(추론 모델)**이다. 하나는 답을 내기 전에 **출력 예산의 97%를 추론 토큰에 썼다**고 측정되었다.
4. 따라서 **토큰 상한은 추론 모델로 짠 스쿼드에 약 10배 더 세게 물린다.**

→ 실무 결론: **instruct 모델(예: `Qwen3-30B-A3B-Instruct-2507-FP8`, non-thinking)을 기본으로 쓰고, reasoning 모델은 정말 필요한 지점에만 국소적으로 투입**하는 설계가 토큰 효율 30점과 벤치마크 40점 양쪽에 유리하다. 자세한 것은 `07-토큰-효율-전략.md`.

`CapsView` / `PublishedCaps` 스키마 필드: `recorded`, `readable`, `per_run_token_cap`, `per_item_wallclock_seconds`, `infra_retries`.

## 9. 리더보드 규칙

> **A row is a run, not a team.** Every evaluation run posts here as soon as it has been graded, so a team that ran more than once appears more than once. Nothing is held back and there is no publish button.

- 리더보드 한 줄 = 팀이 아니라 **실행 하나**. 여러 번 돌리면 여러 줄이 뜬다. 감출 수 없고 게시 버튼도 없다.
- **점수**: 트랙별 정확도에 트랙 가중치를 곱해 합산, 0~1 범위, 높을수록 좋음.
- **동점 처리**: ① **총 토큰 수**가 적은 쪽 ② 그래도 같으면 **wall-clock**이 짧은 쪽.

> Total tokens is the tie-break when two runs score the same, and wall-clock breaks a tie after that, **so the cheaper run wins a draw.**

- 채점 완료 후 **1초 이내**에 리더보드에 게시된다. 채점 자체는 수 분 걸린다. 페이지는 자동 새로고침되지 않는다.
- 리더보드는 세션을 읽지 않고 쿠키도 심지 않는다. 로그인한 팀에게도 똑같은 페이지가 보인다. **각 실행의 문항 단위 상세는 로그인 뒤 그 팀에게만** 보인다.
- 공개되는 항목: rank, team_name, posted_at, run_id, team_id, submission_id, run_status, started_at, completed_at, execution_seconds, overall, 트랙별 결과(accuracy/graded/total/excluded/weight), 모델별 토큰 사용량, `disclosure: public`인 문항의 결과 라인, caps, attribution notices.

## 11. 토큰 효율 점수 — 계산 방식 정리

PDF 24~25페이지 + 포털 정보를 합친 이해다.

```
정규화 비용 = Σ (모델별 토큰수 × 그 모델의 USD/Mtok 기준 단가 × 실행 계수)

실행 계수:
  - AI:GO test run  → 1/5  (0.2배)
  - submission run  → 1    (전액)

모든 제출(평가 제출 포함)의 비용이 누적 합산된다.
총 비용이 낮은 팀이 높은 점수.
```

**주의해야 할 함정 3가지**

1. **제출 횟수가 곧 비용이다.** "일단 넣어보고 점수 보자"를 5번 하면 전액 5회분이 붙는다.
2. **Development usage와 Token efficiency는 다른 계정 체계다.** 개발용 키 사용량은 별도로 집계되며 제출에 직접 카운트되지 않는다(포털 명시). 하지만 PDF의 "AI:GO test runs ... one-fifth"는 카운트된다고 말한다. → **개발 키 사용량과 AI:GO 테스트 런은 다른 것으로 보고 관리할 것.** 애매한 부분이므로 21:00 온보딩 세션에서 반드시 확인할 것.
3. **동점 시 토큰이 적은 쪽이 이긴다.** 즉 토큰 절약은 30점짜리 축이면서 동시에 40점짜리 축의 동점 처리 기준이기도 하다. **이중으로 효과가 있다.**

## 12. 우리가 아직 모르는 것 (온보딩 세션에서 확인할 질문 목록)

1. **모델 3종의 정확한 이름과 USD/Mtok 단가.** 개발 사용량 화면에서 확인된 건 `Qwen3-30B-A3B-Instruct-2507-FP8` 하나뿐이다. 나머지 2개(reasoning 모델)는?
2. `per_run_token_cap`과 `per_item_wallclock_seconds`의 실제 숫자.
3. Squad Template JSON의 정확한 스키마 — AI:GO 템플릿 스키마 그대로인가, 제출 서버 전용 변형이 있는가. (Submit 페이지가 로그인 뒤에 있어 확인 불가)
4. 트랙별 one-shot 프롬프트가 스쿼드에 어떻게 주입되는가 — planner에게 가는가, 전체 에이전트에게 가는가.
5. coding 트랙에서 스쿼드는 도구를 못 쓴다("your squad has no tools during a run and never browses a repository" — practice-sets 페이지). 그렇다면 저장소 컨텍스트는 어떻게 들어오는가? → **judge가 직접 코드를 검색해서 요청에 넣어준다.** 그 결과물이 `coding/context.jsonl` 번들이다. 이 부분은 `04-벤치마크-데이터셋-분석.md`에서 상세히 다룬다.
6. Trace 로그를 우리가 어떤 경로로 확보하는가 — 포털의 `/runs/{run_id}/details`인가, 로컬 AI:GO의 실행 로그인가, 둘 다인가.
