## 1. 트랙 챌린지 전문 (PDF 20페이지)

### Background (배경)

> The best AI models available today run on massive infrastructure. Not everyone can access the services that frontier model developers offer through APIs built on infrastructure owned by the biggest technology companies. That is why Lablup and FuriosaAI are asking you a question:
> **How far can you go with a model you can actually hold in your hands?**

한국어 정리 — 오늘날 최고 성능 AI 모델은 거대한 인프라 위에서만 돌아간다. 프론티어 모델 개발사가 빅테크 인프라 위에 얹어 제공하는 API 서비스에 모두가 접근할 수 있는 것은 아니다. 그래서 Lablup과 FuriosaAI가 던지는 질문: **직접 손에 쥘 수 있는 모델로 어디까지 갈 수 있는가?**

이 문장이 트랙 전체의 설계 의도다. "프론티어 모델을 쓰지 않고, 로컬/온프렘에서 돌릴 수 있는 중형 오픈 모델과 잘 짜인 멀티 에이전트 구조만으로 어디까지 성능을 뽑아내느냐"를 겨루는 것이다.

### Challenge (과제)

> For this challenge, you are going to craft two types of output:
> - Problem-solving AI agent squad formation
> - Interactive visualization (web, animation generator, etc.) of squad's problem-solving processes.
>
> For the former product, your goal is to create and tune an AI agent solving various problems across multiple categories, including but not limited to mathematic, coding and more. You will design the squad entirely on your own, deciding which agents read the code, which ones modify it, which ones verify the results, and which ones determine when it is time to give up. **The critical parts of the problem-solving process must be built on AI:GO's agent squad functionality.**

한국어 정리 — 두 가지 산출물을 만든다.

**산출물 A: 문제 해결형 AI 에이전트 스쿼드 구성**
- 수학, 코딩을 포함한(그에 한정되지 않는) 여러 범주의 문제를 푸는 AI 에이전트를 만들고 튜닝한다.
- 스쿼드 설계는 전적으로 참가자 몫이다. 구체적으로 결정해야 하는 것:
  - 어떤 에이전트가 **코드를 읽을** 것인가
  - 어떤 에이전트가 **코드를 수정할** 것인가
  - 어떤 에이전트가 **결과를 검증할** 것인가
  - 어떤 에이전트가 **포기 시점을 판단할** 것인가 (← 이게 토큰 효율 점수와 직결된다)
- **문제 해결 과정의 결정적 부분은 반드시 AI:GO의 agent squad 기능 위에 올라가야 한다.** 이건 선택이 아니라 요구사항이다.

**산출물 B: 인터랙티브 시각화**
- 스쿼드의 문제 해결 과정을 시각화한다. 매체는 웹, 애니메이션 생성기 등 자유.
- 채점 기준(24페이지)에 따르면 시각화 대상은 **Trace** — 로그(텍스트) 데이터로 표현되는 실행 궤적이다.

## 2. 평가 및 배점 (PDF 24 ~ 25페이지)

세부 내용은 `02-평가-채점-규칙.md`에 전부 정리했다. 여기서는 원문만 옮긴다.

### Benchmark score (40점)

> Scores will be awarded in order of the teams' rankings based on their results in the final benchmark test.

최종 벤치마크 테스트 결과 팀 순위 순으로 점수를 준다.

### Visualization (30점)

> Scores will be awarded based on how effectively the Trace, represented as log (text) data, is visualized with consideration for **observability, interpretability, traceability, explainability, clarity, and insightfulness**.

로그(텍스트) 데이터로 표현된 Trace를 얼마나 효과적으로 시각화했는지로 채점한다. 여섯 가지 축을 명시했다:

| 축 | 원어 | 요구하는 것 |
|---|---|---|
| 관측 가능성 | observability | 지금 무슨 일이 벌어지고 있는지 밖에서 볼 수 있는가 |
| 해석 가능성 | interpretability | 그 일이 무엇을 뜻하는지 읽어낼 수 있는가 |
| 추적 가능성 | traceability | 결과에서 원인까지 거슬러 올라갈 수 있는가 |
| 설명 가능성 | explainability | 왜 그렇게 했는지 설명이 되는가 |
| 명료성 | clarity | 군더더기 없이 한눈에 들어오는가 |
| 통찰력 | insightfulness | 보고 나면 몰랐던 것을 알게 되는가 |

### Token efficiency (30점)

> A reference cost in dollars per million tokens (USD/Mtok) will be set for each model. Teams will be ranked by their total normalized usage cost, with test runs charged at one-fifth of the reference rate and submission runs charged at the full rate. Teams may submit multiple times, and the cost of every submission, including evaluation submissions, will be included. Teams with lower total usage costs will receive higher scores.

- 모델마다 **USD/Mtok** (백만 토큰당 달러) 기준 단가가 정해진다.
- 팀은 **정규화된 총 사용 비용(total normalized usage cost)** 으로 순위가 매겨진다.
- **테스트 실행(test run)은 기준 단가의 1/5**로 과금된다.
- **제출 실행(submission run)은 기준 단가 전액**으로 과금된다.
- 여러 번 제출할 수 있지만, **평가 제출을 포함한 모든 제출의 비용이 합산된다.**
- 총 사용 비용이 낮은 팀이 높은 점수를 받는다.

### Token efficiency — 방법과 설명 (PDF 25페이지 전문)

> - **Validation submissions**: Every run is billed at the full rate. If a team runs a submission once, one run is charged; if it runs the submission 100 times, all 100 runs are charged.
> - **AI:GO test runs**: Test runs are not fully billed. Only one-fifth of the total cost is counted toward token efficiency.
> - **Usage tracking**: Teams can check their total token usage in the Submission Dashboard.
> - **Real-time leaderboard**: Benchmark results submitted by all participants are publicly displayed.
> - **Run-level details**: Participants can view the final score for each benchmark run, along with the number of tokens used by each model during that run.
>
> Teams that achieve comparable benchmark results with lower token usage will receive a higher token-efficiency score.

핵심 함의 — **제출 버튼을 누르는 횟수 자체가 비용이다.** 100번 제출하면 100번 다 과금된다. 반면 AI:GO에서 돌리는 테스트 런은 1/5만 계산된다. 그러니 **로컬/테스트에서 최대한 다듬고, 제출은 아껴서** 해야 한다.

### Submit 탭 — "Submit a squad template"

> One Squad Template JSON, plus one one-shot prompt for each track. Checking is free and can be repeated as often as you like — nothing is queued until you press *Submit to the queue*.

- 제출물 = **Squad Template JSON 1개** + **각 트랙마다 one-shot 프롬프트 1개**
- **Check(검사)는 무료이고 원하는 만큼 반복할 수 있다.** *Submit to the queue*를 누르기 전에는 큐에 아무것도 들어가지 않는다.

**What a submission costs your team** 박스에 표시되는 항목:

| 항목 | 스크린샷의 값 | 의미 |
|---|---|---|
| Right now | `Eligible now` — Nothing of yours is waiting or in flight. | 지금 제출 가능 상태 |
| Waiting submissions | 0 of 3 allowed | 대기 중 제출은 **최대 3개** |
| Runs in flight | 0 of 1 allowed | **팀당 동시 평가는 1개**. 큐에 들어간 제출은 앞 실행이 끝날 때까지 대기 |

입력 필드: `Squad Template JSON` (대형 textarea)

### Development usage 탭

> What your team spent on the shared serving stack while tuning, using your development API keys. Evaluation runs use organizer-held keys and are accounted for separately, so nothing here counts against a submission.

- 튜닝 중 **개발용 API 키**로 공유 서빙 스택에 쓴 사용량을 보여준다.
- **평가 실행(evaluation run)은 주최 측이 보유한 키를 쓰며 별도로 집계된다.** 즉 이 화면의 숫자는 제출 점수에 직접 반영되지 않는다.
- 창(window): `last 1 hour` / `last 1 day` / `last 7 days`. 모두 "지금"에서 끝나는 롤링 윈도우이며 약 30초마다 갱신된다.

**Total 표 컬럼**: Requests · Input tokens · Cached input · Cached share · Output tokens · Total tokens
스크린샷 예시 값: 303 requests / 771,072 input / 60,326 cached input / 8% cached share / 68,076 output / 839,148 total

> **Cached input** is the part of your prompt the stack served from its prefix cache. Your tier meters cached input more cheaply than fresh input, so **a prompt structure that keeps a long stable prefix in front of the varying part buys you real headroom.**

이 문장은 사실상 힌트다. **prefix cache** (프롬프트 앞부분이 이전 요청과 동일하면 재계산하지 않고 캐시에서 꺼내 쓰는 기능) 에 걸리는 캐시된 입력 토큰은 새 입력 토큰보다 싸게 과금된다. 따라서 **길고 고정된 프리픽스를 앞에, 변하는 부분을 뒤에** 두는 프롬프트 구조가 실제로 비용 여유를 만들어 준다. → `07-토큰-효율-전략.md` 참고.

- **멀티 인스턴스 연결** — 고사양 PC에서 큰 모델을 돌리고 엣지 기기에서 mesh 네트워킹으로 접속
- **Backend.AI 클러스터 연동** — 기존 클러스터 추론 활용 또는 새 추론 세션 기동

### 기술 관점 슬라이드 (8 ~ 11페이지)

컴퓨팅 발전 방향에 대한 회사의 시각.

- 8페이지 — HPC에서 AI로, 범용에서 가속으로. "Supercomputing"(FP64, OpenMPI, Fortran, 고정밀 부동소수점)에서 "Accelerated Computing"(FP8, INT8, FP4, PyTorch, Triton, 양자화·응답속도 중시)으로. 표준화·범용 칩에서 이기종·전용 칩으로.
- 9페이지 — 고밀도·고집적 가속 컴퓨팅의 시대
- 10페이지 — 컴퓨팅 수요 증가 (Meta의 RSC 인용)
- 11페이지 — **비용 효율적인 LLM 서비스 구축의 기술적 난이도**
  - 일반 HTTP 워크로드(마이크로서비스): 빠르고 균일하고 저렴. preemption 쉽고 scale in/out 단순.
  - LLM 서비스 워크로드: 느리고 불균일하고 비쌈. **입력 의존적 컨텍스트, 노드 상태 인식 라우팅과 스케일링**이 필요.
  - 따라서 Microservice LB와 LLM-aware LB는 다른 물건이다. (LLM-d, JAX/OpenXLA DevLab 2025 인용)

## 8. 이 트랙이 실제로 요구하는 것 — 요약

PDF 문면과 제출 포털에서 실제로 확인한 내용을 합치면 다음과 같다.

1. **AI:GO Squad 템플릿 JSON 하나**를 설계한다. 여기에 에이전트 구성(역할, 시스템 프롬프트, 도구, 모델 선호)이 전부 들어간다.
2. **트랙별 one-shot 프롬프트**를 각각 작성한다 (coding / math / generic 3개).
3. 제출하면 주최 측 인프라에서 **숨겨진(hidden) 벤치마크 세트**에 대해 평가가 돌아간다. 채점은 전부 결정론적 프로그램이 한다 (LLM 심판 없음).
4. 그 실행의 **Trace(로그)** 를 인터랙티브하게 시각화한 별도 산출물을 만든다.
5. 세 축(정확도 / 시각화 / 토큰 효율)이 각각 40/30/30으로 합산된다.

**따라서 승부처는 셋이다.**
- 정확도: 어떤 에이전트 구성이 3개 트랙 모두에서 잘 푸는가
- 절제: 언제 포기하고 토큰을 아끼는가 (문제 지문이 "which ones determine when it is time to give up"을 명시적으로 물어본 이유)
- 서사: 그 과정을 남이 보고 이해하게 만들 수 있는가

세부 규칙과 실제 벤치마크 스펙은 `02-평가-채점-규칙.md`부터 이어서 읽을 것.
