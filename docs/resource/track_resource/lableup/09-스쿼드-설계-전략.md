# 09. 스쿼드 설계 전략과 실행 계획

> 앞의 문서들이 "무엇이 사실인가"라면, 이 문서는 "그래서 무엇을 만들 것인가"다.
> 여기 적힌 설계는 **제안이며 가설**이다. 연습 세트 364문항으로 검증한 뒤에 확정할 것.

---

## 1. 설계 제약 정리 — 반드시 만족해야 하는 것들

| 제약 | 출처 | 의미 |
|---|---|---|
| 문제 해결 과정의 핵심부는 **AI:GO agent squad 기능** 위에 | PDF 20p | 스쿼드를 안 쓰면 실격 사유 |
| 제출물은 **Squad Template JSON 1개 + 트랙별 one-shot 프롬프트** | 포털 Submit 화면 | **하나의 템플릿이 세 트랙을 모두 처리**해야 한다 |
| **평가 실행 중 스쿼드는 도구가 없다** | 포털 practice-sets 페이지 | 검색·탐색 에이전트는 무의미 |
| 스쿼드 에이전트의 파일 도구는 워크스페이스 범위로 제한, 호스트 경로 도구는 전면 차단 | AI:GO 공식 문서 | 위와 같은 방향 |
| **planner는 정확히 한 명** | AI:GO 공식 문서 | 구조가 강제됨 |
| 문항당 wall-clock 캡 + 실행당 토큰 캡 | 리더보드 | 무한정 돌릴 수 없다 |
| 대기 제출 3개 / 동시 실행 1개 | 포털 Submit 화면 | 제출 슬롯이 희소 자원 |

**가장 중요한 제약: 템플릿은 하나다.** 세 트랙에 각각 다른 스쿼드를 낼 수 없다. 그래서 **트랙 분기는 planner의 시스템 프롬프트 안에서** 일어나야 한다.

> **[갱신됨 2026-08-23]** 아래 내용은 2026-08-21 조사 시점 기준이며 이후 실측으로 뒤집혔다. 최신 사실은 `docs/ideation/final_final_ideation/spec/`를 따른다. 아래 6인 구성과 unified diff 출력은 최종 스펙에서 **5인**(Router · Architect · Editor · Solver · Reviewer) **+ SEARCH/REPLACE**로 바뀌었고, 4절의 **트랙별 예산은 표현 불가능하다** — `BudgetConfig`는 스쿼드당 한 벌이다.

## 2. 스쿼드 구조 제안

### 2-1. 전체 형태

```
                        ┌──────────────┐
   one-shot prompt ───▶ │   Router     │  (Planner 역할)
   + item payload       │  = Planner   │
                        └──────┬───────┘
                               │ payload.kind로 분기
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
   │ CODE PATH   │     │ MATH PATH   │     │ MCQ PATH    │
   │ (swebench / │     │             │     │             │
   │  livecode)  │     │             │     │             │
   └─────────────┘     └─────────────┘     └─────────────┘
```

세 경로가 **비용 구조가 완전히 다르다.** 하나의 파이프라인으로 통일하려 하지 말 것.

### 2-2. 에이전트 목록 제안 (6명)

| # | 이름 | role | 담당 | 모델 · 설정 | 대략 비용 |
|---|---|---|---|---|---|
| 1 | **Router** | `Planner` | 문항 종류 판별, 경로 배정, 태스크 그래프 생성 | instruct, `--no-think`, `max_tokens` 소량 | 매우 낮음 |
| 2 | **Solver** | `Custom` | math / generic 문항을 직접 푼다 | instruct 기본. math에서 선별적 thinking | 낮음~중간 |
| 3 | **CodeReader** | `Custom` | 컨텍스트 발췌에서 관련 위치를 특정. **요약이 아니라 위치 인덱스를 낸다** | instruct, `--no-think` | 입력 큼, 출력 작음 |
| 4 | **PatchWriter** | `Developer` | unified diff 또는 코드 작성 | instruct | 중간 |
| 5 | **Verifier** | `Reviewer` | 형식 유효성과 자기 일관성 검사 | instruct, `--no-think`, 짧은 출력 | 낮음 |
| 6 | **GiveUpJudge** | `Custom` | `continue` 또는 `give_up` 한 단어만 출력 | instruct, `--no-think`, `max_tokens: 5` | **거의 0** |

> **왜 GiveUpJudge를 별도 에이전트로 두는가** — 문제 지문이 명시적으로 물었다("which ones determine when it is time to give up"). 그리고 실질적으로도 총 비용의 큰 몫을 잘라낸다. **출력이 한 단어라 자기 비용은 0에 수렴한다.** 이 트랙에서 가장 비용 대비 효과가 좋은 에이전트다.

> **왜 CodeReader가 "요약"이 아니라 "위치 인덱스"를 내는가** — 컨텍스트가 이미 `{path, start_line, end_line, text}`로 구조화되어 있다(`04-벤치마크-데이터셋-분석.md` 5-3절). 요약은 정보를 잃지만 인덱스는 잃지 않는다. `[3, 7, 9]` 같은 짧은 출력으로 PatchWriter가 볼 발췌를 좁힐 수 있다.

### 2-3. 경로별 웨이브 구성

**CODE PATH (swebench)**
```
Wave 0  Router        문항 종류 판별
Wave 1  CodeReader    컨텍스트에서 관련 발췌 인덱스 산출
Wave 2  PatchWriter   해당 발췌만 보고 unified diff 작성
Wave 3  Verifier      diff 문법 유효성 + 대상 파일/라인 정합성
Wave 4  GiveUpJudge   재시도할지 포기할지  → 재시도면 Wave 2로
```

**CODE PATH (livecodebench)** — 컨텍스트가 없으므로 CodeReader를 건너뛴다
```
Wave 0  Router        stdin/functional 모드 판별
Wave 1  PatchWriter   코드 작성
Wave 2  Verifier      (로컬 실험 시) public_test_cases로 실행 검증
Wave 3  GiveUpJudge
```

**MATH PATH**
```
Wave 0  Router        answer_format 판별 (integer / expression)
Wave 1  Solver        문제 풀이 → \boxed{} 형식으로 답
Wave 2  Verifier      형식 검사만 (정수 문항인데 수식이면 반려)
```
`run_repeats: 2`이므로 실행이 2배다. **웨이브를 늘리면 2배로 비싸진다.** 최소로 유지할 것.

**MCQ PATH (generic)**
```
Wave 0  Router        (사실상 통과)
Wave 1  Solver        보기 문자 하나만 출력
```
**웨이브 1개.** hidden 448~698문항 × 가중치 0.25다. 여기에 검증 웨이브를 붙이면 손해다.

## 3. 프롬프트 설계 — 캐시를 사수하는 순서

`07-토큰-효율-전략.md` 3절의 원칙을 템플릿에 그대로 반영한다.

### 시스템 프롬프트 구조 (모든 에이전트 공통 접두부)

```
┌─ 절대 변하지 않는 부분 (전 요청 캐시 대상) ────────────┐
│ 1. 대회 컨텍스트 (이 스쿼드가 무엇을 하는가)           │
│ 2. 출력 형식 규약 (트랙별 형식 규칙 전부)              │
│ 3. 공통 금칙 (설명 금지, 서두 금지, 마크다운 펜스 규칙)│
│ 4. few-shot 예시 (트랙별 1~2개씩)                      │
└────────────────────────────────────────────────────────┘
┌─ 문항 단위로 변하는 부분 (문항 내 재사용 캐시 대상) ───┐
│ 5. item payload (지문, 컨텍스트 발췌)                  │
└────────────────────────────────────────────────────────┘
┌─ 에이전트 단위로 변하는 부분 (캐시 안 됨, 짧게) ───────┐
│ 6. 이 에이전트의 역할과 이번 태스크 지시               │
└────────────────────────────────────────────────────────┘
```

**6번을 1번 앞이나 사이에 넣으면 캐시가 전부 깨진다.** AI:GO의 `systemPrompt` 필드는 에이전트별이므로, 1~4번을 **모든 에이전트의 systemPrompt에 동일한 문자열로 복제**하고, 그 뒤에 에이전트별 지시를 붙이는 형태가 된다.

### 출력 형식 규약 예시

```
OUTPUT CONTRACT — obey exactly, no exceptions.

multiple_choice : output exactly one letter from the option_letters given.
                  Nothing before it, nothing after it.
math            : output the final answer inside \boxed{ }. Nothing else.
                  If answer_format is "integer", the content of \boxed{} must be
                  a bare integer with no units, no commas, no words.
swebench        : output exactly one unified diff. It must start with "--- a/"
                  and apply cleanly against the stated base_commit.
                  No commentary before or after the diff.
livecodebench   : if evaluation_mode is "stdin", output one complete program that
                  reads stdin and writes stdout.
                  if evaluation_mode is "functional", fill in the given starter_code
                  signature and output only that function.
                  In both cases output only code, in a single fenced block.
give_up_judge   : output exactly one word, "continue" or "give_up".
```

**`option_letters`를 프롬프트에 그대로 주입할 것.** MMLU-Pro 문항의 보기 수가 3~10개로 들쭉날쭉하다 (`04-벤치마크-데이터셋-분석.md` 4절).

### 트랙별 one-shot 프롬프트

포털이 트랙마다 하나씩 요구한다. 이건 **그 트랙의 문항 하나가 어떻게 처리되어야 하는지를 보여주는 지시문**으로 보는 것이 자연스럽다. 정확한 의미는 로그인 후 `/submit` 페이지에서 확인해야 한다.

여기에 넣을 것:
- 그 트랙의 정확한 출력 계약
- 그 트랙에서 쓸 웨이브 구성
- 그 트랙의 포기 규칙 (턴 상한, 재시도 횟수)
- 그 트랙 고유의 함정 (예: coding이면 django/sympy 관례, generic이면 보기 수 가변)

## 4. 예산 설정 초기값 제안

`03-AIGO-Squad-완전가이드.md` 7절의 기본값에서 출발해, 트랙 성격에 맞춰 낮춘 값이다. **스윕으로 검증할 것.**

| 설정 | AI:GO 기본 | 제안 초기값 | 근거 |
|---|---|---|---|
| Max total tokens | 100,000 | **coding 80,000 / math 8,000 / generic 3,000** | 문항당 입력 규모 차이 |
| Max tokens per agent | 30,000 | coding 30,000 / 그 외 3,000 | CodeReader만 크게 |
| Max tokens per task | 10,000 | coding 20,000 / math 2,000 / generic 800 | 출력 계약이 짧다 |
| Max concurrent agents | 3 | **2** | 웨이브가 대부분 직렬 |
| Max tasks per plan | 20 | **6** | 웨이브 5개면 충분 |
| Max plan iterations | 3 | **1** | 재계획은 통째로 비싸다 |
| Max agent turns | 20 | **coding 6 / math 3 / generic 1** | 최대 절감 지점 |
| Execution timeout | 1,800초 | 문항 wall-clock 캡 아래로 | 캡 값 확인 후 결정 |
| Task timeout | 300초 | **120초** | 멈춘 에이전트 조기 차단 |
| Agent idle timeout | 60초 | 30초 | |
| Warning threshold | 80% | 70% | 조기 경보 |

> **토큰 카운팅이 근사치라 한도를 약간 넘길 수 있다**는 공식 경고를 감안해 여유를 둘 것.

| **SWE-bench 로컬 채점이 무겁다** (Docker 필요) | coding 트랙 검증 불가 | LiveCodeBench(로컬 실행 가능)를 코딩 능력 대리 지표로. SWE-bench는 패치 형식 유효성 + 수동 샘플 검토 |
| **평가 엔드포인트가 간헐적으로 불안정** (스펙에 "한 오후에 5회 장애 관측"이라 기록됨) | 실행 실패를 우리 실력으로 오인 | `FailureOwner`로 구분. 재시도 로직. **시각화에서 이 구분을 보여주면 오히려 가점** |
| **AI:GO의 failure-as-context 의미론** — 재시도 안 된 connect timeout이 "완료, 전 태스크 실패"로 보고됨 | 0점 처리 | 러너 레벨에서 네트워크 오류를 명시적으로 분리 기록 |
| **토큰 캡 초과로 실행 중단** | 부분 채점 | 예산 한도를 캡보다 낮게. 조기 종료 규칙 |
| **`extraction_failed` 다발** | 팀 책임 0점 | `max_tokens`를 너무 낮추지 말 것. 연습 세트로 잘림 비율 실측 |
| **시각화를 나중에 붙이려 함** | 트레이스가 없어 30점 손실 | **Phase 2에서 로거부터 심는다** |
| **동시 실행 1건 제약** | 마감 직전 병목 | 마지막 제출 시각을 역산해서 계획 |
| **데모 중 네트워크 실패** | 시각화 시연 불가 | 녹화 재생 모드 필수 |

## 7. 차별화 포인트 정리 — 왜 우리가 이겨야 하는가

세 축 각각에서 다른 팀이 놓칠 것들이다.

### 벤치마크 40점
- **가중치가 coding 0.5임을 안다.** 대부분의 팀은 세 트랙을 균등하게 다룬다.
- **평가 중 도구가 없다는 것을 안다.** 검색 에이전트를 만드는 팀은 시간을 버린다.
- **컨텍스트가 60,000자로 고정 제공된다는 것을 안다.** 이 조건에 맞춘 프롬프트를 짤 수 있다.
- **django 15 / sympy 10 편중을 안다.** 두 프로젝트 관례를 시스템 프롬프트에 넣을 수 있다.

### 시각화 30점
- **OpenTelemetry GenAI 표준 어휘를 쓴다.** "예쁜 로그 뷰어"가 아니라 "표준 준수 관측 파이프라인"이 된다.
- **주최 측의 `Outcome`/`FailureOwner` 열거형을 그대로 쓴다.** 심사위원의 학습 비용 0.
- **정확도 대 비용을 정면으로 시각화한다.** 이 대회의 채점 구조 자체를 화면으로 만든 팀은 드물 것이다.
- **인터랙티브 포기 시점 슬라이더.** 심사위원이 직접 만져보게 한다.

### 토큰 효율 30점
- **reasoning 모델의 97% 사고 토큰 사실을 안다.** instruct 기본 정책.
- **prefix cache 순서를 안다.** `cached_input_share` 8% → 60%대는 그대로 비용 절감.
- **제출 1회 = 테스트 5회임을 안다.** 제출 횟수를 계획한다.
- **트랙별 차등 정책.** generic에 토큰을 붓지 않는다.
- **동점 시 토큰이 이긴다는 것을 안다.** 효율은 30점이면서 40점의 승부 조건이기도 하다.
