# 06. Trace 시각화 설계 가이드 (30점)

> 채점 기준 원문 (PDF 24페이지):
> *"Scores will be awarded based on how effectively the **Trace, represented as log (text) data**, is visualized with consideration for **observability, interpretability, traceability, explainability, clarity, and insightfulness**."*
>
> 이 문서는 ① 그 여섯 축을 구체적 화면 요소로 번역하고 ② 업계 표준(OpenTelemetry GenAI Semantic Conventions)을 근거로 데이터 스키마를 제안하고 ③ 심사위원이 이미 매일 보는 화면(AI:GO 자체 대시보드)과 어떻게 차별화할지를 정리한다.

---

## 1. 먼저 알아야 할 것 — 심사위원의 기준선

**Lablup은 이미 스쿼드 모니터링 대시보드를 만들어 팔고 있다.** 우리 시각화는 그것과 비교된다. AI:GO가 이미 제공하는 것을 확인하고 시작하자 (`03-AIGO-Squad-완전가이드.md` 8절):

이미 있는 것 — 따라 만들면 감점은 없지만 가점도 없다:
- 에이전트별 상태 전이 가로 스윔레인 (색상: running 초록 / error 빨강 / created 호박 / completed 파랑 / idle 회색)
- 칸반 태스크 보드 (Pending / In Progress / Review / Done / Failed)
- 실시간 활동 피드 (최근 200개)
- 예산 미터 (토큰·비용 진행률, 실행 중 애니메이션)
- Hero stats (Active/Total agents, Session tokens, Execution phase)
- 에이전트별 토큰 사용량 분해, 일별 사용량 막대 차트, 성공률·평균 실행시간

**차별화 지점은 여기다:**
- AI:GO 대시보드는 **한 실행 안**을 본다. 우리는 **364문항 × 여러 실행**의 패턴을 본다.
- AI:GO 대시보드는 **무슨 일이 있었나**를 보여준다. 우리는 **왜 그 일이 일어났고, 그래서 무엇을 바꿔야 하나**까지 간다.
- AI:GO 대시보드는 **토큰을 센다**. 우리는 **토큰이 정답에 기여했는지**를 보여준다. ← 이 트랙의 채점 구조(정확도 40 + 효율 30)를 정면으로 시각화하는 것은 우리뿐이다.

## 2. 여섯 개 채점 축을 화면 요소로 번역

| 축 | 질문 | 이걸로 답한다 |
|---|---|---|
| **Observability**<br>관측 가능성 | 지금 무슨 일이 벌어지고 있나 | 실시간 웨이브 진행 뷰. 어떤 에이전트가 어떤 태스크에서 몇 번째 턴을 돌고 있는지. 상태 배지와 진행 카운터 |
| **Traceability**<br>추적 가능성 | 이 결과는 어디서 왔나 | **최종 답 → 그 답을 쓴 에이전트 → 그 에이전트가 읽은 입력 → 그 입력을 만든 앞 태스크**로 클릭해 거슬러 올라가는 경로. 링크가 끊기면 이 축은 0점이다 |
| **Interpretability**<br>해석 가능성 | 이 숫자가 무슨 뜻인가 | 원시 로그가 아니라 **분류된 사건**을 보여준다. `extraction_failed`와 `capped_tokens`와 `graded but wrong`을 시각적으로 구분 |
| **Explainability**<br>설명 가능성 | 왜 그렇게 했나 | **결정 지점(decision point)** 을 1급 객체로 승격. "planner가 이 문항을 코딩 경로로 보냈다", "reviewer가 패치를 반려했다", "포기 판단기가 3턴에서 중단했다" |
| **Clarity**<br>명료성 | 한눈에 들어오나 | 기본 화면은 요약, 상세는 드릴다운. 색·모양의 의미를 일관되게. 범례를 항상 노출 |
| **Insightfulness**<br>통찰력 | 보고 나서 뭘 알게 되나 | **정답률 대비 토큰 산점도**, **웨이브별 한계 수익 곡선**, **포기 시점 최적값**, **캐시 히트율 대 비용**. 우리가 스쿼드를 어떻게 고쳤는지의 근거를 화면이 스스로 말하게 한다 |

**가장 배점을 크게 가져갈 축은 `insightfulness`다.** 나머지 다섯은 잘 만든 트레이스 뷰어면 다 채워진다. 통찰은 **이 대회의 채점 구조를 이해한 팀만** 만들 수 있다.

## 3. 데이터 스키마 — OpenTelemetry GenAI Semantic Conventions를 쓴다

바퀴를 새로 만들지 말 것. 2024년 4월 발족한 OpenTelemetry GenAI SIG가 만든 표준이 있고, 2026년 현재 v1.41까지 왔으며 Langfuse·Arize·Datadog·Honeycomb·AWS Bedrock AgentCore가 모두 이 형식을 소비한다. **표준을 쓰면 "그냥 예쁘게 그린 로그"가 아니라 "표준 준수 관측 파이프라인"이 된다. 심사에서 이건 큰 차이다.**

### 3-1. 스팬 종류 (`gen_ai.operation.name`)

| 값 | 나타내는 것 | 이 트랙에서의 대응 |
|---|---|---|
| `create_agent` | 에이전트 생성·등록 | 스쿼드 초기화 |
| `invoke_agent` | 한 에이전트가 턴을 갖거나 제어를 넘겨받음 | **웨이브 안의 태스크 실행 1건** |
| `chat` | LLM 채팅 완성 호출 | 모델 호출 1회 |
| `execute_tool` | 도구·함수 호출 | (평가 실행 중엔 도구 없음. 로컬 실험에서는 발생) |
| `embeddings` | 임베딩 생성 | 해당 없음 |
| `generate_content` | 멀티모달 생성 | 해당 없음 |

**스팬 트리 형태**: 최상위 `invoke_agent` 아래에 `chat`과 `execute_tool`이 자식으로 붙는다. **중첩 구조가 곧 에이전트의 제어 흐름이다.**

멀티 에이전트 규칙 두 가지 (반드시 지킬 것):
1. **모든 에이전트(하위 에이전트 포함)가 각자 고유한 `gen_ai.agent.name`을 가진다.** 이 속성이 스윔레인과 인계(handoff) 가시성을 만든다. 없으면 `Unknown` 레인으로 뭉개진다.
2. **호출하는 에이전트가 `invoke_agent` 스팬을 낸다.** 호출당하는 쪽이 아니다. 그러면 인계 자체가 명시적이고 질의 가능한 사건이 된다.

### 3-2. 모든 스팬에 붙이는 세 개의 결속 속성

| 속성 | 역할 |
|---|---|
| `gen_ai.conversation.id` | 한 실행(run)의 모든 작업을 묶는 공유 ID |
| `gen_ai.agent.name` | 이 스팬을 만든 에이전트 |
| `gen_ai.operation.name` | 이 스팬이 무슨 종류의 작업인가 |

> **핵심 개념** — "GenAI 스팬은 LLM 호출만이 아니다." 에이전트가 무언가를 했기 때문에 존재하는 스팬이면 전부 conversation ID를 달아야 한다. 채점기 실행도, HTTP 재시도도, 파일 쓰기도.

### 3-3. 토큰·모델 속성

```
gen_ai.request.model               # 요청한 모델
gen_ai.response.model              # 실제로 응답한 모델 (다를 수 있다)
gen_ai.usage.input_tokens
gen_ai.usage.output_tokens
gen_ai.usage.cache_read.input_tokens      # ★ prefix cache 히트
gen_ai.usage.cache_creation.input_tokens
gen_ai.response.finish_reasons     # stop / tool_calls / length …
```

> `gen_ai.usage.cache_read.input_tokens`가 표준 속성으로 존재한다는 사실이 중요하다. **포털의 `cached_input_tokens`를 이 필드에 매핑하면**, 토큰 효율 전략(07번 문서)의 성과가 트레이스 뷰에서 그대로 보인다.

### 3-4. 도구 속성

```
gen_ai.tool.name
gen_ai.tool.call.id
gen_ai.tool.type
error.type                         # 실패 시. 부모 스팬으로 오류 상태 전파
```

### 3-5. 콘텐츠 캡처 (옵트인)

```
gen_ai.system_instructions
gen_ai.input.messages
gen_ai.output.messages
```

표준은 **기본적으로 프롬프트·응답 본문을 스팬에 넣지 않는다.** 크고, 민감할 수 있기 때문이다. 이번 트랙은 벤치마크 데이터라 PII 문제가 없으므로 **켜는 것이 옳다** — 심사위원이 "이 에이전트가 실제로 뭐라고 했나"를 클릭해서 볼 수 있어야 explainability 점수가 나온다.

다만 화면에는 **원시 JSON을 그대로 뿌리지 말 것.** 채팅 형태로 렌더링해야 한다. OpenTelemetry 공식 블로그도 이 점을 지적한다 — "many observability platforms render them as raw JSON, making them difficult to read."

### 3-6. 평가 결과 (v1.41 신규)

```
gen_ai.evaluation.result           # 스팬에 붙이는 이벤트
```

**이 트랙에 딱 맞는 필드다.** 문항 채점 결과(`graded` / `extraction_failed` / `capped` 등)를 해당 `invoke_agent` 스팬에 이벤트로 붙이면, **비용과 지연과 품질이 하나의 질의 가능한 그래프**가 된다. 이게 곧 `insightfulness`다.

## 4. 이 트랙 전용 트레이스 스키마 제안

표준 속성 위에 우리 트랙 고유의 것을 `jxc.*` 네임스페이스로 얹는다. (표준을 오염시키지 않으면서 확장하는 정석 방법이다.)

```jsonc
{
  // ── OTel GenAI 표준 ────────────────────────────────
  "trace_id": "…",
  "span_id": "…",
  "parent_span_id": "…",
  "name": "invoke_agent PatchWriter",
  "start_time": "2026-08-22T03:14:15.926Z",
  "end_time":   "2026-08-22T03:14:22.418Z",
  "status": "ok | error",
  "attributes": {
    "gen_ai.conversation.id": "run-abc123",
    "gen_ai.agent.name": "PatchWriter",
    "gen_ai.operation.name": "invoke_agent",
    "gen_ai.request.model": "Qwen3-30B-A3B-Instruct-2507-FP8",
    "gen_ai.response.model": "Qwen3-30B-A3B-Instruct-2507-FP8",
    "gen_ai.usage.input_tokens": 17342,
    "gen_ai.usage.output_tokens": 1204,
    "gen_ai.usage.cache_read.input_tokens": 16800,
    "gen_ai.response.finish_reasons": ["stop"],

    // ── 이 트랙 고유 ─────────────────────────────────
    "jxc.item.id": "coding-visible-0007",
    "jxc.item.track": "coding",
    "jxc.item.kind": "swebench",           // swebench | livecodebench | multiple_choice | (math)
    "jxc.item.subject": null,              // generic 트랙일 때 MMLU-Pro 과목
    "jxc.item.repo": "django/django",      // swebench일 때
    "jxc.wave.index": 2,
    "jxc.task.id": "task-patch-write",
    "jxc.agent.role": "Developer",         // Planner | Developer | Reviewer | Writer | Custom
    "jxc.decision.kind": "route|patch|verify|give_up|retry",
    "jxc.decision.reason": "reviewer rejected: patch did not apply",
    "jxc.budget.turns_used": 3,
    "jxc.budget.turns_max": 8,
    "jxc.outcome": "graded",               // graded | extraction_failed | capped | grader_error | infrastructure_failed
    "jxc.item.status": "ok",               // ok | capped_tokens | capped_wallclock | error
    "jxc.failure.kind": null,              // infrastructure | upstream_error | token_cap | wallclock_cap | runner
    "jxc.failure.owner": "team",           // team | policy | configuration | organizer
    "jxc.score": 1.0                       // 0.0 ~ 1.0
  },
  "events": [
    { "name": "gen_ai.evaluation.result",
      "time": "…",
      "attributes": { "jxc.outcome": "graded", "jxc.score": 1.0 } }
  ]
}
```

**`jxc.outcome`, `jxc.item.status`, `jxc.failure.kind`, `jxc.failure.owner`의 값은 제출 서버의 OpenAPI 열거형을 그대로 가져온 것이다** (`05-제출-포털-API.md` 참고). 주최 측 어휘를 그대로 쓰면 심사위원이 화면을 읽는 데 학습 비용이 0이다. 이건 공짜로 얻는 점수다.

## 5. 화면 설계 — 4단계 줌 레벨

한 화면에 다 넣지 말고 **줌 레벨**로 구성한다. 각 레벨이 여섯 축 중 다른 것을 담당한다.

### Level 0 — 실행 하나의 요약 (Observability)

한 줄로 답해야 하는 것: **"이 실행은 잘 됐나, 얼마 들었나."**

```
┌─────────────────────────────────────────────────────────────┐
│ run-abc123   ● finished   1,247s                            │
│                                                             │
│ overall  0.612    coding 0.55 (×0.5)  math 0.71 (×0.25)     │
│                   generic 0.68 (×0.25)                      │
│                                                             │
│ tokens   in 2,841,003  ·  out 214,882  ·  cached 61% ▓▓▓▓░░ │
│ items    364 total   338 graded   14 capped   12 extraction │
└─────────────────────────────────────────────────────────────┘
```

- 트랙별 정확도에 **가중치를 함께 표기**한다. 0.5/0.25/0.25가 화면에 보이면 심사위원은 우리가 규칙을 읽었다는 걸 안다.
- `cached` 비율 막대는 **다른 팀 화면에 없을 가능성이 높다.**

### Level 1 — 실행 전체의 흐름 (Traceability + Clarity)

**웨이브 × 에이전트 히트맵 + 타임라인.** `BreakdownRow`가 `(agent_id, task_id, wave_index, model_id, calls, input_tokens, output_tokens)`로 오므로 그대로 그릴 수 있다.

```
             wave 0      wave 1      wave 2      wave 3
Planner      ████ 41k    ·           ·           ·
Reader       ·           ████████ 680k          ·
PatchWriter  ·           ·           ██████ 512k ·
Verifier     ·           ·           ·           ███ 118k
GiveUpJudge  ·           ▪ 3k        ▪ 4k        ▪ 3k
```

- 블록 크기 = 토큰, 색 = 모델, 채도 = 캐시 히트율.
- 클릭하면 Level 2로.
- **`GiveUpJudge`처럼 토큰을 거의 안 쓰면서 전체 비용을 좌우하는 에이전트가 시각적으로 드러나는 것**이 이 뷰의 핵심 가치다.

### Level 2 — 문항 하나의 스팬 워터폴 (Explainability)

표준 트레이스 워터폴. OpenSearch Agent Traces나 Honeycomb Agent Timeline이 쓰는 색상 규약을 따르면 좋다:

| `gen_ai.operation.name` | 범주 | 색 |
|---|---|---|
| `invoke_agent`, `create_agent` | Agent | 파랑 |
| `chat` | LLM | 주황 |
| `text_completion`, `generate_content` | Content | 청록 |
| `execute_tool` | Tool | 보라 |
| `embeddings` | Embeddings | 초록 |
| `retrieval` | Retrieval | 빨강 |
| 기타 | Other | 회색 |

세 가지 동기화된 뷰를 제공하면 강력하다 (OpenSearch가 쓰는 패턴):
1. **Agent Graph** — DAG. 부모 스팬이 아래로 흐르고 같은 깊이의 형제는 가로로 배치. 노드에 범주 배지, 스팬 이름, 지속 시간 막대, 오류 배지.
2. **Trace Tree** — 계층 트리. 각 행에 범주 배지, 이름, 토큰 수, 지연.
3. **Timeline** — 간트 차트. 막대 폭 = 지속 시간 비율, 색 = 범주, 들여쓰기 = 깊이.

**세 뷰가 선택 상태를 공유한다.** 하나에서 스팬을 고르면 나머지 둘에서 하이라이트된다. 이게 `traceability`를 눈에 보이게 만드는 가장 확실한 장치다.

### Level 3 — 결정 지점 상세 (Explainability의 정점)

스팬 하나를 열면 **채팅 형태**로 렌더링한다. 원시 JSON 금지.

```
┌─ PatchWriter · wave 2 · task-patch-write ────────────────┐
│ model  Qwen3-30B-A3B-Instruct-2507-FP8                   │
│ in 17,342 (cached 16,800 · 97%)   out 1,204   6.5s       │
│ finish_reason  stop                                      │
├──────────────────────────────────────────────────────────┤
│ SYSTEM   You are a patch author. …            [펼치기]    │
│ USER     [item coding-visible-0007 · django/django]      │
│          problem_statement (999자)             [펼치기]   │
│          context: 10 files, 59,966자           [펼치기]   │
│ ASSISTANT --- a/django/db/models/…             [diff 뷰]  │
├──────────────────────────────────────────────────────────┤
│ ▸ DECISION  patch                                        │
│   reason: applied cleanly against base_commit            │
│ ▸ EVALUATION  graded · score 1.0                         │
└──────────────────────────────────────────────────────────┘
```

- diff는 반드시 **diff 뷰어**로 렌더링한다. 코딩 트랙이 점수의 절반이므로 여기에 공을 들일 가치가 있다.
- `DECISION` 블록이 이 화면의 차별점이다. **에이전트가 무엇을 결정했고 왜 그랬는지를 별도 블록으로 승격**하는 것.

## 6. Insightfulness — 여기서 승부가 난다

앞의 네 레벨은 "잘 만든 트레이스 뷰어"다. 여기부터가 **이 대회에서만 나올 수 있는 화면**이다.

### 6-1. 토큰 대 정답 산점도

x축 = 문항당 소비 토큰, y축 = 점수(0/1), 점 = 문항, 색 = 트랙.

읽어낼 수 있는 것:
- **오른쪽 아래 사분면**(토큰 많이 쓰고 틀림)이 낭비의 총량이다. 이걸 줄이는 게 곧 토큰 효율 30점.
- **왼쪽 위**(적게 쓰고 맞춤)는 우리 스쿼드가 잘하는 문항 유형.
- **수직 절단선**을 그으면 "여기서 포기했으면 얼마를 아끼고 몇 점을 잃었을까"가 바로 계산된다. → **인터랙티브 슬라이더로 만들 것.** 심사위원이 직접 끌어보게 하는 순간 30점의 상단이 열린다.

### 6-2. 포기 시점 최적화 곡선

x축 = 최대 턴 수(또는 문항당 토큰 상한), 두 개의 y축:
- 왼쪽: 그 상한에서의 정확도
- 오른쪽: 그 상한에서의 총 비용

두 곡선의 교차 구간이 **최적 포기 지점**이다. 문제 지문이 "which ones determine when it is time to give up"이라고 물었다. **이 그래프가 그 질문에 대한 우리의 답 그 자체다.**

### 6-3. 웨이브별 한계 수익

"웨이브 2(검증)를 추가해서 정확도가 얼마나 올랐고 토큰을 얼마나 더 썼는가."
스택 막대로 웨이브별 누적 토큰을, 선으로 웨이브별 누적 정확도를 겹쳐 그린다.
**어느 웨이브가 본전을 못 뽑는지가 한눈에 보인다.**

### 6-4. 캐시 히트율 대 비용

시간축에 `cached_input_share`(포털 API에서 가져옴)를 그리고, 프롬프트 구조를 바꾼 시점에 세로 주석선을 긋는다.
**"우리가 프리픽스를 고정한 순간 캐시 히트율이 8%에서 61%로 올랐고 비용이 X% 떨어졌다"** 를 한 장으로 증명한다. 07번 문서의 전략이 실제로 작동했음을 보여주는 화면이다.

### 6-5. 실패 소유권 분해

`FailureOwner`(`team` / `policy` / `configuration` / `organizer`)와 `FailureKind`로 실패를 분해한 스택 막대.
**"우리 잘못 vs 인프라 잘못"을 구분해 보여주는 것 자체가 성숙도의 증거다.** 리더보드 스펙이 이 구분을 왜 만들었는지 설명해 놓았으니(`02-평가-채점-규칙.md` 7절), 그 의도를 이해했다는 신호가 된다.

### 6-6. (선택) 리더보드 대비 위치

`GET /api/leaderboard`는 인증 없이 열려 있고 트랙별 정확도·모델별 토큰·캡까지 담고 있다. 전체 실행의 분포 위에 우리 실행을 얹어 보여주면 강력하다. 다른 팀 이름 표시는 신중하게 (익명화하거나 우리 것만 강조).

## 7. 구현 스택 제안

시각화 산출물은 **인터랙티브**여야 한다 ("Interactive visualization (web, animation generator, etc.)").

### 최소 리스크 조합

| 층 | 선택 | 이유 |
|---|---|---|
| 데이터 | JSONL 트레이스 파일 (위 4절 스키마) | 파일 하나로 끝. 서버 불필요 |
| 프론트 | 정적 HTML + 인라인 JS/CSS | 배포·시연이 파일 하나. 네트워크 의존 0 |
| 차트 | D3 또는 Observable Plot | 산점도·간트·히트맵 전부 커버 |
| 그래프 | Dagre 레이아웃 (DAG) | OpenSearch Agent Graph가 쓰는 것과 같은 알고리즘 |
| diff | diff2html 또는 자체 unified diff 파서 | 코딩 트랙 렌더링 |

**시연 환경이 오프라인일 수 있다.** CDN 의존을 없애고 전부 인라인하거나 번들에 포함시킬 것.

### 실시간이 필요하면

`GET /runs/{run_id}/progress` 프래그먼트를 폴링하거나, AI:GO의 `GET /api/v1/sessions/events` SSE 스트림을 구독한다. 다만 **실시간은 데모 리스크가 크다.** 녹화된 실행을 재생(replay)하는 모드를 반드시 같이 만들 것. 재생 모드는 심사 중 네트워크가 죽어도 살아남고, 타임라인 스크러빙까지 공짜로 얻는다.

## 8. 데이터 수집 파이프라인 — 지금 당장 시작할 것

**시각화를 나중에 붙이려 하면 늦는다.** 로그를 안 남긴 실행은 되살릴 수 없다.

수집 지점 세 곳:

| 원천 | 얻는 것 | 방법 |
|---|---|---|
| **AI:GO 워크스페이스 `logs/`** | 스쿼드 실행 로그 (텍스트) | 파일 감시 또는 실행 후 수집 |
| **AI:GO Discussion export (JSON)** | 대화록. 디스크의 룸 파일과 바이트 동일 | `aigo squad discussion export <ID> --format json` |
| **제출 포털 `/api/teams/me/runs/{id}/details`** | `breakdown`(에이전트/태스크/웨이브/모델 토큰), `items`, `diagnosis`, `score` | 실행 종료 후 폴링 |
| **제출 포털 `/api/teams/me/dev-usage`** | 캐시 히트율, 지연 | 30~60초 주기 폴링 |
| **로컬 러너** | 우리가 직접 심는 스팬 (가장 풍부) | 코드에 계측 |

**로컬 러너에 직접 계측하는 것이 가장 중요하다.** 포털의 `breakdown`은 문항별로 쪼개지지 않기 때문이다(hidden 실행 보호 목적). 문항 단위 트레이스는 우리가 로컬에서 만들어야 한다.

### 최소 계측 코드 형태 (Python 의사코드)

```python
import time, json, uuid

class TraceWriter:
    def __init__(self, path, run_id):
        self.f = open(path, "a")
        self.run_id = run_id

    def span(self, name, agent, op, parent=None, **attrs):
        return _Span(self, name, agent, op, parent, attrs)

class _Span:
    def __enter__(self):
        self.span_id = uuid.uuid4().hex[:16]
        self.t0 = time.time()
        return self

    def __exit__(self, exc_type, exc, tb):
        rec = {
            "trace_id": self.w.run_id,
            "span_id": self.span_id,
            "parent_span_id": self.parent,
            "name": self.name,
            "start_time": self.t0,
            "end_time": time.time(),
            "status": "error" if exc else "ok",
            "attributes": {
                "gen_ai.conversation.id": self.w.run_id,
                "gen_ai.agent.name": self.agent,
                "gen_ai.operation.name": self.op,
                **self.attrs,
            },
        }
        self.w.f.write(json.dumps(rec, ensure_ascii=False) + "\n")
        self.w.f.flush()
```

핵심은 **`flush()`** 다. 실행이 캡에 걸려 죽어도 그때까지의 트레이스는 남아야 한다. 그리고 **캡에 걸린 실행이야말로 시각화에서 가장 흥미로운 자료다.**

## 9. 흔한 함정

| 함정 | 왜 문제인가 | 대신 |
|---|---|---|
| 원시 JSON을 화면에 그대로 뿌림 | interpretability 0점 | 분류된 사건 + 채팅 렌더링 |
| AI:GO 대시보드를 그대로 재현 | 심사위원이 매일 보는 화면. 가점 없음 | 문항 단위 · 실행 간 비교 · 비용 대 정확도 |
| 실시간에만 의존 | 데모 중 네트워크·인프라 실패 시 전멸 | 녹화 재생 모드 필수 |
| 예쁜데 질문에 답 못 함 | clarity는 얻어도 insightfulness 0 | 각 화면이 답하는 질문 한 줄을 화면에 적어둘 것 |
| 성공한 실행만 보여줌 | 실패 분석이 없으면 explainability 약함 | 캡·추출 실패·인프라 오류를 1급 시민으로 |
| 색 의미가 화면마다 다름 | clarity 붕괴 | 색 규약 한 벌을 정하고 범례를 고정 노출 |
| conversation ID를 하위 스팬에 안 넘김 | 트레이스가 끊겨 traceability 붕괴 | 모든 스팬에 세 개 결속 속성 강제 |
| 에이전트 이름 누락 | 스윔레인이 `Unknown`으로 뭉개짐 | 모든 에이전트에 고유 `gen_ai.agent.name` |
