## 2. 문항의 공통 스키마

세 트랙 모두 JSONL 한 줄이 한 문항이고 최상위 키가 동일하다.

```json
{
  "item_id":    "…",        // 문항 식별자
  "track":      "math|coding|generic",
  "visibility": "visible",  // 연습 세트는 전부 visible
  "source":     { … },      // 출처: dataset, revision, native_id, seed, license, attribution
  "payload":    { … },      // 모델에게 보여줄 내용
  "grading":    { … },      // 채점 정보 (hidden 세트에서는 당연히 안 보임)
  "weight":     1.0         // 문항 가중치. 연습 세트는 전부 1.0
}
```

**중요** — `grading` 블록은 연습 세트라서 공개된 것이다. 실제 평가에서 스쿼드는 `payload`만 본다. 연습할 때 `grading`을 프롬프트에 넣지 않도록 파이프라인을 짜야 실제 실행과 조건이 같아진다.

## 3. math 트랙 (164문항)

### 구성

| 데이터셋 | 문항 수 |
|---|---|
| `math-500-level5` (MATH-500의 난이도 5 부분집합) | 134 |
| `aime-2024` (AIME 2024) | 30 |

샘플링 없음 — "whole pinned subsets; nothing is drawn, so there is no sampling seed". 고정된 부분집합 전체를 그대로 쓴다.

### payload 구조

```json
"payload": {
  "problem": "What is the smallest real number $x$ in the domain of the function $$g(x) = \\sqrt{(x-3)^2-(x-8)^2}~?$$",
  "answer_format": "expression",
  "disclosure": "public"
}
```

필드는 `problem`, `answer_format`, `disclosure` 셋뿐이다. **문제 지문 하나만 주어진다.**

### 답 형식 분포

| `answer_format` | 문항 수 | 채점기 |
|---|---|---|
| `integer` | 104 | `integer_exact` + `math_verify` (둘 다) |
| `expression` | 60 | `math_verify` |

grading 블록: `grader`(항상 `math_answer`), `answer_format`, `gold`, `gold_latex`, `checks`.
`gold`는 `"\\frac{11}{2}"` 같은 순수 표현, `gold_latex`는 `"$\\boxed{\\frac{11}{2}}$"` 형태다.

### 지문 길이

최소 47자 / 중앙값 217자 / 최대 1,733자. **매우 짧다.** 입력 토큰이 거의 안 든다는 뜻이고, 따라서 math 트랙의 토큰 비용은 거의 전부 **출력 토큰**이다. reasoning 모델을 여기 쓰면 비용이 폭발한다.

### 실전 함의

1. `gold_latex`가 `\boxed{}` 형식이다. **`\boxed{}`로 답을 감싸도록 프롬프트하면 추출 실패(`extraction_failed`)를 크게 줄일 수 있다.**
2. 104문항이 정수 답이다. AIME는 정의상 000~999의 정수다. **정수형은 답 추출과 검증이 훨씬 쉬우므로 별도 경로로 처리할 가치가 있다.**
3. `math_verify`는 수식 동치를 판정하므로 `1/2`와 `\frac{1}{2}`와 `0.5`가 같게 처리될 가능성이 높다. 그래도 **`gold` 형식에 맞추는 것이 안전하다.**
4. **hidden 세트의 math는 60~66문항으로 훨씬 작다.** 그런데 `run_repeats: 2`라 실제 실행은 120~132회다.

## 4. generic 트랙 (140문항)

### 구성

MMLU-Pro 단일 데이터셋. 14개 과목 × 정확히 10문항씩, MMLU-Pro 카테고리 기준 균등 층화 추출. 시드 `20260819` 공개.

과목: biology, business, chemistry, computer science, economics, engineering, health, history, law, math, other, philosophy, physics, psychology.

### payload 구조

```json
"payload": {
  "kind": "multiple_choice",
  "disclosure": "public",
  "subject": "physics",
  "question": "A rotating mirror experiment, to measure the speed of light, …",
  "options": ["2.00 ×10^8 m/sec", "3.00 ×10^8 m/sec", …],
  "option_letters": ["A","B","C","D","E","F","G","H","I","J"]
}
```

### grading 구조

```json
"grading": {
  "kind": "letter_match",
  "answer": "B",
  "answer_index": 1,
  "answer_text": "3.00 ×10^8 m/sec",
  "num_options": 10,
  "case_sensitive": false
}
```

### 보기 개수 분포 — ★ 함정

| 보기 수 | 문항 수 |
|---|---|
| 10 | 117 |
| 4 | 8 |
| 7 | 5 |
| 9 | 4 |
| 8 | 4 |
| 3 | 2 |

**MMLU-Pro는 원래 10지선다지만 실제로는 3~10개로 들쭉날쭉하다.** "A부터 J 중에 고르라"고 하드코딩하면 보기가 3개인 문항에서 존재하지 않는 보기를 고를 수 있다. **`option_letters`를 프롬프트에 그대로 주입해야 한다.**

### 지문 길이

최소 21자 / 중앙값 178자 / 최대 2,282자. 역시 짧다.

### 실전 함의

1. **채점은 `letter_match`, 대소문자 무시.** 추론 과정은 아예 채점하지 않는다. → **가장 짧게 답만 뽑는 것이 정확도 손해 없이 토큰을 아끼는 지점.**
2. **문항 수가 압도적으로 많다** (hidden 448~698문항). 그런데 가중치는 0.25다. **문항당 토큰 예산을 가장 빡빡하게 잡아야 할 트랙이 여기다.**
3. 14개 과목 균등이므로 특정 과목에 최적화해도 이득이 1/14로 희석된다. 범용 전략이 낫다.
4. 객관식은 **자기 일관성(self-consistency, 같은 문제를 여러 번 풀어 다수결)** 이 잘 듣는 대표적 과제다. 하지만 그건 토큰을 n배 쓴다. **가중치 0.25짜리 트랙에 n배 토큰을 붓는 것은 대부분 손해다.** 트랙별로 다른 정책을 쓰는 것이 정답에 가깝다.

### 5-3. ★ 컨텍스트 번들 — 이 트랙에서 가장 중요한 한 가지

practice-sets 페이지의 설명을 그대로 옮긴다.

> The coding track ships one file more: the **context bundle**. A SWE-bench item names a repository and a commit but carries no code, because **at evaluation the judge retrieves the code itself and puts it in the request.** The bundle is exactly what it retrieved, so you can work those items with no network and no cloning — and **what you rehearse against is byte-for-byte what the evaluation sends.** It is the judge's output, not a copy of the repositories: **your squad has no tools during a run and never browses a repository**, so pointing a retrieval tool at the bundle as if it were a checkout would produce a different request than the judge builds. The composer refuses that outright rather than compose something plausible.

**이 문단이 뜻하는 바를 정확히 새길 것.**

1. SWE-bench 문항은 저장소 이름과 커밋만 담고 **코드를 담지 않는다.**
2. **평가 시점에 judge가 직접 코드를 검색해서 요청에 넣어준다.**
3. `context.jsonl`은 그 검색 결과 자체다. 즉 **연습에 쓰는 컨텍스트가 실제 평가에서 오는 것과 바이트 단위로 동일하다.**
4. **평가 실행 중 스쿼드는 도구가 없다. 저장소를 뒤지지 않는다.** 파일을 더 읽을 수 없다.

→ **전략적 결론: 코딩 트랙의 실력은 "코드를 잘 찾는 능력"이 아니라 "주어진 60KB 발췌만 보고 정확한 패치를 쓰는 능력"이다.** 검색·탐색 에이전트를 설계하는 것은 헛수고다. 필요한 것은 **읽기 → 가설 → 패치 작성 → (테스트 없이) 자기 검증** 파이프라인이다.

### 컨텍스트 번들 구조

```json
{
  "item_id": "coding-visible-0001",
  "repo": "astropy/astropy",
  "commit": "a5917978be39d13cd90b517e1de4e7a539ffaa48",
  "candidates": 489,
  "excerpts": [
    {
      "path": "astropy/table/connect.py",
      "start_line": 1,
      "end_line": 130,
      "total_lines": 130,
      "text": "…파일 내용…",
      "omitted": …
    }
  ]
}
```

### 컨텍스트 예산 (`context.manifest.json`의 `budget`) ★★

| 상한 | 값 | 의미 |
|---|---|---|
| `max_candidate_chars` | 400,000 | 후보로 고려하는 소스 총량 |
| **`max_context_chars`** | **60,000** | **한 문항에 실제로 들어가는 컨텍스트 총량** |
| `max_file_chars` | 12,000 | 파일 하나에서 뽑는 최대 분량 |
| `max_files` | 10 | 한 문항에 포함되는 최대 파일 수 |
| `max_query_terms` | 120 | 검색 질의어 최대 개수 |

실측 통계 (연습 세트 40문항):
- 문항당 발췌 파일 수: 최소 5 / 중앙값 10 / 최대 22
  (※ `max_files: 10`이 파일 수 상한인데 발췌 항목이 22개인 문항이 있다 — 한 파일에서 여러 구간을 뽑으면 항목이 늘어나는 것으로 보인다.)
- 문항당 컨텍스트 문자 수: 최소 59,634 / 중앙값 59,966 / 최대 60,000 / 합계 2,396,205
  → **거의 모든 문항이 60,000자 상한을 꽉 채운다.**

**60,000자는 대략 15,000~20,000 토큰이다.** SWE-bench 문항 하나당 입력 토큰이 최소 이만큼 든다는 뜻이다. hidden 세트의 SWE-bench가 150문항이면 **입력 토큰만 약 225만~300만 토큰**이 기본으로 깔린다.

레시피 버전은 `R1`, 지문(fingerprint) `f2bcf89a…95ec1851`. 레시피가 바뀌면 fingerprint가 바뀌므로 우리가 연습한 조건과 평가 조건이 같은지 확인할 수 있다.

### 실전 함의 (coding)

1. **입력 토큰이 지배적이다.** 60,000자 컨텍스트를 여러 에이전트가 각자 다시 읽으면 토큰이 배수로 든다. **컨텍스트를 여러 에이전트에게 중복 전달하지 않는 설계**가 토큰 효율의 핵심이다. → `07-토큰-효율-전략.md`
2. **prefix cache가 여기서 가장 크게 작동한다.** 같은 문항을 여러 에이전트가 볼 때, 60,000자 컨텍스트를 **고정 프리픽스**로 앞에 두고 에이전트별 지시만 뒤에 붙이면 캐시 히트가 난다. 포털 안내문이 정확히 이 얘기다.
3. **패치 형식이 생명이다.** SWE-bench 채점은 패치를 적용해야 시작된다. unified diff가 깨지면 그냥 0점이다. **패치 형식 검증 전용 에이전트**를 두는 것이 정확도에 직접 기여한다.

3. **패치 형식이 생명이다.** SWE-bench 채점은 패치를 적용해야 시작된다. 형식이 깨지면 그냥 0점이다. **패치 형식 검증 전용 에이전트**를 두는 것이 정확도에 직접 기여한다.
   **[정정 2026-08-22]** 이 문서가 쓰인 시점에는 출력 형식을 unified diff로 알고 있었으나, 포털이 공개한 `required_output.txt`는 `*** PATCH START ***` + SEARCH/REPLACE다. unified diff는 0점이다.
4. **django 15 + sympy 10.** 두 프로젝트의 코딩 관례에 맞춘 지시를 시스템 프롬프트에 넣는 것이 실제 이득이 있다.
5. **LiveCodeBench는 SWE-bench와 완전히 다른 과제다.** 짧은 알고리즘 문제이고 컨텍스트도 없다. **같은 에이전트 구성으로 둘 다 처리하려 하지 말 것.** planner가 `payload.kind`로 분기하도록 설계한다.

## 6. hidden 세트 규모 추정과 토큰 예산 개략 계산

`set.manifest.json`의 `config.splits.hidden`:

```json
"hidden": {
  "coding":  { "livecodebench": 40, "swebench": 150 },
  "generic": { "per_category": 20 },
  "math":    {},
  "targets": {
    "coding":  { "min_items": 140, "max_items": 240 },
    "generic": { "min_items": 448, "max_items": 698 },
    "math":    { "min_items": 60,  "max_items": 66  }
  }
}
```

이걸로 한 번의 평가 실행에 드는 **입력 토큰의 하한**을 대략 잡아보면:

| 트랙 | 문항 수 | 문항당 입력(추정) | 소계(입력) |
|---|---|---|---|
| coding / SWE-bench | 150 | 컨텍스트 60,000자 ≈ 17k 토큰 + 지문 | **≈ 2,600,000** |
| coding / LiveCodeBench | 40 | 지문 위주, ≈ 1k 토큰 | ≈ 40,000 |
| generic | 448~698 | ≈ 0.3k 토큰 | ≈ 150,000~210,000 |
| math | 60~66 × 2회 반복 | ≈ 0.15k 토큰 | ≈ 20,000 |
| **합계(입력, 에이전트 1명 기준)** | | | **≈ 2,800,000 토큰** |

**여기에 에이전트 수를 곱해야 한다.** 4명짜리 스쿼드가 각자 전체 컨텍스트를 다시 읽으면 1,100만 토큰이다. 출력 토큰은 별도다.

→ **`per_run_token_cap`이 존재하는 이유가 이것이다.** 캡 값을 모르는 상태에서도, **컨텍스트 중복 전달을 줄이는 것이 이 트랙의 1번 최적화 과제**라는 결론은 확정적이다.

## 7. 로컬 실험 파이프라인 설계 제안

```
practice-sets/
  ├─ math/items.jsonl      164
  ├─ generic/items.jsonl   140
  ├─ coding/items.jsonl     60
  └─ coding/context.jsonl   40   ← SWE-bench 문항에 join
```

만들어야 할 것:

1. **로더** — `item_id`로 `coding/items.jsonl`과 `coding/context.jsonl`을 조인해서, 평가 시점의 요청과 동일한 입력을 재구성한다. 절대 `grading` 블록을 넣지 말 것.
2. **러너** — Squad Template + 트랙별 one-shot 프롬프트를 받아 문항을 돌리고, 응답과 토큰 사용량과 타임스탬프를 기록한다.
3. **로컬 채점기** — 세 트랙의 grader를 재현한다.
   - `letter_match`: 대소문자 무시 문자 비교. 쉽다.
   - `integer_exact` / `math_verify`: `math-verify` 파이썬 패키지가 공개되어 있다. 없으면 정수 비교 + LaTeX 정규화로 근사.
   - `livecodebench_tests`: `public_test_cases`로 stdin/stdout 대조. 샌드박스 실행 필요.
   - `swebench_docker`: 가장 무겁다. 시간이 없으면 **SWE-bench는 패치 형식 유효성 + 수동 샘플 검토**로 대체하고, LiveCodeBench로 코딩 능력의 대리 지표를 삼는다.
4. **트레이스 로거** — 시각화 산출물(30점)의 입력이 될 구조화 로그를 이 단계부터 남긴다. 나중에 붙이려 하면 늦다. → `06-시각화-설계-가이드.md`의 스키마 사용.

## 8. 라이선스 · 고지 의무

연습 세트 파일들과 함께 배포해야 하는 고지문이다. 우리 산출물이 이 데이터를 재배포하면 같이 실어야 한다.

- SWE-bench (Jimenez et al., ICLR 2024); 인스턴스는 업스트림 저장소에서 파생
- LiveCodeBench (Jain et al., 2024); 문제 지문은 LeetCode / AtCoder / CodeForces에서 수집
- MATH-500: Hendrycks et al., 'Measuring Mathematical Problem Solving With the MATH Dataset' (MIT), level-5 부분집합, `HuggingFaceH4/MATH-500` 경유
- AIME 2024: Mathematical Association of America 자료, `HuggingFaceH4/aime_2024` 경유, 데이터셋 카드에 라이선스 미선언
- MMLU-Pro (TIGER-Lab), MIT

컨텍스트 번들의 저장소 발췌는 **업스트림 프로젝트의 무수정 소스**이며 각 프로젝트 라이선스로 재배포된다. 라이선스 전문은 `context.manifest.json` 안에, 그리고 zip 안 `NOTICE.txt`에 들어 있다.

대상 프로젝트와 문항 수: astropy/astropy 1, django/django 15, matplotlib/matplotlib 3, mwaskom/seaborn 1, psf/requests 1, pydata/xarray 1, pylint-dev/pylint 1, pytest-dev/pytest 2, scikit-learn/scikit-learn 3, sphinx-doc/sphinx 2, sympy/sympy 10.
