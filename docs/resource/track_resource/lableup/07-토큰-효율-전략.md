# 07. 토큰 효율 전략 (30점 + 동점 처리 기준)

> 토큰 효율은 **두 번 작동한다.**
> ① 독립 배점 30점 — 정규화된 총 사용 비용이 낮을수록 높은 점수.
> ② 벤치마크 40점의 **동점 처리 1순위** — *"Total tokens is the tie-break when two runs score the same … so the cheaper run wins a draw."*
>
> 즉 토큰 절약은 30점짜리 항목이면서 동시에 40점짜리 항목의 승부 조건이다. **이 트랙에서 가장 레버리지가 큰 축이다.**

---

## 1. 비용 모형 정리

```
정규화 비용 = Σ over 모델 m, 실행 r [ tokens(m, r) × price(m) × factor(r) ]

price(m)  = 그 모델의 USD/Mtok 기준 단가   ← 아직 미공개, 온보딩에서 확인 필요
factor(r) = AI:GO test run  → 0.2  (1/5)
            submission run  → 1.0  (전액)

모든 제출(평가 제출 포함)이 누적 합산된다.
```

### 여기서 즉시 나오는 세 가지 결론

1. **제출 버튼 한 번이 테스트 다섯 번과 같다.** 확신 없이 제출하지 말 것. 포털의 `check`는 무료이고 무제한이다.
2. **모델 단가가 다르면 모델 선택이 곧 비용 정책이다.** 큰 모델을 어디에 쓰느냐가 전부다.
3. **비용은 토큰 수 × 단가다.** 토큰을 줄이는 길과 단가를 낮추는 길, 둘 다 있다.

## 2. 최대 레버 ─ reasoning 모델을 피한다

리더보드 페이지가 직접 알려준 사실:

> Two of the three evaluation models are reasoning models — **one was measured spending 97% of its output budget on reasoning tokens before it answered** — so a token cap bites roughly **an order of magnitude harder** on a squad built from reasoning models than on one built from an instruct model.

정리하면:

- 쓸 수 있는 모델은 **3개**. 그중 **2개가 reasoning(사고) 모델**, 1개가 instruct 모델.
- 확인된 instruct 모델: **`Qwen3-30B-A3B-Instruct-2507-FP8`** (포털 개발 사용량 화면에서 실제 관측)
- reasoning 모델 중 하나는 **출력 토큰의 97%를 `<think>` 블록에 쓴다.** 답 100토큰을 얻으려고 3,300토큰을 태운다는 뜻이다.
- 토큰 캡이 reasoning 스쿼드에 **약 10배 세게** 물린다.

### 그래서 기본 정책

**instruct 모델을 기본값으로 삼고, reasoning 모델은 국소적으로만 투입한다.**

reasoning 모델을 쓸 만한 유일한 지점: **AIME 계열 수학 문항**. 이건 사고 사슬이 정확도에 실제로 크게 기여하는 과제다. 하지만 math 트랙 가중치는 0.25이고 hidden 문항이 60~66개뿐이다. **투자 대비 회수를 반드시 실측하고 결정할 것.**

절대 쓰지 말아야 할 지점:
- **generic 트랙** — 객관식이고 `letter_match`로 채점한다. 추론 과정은 채점 대상이 아니다. hidden 448~698문항으로 가장 많다.
- **coding 트랙의 컨텍스트 읽기** — 입력이 이미 17k 토큰인데 여기에 사고 토큰까지 얹으면 캡이 즉시 터진다.

### 사고 모드를 끄는 정확한 방법

AI:GO가 제공하는 스위치는 세 개이고, 요청 바디로 그대로 전달되어 llama-server·mlxcel-server·continuum-router 패스스루 경로에 모두 적용된다.

| 방법 | 요청에 실리는 것 | 효과 |
|---|---|---|
| `--no-think` | `chat_template_kwargs: {"enable_thinking": false}` | **Qwen3/3.5 하이브리드 사고 모델에서 `<think>` 블록을 억제하는 올바른 방법** |
| `--reasoning-effort none` | 위와 동일 | 같음 |
| `--thinking-budget 0` | `thinking_budget_tokens: 0` | 즉시 종료. 엔진이 구현했다면 `--no-think`와 동등 |
| `--thinking-budget N` (N>0) | `thinking_budget_tokens: N` | **`<think>` 안에서 낼 수 있는 토큰을 N개로 하드 캡.** 엔진 무관하게 동작 |
| `--reasoning-effort low\|medium\|high\|xhigh` | `reasoning_effort` + `enable_thinking: true` | 사고를 켜되 강도 조절 |

우선순위: `--no-think`가 `--reasoning-effort`보다 우선한다.

> **가장 실용적인 조합** — 사고가 정확도에 필요한 지점에서는 `--thinking-budget`으로 상한을 걸어 **비용을 예측 가능하게** 만든다. "사고를 하되 64토큰까지만"은 켜고 끄는 이분법보다 나은 지점을 만들 수 있다. 트랙별로 스윕(sweep)해서 최적값을 찾을 것.

### `--preserve-thinking`의 함정과 기회

`--preserve-thinking`은 이전 assistant 턴의 `<think>` 블록을 제거하지 않고 유지한다 (Qwen3.6+ 기능). 공식 문서가 **"improves agent KV cache reuse"** 라고 명시한다.

- **함정**: 사고 블록이 프롬프트에 누적되어 입력 토큰이 늘어난다.
- **기회**: 프롬프트 프리픽스가 안정되어 **캐시 히트율이 올라간다.** 캐시된 입력은 새 입력보다 싸다.

**어느 쪽이 이기는지는 실측이 정한다.** 멀티턴 에이전트에서는 후자가 이길 가능성이 있다. `cached_input_share`를 보면서 A/B 하라.

## 3. 두 번째 레버 ─ prefix cache 히트율

포털 안내문이 사실상 전략을 알려준다.

> **Cached input** is the part of your prompt the stack served from its prefix cache. Your tier meters cached input more cheaply than fresh input, so **a prompt structure that keeps a long stable prefix in front of the varying part buys you real headroom.**

### 원리

prefix cache는 **프롬프트의 앞부분이 이전 요청과 토큰 단위로 완전히 동일하면** 그 부분의 KV(키-값) 계산을 재사용한다. 앞에서부터 한 토큰이라도 달라지는 순간, 그 지점 이후는 전부 새로 계산된다.

**따라서 순서가 전부다.**

### 잘못된 프롬프트 구조 (캐시 히트 0%)

```
[문항 ID: coding-visible-0007]          ← 매번 다름. 여기서 캐시 끝
[저장소 컨텍스트 60,000자]
[시스템 지시 2,000자]
[에이전트 역할 500자]
```
→ 첫 토큰부터 달라지므로 **62,500자 전부가 새 입력.**

### 올바른 프롬프트 구조 (캐시 히트 최대)

```
[시스템 지시 2,000자]          ← 모든 요청에서 동일. 캐시됨
[에이전트 역할 500자]          ← 그 에이전트의 모든 요청에서 동일. 캐시됨
[출력 형식 규약 800자]         ← 동일. 캐시됨
[few-shot 예시 3,000자]        ← 동일. 캐시됨
─────────────────────────────  캐시 경계
[저장소 컨텍스트 60,000자]     ← 문항마다 다름
[문항 지문]
```
→ 앞 6,300자가 캐시된다.

### 한 단계 더 ─ 문항 단위 프리픽스 공유

같은 문항을 여러 에이전트가 볼 때, **컨텍스트까지 프리픽스에 포함**시킬 수 있다.

```
[공통 시스템 지시]             ← 전 요청 캐시
[문항 컨텍스트 60,000자]       ← 이 문항의 모든 에이전트 요청에서 동일. 캐시됨!
─────────────────────────────  캐시 경계
[이 에이전트의 역할과 지시]    ← 에이전트마다 다름. 짧다
```

**이 배치가 coding 트랙에서 압도적으로 중요하다.** 4명의 에이전트가 같은 60,000자 컨텍스트를 보는데:
- 잘못 배치: 60,000자 × 4 = 240,000자 전부 새 입력
- 올바른 배치: 첫 에이전트만 새 입력, 나머지 3명은 캐시 히트

**입력 비용이 이론상 1/4에 가까워진다.**

단, 에이전트별 역할 지시가 컨텍스트 **앞**에 오면 이 효과가 전부 사라진다. 시스템 프롬프트를 짜는 순간 이 순서를 사수해야 한다.

### 측정 방법

`GET /api/teams/me/dev-usage`가 `cached_input_tokens`와 `cached_input_share`를 직접 준다.

```bash
curl -sS -b "$COOKIES" "$BASE/api/teams/me/dev-usage" \
  | jq '.totals | {input: .input_tokens, cached: .cached_input_tokens, share: .cached_input_share}'
```

프롬프트 구조를 바꿀 때마다 이 수치를 기록하라. **8% → 60%는 그대로 비용 절감이다.** 그리고 이 개선 곡선은 시각화 산출물의 좋은 재료가 된다 (`06-시각화-설계-가이드.md` 6-4절).

## 4. 세 번째 레버 ─ 컨텍스트 중복 제거

`04-벤치마크-데이터셋-분석.md`에서 계산한 대로, hidden 세트 한 번 실행의 **입력 토큰 하한이 에이전트 1명 기준 약 280만 토큰**이다. 에이전트 수만큼 곱해진다.

### 안티패턴 — 모든 에이전트가 원본 컨텍스트를 본다

```
Reader      ← 60,000자
PatchWriter ← 60,000자
Verifier    ← 60,000자
Judge       ← 60,000자
합계 240,000자
```

### 패턴 A — 압축 릴레이

```
Reader      ← 60,000자 원본        →  4,000자 요약 산출
PatchWriter ← 4,000자 요약 + 지문  →  패치
Verifier    ← 4,000자 요약 + 패치  →  판정
합계 약 72,000자
```

**위험**: 요약 단계에서 정보를 잃으면 정확도가 떨어진다. 코딩 트랙은 정확한 줄 번호와 시그니처가 필요하다. **요약이 아니라 "관련 파일만 골라내기"에 가깝게 설계할 것.** 컨텍스트가 이미 `path`, `start_line`, `end_line`으로 구조화되어 있으므로(`context.jsonl`), Reader가 "필요한 발췌의 인덱스 목록"만 내놓게 하면 손실이 적다.

### 패턴 B — 캐시 프리픽스 공유 (3절)

컨텍스트를 프리픽스에 두고 모든 에이전트가 그대로 본다. **정보 손실 0, 비용은 캐시가 흡수.**
`cached_input_share`가 높게 나오는지 확인해야 하고, 캐시가 기대만큼 안 걸리면 패턴 A로 후퇴한다.

### 패턴 C — 단일 에이전트 + 다단 프롬프트

에이전트를 늘리는 대신 한 에이전트가 여러 턴에 걸쳐 읽기→수정→검증을 한다. 대화 이력이 누적되므로 프리픽스가 자연히 안정되어 캐시가 잘 걸린다.
**단점**: 트랙 요구사항이 "squad formation"이고 "which agents read / modify / verify / give up"을 명시적으로 물었다. 에이전트를 하나로 줄이면 **문제 요구를 위반한다.** 최소한 역할이 구분된 복수 에이전트를 유지해야 한다.

> **권고** — B를 기본으로 하고, 캐시가 기대만큼 안 걸리는 것이 확인되면 A로 전환한다. C는 쓰지 않는다.

## 5. 네 번째 레버 ─ 포기 판단 (give-up)

문제 지문이 명시적으로 요구한 설계 요소다. 그리고 비용 곡선의 꼬리를 자르는 유일한 방법이다.

### 왜 꼬리가 중요한가

에이전트 실행의 토큰 분포는 극단적으로 한쪽으로 치우친다. 쉬운 문항은 몇 백 토큰, 어려운 문항은 턴 상한까지 가서 수만 토큰을 태우고 결국 틀린다. **총 비용의 대부분이 못 푸는 문항에서 나온다.**

산점도의 오른쪽 아래 사분면(많이 쓰고 틀림)이 정확히 이 영역이다.

### 세 층위의 포기 장치

**층위 1 — 예산 한도 (설정만 하면 되는 가장 싼 장치)**

AI:GO Budget Config에서 (`03-AIGO-Squad-완전가이드.md` 7절):

| 설정 | 기본값 | 권고 |
|---|---|---|
| `Max agent turns` | 20 | **공격적으로 낮출 것.** 4~8로 시작해 스윕 |
| `Max tokens per task` | 10,000 | 트랙별로 다르게. generic은 1,000 이하도 가능 |
| `Max tokens per agent` | 30,000 | 역할별로 차등 |
| `Max total tokens` | 100,000 | 문항당 총액 |
| `Task timeout` | 300초 | wall-clock 캡이 별도로 있으므로 그 아래로 |
| `Max tasks per plan` | 20 | planner가 태스크를 남발하지 못하게 |
| `Max plan iterations` | 3 | 재계획은 통째로 비싸다. 1~2 권고 |

> 주의: 토큰 카운팅은 근사치이며 시스템이 초과를 감지하기 전에 한도를 약간 넘길 수 있다. 여유를 둘 것.

**층위 2 — 명시적 포기 판단 에이전트**

역할이 하나뿐인 아주 싼 에이전트를 둔다.
- 입력: 지금까지의 시도 요약 (짧게 — 원본 컨텍스트 금지)
- 출력: `continue` 또는 `give_up` 한 단어
- 모델: instruct 모델, `--no-think`, `max_tokens` 5 내외

**출력이 한 단어이므로 출력 비용이 사실상 0이다.** 입력도 요약만 받으므로 짧다. 이 에이전트 하나가 전체 비용의 30~50%를 잘라낼 수 있다.

`06-시각화-설계-가이드.md` 6-2절의 "포기 시점 최적화 곡선"이 이 에이전트의 임계값을 정하는 근거가 된다.

**층위 3 — 트랙별 조기 종료 규칙 (LLM 없이, 프로그램으로)**

가장 싸다. LLM 호출이 0이다.

| 트랙 | 규칙 |
|---|---|
| generic | 답 문자가 한 번 나오면 **즉시 종료.** 검증 웨이브를 아예 돌리지 않는다 |
| math | 답이 `answer_format`(정수 / 수식)에 맞으면 종료. 정수 문항인데 수식이 나오면 1회 재시도 |
| coding / livecodebench | 코드 블록이 나오면 `public_test_cases`로 **로컬 실행 검증**. 통과하면 즉시 종료 |
| coding / swebench | unified diff가 문법적으로 유효하면 종료. 유효하지 않으면 1회 재시도 후 포기 |

**"검증 에이전트를 항상 돌린다"가 아니라 "프로그램으로 검증 가능한 것은 프로그램이 하고, LLM은 프로그램이 실패했을 때만 부른다"** 가 원칙이다.

## 6. 다섯 번째 레버 ─ 트랙별 차등 정책

세 트랙을 같은 스쿼드 설정으로 돌리면 반드시 손해다. 성격이 완전히 다르다.

| 항목 | coding | math | generic |
|---|---|---|---|
| 가중치 | **0.50** | 0.25 | 0.25 |
| hidden 문항 수 | 140~240 | 60~66 (×2회 반복) | **448~698** |
| 문항당 입력 | **매우 큼** (SWE-bench 17k 토큰) | 매우 작음 (~150 토큰) | 작음 (~300 토큰) |
| 채점 | 테스트 통과 여부 | 최종 답 정확 대조 | 보기 문자 대조 |
| 추론이 정확도에 기여하는가 | 중간 | **큼** (특히 AIME) | 낮음 |
| 권고 모델 | instruct + `--no-think` | 선별적 reasoning 또는 `--thinking-budget N` | instruct + `--no-think` |
| 권고 에이전트 수 | 3~4 (읽기·수정·검증·포기) | 1~2 (풀기·검산) | **1** (답하기) |
| 권고 턴 상한 | 6~10 | 3~4 | **1~2** |
| 문항당 토큰 목표 | 최대한 캐시로 흡수 | 수천 | **수백** |

### 계산해 보면 왜 중요한지 보인다

generic이 hidden에서 최대 698문항이다. 문항당 500토큰이면 349,000토큰, 문항당 3,000토큰이면 2,094,000토큰이다. **차이가 175만 토큰**이고 정확도 차이는 거의 없다 (`letter_match`이므로). **가중치 0.25짜리에서 나오는 낭비다.**

반대로 coding은 문항이 최대 240개인데 문항당 입력이 17k라 4백만 토큰이 기본이다. **여기서는 토큰을 아끼는 게 아니라 캐시로 흡수시키는 것이 답이다.** 성능을 깎으면 가중치 0.5를 잃는다.

**한 줄 요약: generic에서 아끼고, coding에서 캐시하고, math에서만 선별적으로 쓴다.**

---

## 7. 여섯 번째 레버 ─ Discussion Room 전략 선택

Discussion Room을 쓴다면 전략에 따라 **화자 선택에만 드는 LLM 호출**이 달라진다 (`03-AIGO-Squad-완전가이드.md` 9절).

| 전략 | 화자 선택 LLM 호출 | 비용 |
|---|---|---|
| **Brainstorm (legacy)** | 없음 (결정론적) | 0 |
| **Round Robin** | 없음 (결정론적) | 0 |
| **Moderated** | moderator 호출 | 중간 |
| **Autonomous** | **참가자 수 × 턴마다 1회** | **가장 비쌈** |

또한 Moderated 모드는 **3턴마다 facilitator에게 수렴 여부를 묻는다.** 이것도 추가 호출이다.

> **권고** — 벤치마크 실행에는 Discussion Room을 쓰지 않는 것이 기본이다. 쓴다면 `Round Robin`이나 `Brainstorm (legacy)`. **`Autonomous`는 절대 쓰지 말 것.**

## 8. 일곱 번째 레버 ─ 메모리 정책

`memoryEnabled: true`인 에이전트는 (`03-AIGO-Squad-완전가이드.md` 6절):
- 태스크 시작마다 메모리 파일이 컨텍스트에 **로드**된다 → 입력 토큰 증가
- `trigger_interval` 턴마다 **LLM 추출 패스**가 돈다 → 추가 호출

벤치마크는 문항마다 독립적인 일회성 작업이므로, 메모리에서 얻는 이득이 크지 않다.

**단, 반대 논리도 있다.** 메모리 블록이 프롬프트 앞쪽의 고정 프리픽스가 되면 캐시 히트를 만든다. 그리고 "이 저장소에서 자주 나오는 함정" 같은 지식이 누적되면 django 15문항·sympy 10문항에서 실제 이득이 있을 수 있다.

> **권고** — 기본은 **끈다.** Planner에만 켜서 A/B 하고, `cached_input_share`와 정확도를 같이 본다. 켜기로 했다면 Settings → Memory → Per-agent memory read-back에서 **예산을 명시적으로 작게 잡을 것** (기본은 `memory.maxTokens` ×1.0).

## 9. 여덟 번째 레버 ─ 출력 형식 최소화

채점 방식을 다시 보면:

- generic: **보기 문자 하나만** 본다. 대소문자 무시.
- math: **최종 답만** 본다. 과정은 안 본다.
- coding: **패치/코드만** 본다.

그런데 모델은 기본적으로 설명을 붙인다. 그 설명이 전부 출력 토큰이고 전부 비용이다.

### 프롬프트 지시 예

```
Answer with exactly one letter from [A,B,C,...]. No explanation. No preamble.
```
```
Output only the final answer inside \boxed{}. Nothing else.
```
```
Output only a unified diff. No commentary before or after.
```

동시에 `max_tokens`를 **하드 캡**으로 건다.
- generic: `max_tokens: 4` 수준까지 가능
- math: `max_tokens: 32~64` (`\boxed{...}`만)
- coding/swebench: 패치 크기에 맞춰 1,000~2,000

> **주의 — 여기에 함정이 있다.** `max_tokens`를 너무 낮추면 답이 잘려서 `extraction_failed`가 된다. 그리고 `extraction_failed`는 **팀 책임**으로 분류되어 점수에 그대로 반영된다 (`02-평가-채점-규칙.md` 7절). **연습 세트로 잘림 비율을 반드시 측정하고 여유를 둘 것.**

## 10. 실험 계획 — 무엇을 어떤 순서로 잰다

연습 세트 364문항이 있고, test run은 1/5 과금이다. **측정에 투자하는 것이 옳다.**

### 1단계: 기준선 (baseline)

기본 설정으로 세 트랙 각각 20문항씩만 돌려서 다음을 기록한다.
- 문항당 입력·출력 토큰
- 정확도
- `cached_input_share`
- 실패 유형 분포 (`extraction_failed` 비율이 특히 중요)

### 2단계: 단일 변수 스윕

한 번에 하나씩만 바꾼다.

| 실험 | 변수 | 관찰 |
|---|---|---|
| E1 | `--no-think` on/off | 정확도 변화 vs 출력 토큰 변화 |
| E2 | 프롬프트 순서 (컨텍스트 앞/뒤) | `cached_input_share` |
| E3 | `Max agent turns` = 2, 4, 6, 8, 12 | 정확도-비용 곡선 |
| E4 | `max_tokens` 상한 | `extraction_failed` 비율 |
| E5 | 에이전트 수 1, 2, 3, 4 | 트랙별 정확도-비용 |
| E6 | `--thinking-budget` = 0, 32, 128, 512 | math 트랙 정확도 |
| E7 | 메모리 on/off (Planner만) | 정확도 + 캐시 히트율 |

### 3단계: 트랙별 최적 조합 확정

E1~E7 결과로 트랙마다 다른 설정을 확정한다. **하나의 Squad Template으로 세 트랙을 다 커버해야 하므로**, 트랙 분기는 planner의 시스템 프롬프트와 트랙별 one-shot 프롬프트에서 이뤄져야 한다.

### 4단계: 전체 연습 세트 1회 완주

364문항 전체를 돌려 최종 확인. 이때의 총 토큰이 hidden 세트에서 얼마가 될지 추정하는 근거가 된다 (hidden은 대략 2~3배 규모).

### 5단계: 제출

**여기서 처음으로 `Submit to the queue`를 누른다.**
