# 04. 아트 레퍼런스 조사 — "따스한 도트 아케이드"를 실제 값으로

요구사항 원문:

> 따스한 색감 · 도트 디자인 · 아기자기 · 아케이드틱 · 게임 같고 · 애니메이션 많고 · 가독성 엄청 좋고 · 한눈에 쉽게 파악하면서 재밌게

이 여섯 개 중 **넷은 서로 당긴다.** 도트↔가독성, 애니메이션 많음↔한눈에 파악. 이 문서는 그 긴장을 어떻게 풀지를 조사하고, **버린 선택지를 먼저 적는다.**

## 2. 도트 디자인을 어떻게 낼 것인가 — 세 갈래와 결론

### 갈래 A — 한글 픽셀 폰트를 임베드한다 ❌ 버림

한글 픽셀 폰트로 본문을 찍는 방법.

**버린 이유 세 가지:**

1. **용량.** 한글 완성형 2,350자 + 라틴 + 기호를 담은 픽셀 폰트는 woff2로 200KB~1MB다. base64는 여기에 33%를 더한다. 현재 파일이 약 180KB인데 **파일이 6배가 된다.**
2. **가독성.** 픽셀 한글은 8×8~12×12 격자에 복잡한 자소를 구겨 넣는다. `읽`·`웨`·`뷸` 처럼 획이 많은 글자가 10px에서 뭉갠다. **요구사항 중 "가독성 엄청 좋고"와 정면충돌한다.**
3. **라이선스.** 오프라인 임베드 재배포를 허용하는 한글 픽셀 폰트를 확정하지 못했다. 확인 안 된 것을 제출물에 넣을 수 없다.

### 갈래 B — 라틴 전용 픽셀 폰트만 임베드한다 🟡 선택 가능, 기본은 아님

`MONSTROUS` · `CREDITS` · `WAVE 2/3` · `GRADED` 같은 **대문자 라틴 라벨에만** 픽셀 폰트를 쓰고, 한글은 절대 그 폰트로 안 찍는 방법.

- 용량: 라틴 대문자 + 숫자 + 기호 약 70자 → woff2 8~20KB, base64 11~27KB. **감당 가능.**
- 위험: 폰트 파일을 새로 구해야 하고 라이선스 확인이 필요하다.

> **판정: 선택 항목(P2)으로 남긴다.** 기본 설계는 픽셀 폰트 없이 성립해야 하고, 나중에 폰트가 확보되면 `--font-display` 하나를 바꿔서 켠다.

### 갈래 C — 픽셀을 폰트가 아니라 **형태**로 만든다 ✅ 채택

도트 감각은 글꼴에서만 나오지 않는다. 실제로 아케이드 화면을 아케이드처럼 보이게 하는 것은 대부분 글꼴이 아니라 **격자·하드 엣지·셀·계단 모션**이다.

| 수단 | 어떻게 | 비용 |
|---|---|---|
| **4px 기준 격자** | 모든 간격·크기가 4의 배수. 8px 단위 정렬 | 0 |
| **하드 엣지** | `border-radius: 0` 또는 계단형 모서리. 그림자 대신 1px 오프셋 블록 | 0 |
| **셀 게이지** | 진행률을 연속 막대가 아니라 **칸 단위**로. 12칸 중 7칸 채움 | 0 |
| **인라인 SVG 도트 아트** | 로고·에이전트 아바타·판정 도장·아이콘을 4px 격자 `<rect>` 로 | 파일당 0.3~1KB |
| **`steps()` 이징** | 게이지·카운터·깜빡임이 계단으로 움직인다 | 0 |
| **디더 패턴** | `repeating-linear-gradient` 로 45° 체크. 배경·비활성 영역 | 0 |
| **스캔라인** | 2px 주기 가로줄, 불투명도 4% | 0 |
| **모노 대문자 + 자간** | HUD 라벨을 `letter-spacing: .16em` 대문자로 | 0 |

이 여덟 개면 **한 픽셀도 폰트에 의존하지 않고** 화면이 아케이드가 된다. 그리고 본문은 시스템 산세리프라 한글 가독성이 최고치를 유지한다.

> **채택 규칙: 도트는 그림이 담당하고, 글자는 읽히는 것이 담당한다.**

## 3. 폰트 스택 — 네트워크 0에서 고를 수 있는 것

임베드 없이 쓸 수 있는 것은 시스템에 이미 있는 폰트뿐이다.

### 3-1. 본문 (한국어 + 라틴)

```css
--font-ui: "Pretendard Variable", Pretendard, -apple-system, BlinkMacSystemFont,
           "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", system-ui, sans-serif;
```

| 폰트 | 어디에 있나 | 한글 |
|---|---|---|
| Pretendard | 개발자 PC에 설치돼 있는 경우가 많다. **있으면 최고** | ✅ |
| Apple SD Gothic Neo | macOS 기본 | ✅ |
| Malgun Gothic | Windows 기본 | ✅ |
| Noto Sans KR | Linux 배포판·일부 Windows | ✅ |

**시연 환경(macOS)에서는 Pretendard 또는 Apple SD Gothic Neo 가 잡힌다.** 둘 다 한글 가독성이 좋고 숫자가 깔끔하다.

### 3-2. 숫자·코드·로그

```css
--font-mono: ui-monospace, "SF Mono", "Cascadia Mono", "JetBrains Mono",
             Consolas, "DejaVu Sans Mono", monospace;
```

현행 스택 그대로다. **다만 쓰는 자리를 세 곳으로 제한한다** — 숫자 열, 요청·응답 원문, 코드/마커. 본문 전체에 걸지 않는다.

### 3-3. HUD 라벨 (라틴 대문자)

```css
--font-display: var(--font-mono);   /* 픽셀 폰트를 확보하면 여기만 바꾼다 */
```

`text-transform: uppercase` + `letter-spacing: .16em` + `font-weight: 700` 으로 아케이드 계기판 느낌을 낸다.

## 4. 색 — "따스한"을 좌표로 바꾸면

### 4-1. 조사: 현행 팔레트가 왜 차가운가

| 토큰 | 값 | 색상(hue) | 성격 |
|---|---|---|---|
| `--bg` | `#0e1116` | 218° (청) | GitHub 다크의 파생. **개발자 도구의 기본값** |
| `--accent` | `#4cc2ff` | 199° (시안) | 같은 이유 |
| `--prog` | `#a371f7` | 264° (보라) | 같은 이유 |

**AI:GO 대시보드를 포함해 심사위원이 그날 볼 모든 화면이 이 계열이다.** 차별화 수단으로서 색을 바꾸는 것이 정당하다 (`03-채점-6축-매핑.md` §1).

### 4-2. 색상 범위를 340° → 100° 으로 고정한다

따스함을 지키면서 여섯 개를 구별하려면 **자홍 → 빨강 → 주황 → 금 → 라임** 의 원호 안에서 골라야 한다. 파랑·시안·청록은 쓰지 않는다.

| 이름 | 다크 | 색상 | 배경 대비 |
|---|---|---|---|
| EMBER (주황) | `#FF8A3D` | 25° | **7.97 : 1** |
| GOLD (금) | `#FFC24B` | 40° | **11.64 : 1** |
| LIME (라임) | `#B5D94A` | 74° | **11.57 : 1** |
| CORAL (빨강) | `#FF6B5E` | 5° | **6.69 : 1** |
| MAGENTA (자홍) | `#FF7FB8` | 335° | **8.00 : 1** |
| PLUM (자주) | `#C08CE0` | 279° | **7.19 : 1** |

PLUM만 원호를 살짝 벗어난다. **여섯 번째 계열색으로만 쓰고 판정색으로는 쓰지 않는다.**

### 4-3. 명암비 검증 — 결함 B-1을 수치로 해결

배경 `#17110E` (따뜻한 흑갈), 패널 `#211812`, 패널2 `#2C201A` 기준.

| 토큰 | 값 | vs 배경 | vs 패널2(최악) | AA |
|---|---|---|---|---|
| `--fg` | `#FFF3E3` | 17.08 | 14.44 | ✅ |
| `--fg-dim` | `#D8BCA1` | 10.35 | 8.75 | ✅ |
| `--fg-faint` | `#AB8E76` | **6.11** | **5.17** | ✅ |

**현행 `--fg-faint` 는 3.25:1 이었다.** 새 값은 최악의 경우에도 5.17:1 로, 9px 라벨에 써도 AA를 넘는다.

### 4-4. 라이트 모드 — "크림 배경"이라는 함정

크림 배경(#F4F1EA 근처) + 고대비 세리프 + 테라코타 액센트는 **지금 AI가 만드는 디자인의 가장 흔한 기본값** 중 하나다. 우리 라이트 모드가 거기로 굴러떨어지지 않는다는 것을 명시적으로 확인했다.

| 그 기본값 | 우리 |
|---|---|
| 고대비 **세리프** 디스플레이 | 픽셀 SVG 워드마크 + 모노 대문자 |
| **테라코타** 단일 액센트 | 6색 아케이드 램프 |
| 여백 큰 **에디토리얼** 레이아웃 | 셀·격자 기반 계기판 |
| 부드러운 그림자 | 1px 오프셋 하드 블록 |

배경도 조금 더 따뜻하고 채도가 있다 (`#FBF1DF`, 39° / 채도 약 20%).

| 토큰 | 라이트 | vs 배경 |
|---|---|---|
| `--fg` | `#241813` | 15.43 |
| `--fg-dim` | `#5C4436` | 8.03 |
| `--fg-faint` | `#7A5C48` | 5.43 |
| EMBER | `#B33C09` | 5.26 |
| GOLD | `#8A5D00` | 5.14 |
| LIME | `#3F6A0B` | 5.72 |
| CORAL | `#C22F26` | 5.03 |
| MAGENTA | `#B32B76` | 5.32 |

**라이트 모드에서는 액센트를 어둡게 눌러야 AA를 넘는다.** 다크의 밝은 값을 그대로 쓰면 3:1 대에서 논다.

## 5. 게임 은유 — 어디까지가 진짜이고 어디부터가 장식인가

아케이드 은유가 정당한 이유는 **데이터 자체가 이미 그 구조**이기 때문이다. 억지로 씌운 것이 아니다.

| 도메인 사실 | 게임 어휘 | 억지인가 |
|---|---|---|
| AI:GO가 태스크를 **`wave`** 로 묶는다 (`task-wave-started`) | 웨이브 | **아니다. 로그의 실제 필드명이다** |
| 토큰 효율이 30점 축이고, 동점 처리 1순위다 | 크레딧 / 코인 | **아니다. "토큰"은 원래 아케이드 코인을 뜻하는 말이다** |
| 실행 하나 = 문항 하나 = 한 번의 시도 | 한 판 | **아니다. 실제로 그렇다** |
| 채점 적격 / 부적격 | CLEAR / MISS | 표기 선택. 한국어 라벨을 주로 쓰고 영문은 보조 |
| 에이전트 5명이 역할별로 다르다 | 캐릭터 | **아니다. `.squad.json` 에 이름·아이콘·역할이 있다** |
| 실패 소유권 (`team` / `organizer`) | — | 게임 어휘 없음. 그대로 쓴다 |

> **경계선: 이름을 새로 짓지 않는다.** `실행`은 계속 `실행`이고, `웨이브`는 계속 `웨이브`다. 게임 어휘는 **시각 언어(계기판·셀 게이지·도트 캐릭터·도장)로만** 들어가고, **용어를 바꾸지 않는다.**

이건 취향이 아니라 규칙이다. 심사위원이 화면의 단어를 문서와 대조할 수 있어야 한다.

### 5-1. 시그니처 — 크레딧 계기

이 화면이 기억될 하나를 고른다면 **상단 HUD의 크레딧 계기**다.

- 토큰을 **칸으로 센다.** 1칸 = 1,000 토큰. 숫자도 항상 같이 적는다.
- 낭비 사분면의 절단선 슬라이더를 끌면 **이 계기가 실시간으로 줄어든다.**
- 즉 **30점짜리 토큰 효율 축이 화면의 주인공**이 된다. 심사위원이 직접 만져서 스스로 발견하는 자리다.

**정직성 규칙:** 칸은 보조 표기다. 실제 토큰 수를 항상 병기하고, 환산 비율(1칸 = 1,000 토큰)을 계기 옆에 적는다. 칸만 보여주면 화면이 단위를 지어내는 것이 된다.

## 6. 모션 — "애니메이션 많고"와 "한눈에 파악"을 어떻게 둘 다

이 둘은 정면으로 부딪친다. 푸는 방법은 **동작을 빈도로 나누는 것**이다.

| 빈도 | 예 | 방침 |
|---|---|---|
| **하루 수백 번** | `j`/`k` 실행 이동, 탭 전환, 검색 타이핑 | **애니메이션 0.** 즉시 바뀐다 |
| **수십 번** | 호버, 프레스, 필터 변경 | 100~160ms 색·스케일만 |
| **가끔** | 모드 전환, 실행 선택, 패널 진입 | 180~260ms 진입 |
| **드물게** | 오프닝, 재생 시작, 판정 도장, 슬라이더 결과 갱신 | **여기에 전부 쓴다.** 연출 허용 |
| **상시(주변)** | 스캔라인, 간선 흐름, 실행 중 맥동 | 저진폭·저주파. 시선을 안 끈다 |

**"애니메이션이 많다"는 인상은 드물게·상시 두 층에서 만든다.** 고빈도 경로는 오히려 지금보다 **덜** 움직인다 (현행 결함 D-1).

### 6-1. 모션 성격

`motion-design` 의 네 원형 중 **Playful** (150~300ms, ease-out-back, 오버슈트 10~20%) 을 고르되, 데이터 화면이므로 **오버슈트를 8~12%로 낮춘다.** 계기 숫자가 튀면 값이 튀는 것처럼 보인다.

시그니처 이징 하나로 80%를 처리한다.

```css
--ease: cubic-bezier(0.23, 1, 0.32, 1);        /* 진입 · 강한 ease-out */
--ease-pop: cubic-bezier(0.34, 1.4, 0.5, 1);   /* 도장 · 팝. 오버슈트 12% */
--ease-move: cubic-bezier(0.77, 0, 0.175, 1);  /* 화면 안 이동 */
--ease-step: steps(N, end);                    /* 셀 게이지 · 카운터 */
```

**`ease-in` 은 UI에 쓰지 않는다.** 시작이 느려서 같은 시간이어도 느리게 느껴진다.

### 6-2. 픽셀 모션 — 계단이 정체성이다

일반 UI는 부드러운 보간이 정답이지만, 도트 화면에서는 **`steps()` 가 성격을 만든다.**

| 대상 | 이징 | 왜 |
|---|---|---|
| 셀 게이지 채움 | `steps(칸수)` | 칸이 하나씩 켜져야 칸의 의미가 산다 |
| 숫자 카운트업 | `steps(12)` | 아날로그 카운터 느낌 |
| 판정 도장 | `--ease-pop` | 찍히는 감각은 부드러워야 무게가 산다 |
| 간선 흐름 | `linear` 무한 | 주변 모션. 계단이면 산만하다 |
| 커서 깜빡임 | `steps(1)` | 터미널 커서 |

## 7. 참고한 시각 언어 — 무엇을 빌리고 무엇을 안 빌렸나

| 출처 | 빌린 것 | 안 빌린 것 |
|---|---|---|
| 아케이드 캐비닛 계기판 | 상시 HUD, 셀 게이지, 대문자 라벨, 크레딧 개념 | 네온 글로우 남발, 원색 대비 |
| 8-bit / 16-bit 게임 UI | 하드 엣지, 4px 격자, 도트 캐릭터, 도장 연출 | **픽셀 폰트 본문**, 저해상도 스케일링 |
| CRT 화면 | 스캔라인(4%), 미세한 비네팅 | 곡률 왜곡, 색수차, 플리커 — **가독성을 깎는다** |
| 관측 도구(OpenSearch Agent Traces 등) | 3뷰 선택 상태 공유, `gen_ai.operation.name` 범주 색 규약 | 차가운 팔레트, 밀도 균일 |
| `06-시각화-설계-가이드.md` §5 | 4단계 줌 레벨, Level 3 채팅 렌더링 | OTel 스팬 트리 — **로그에 스팬이 없다** |

### 7-1. 명시적으로 버린 것

| 버린 것 | 왜 |
|---|---|
| 픽셀 한글 폰트 | §2 갈래 A |
| CRT 곡률·색수차 | 텍스트 가독성을 직접 깎는다. 프로젝터에서 더 나빠진다 |
| 파티클·꽃가루 | 실행 1,000건 목록에서 프레임을 잡아먹는다. 정보가 0 |
| 8비트 사운드 | 심사·시연 환경에서 소리는 위험하다. 무음이 기본 |
| 스프라이트 시트 이미지 | 외부 파일 금지. SVG로 그린다 |
| 체력바·레벨·경험치 은유 | 대응하는 데이터가 없다. **없는 값에 은유를 씌우면 거짓말이 된다** |
| "GAME OVER" 같은 실패 연출 | 실패는 이 도구에서 **분석 대상**이지 벌칙이 아니다. 실패 화면이 놀림처럼 보이면 안 된다 |

마지막 항목이 특히 중요하다. 이 뷰어가 보여주는 실패의 상당수는 **주최 인프라 책임(`owner: organizer`)** 이다. 게임 연출이 그것까지 "졌다"로 표현하면 화면이 틀린 말을 한다.
