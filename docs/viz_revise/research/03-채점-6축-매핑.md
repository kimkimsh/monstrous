# 03. 채점 6축 매핑 — 이번 개편이 어느 점수를 가지러 가나

시각화 배점 30점의 원문 (PDF 24페이지):

> Scores will be awarded based on how effectively the **Trace, represented as log (text) data**, is visualized with consideration for **observability, interpretability, traceability, explainability, clarity, and insightfulness**.

이 문서는 여섯 축을 화면 요소로 환산하고, **현행이 이미 채운 것 / 개편이 더 가져올 것**을 갈라 적는다.

근거: `docs/resource/track_resource/lableup/06-시각화-설계-가이드.md` · `02-평가-채점-규칙.md`

---

## 1. 심사위원의 기준선 — 이미 존재하는 화면

**Lablup은 스쿼드 모니터링 대시보드를 만들어 팔고 있다.** 우리 시각화는 그것과 비교된다. AI:GO가 이미 제공하는 것:

- 에이전트별 상태 전이 가로 스윔레인 (running 초록 / error 빨강 / created 호박 / completed 파랑 / idle 회색)
- 칸반 태스크 보드 (Pending / In Progress / Review / Done / Failed)
- 실시간 활동 피드 (최근 200개)
- 예산 미터 (토큰·비용 진행률, 실행 중 애니메이션)
- Hero stats (Active/Total agents, Session tokens, Execution phase)
- 에이전트별 토큰 분해, 일별 사용량 막대, 성공률·평균 실행시간

**따라 만들면 감점은 없지만 가점도 없다.**

차별화 지점 셋:

| | AI:GO 대시보드 | 우리 |
|---|---|---|
| 범위 | 한 실행 안 | **수백 문항 × 여러 실행 × 여러 스쿼드** |
| 질문 | 무슨 일이 있었나 | **왜 일어났고, 그래서 무엇을 바꿔야 하나** |
| 토큰 | 센다 | **정답에 기여했는지를 본다** |

세 번째가 결정적이다. 이 트랙의 채점 구조(정확도 40 + 효율 30)를 **정면으로 시각화**하는 것은 우리뿐이다.

> **개편의 시각적 함의:** 색·질감·모션이 AI:GO 대시보드와 **한눈에 달라야** 한다. 현행 다크 네이비(#0e1116) + 시안 액센트(#4cc2ff)는 AI:GO를 포함한 모든 개발자 도구의 기본값이다. **따스한 도트 아케이드 방향은 취향이 아니라 차별화 수단이다.**

## 2. 여섯 축 → 화면 요소 → 현행 상태

| 축 | 질문 | 이걸로 답한다 | 현행 | 개편 |
|---|---|---|---|---|
| **Observability** | 지금 무슨 일이 벌어지고 있나 | 웨이브 진행 뷰, 에이전트별 상태, 진행 카운터 | ✅ 재생 탭 · 스쿼드 맵 · 레인 | 계기가 **HUD로 상시 노출** |
| **Traceability** | 이 결과는 어디서 왔나 | 최종 답 → 그 답을 쓴 에이전트 → 그가 읽은 입력 → 앞 태스크 | 🟡 장부 대조는 있으나 **클릭 경로가 끊긴다** | **선택 상태 공유** — 맵·레인·장부·로그가 같은 대상을 함께 비춘다 |
| **Interpretability** | 이 숫자가 무슨 뜻인가 | 원시 로그가 아니라 **분류된 사건** | ✅ `blocker` 4분류 · 실패 규칙표 | 분류를 **색·글리프 규약**으로 고정, 범례 상시 |
| **Explainability** | 왜 그렇게 했나 | **결정 지점을 1급 객체로** | 🟡 라우팅 카드·플래너 폴백 경고가 흩어져 있다 | **결정 지점 배지**를 타임라인·맵·티커에 공통으로 |
| **Clarity** | 한눈에 들어오나 | 요약 → 드릴다운, 일관된 색·모양, 범례 상시 | ❌ **밀도 균일, 글자 16종, 명암비 3.25:1** | **3층 위계 + 7단 타입 스케일 + 4.5:1 하한** |
| **Insightfulness** | 보고 나서 뭘 알게 되나 | 토큰 대비 정답, 포기 시점, 웨이브 한계수익 | 🟡 낭비 사분면이 **250px 곁다리 카드** | **전체 분석의 주인공으로 승격** |

**현행에서 가장 약한 두 축이 clarity와 insightfulness다.** 그리고 이 둘이 개편으로 가장 크게 움직인다.

## 3. Insightfulness — 여기서 승부가 난다

가이드 §6이 제시한 여섯 화면 중, 로그로 만들 수 있는 것과 없는 것을 갈랐다.

| 가이드가 제시한 화면 | 만들 수 있나 | 현행 | 개편 |
|---|---|---|---|
| **6-1. 토큰 대 정답 산점도 + 절단선 슬라이더** | ✅ | `drawWaste` (520×250) | **주인공으로 승격.** 절단선을 끌면 상단 HUD의 토큰 계기가 같이 줄어든다 |
| **6-2. 포기 시점 최적화 곡선** | 🟡 부분 | 없음 | 실행별 총 토큰 상한 곡선으로 근사. **턴 수 축은 로그에 없다** |
| **6-3. 웨이브별 한계 수익** | 🟡 부분 | 없음 | 웨이브 수 대비 적격률·토큰. **문항당 웨이브가 1~2개라 표본이 얇다** |
| **6-4. 캐시 히트율 대 비용** | ❌ | 없음 | **캐시 필드가 로그에 없다.** 만들지 않는다 |
| **6-5. 실패 소유권 분해** | ✅ | `paneFailure` 규칙표 | **스택 막대 + 규칙표**로 승격. `FailureOwner` 열거형 사용 |
| **6-6. 리더보드 대비 위치** | ❌ | 없음 | 네트워크 의존 0 원칙을 깬다. 만들지 않는다 |

### 3-1. 현행에만 있는, 가이드에 없던 통찰 화면

이것들은 실제 로그를 파 보고 나서야 나온 것이라 **다른 팀이 만들 수 없다.** 개편에서 승격 대상이다.

| 화면 | 무엇을 말하나 |
|---|---|
| **채점 적격성 대조** | AI:GO가 성공이라 한 실행 중 실제로 점수가 되는 것이 몇 개인가. **리포트 `completed` 15건이 부적격이었다** |
| **0점 4분류** | 설정 / 러너 / 검사기 / 프롬프트 — **고칠 사람이 다르다** |
| **스쿼드 라우팅 대조** | 스쿼드가 스스로 찍은 트랙 vs 지문 기준. **conf 0.99로 틀렸다** |
| **답 근접도** | 형식을 못 맞춘 실행이 얼마나 아까웠는지. 통과 검사 비율 순 |
| **값은 맞고 문자를 안 냄** | `\boxed{1680}` vs 보기 `D. $1,680` — **한 글자 때문에 0점** |
| **워크스페이스 파일 경고** | 답이 `artifacts/final_answer.txt` 에만 있고 응답에 없다 |
| **큐 대기 시간** | 평균 33.4초, 최대 361초. **실행 시간만 보면 안 보인다** |

## 4. Traceability — 개편에서 새로 만드는 것

가이드 §5 Level 2가 제시한 패턴: **세 뷰가 선택 상태를 공유한다.** 하나에서 스팬을 고르면 나머지 둘에서 하이라이트된다.

현행은 뷰가 넷인데 서로를 모른다.

```
스쿼드 맵     ← 클릭하면 그 구간만 재생 (2772 focusNode)  ✅
레인 막대      ← 클릭 불가                                ❌
이벤트 티커    ← 클릭 불가                                ❌
장부 대조      ← 다른 탭. 연결 없음                        ❌
```

> **개편 목표:** 하나의 `선택 대상(태스크 / 에이전트 / 시각)` 을 상태로 올리고, **맵·레인·티커·장부가 전부 그것을 비춘다.** 이게 traceability를 눈에 보이게 만드는 가장 확실한 장치다.

## 5. 채점 규칙에서 나온 어휘 — 화면에 그대로 쓴다

주최 측 어휘를 그대로 쓰면 심사위원의 학습 비용이 0이다. **공짜로 얻는 점수다.**

제출 서버 OpenAPI 열거형 (출처: `05-제출-포털-API.md`):

| 열거형 | 값 | 현행 사용 |
|---|---|---|
| `FailureKind` | `context_overflow` · `upstream_error` · `rate_limit` · `wallclock_cap` · `unclassified` | ✅ `RULES` (782) |
| `FailureOwner` | `team` · `policy` · `configuration` · `organizer` | ✅ `RULES` |
| `Outcome` | `graded` · `extraction_failed` · `capped` · `grader_error` · `infrastructure_failed` | 🟡 개념은 있으나 이름을 안 쓴다 |
| `ItemStatus` | `ok` · `capped_tokens` · `capped_wallclock` · `error` | ❌ |

> **개편:** 우리 4분류(`blocked` / `nocontract` / `unknown` / `markers`)에 **주최 어휘를 병기**한다. 예: `답 형식 없음` 옆에 작게 `extraction_failed`. 우리 분류가 더 정밀하다는 것을 보여주면서 학습 비용도 없앤다.

## 6. 흔한 함정 — 개편이 새로 만들면 안 되는 것

가이드 §9의 표를 개편 관점으로 다시 읽었다.

| 함정 | 현행 | 개편 위험 |
|---|---|---|
| 원시 JSON을 화면에 그대로 뿌림 | 🟡 `paneRaw` 가 그렇지만 **그 탭의 목적이 원문 제시**라 정당 | — |
| AI:GO 대시보드를 그대로 재현 | ✅ 피함 | — |
| 실시간에만 의존 | ✅ 재생 모드 | — |
| **예쁜데 질문에 답 못 함** | ✅ `.q` 한 줄 | ⚠️ **아케이드 방향이 가장 크게 걸리는 함정.** 장식이 질문을 덮으면 clarity와 insightfulness를 동시에 잃는다 |
| 성공한 실행만 보여줌 | ✅ 실패가 1급 시민 | — |
| **색 의미가 화면마다 다름** | ❌ 트랙색과 상태색이 같은 변수를 공유한다 (`TRACK.coding.c === "var(--accent)"`) | ⚠️ **색 규약을 먼저 확정하고 시작한다** |
| conversation ID를 하위 스팬에 안 넘김 | ✅ `executionId` 로 묶는다 | — |
| 에이전트 이름 누락 | ✅ `.squad.json` 로 보강 | — |

**두 개의 ⚠️ 가 이번 개편의 실패 시나리오다.** 스펙에서 각각 다음으로 막는다:

- 장식이 질문을 덮는 것 → `../spec/01-컴포넌트-스펙.md` §1 「질문 줄은 모든 패널의 첫 요소이고, 어떤 장식도 그 위에 오지 않는다」
- 색 의미 충돌 → `../spec/00-디자인-토큰.md` §2-4 「색 3층 규약: 판정색 · 계열색 · 트랙은 색을 안 쓴다」

## 7. 개편이 노리는 점수 이동

| 축 | 현행 추정 | 개편 후 목표 | 무엇으로 |
|---|---|---|---|
| Observability | 상 | 상 | 유지 (HUD 상시 노출로 소폭 개선) |
| Interpretability | 상 | 상 | 유지 (규약 고정으로 안정화) |
| Traceability | 중 | **상** | 선택 상태 공유 4뷰 |
| Explainability | 중상 | **상** | 결정 지점 1급 객체화 |
| **Clarity** | **하** | **상** | 타입 스케일 · 명암비 · 3층 위계 |
| **Insightfulness** | 중 | **상** | 낭비 사분면 승격 · 4분류 전면화 · "한 글자 때문에 0점" 전면화 |

**clarity와 insightfulness 둘이 이번 작업의 전부다.** 나머지 넷은 유지가 목표다 — 개편이 이것들을 깨면 순손실이다.
