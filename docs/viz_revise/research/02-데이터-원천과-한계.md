# 02. 데이터 원천과 한계 — 새 디자인이 넘을 수 없는 벽

디자인 요구가 아무리 화려해도 **로그에 없는 값은 그릴 수 없다.** 이 문서는 새 화면을 설계하기 전에 "무엇이 실제로 존재하는가"를 확정한다.

출처: `viz/README.md` (실측 기록) · `viz/src/app.html` 수집·조립 코드 · `docs/resource/track_resource/lableup/` · `squad/` 실제 워크스페이스 3곳

---

## 1. 입력 — 워크스페이스 폴더 하나 또는 여럿

| 파일 | 필수 | 여기에만 있는 것 |
|---|---|---|
| `logs/history.json` | **필수** | 응답 본문(`output`), 에이전트 이름, 요청 원문 |
| `logs/events.jsonl` | **필수** | 웨이브 구조, `plannerWarning`, 토큰 시계열, 실패 에러 |
| `logs/<executionId>.jsonl` | 선택 | 사람이 읽는 로그, **웨이브가 끝난 시각** |
| `tasks/*.json` | 선택 | `dependsOn`, 큐 대기 시간, `retryCount`, `priority` |
| `tasks/*.md` | 선택 | 시도 단위 기록 (Progress Log) |
| `.squad.json` | **강력 권장** | 스쿼드 구성·모델·도구·시스템 프롬프트, `minContextWindow` |
| `artifacts/*` | 선택 | 에이전트가 워크스페이스에 쓴 파일 |
| `artifacts/reports/*.md` | 선택 | AI:GO 자체 실행 요약 |
| `logs/index.json` | 참고만 | 실행의 `squadId`. **개수·시각은 못 믿는다** |

**로그는 롤링 윈도우다.** 실측: 이벤트 id `0~50` 을 담던 파일이 `51~100` 으로 통째로 갈렸다. 실행 하나당 이벤트 9개이므로 42문항을 돌리면 마지막 몇 개만 남는다. → `viz/tools/snapshot-logs.sh` 로 실행 중에 스냅샷을 떠야 한다. **중복 제거는 뷰어가 `executionId` 로 한다.**

## 2. 없는 데이터 — 그리면 안 되는 화면

| 그리고 싶은 것 | 왜 못 그리나 |
|---|---|
| 캐시 히트율 곡선 | **캐시 필드가 로그에 없다.** 제출 포털 `dev-usage` 에만 있다 |
| 모델별 비용 | **모델 이름이 로그 어디에도 없다.** payload 키 39종 전수 확인 |
| 태스크별 토큰 | `history.json` 의 태스크별 `tokenUsage` 가 전부 `{0,0}` |
| 에이전트별 토큰 | `perAgentTokenUsage` 전부 `{0,0}`. `token-usage-update` 는 **에이전트의 평생 누적**이라 실행별 귀속 불가 |
| 캘리브레이션 곡선 | confidence 신호가 없다 |
| 도구 호출 트레이스 | `tool_use` / `tool_calls` / `toolName` 키가 전 워크스페이스에 **0건**. `write_file` 은 가장 많이 쓰였는데 호출 기록이 하나도 없다 |

실행별 총 토큰(`totalTokenUsage`)은 정확하다. **문항 = 실행**이므로 문항 단위 비용 분석에는 문제가 없다.

> **디자인 규칙 1 — 없는 값에는 카드를 세우지 않는다.**
> 현행 코드는 이미 이 규칙을 지킨다 (`routeCard` 는 마커가 있을 때만, `artifactCard` 는 파일이 있을 때만 렌더). 새 UI도 같은 규칙을 유지한다. **빈 카드에 "데이터 없음"을 띄우는 것이 아니라, 카드 자체가 나오지 않는다.**

> **디자인 규칙 2 — 추정값에는 반드시 표시를 붙인다.**
> 에이전트별 토큰은 누적 곡선의 증분을 그 시각에 돌던 태스크에 귀속시킨 **추정**이다. 동시 실행 구간은 나누지 않고 미귀속으로 남긴다. 화면에는 `(추정)` 과 미귀속 총량을 같이 적는다.

> **디자인 규칙 3 — 보간하지 않는다.**
> 누적 토큰은 **보고된 시점에만 계단식으로** 오른다. 실측 첫 보고는 +84초다. 사이를 선형 보간하면 "20초 시점에 661토큰" 같은 로그에 없는 숫자를 화면이 지어낸다.

## 3. 실측 숫자 — 새 화면이 견뎌야 할 규모

### 3-1. 실행 규모

| 항목 | 실측 |
|---|---|
| 워크스페이스 | 3곳 (`squad/test`, `squad/test_2`, `squad/ikkim`) |
| 파일 | 109개 |
| 실행 | 13 ~ 28건 (스냅샷 병합 범위에 따라) |
| 태스크 | 50건 |
| 한 워크스페이스 안의 스쿼드 | **최대 4개** (ikkim) |
| 한 스쿼드의 에이전트 | 최대 8명 |

**본선 규모는 다르다.** hidden 세트는 coding 140~240 · math 60~66(×2회) · generic 448~698 문항이다. 문항 하나가 실행 하나이므로 **실행 수백~천 건**이 목록에 들어올 수 있다.

> **디자인 규칙 4 — 목록은 1,000행에서 버텨야 한다.**
> 현행 `renderList()` 는 매번 전체를 다시 그린다(1934). 100건까지는 문제없지만 1,000건에서는 검색 입력마다 렉이 걸린다. 새 UI는 가상 스크롤이나 상한 렌더가 필요하다. → `../spec/04-구현-계약.md` §6

### 3-2. 판정 분포 (실행 28건 기준)

| 판정 | 건수 |
|---|---|
| 호출 거부 (`blocked`) | 5 |
| 계약 미전송 (`nocontract`) | 8 |
| 답 형식 없음 (`markers`) | 9 |
| **채점 적격** | **6** |

트랙별로는 coding 4 · math 22 · generic 2.

**이 네 갈래가 이 뷰어의 논지 전부다.** 합치면 "무엇을 고쳐야 하는가"가 화면에서 사라진다.

| 갈래 | 뜻 | 누가 고치나 |
|---|---|---|
| **호출 거부** | 모델이 요청을 받지도 못했다 (컨텍스트 초과·인프라) | **설정** |
| **계약 미전송** | 지문에 `=== REQUIRED OUTPUT ===` 절 자체가 없었다 | **러너** |
| **판정 보류** | 계약 절은 있는데 우리가 못 알아봤다 | **검사기** |
| **답 형식 없음** | 계약도 보냈고 실행도 됐는데 형식이 안 나왔다 | **프롬프트** |

앞의 셋은 분모에서 뺀다. 비율은 네 번째 위에서만 낸다.

### 3-3. 시간 분포

| 항목 | 실측 |
|---|---|
| 플래닝 | 49.0s |
| 승인 대기 | 20.8s (`autoApprove:false` 일 때는 사람 대기 시간) |
| 실행 | 23.2s |
| 태스크 큐 대기 평균 | 33.4s |
| 태스크 큐 대기 최대 | **361s** |

**대기가 실행보다 길다.** 현행 UI는 이걸 타임라인 탭 안쪽 막대의 흐린 앞부분으로만 보여준다. 첫 화면에서는 안 보인다.

### 3-4. 판정이 갈리는 지점

AI:GO 리포트가 `completed` 라고 적은 실행 **15건**이 채점 적격이 아니었다.

AI:GO는 "태스크가 끝났는가"를 보고, 제출 서버는 "응답에 요구된 형식이 있는가"를 본다. **이 두 판정이 갈리는 순간이 이 도구의 존재 이유다.**

## 4. 트랙과 출력 계약 — 화면에 반드시 나와야 하는 축

벤치마크는 트랙이 셋이고 **트랙마다 계약이 다르다.**

| 트랙 | 문항(연습 121개) | `kind` | 출력 계약 | 가중치 |
|---|---|---|---|---|
| **coding** | 20 | `swebench` 13 · `livecodebench` 7 | `*** PATCH START ***` … SEARCH/REPLACE … `*** PATCH END ***` | **0.50** |
| **math** | 59 | `math` | `FINAL ANSWER: \boxed{<answer>}` | 0.25 |
| **generic** | 42 | `letter_match` | `ANSWER: <letter>` | 0.25 |

**전체를 한 숫자로 합치면 어느 트랙이 새는지 사라진다.** coding이 총점의 절반이므로 coding 20건과 math 59건을 한 비율에 넣으면 화면이 거짓말을 한다.

세 트랙 공통 규칙 두 줄이 설계의 지렛대다.

> If more than one appears, **the last one is used**.
> Anything before it is **ignored, not penalised**.

### 4-1. 객관식은 보기 목록이 곧 계약이다

`generic` 은 MMLU-Pro 객관식이다. `Options:` 절과 `A.`…`J.` 가 있다는 것 자체가 계약이라, `=== REQUIRED OUTPUT ===` 절이 잘려도 판정을 미루지 않는다.

**값은 맞히고 문자를 안 낸 경우가 실제로 있다.** 보기가 `D. $1,680` 인 문항에 스쿼드가 `FINAL ANSWER: \boxed{1680}` 을 냈다. 계산은 맞았는데 `letter_match` 는 값이 아니라 문자를 보므로 0점이다.

> **디자인 규칙 5 — "한 글자 때문에 0점" 자리는 화면에서 가장 눈에 띄어야 한다.**
> 이건 insightfulness 그 자체다. 현행에서는 `.note` 문단(2091-2103)으로 본문 중간에 묻혀 있다.

### 4-2. 스쿼드가 스스로 찍은 트랙

`LEDGER Squad` 는 응답 끝에 `{"a":"Reasoner","track":"math","conf":0.99}` 를 남긴다. 실측 4건 중 **1건이 어긋났고, 그 건의 `conf` 는 0.99** 였다.

**확신도로는 이 오류를 걸러낼 수 없다.** 지문에 `Options:` 절이 있는지 같은 모양으로 먼저 갈라야 한다.

## 5. 스쿼드 로스터 — 로그에 없는 것

로그에는 **태스크를 배정받은 에이전트만** 남는다. 한 번도 일하지 않은 구성원과 **플래너는 이름 자체가 안 나온다.**

실측: 로그의 에이전트는 3명인데 실제 스쿼드는 4명이었다. 4번째가 플래너다.

`.squad.json` 이 유일한 정답이다. 여기에 이름·아이콘·역할·모델·도구·시스템 프롬프트가 전부 있다.

### 5-1. 제출 스쿼드 로스터 (`squad/squad_template/monstrous_squad/squad-template.json`)

| 아이콘 | 이름 | `role` | 모델 |
|---|---|---|---|
| 🗺 | **Router** | Planner | `furiosa-ai/gpt-oss-120b` |
| 📐 | **Architect** | Architect | `furiosa-ai/gpt-oss-120b` |
| 🔧 | **Editor** | Developer | `furiosa-ai/gpt-oss-120b` |
| 🧮 | **Solver** | Solver | `furiosa-ai/K-EXAONE-236B-A23B-NVFP4A16` |
| 📤 | **Reviewer** | Reviewer | `furiosa-ai/gpt-oss-120b` |

여기에 에이전트가 아닌 프로그램 `Preflight` 가 붙는다 — **LLM 호출 0회의 형식 검사기**이며, 이 뷰어의 장부 대조 탭이 하는 일과 같은 검사다.

> **디자인 기회:** 다섯 역할이 고정돼 있고 아이콘까지 정해져 있다. **역할별 도트 아바타 5종**을 그려 두면 스쿼드 맵·로스터·재생 화면이 전부 같은 캐릭터를 쓴다. `.squad.json` 이 없거나 다른 스쿼드면 `icon` 이모지로 폴백한다.

## 6. 스쿼드 = 워크스페이스가 아니다

실측: `squad/ikkim` 한 폴더에서 스쿼드 넷이 돌았다.

| squadName | 실행 |
|---|---|
| 코드 리뷰 스쿼드2 | 7 |
| 풀스택 개발 스쿼드 | 4 |
| 코드 리뷰 스쿼드 | 1 |
| 풀스택 개발 스쿼드2 | 1 |

그런데 `.squad.json` 에는 **마지막으로 초기화된 스쿼드 하나만** 들어 있다. 그래서 묶는 단위는 `squadId` 다 (`history.json` → `events.jsonl` → `logs/index.json` 순으로 찾는다).

> **디자인 규칙 6 — 스쿼드 이름 아래에 워크스페이스와 `squadId` 앞 8자를 같이 적는다.** 이름만으로는 두 스쿼드가 같은 것인지 알 수 없다.

## 7. 신뢰할 수 없는 값

| 값 | 실측 | 처리 |
|---|---|---|
| `logs/index.json` 의 `entryCount` | 21개 실행 **전부** 실제 줄 수보다 적었다 (13 vs 15, 11 vs 17…) | 개수·시각 근거로 안 쓴다. `squadId` 만 가져온다. **얼마나 어긋나는지는 화면에 적는다** |
| `tasks/*.json` 의 `result` | 50건 전부 `null` | 안 쓴다 |
| `tasks/*.json` 의 `artifacts` | 50건 전부 `[]` | 안 쓴다 |
| `tasks/*.json` 의 `tokenUsage` | 전부 `0` | 안 쓴다 |
| 리포트의 태스크별 `Tokens` | 전부 0 | 안 쓴다 |
| 플래너 호출 토큰 | 49초를 썼는데 토큰 이벤트가 0건 | **로컬 집계와 포털 청구가 어긋난다**는 사실을 적는다 |

**값이 하나뿐이라도 그 사실 자체가 답인 것**은 화면에 올린다.

| 값 | 실측 | 왜 올리나 |
|---|---|---|
| `retryCount` / `maxRetries` | 전부 `1` / `3` | **한 번도 재시도되지 않았다.** 재시도 여지가 2회 남아 있다 |
| `priority` | high 22 · medium 26 · low 2 | 플래너가 실제로 우선순위를 나눠 붙인다 |
| `dependsOn` | 50건 중 5건 | 나머지는 평평하다 — 웨이브를 나눌 근거가 얇다 |
| `minContextWindow` | 전부 `null` | 컨텍스트 상한을 안 걸어 놓은 상태 자체가 소견이다 |
| `instructions` | 전부 비어 있음 | 공통 규칙을 넣을 자리가 비어 있다 |

## 8. 정리 — 새 디자인이 반드시 지켜야 할 6줄

1. 없는 값에는 카드를 세우지 않는다.
2. 추정값에는 표시를 붙이고, 미귀속은 나누지 않는다.
3. 시계열을 보간하지 않는다. 계단으로만 오른다.
4. 실행 1,000건에서 버틴다.
5. 0점을 네 갈래로 갈라서 보여준다. 합치지 않는다.
6. 트랙을 합치지 않는다. coding은 총점의 절반이다.
