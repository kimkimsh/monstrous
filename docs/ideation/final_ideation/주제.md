# 최종 주제 — LEDGER Squad (장부를 쓰는 스쿼드)

> 모든 토큰이 자기 존재를 증명해야 하는 에이전트 스쿼드.

> **[갱신됨 2026-08-23 · 이 문서는 역사 기록이다]** 주제를 확정하던 2026-08-22 판이고 최종 설계가 아니다. 현행은 `../final_final_ideation/spec/`이다. `Auditor`는 `Reviewer`가 되어 전 문항에서 돌고, `Preflight`는 러너가 아니라 Reviewer 프롬프트 안의 체크리스트이며, 60,000자를 읽는 것은 Architect가 아니라 Router다. `Qwen3-30B-A3B-Instruct-2507` 수치는 이 플랫폼의 모델이 아니다. **제출 폼 원고는 이 문서가 아니라 `submission-copy.md`가 현행이다.**
> 검증할 수 있는 것은 LLM이 아니라 **프로그램**이 검증하고, 포기는 판단이 아니라 **산수**이며, 실행 기록(ledger, 장부)은 **채점되는 응답 본문 안**에 쓰여서 계측 비용이 0이다. 그리고 한 번 녹화한 실행 위에서 심사위원이 정책을 **무료로** 바꿔볼 수 있다.

`ledger` = 장부. 각 에이전트가 무엇을 했는지 한 줄씩 적어 내려가는 실행 기록.

---

## 1. 딛고 선 사실 다섯 (전부 원문·실측 확인)

1. 총점 = `0.5×coding + 0.25×generic + 0.25×math`. 문항 수는 generic이 압도적인데 **점수의 절반은 coding**에 있다.
2. coding 출력 형식은 unified diff가 **아니라** `*** PATCH START ***` + `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` 블록이다. SWE-bench·LiveCodeBench 양쪽 다.
3. 세 트랙 모두 *"If more than one appears, the last one is used. Anything before it is ignored, not penalised."* → **응답 본문 앞부분은 감점 없는 자유 공간.**
4. 평가 중 스쿼드는 **도구가 없다.** 컨텍스트는 judge가 60,000자로 잘라 넣어준다 (중앙값 59,966자 / 발췌 10개 / 후보 696개).
5. 저장소가 같아도 문항 간 컨텍스트 재사용은 거의 없다 (django 2.7%, 나머지 0%). 캐시 이득은 **한 문항 안에서 여러 에이전트가 같은 60,000자를 볼 때만** 난다.

모델 사실 하나 더 — `Qwen3-30B-A3B-Instruct-2507`은 MMLU-Pro 78.4 / AIME25 61.3 / LiveCodeBench v6 43.2인데 **Aider-Polyglot(코드 편집 형식 준수)만 35.6**이다. 못 고치는 게 아니라 **편집 형식을 못 낸다.** 이 트랙의 coding 출력이 정확히 그 능력을 요구한다.

## 2. 구조

### 에이전트 5명 + 프로그램 1개

템플릿은 하나뿐이므로 트랙 분기는 Router의 시스템 프롬프트 안에서 일어난다.

| 에이전트 | AI:GO role | 하는 일 |
|---|---|---|
| **Router** | `Planner` (스쿼드당 정확히 1명) | `payload.kind`로 경로 배정, 예산선 설정. 출력은 JSON 한 줄 |
| **Architect** | `Custom` | coding 전용. 60,000자를 읽고 **요약이 아니라 앵커**(발췌 인덱스 + 줄 범위)를 낸다 |
| **Editor** | `Developer` | 앵커 주변 발췌만 보고 SEARCH/REPLACE 블록을 쓴다 |
| **Solver** | `Custom` | math·generic 전용. 1턴, `--no-think`, 최소 출력 |
| **Auditor** | `Reviewer` | **유일한 승급 호출.** Preflight가 실패했거나 무료 신호 두 개가 엇갈릴 때만 |
| *Preflight* | *에이전트 아님* | 순수 프로그램. 아래 |

에이전트를 6~7명으로 늘리지 않은 건 의도다. Anthropic 멀티 에이전트 보고: 멀티 에이전트는 채팅의 약 15배 토큰을 쓰고 **대부분의 코딩 과제에 잘 맞지 않는다.** 그래서 검증자 하나를 아예 LLM이 아니게 만들었다.

### 프롬프트 3층 — 캐시 경계 사수

```
[Layer 1] 대회 컨텍스트 + 출력 계약 + few-shot     ← 전 요청 동일. 캐시 히트
[Layer 2] 이 문항 payload + 60,000자 컨텍스트      ← 문항 안 전 에이전트 공유. 캐시 히트
────────────────────────────────────────────── 캐시 경계
[Layer 3] 이 에이전트의 역할 지시 (짧게)           ← 여기만 새로 계산
```

Layer 3이 앞에 오면 효과가 전부 사라진다. 4명이 한 문항을 보면 입력 비용이 이론상 1/4에 근접. `cached_input_share`로 실측된다.

### 검증은 프로그램이 한다 — Preflight (LLM 호출 0회)

마커 짝 맞춤 · path 줄 존재 · **SEARCH 문자열이 발췌 안에 글자 그대로 있는가**(가장 흔한 실패. 모델이 코드를 기억으로 지어냄) · 온전한 줄 여부 · 공백/들여쓰기 · `\boxed{}` 모양 · `answer_format: integer`인데 수식인가 · 답 문자가 그 문항의 `option_letters` 안에 있는가(보기 수 3~10개로 들쭉날쭉).

돌려주는 것이 "다시 해봐"가 아니라 `"SEARCH 블록 2의 3번째 줄이 발췌에 없음. 가장 가까운 줄:"` 이다. **구체적 실패 신호가 붙은 재시도만 실제로 효과가 있다.**
→ 문제 지문의 *"which ones verify the results"* 에 대한 답: **검증자는 LLM이 아니어도 된다.**

### 포기는 판단이 아니라 산수다

s1(arXiv:2501.19393, EMNLP 2025) 실측 — "토큰 N개 안에 끝내라"는 프롬프트 지시는 **지켜지지 않는다.** 모델은 자기 토큰을 못 센다. 단계 수로 지시하면 "많은 단계 × 짧은 토큰"으로 갈아타고 총 토큰은 그대로다. **하드 캡만 작동했다.**

| 층 | 수단 | LLM 관여 |
|---|---|---|
| 1 | 요청 파라미터 `max_tokens` 하드 캡 | 0 |
| 2 | AI:GO Budget Config — `Max agent turns` 20 → **coding 6 / math 3 / generic 1**, `Max plan iterations` 3 → 1 | 0 |
| 3 | 러너 산수 — `잔액 < 다음 시도 견적`이면 **다음 호출을 하지 않는다** | 0 |

승급도 같다. 무료 신호 둘(형식 검사, 2회 샘플 일치)이 갈릴 때만 Auditor를 부른다. 고정 예산에서는 **검증자보다 다수결이 낫다**(arXiv:2504.01005 — GenRM이 다수결을 따라잡는 데만 8배 연산). 단 다수결은 특정 오답으로 수렴할 수 있으므로 **마지막에 항상 Preflight를 통과시킨다.**

### 장부는 채점되는 응답 본문 안에 쓴다

```
{"a":"Router","lane":"code","budget":18000}
{"a":"Architect","anchors":["astropy/io/ascii/rst.py:27-45"],"conf":0.72}
{"a":"Editor","try":1}
*** PATCH START ***  … 1차 시도 (버려질 예정)  *** PATCH END ***
{"a":"Preflight","fail":"SEARCH_NOT_VERBATIM","block":2}
{"a":"Editor","try":2}
*** PATCH START ***  … 마지막 것 = 실제로 채점되는 것  *** PATCH END ***
```

1. **계측 비용 0.** 별도 로거·요약 호출이 없다. 재시도가 덧붙이기라 앞 시도가 프리픽스로 남아 캐시도 걸린다.
2. **"이 화면이 렌더링하는 바이트는 채점기가 읽은 그 바이트입니다."** 옆에서 따로 수집한 트레이스는 실제 채점 실행과 어긋날 수 있고 심사위원은 검증할 방법이 없다. 이 방식은 어긋남이 **구조적으로 불가능**하다.

통제 두 개를 같이 건다 — 장부 줄은 JSON 한 줄(약 30토큰)로 제한, **꼬리 예산을 예약**해 마지막 블록이 잘리지 않게. 잘림 = `extraction_failed` = 팀 책임 0점.

## 3. 시각화 — 무료 반사실 재생기

채점 6축 중 다섯(observability·interpretability·traceability·explainability·clarity)은 잘 만든 트레이스 뷰어면 채워진다. 남는 **insightfulness**가 승부처다.

**녹화는 한 번, 재생은 무한.** 각 중간 시도를 로컬 채점기에 미리 돌려 점수를 붙여 둔다(`letter_match` / `math_verify` / LiveCodeBench 공개 테스트 / 패치 적용 가능성). 그러면 "n번째에서 멈췄다면 몇 점이었나"가 **재실행 없이 조회**된다.

심사위원이 끄는 슬라이더 — 전부 **LLM 호출 0회**: 최대 시도 횟수 · 승급 문턱 · 트랙별 예산 · **에이전트 한 명 제거(= 무료 ablation)**. 마지막 것이 핵심이다. "이 에이전트가 밥값을 하는가"를 **토큰 하나 더 안 쓰고** 증명한다.

화면: **장부 대조 뷰**(좌 `request.txt` 원문 / 우 우리 응답. 마지막 블록에만 `GRADED` 도장, 그 위 실패 시도엔 규칙 원문 *"ignored, not penalised"*) · **앵커 정확도 띠** · **패치 해부도**(SEARCH 불일치를 글자 단위로) · **낭비 사분면**(x=문항당 토큰, y=정답 여부. 수직 절단선이 슬라이더) · **포기 최적 곡선** · **캘리브레이션 곡선** · **실패 소유권 Sankey**(주최 열거형 `Outcome`/`FailureKind`/`FailureOwner` 그대로) · **캐시 히트 곡선**.

어휘는 OpenTelemetry GenAI Semantic Conventions 위에 `jxc.*`를 얹는다. 주최 열거형을 그대로 쓰면 심사위원 학습 비용이 0이다. **오프라인 재생이 기본** — 데모 중 네트워크가 죽어도 살아남고 타임라인 스크러빙이 공짜로 따라온다.

## 5. 정직한 한계

- **반사실은 완전하지 않다.** 시도 2가 시도 1의 실패를 보고 쓰였다면, 시도 1을 지운 세계에서 시도 2가 그대로 나온다는 보장이 없다 → 화면에 그대로 적는다. 한계를 표시한 화면이 표시 안 한 화면보다 심사에서 낫다.
- **앵커가 빗나가면 그 문항은 끝이다** → 앵커 복수(상위 2~3곳), 빗나감 비율을 연습 세트로 실측하고 화면에 노출.
- **장부가 출력 토큰을 늘린다** → 한 줄 JSON + 꼬리 예산 예약, 잘림 비율 실측.
- **SWE-bench 로컬 채점은 Docker가 필요해 무겁다** → 패치 적용 가능성과 앵커 정확도를 대리 지표로.
- **평가 중 러너 레벨 검사가 허용되는지 미확인** → 온보딩 최우선 질문. 안 되면 Preflight를 프롬프트 안 체크리스트로 다운그레이드(효과는 줄지만 0은 아님).
