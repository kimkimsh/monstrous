# 주제 1. 답은 맨 끝에 — 스스로를 기록하는 스쿼드 (Self-Narrating Squad)

> **한 줄 요약**
> 스쿼드의 토론 과정을 별도 로그가 아니라 **채점되는 응답 본문 안에** 구조화된 형태로 적어 넣고, 그 똑같은 바이트를 시각화가 읽는다. 계측 비용 0, 그리고 "우리가 보여주는 화면이 심사위원이 채점한 그 바이트"임을 증명할 수 있다.

---

## 1. 이 주제의 근거가 된 사실

제출 서버가 `/practice-sets/requests`에서 **judge가 실제로 보내는 요청 원문 364건 전부**를 공개하고 있다. 세 트랙 모두 요청 맨 끝에 `=== REQUIRED OUTPUT ===` 블록이 붙고, 그 블록의 문구가 이렇다.

```
generic : End your answer with a line of exactly this form:  ANSWER: <letter>
math    : End your answer with a line of exactly this form:  FINAL ANSWER: \boxed{<answer>}
coding  : *** PATCH START *** ... *** PATCH END ***

세 트랙 공통 문장:
  If more than one appears, the last one is used.
  Anything before it is ignored, not penalised.
```

두 문장이 이 주제의 전부다.

- **여러 번 나오면 마지막 것이 쓰인다.**
- **그 앞에 뭐가 있든 무시되며, 감점되지 않는다.**

즉 **응답 본문의 앞부분은 완전히 자유 공간**이다. 초안, 반론, 재작성, 근거, 신뢰도 — 뭘 적어도 점수에 영향이 없고, 오직 마지막 블록만 채점된다.

또 하나. 같은 페이지가 프롬프트 합성 규칙을 이렇게 공개한다.

```
1. 우리 one-shot 프롬프트의 {{TASK}}를 문항 내용으로 치환   (여러 번 쓰면 여러 번 들어감)
2. 줄바꿈 정규화 (\r\n, \r → \n)
3. 뒤쪽 공백 제거
4. 빈 줄 + 트랙의 REQUIRED OUTPUT 블록 원문 + 마지막 줄바꿈 을 덧붙임
```

**`{{TASK}}` 앞에 우리가 쓰는 글은 그 트랙의 모든 문항에서 글자 하나까지 동일하다.** 이게 prefix cache(프롬프트 앞부분이 이전 요청과 완전히 같으면 계산을 재사용하는 기능)가 걸리는 구간이 된다. 포털이 `cached_input_share`를 API로 알려주므로 효과를 숫자로 잴 수 있다.

---

## 2. 무엇을 만드는가

### 산출물 A — 스쿼드

에이전트들이 각자 따로 결과를 반환하는 대신, **하나의 성장하는 대본(transcript)에 순서대로 써 내려간다.** 각 블록은 정해진 태그를 달고 나간다.

```
[[SQUAD trace v1]]
{"agent":"Router","decision":"route","to":"code","cost_est":18000}
{"agent":"Architect","anchors":["astropy/io/ascii/rst.py:27-45"],"conf":0.72}
{"agent":"Editor","attempt":1,"conf":0.55}
*** PATCH START ***   ← 1차 시도 (버려질 예정)
...
*** PATCH END ***
{"agent":"Preflight","verdict":"SEARCH text not found verbatim","retry":true}
{"agent":"Editor","attempt":2,"conf":0.88}
*** PATCH START ***   ← 마지막 것 = 실제로 채점되는 것
...
*** PATCH END ***
```

1차 시도가 통째로 남아 있어도 **감점이 0이다.** 마지막 블록만 채점되기 때문이다.

### 산출물 B — 시각화

이 대본을 그대로 파싱해서 그린다. 별도 로거를 심을 필요가 없다.

---

## 3. 왜 1등감인가

### 시각화 30점 — 다른 팀이 절대 주장할 수 없는 한 문장

> **"이 화면이 렌더링하는 바이트는, 채점기가 읽은 바이트와 같은 파일입니다."**

보통 팀은 트레이스를 옆에서 따로 수집한다. 그러면 "실제 채점된 실행"과 "우리가 보여주는 화면" 사이에 어긋남(drift)이 생길 수 있고, 심사위원은 그걸 검증할 방법이 없다. 이 방식은 **어긋남이 구조적으로 불가능하다.** 채점 기준 6축 중 `traceability`(결과에서 원인까지 거슬러 올라가기)와 `explainability`(왜 그렇게 했는지)를 정면으로 때린다.

### 토큰 효율 30점

- 재시도가 **덧붙이기(append)**라서, 앞선 시도가 프롬프트 프리픽스로 그대로 남는다 → 캐시가 걸린다.
- 별도 계측 호출·요약 호출이 0이다.
- `{{TASK}}` 앞 고정 프리픽스로 트랙 단위 캐시 확보.

### 벤치마크 40점

`extraction_failed`(답을 못 뽑아낸 경우, **팀 책임**으로 분류되어 그대로 0점)를 구조적으로 없앤다. 형식이 틀려도 마지막에 한 번 더 제대로 쓰면 그게 정답으로 채택되기 때문이다. 형식 실패로 잃는 점수가 0에 수렴한다.

## 4. 데모에서 보여줄 장면

화면 왼쪽에 `request.txt` 원문, 오른쪽에 우리 응답 원문을 나란히 놓는다. 응답 위에서 마우스를 올리면 각 블록이 하이라이트되고, **맨 아래 마지막 PATCH 블록에만 "GRADED" 도장이 찍힌다.** 그 위의 실패한 1차 시도에는 "ignored, not penalised"라는 규칙 원문이 뜬다.

심사위원이 규칙을 다시 확인하러 갈 필요가 없다. 화면이 규칙을 인용한다.

## 5. 리스크와 솔직한 한계

| 리스크 | 내용 | 대응 |
|---|---|---|
| 출력 토큰이 늘어난다 | 버려질 초안도 출력 토큰이다. 토큰 효율 30점을 갉아먹는다 | 초안은 **극단적으로 짧게**. JSON 한 줄 수준. 전체 재작성이 아니라 "무엇이 틀렸는지"만 적기 |
| 자기 수정이 항상 이롭지는 않다 | 외부 신호 없는 self-correction은 효과가 엇갈린다는 보고가 많다 | 재시도 트리거를 **LLM 판단이 아니라 결정론적 검사**로 건다 (주제 5의 preflight 참고) |
| 트랙 요구 위반 우려 | "핵심부는 AI:GO agent squad 기능 위에" | 대본을 쓰는 주체는 어디까지나 **복수의 AI:GO 에이전트**다. 단일 에이전트로 줄이면 안 된다 |
| one-shot 프롬프트 주입 방식 미확인 | 프롬프트가 planner에게만 가는지 전원에게 가는지 모른다 | 온보딩 세션에서 확인 필요. 확인 전까지는 양쪽 다 되게 설계 |

---

## 6. 확인해야 할 것

- `/practice-sets/requests/<item_id>/request.txt` 를 트랙별로 3개씩 받아 REQUIRED OUTPUT 블록 원문을 손으로 대조할 것.
- 포털이 언급한 `docs/contracts/composition-rule.md`, `docs/contracts/patch-format.md`의 실제 위치 (로그인 후에 있을 가능성).
- 대본이 길어질 때 `max_tokens`에 걸려 **마지막 블록이 잘리는** 사고. 이건 곧바로 `extraction_failed`다. 연습 세트로 잘림 비율을 실측할 것.
