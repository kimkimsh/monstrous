# 주제 5. 설계자와 편집자 — 점수의 절반을 가진 트랙만 정조준 (Architect & Editor)

> **한 줄 요약**
> coding 트랙 하나가 점수의 **절반**이고, 우리 모델이 가장 못하는 곳도 거기다. 읽는 일과 고치는 일을 분리하고, 그 사이에 **LLM을 전혀 쓰지 않는 결정론적 검사**를 끼워 넣는다. 시각화는 "패치 해부도"가 된다.

---

## 1. 숫자가 말하는 것

### 가중치는 문항 수 비율이 아니다

`set.manifest.json`에 명시된 값:

```json
"weights": { "coding": 0.5, "generic": 0.25, "math": 0.25 }
```

```
총점 = 0.5 × 정확도(coding) + 0.25 × 정확도(generic) + 0.25 × 정확도(math)
```

그런데 hidden 문항 수는 generic이 448~698개로 압도적이고 coding은 140~240개다. **문항이 적은 쪽이 점수의 절반을 가진다.** 여기를 정조준하지 않는 팀은 시작부터 손해다.

### 우리 모델이 가장 약한 곳

| 벤치마크 | Qwen3-30B-A3B-Instruct-2507 |
|---|---|
| MMLU-Pro | 78.4 |
| AIME25 | 61.3 |
| LiveCodeBench v6 | 43.2 |
| **Aider-Polyglot (코드 편집 형식 준수)** | **35.6** |

Aider-Polyglot이 유독 낮다. 이건 "문제를 못 푼다"가 아니라 **"고칠 줄은 아는데 편집 형식을 제대로 못 낸다"**에 가깝다. 그리고 이 트랙의 coding 출력 형식이 정확히 그 능력을 요구한다.

### 실제 출력 형식 — 팀 자료가 틀렸던 부분

기존 자료(`09-스쿼드-설계-전략.md`)는 unified diff를 가정했다. **틀렸다.** 제출 서버가 공개한 요청 원문의 REQUIRED OUTPUT 블록은 이렇다.

```
*** PATCH START ***
path/to/file.py
<<<<<<< SEARCH
<the exact lines currently in the file>
=======
<the lines that replace them>
>>>>>>> REPLACE
*** PATCH END ***

Rules: one path line before every <<<<<<< SEARCH; repeat the three-marker block once per
edit; paths are relative to the repository root; SEARCH must be whole lines copied from
the file; an empty SEARCH section creates a new file.
```

**SEARCH/REPLACE 편집 블록**이다. SWE-bench와 LiveCodeBench **양쪽 모두** 이 형식을 쓴다 (LiveCodeBench는 빈 SEARCH로 새 파일을 만든다). 이걸 모르고 unified diff나 코드 블록을 출력하는 팀은 `extraction_failed`로 통째로 0점이다.

## 2. 어떻게 작동하는가

### 3단 구조

```
[Architect 설계자]   60,000자 컨텍스트를 읽는다.
                     요약하지 않는다. 고칠 자리의 앵커(anchor)만 낸다.
                     출력: {"path": "...", "anchor_lines": [412, 418], "why": "..."}
        ↓  (입력 크다, 출력 아주 작다)
[Editor 편집자]      앵커 주변 발췌만 보고 SEARCH/REPLACE 블록을 쓴다.
        ↓
[Preflight 검사]     LLM 아님. 순수 프로그램. 아래 3절.
        ↓  실패하면 Editor로 돌려보냄 (구체적 실패 코드와 함께)
[제출]
```

### 왜 나누는가 — 측정된 근거

Aider 프로젝트의 architect 모드(설계 담당과 편집 담당을 분리) 실측 보고:

> Qwen2.5-Coder-32B-Instruct 단독 diff 편집: **형식이 올바른 비율 92%**
> 같은 모델을 architect + editor로 분리: **100%**

8%p는 coding 트랙에서 가중치 0.5짜리 점수다. 그리고 이 분리는 문제 지문이 명시적으로 요구한 것이기도 하다 — *"which agents read the code, which ones modify it."*

또 하나. Diff-XYZ 벤치마크(JetBrains Research, 2025)의 형식 비교 결과: **패치를 생성하는 과제에서는 search-replace 형식이 가장 좋다.** Qwen2.5-Coder-32B 기준 diff generation EM이 search-replace 0.68 vs unified diff 0.23이다. 주최 측이 고른 형식이 마침 우리에게 유리한 형식이다 — **다만 그 형식을 정확히 따를 때만.**

### 왜 요약이 아니라 앵커인가

컨텍스트가 이미 `{path, start_line, end_line, text}`로 구조화되어 있다. **요약은 정보를 잃지만 줄 번호는 잃지 않는다.** 그리고 SEARCH 블록은 원문을 **글자 그대로** 복사해야 하므로, 요약본을 본 Editor는 반드시 실패한다.

## 3. Preflight — 이 주제의 심장

LLM을 한 번도 쓰지 않고, 다음을 **전부 결정론적으로** 검사한다.

| 검사 | 방법 | 잡아내는 실패 |
|---|---|---|
| 마커 짝 맞춤 | `*** PATCH START ***` / `*** PATCH END ***`, `<<<<<<<` / `=======` / `>>>>>>>` 개수 | 형식 붕괴 |
| path 줄 존재 | 모든 `<<<<<<< SEARCH` 앞에 경로 한 줄 | 규칙 위반 |
| **SEARCH 문자열 실재 확인** | 우리가 받은 발췌 텍스트 안에 그 문자열이 **글자 그대로** 있는가 | **가장 흔한 실패.** 모델이 코드를 기억으로 지어냄 |
| 줄 단위 정합 | SEARCH가 온전한 줄들인가 (줄 중간에서 시작·끝나지 않는가) | 규칙 위반 |
| 공백·들여쓰기 | 탭/스페이스, 후행 공백 | 조용한 불일치 |
| 빈 SEARCH 규칙 | 빈 SEARCH면 새 파일 생성 의도가 맞는가 | LiveCodeBench 오용 |

**비용이 0이고, 결과가 구체적이다.** "다시 해봐"가 아니라 `"SEARCH 블록 2의 3번째 줄이 발췌 안에 없음. 발췌에 있는 가장 가까운 줄은 이것이다:"`를 돌려준다. 이런 구체적 피드백이 있는 재시도만이 실제로 효과가 있다.

> 이게 곧 문제 지문의 세 번째 질문 — *"which ones verify the results"* — 에 대한 답이다. **검증자는 LLM이 아니어도 된다.** 평가 중 도구가 없다는 제약은 "프로그램을 못 쓴다"가 아니라 "스쿼드가 도구를 못 쓴다"이며, 러너 레벨의 검사는 별개다. (온보딩에서 재확인할 것.)

## 4. 시각화 30점 — 패치 해부도

coding이 점수의 절반이므로 시각화도 여기에 공을 들일 가치가 있다.

| 화면 | 답하는 질문 | 형태 |
|---|---|---|
| **앵커 정확도** | 설계자가 옳은 자리를 짚었나 | 60,000자 컨텍스트를 세로 띠로 그리고, Architect가 고른 앵커와 실제 정답 패치 위치를 겹쳐 표시. **겹치면 초록, 빗나가면 빨강** |
| **패치 해부도** | 이 패치가 왜 붙었나/안 붙었나 | 왼쪽에 원본 발췌, SEARCH 문자열이 매칭된 구간을 하이라이트. 실패 시 **어디서 어긋났는지 글자 단위로** 표시 |
| **실패 코드 파레토** | 우리가 지는 이유의 순위 | Preflight 실패 코드별 막대. 위에서부터 고치면 된다 |
| **재시도 수렴 곡선** | 재시도가 실제로 도움이 되나 | 시도 회차별 Preflight 통과율. 평평해지는 지점이 포기 시점 |
| **저장소별 성적** | 어느 프로젝트에서 약한가 | 연습 세트 실측: django 15문항, sympy 10문항, matplotlib 3, scikit-learn 3 … 편중이 크다 |

**패치 해부도는 이 대회에서만 나올 수 있는 화면이다.** 일반 에이전트 관측 도구에는 "패치가 왜 안 붙었는지 글자 단위로 보여주는 뷰"가 없다.

## 5. 실측으로 확인한 컨텍스트의 성질

연습 세트 `coding/context.jsonl` 40건을 직접 집계한 값이다.

| 항목 | 값 |
|---|---|
| 번들 크기 | 최소 59,634자 / 중앙값 59,966자 / 최대 60,000자 — **사실상 항상 60,000자 상한에 붙어 있다** |
| 문항당 발췌 수 | 5 ~ 22개, 중앙값 10개 |
| 후보 파일 수 | 53 ~ 811개, 중앙값 696개 |
| 실제 요청 원문 크기 | 63,481 ~ 85,004 바이트 (중앙값 약 66,000) |

**judge는 696개 후보 중 10개만 골라 넣어준다.** 이 검색은 거친 것이고, 진짜 위치 특정(localization)은 여전히 우리 몫이다. 그게 Architect가 존재하는 이유다.

한 가지 더 확인한 것: **저장소가 같아도 문항 간 컨텍스트 재사용은 거의 없다.** django 15문항의 발췌 텍스트 중복은 2.7%, 나머지 저장소는 0%다. 커밋이 문항마다 전부 다르기 때문이다. **따라서 문항을 저장소별로 묶어 캐시를 노리는 전략은 무효다.** 캐시 이득은 오직 **한 문항 안에서 여러 에이전트가 같은 60,000자를 볼 때** 나온다 — 그리고 그 이득은 크다. 4명이 보면 이론상 입력 비용이 1/4에 가까워진다.

## 7. 확인해야 할 것

- 포털이 언급한 **`docs/contracts/patch-format.md`** — "worked examples and every failure code"가 들어 있다고 명시되어 있다. 실패 코드 전체 목록을 얻으면 Preflight를 그대로 맞춰 만들 수 있다. 로그인 후 위치 확인 필요.
- LiveCodeBench 문항에서 새 파일을 만들 때 **경로를 무엇으로 써야 하는지** (starter code가 주어지는데 파일 경로는 안 주어진다).
- 평가 실행 중 러너가 재시도를 시킬 수 있는가, 아니면 문항당 응답이 1회인가.

## 8. 추가 조사 — Architect가 비용 절감 장치가 아니라 **정확도 장치**인 이유

이 주제의 Architect를 "토큰 아끼려고 컨텍스트를 줄이는 애"로 이해하면 절반만 맞다. 더 중요한 이유가 따로 있다.

### 컨텍스트 부패 (context rot)

Chroma Research, 2025년 7월. **18개 최신 모델**을 대상으로 측정한 결과:

> 모델의 신뢰도는 입력이 길어질수록 떨어진다. **검색이나 텍스트 복제 같은 사소한 과제에서도**, 그리고 **컨텍스트 창 한계와 한참 멀어도** 그렇다. 200K 창을 가진 모델이 50K 토큰 지점에서 이미 유의미한 정확도 손실을 보인다.

우리 coding 요청 원문은 **63,000~85,000 바이트, 대략 17,000~22,000 토큰**이다. 위험 구간에 들어와 있다.

Qwen3-30B-A3B-Instruct-2507의 공식 장문 성능(RULER)도 같은 방향이다.

| 컨텍스트 길이 | 4k | 32k | 64k | 128k |
|---|---|---|---|---|
| 점수 | 98.0 | 97.2 | 93.4 | 91.0 |

**즉 60,000자 전부를 Editor에게 그대로 넘기면, 아끼는 것만 못한 게 아니라 정확도를 잃는다.** Architect가 앵커로 좁혀 주는 것은 비용과 정확도를 **동시에** 개선하는 드문 수다.

### 그런데 "요약"은 절대 안 된다

컨텍스트 압축 연구는 성과가 좋다. LLMLingua-2(Microsoft, ACL Findings 2024)는 GSM8K 사고 사슬을 **14배 압축하고 정확도 −1.06%p**에 그쳤다.

**하지만 이 트랙에서는 쓸 수 없다.** SEARCH 블록은 원문을 **글자 그대로** 복사해야 한다. 압축·요약된 텍스트를 본 Editor는 존재하지 않는 문자열을 SEARCH에 쓰게 되고, Preflight에서 전량 탈락한다.

→ **압축이 아니라 선택.** 원문 발췌를 **그대로 유지한 채 개수만 줄인다.** 관련 선행 연구는 Provence(NAVER Labs, ICLR 2025)로, 문장 단위 가지치기를 리랭커와 통합해 "거의 공짜"로 만들고 **50~80% 가지치기에서 성능 하락이 거의 없으며, PopQA에서는 오히려 정확도가 올랐다**(잡음 제거 효과). 우리가 하려는 것과 같은 방향이다.

## 9. 솔직해야 할 반대 증거 — 멀티 에이전트는 코딩에 잘 안 맞는다

Anthropic이 자사 멀티 에이전트 리서치 시스템을 공개하며 적은 문장들이다.

> 에이전트는 보통 채팅보다 **4배** 많은 토큰을 쓰고, **멀티 에이전트 시스템은 채팅보다 약 15배** 많은 토큰을 쓴다.

> 잘 맞지 않는 경우: 컨텍스트를 공유해야 하는 일, 에이전트 간 의존이 큰 일, 그리고 **대부분의 코딩 과제**. ("리서치보다 진짜로 병렬화 가능한 일이 적다.")

그리고 성능 분산 분석에서:

> BrowseComp에서 **토큰 사용량 하나가 분산의 80%를 설명**한다. 그런데 — **Sonnet 3.7의 토큰 예산을 두 배로 늘리는 것보다 Sonnet 4로 모델을 바꾸는 것이 더 큰 성능 향상이다.**

### 이걸 어떻게 받아들일 것인가

세 가지 결론이 나온다.

1. **에이전트를 늘리는 것 자체는 미덕이 아니다.** 트랙 요구사항("squad formation")을 만족하는 최소 구성으로 가고, 늘릴 때마다 근거를 요구한다. Architect + Editor + Preflight는 **3개이고, 그중 하나는 LLM이 아니다.**
2. **컨텍스트 공유가 필요한 일이라는 지적이 정확하다.** 우리 대응은 에이전트를 늘리지 않는 것이 아니라, **같은 프리픽스를 공유해 캐시로 흡수시키는 것**이다 (5절: 한 문항 안에서 4명이 같은 60,000자를 보면 입력 비용이 이론상 1/4에 근접).
3. **모델·강도 선택이 스캐폴딩보다 레버가 크다.** 우리는 모델을 3개 중에서만 고를 수 있지만, 그 선택과 `--thinking-budget` 스윕에 프롬프트 튜닝보다 먼저 시간을 써야 한다.

> **이 반대 증거를 피칭에 그대로 넣는 것이 낫다.** "멀티 에이전트가 코딩에 불리하다는 보고를 알고 있고, 그래서 우리는 에이전트를 3개로 줄이고 하나는 LLM이 아니게 만들었다"는 서사는, 에이전트를 6개 늘어놓고 자랑하는 팀보다 훨씬 성숙하게 들린다.
