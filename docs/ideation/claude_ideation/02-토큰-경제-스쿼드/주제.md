# 주제 2. 토큰 경제 스쿼드 — 예산을 쥐고 일하는 팀 (Token Economy Squad)

> **한 줄 요약**
> 스쿼드에 **화폐**를 도입한다. 문항마다 토큰 예산이 배정되고, 에이전트는 일을 하려면 예산을 청구해야 하며, 예산이 바닥나면 파산 = 포기다. 시각화는 트레이스 뷰어가 아니라 **경제 대시보드**가 된다.

---

## 1. 왜 이 주제인가

이 트랙의 채점 구조 자체가 경제 문제다.

| 축 | 배점 | 성격 |
|---|---|---|
| 벤치마크 정확도 | 40 | 수익 |
| 시각화 | 30 | — |
| 토큰 효율 | 30 | 비용 |

게다가 **동점이면 토큰이 적은 쪽이 이긴다.** 즉 비용은 30점짜리 독립 항목이면서 동시에 40점짜리 항목의 승부 조건이다. 이 대회에서 비용은 부수적 제약이 아니라 **일급 목표**다.

그런데 대부분의 팀은 스쿼드를 "역할 분담"으로 짤 것이다. 읽는 애, 고치는 애, 검증하는 애. 그건 문제 지문이 예시로 든 것을 그대로 옮긴 것이고, 비용은 나중에 예산 설정 화면에서 숫자를 낮추는 것으로 처리한다.

이 주제는 순서를 뒤집는다. **비용 배분이 곧 스쿼드의 구조다.**

문제 지문이 명시적으로 물은 네 가지 중 마지막이 이것이었다는 점도 근거다.

> "...which ones **determine when it is time to give up**."

## 2. 어떻게 작동하는가

### 등장 인물

| 에이전트 | 하는 일 | 비용 |
|---|---|---|
| **Assessor (감정인)** | 문항을 보고 "이건 얼마짜리다"를 매긴다. 트랙, 지문 길이, 저장소, 보기 수 등으로 예산을 배정 | 매우 낮음 (출력 숫자 하나) |
| **Treasurer (회계)** | 남은 예산을 추적하고, 각 시도 전에 승인/거절한다 | 거의 0 (출력 한 단어) |
| 실무 에이전트들 | 실제로 문제를 푼다. 단, **시작 전에 견적을 내고 예산을 청구**해야 한다 | 대부분의 비용 |

### 파산 규칙 = 포기 판단

포기를 "판단"으로 두지 않고 **회계 규칙**으로 만든다. 이게 이 주제의 핵심이다.

```
잔액 = 배정 예산 - 지금까지 쓴 토큰
다음 시도의 견적 > 잔액   →   파산. 지금까지의 최선을 제출하고 종료.
```

LLM에게 "포기할까요?"라고 묻는 호출이 아예 없어진다. **가장 싼 포기 장치는 산수다.**

### 트랙별 초기 배정 (연습 세트 364문항 실측 기반)

| 트랙 | 가중치 | 문항당 입력 규모 | 초기 배정 근거 |
|---|---|---|---|
| coding | **0.50** | 요청 원문 **63,000~85,000 바이트** (실측, 중앙값 약 66,000) | 크게 준다. 여기가 점수의 절반 |
| math | 0.25 | 문제 지문 중앙값 **217자** | 적게. 단 `run_repeats: 2`라 실제 비용은 2배 |
| generic | 0.25 | 질문 중앙값 **178자**, hidden 448~698문항 | **가장 적게.** 아래 4절 참고 |

## 3. 시각화 30점 — 경제 대시보드

트레이스 뷰어를 만들지 않는다. **한 나라의 국민경제 계정 같은 화면**을 만든다.

| 화면 | 답하는 질문 | 형태 |
|---|---|---|
| **예산 흐름도** | 토큰이 어디로 갔나 | Sankey. 총 예산 → 트랙 → 에이전트 → 성공/실패 |
| **에이전트별 ROI** | 이 에이전트는 밥값을 하나 | x=쓴 토큰, y=그 에이전트가 관여한 문항의 정답률 기여 |
| **한계 수익 곡선** | 몇 번째 시도부터 손해인가 | 시도 회차별 누적 비용(막대) + 누적 정답률(선) |
| **파산 장부** | 포기가 옳았나 | 파산한 문항들을 모아, "예산을 20% 더 줬으면 몇 개가 살아났을까"를 슬라이더로 |
| **낭비 사분면** | 우리가 버린 돈의 총액 | x=문항당 토큰, y=정답 여부. **오른쪽 아래 = 많이 쓰고 틀림 = 낭비** |

**심사위원이 직접 슬라이더를 끌 수 있게 만드는 것**이 이 주제의 승부처다. 예산 상한 슬라이더를 움직이면 정답률과 총비용이 동시에 움직인다. `insightfulness`(보고 나서 몰랐던 것을 알게 되는가) 축은 이런 화면에서만 나온다.

## 4. 즉시 계산되는 절감 효과

generic 트랙 hidden 문항 수는 최대 698개다.

| 정책 | 문항당 토큰 | 총 토큰 |
|---|---|---|
| 검증 웨이브까지 붙임 | 3,000 | 2,094,000 |
| 답 한 글자만 | 500 | 349,000 |
| **차이** | | **175만 토큰** |

그런데 정확도 차이는 거의 없다. `letter_match`(보기 문자 대조)로 채점하므로 추론 과정은 채점 대상이 아니고, 모델 자체가 MMLU-Pro에서 이미 **78.4점**을 낸다 (Qwen3-30B-A3B-Instruct-2507 공식 수치). 가중치 0.25짜리 트랙에서 나오는 순수한 낭비다.

**Assessor는 이 계산을 자동으로 한다.** 사람이 정책을 손으로 정하는 게 아니라, 화면이 "이 배분이 최적이다"를 증명한다.

## 5. 리스크와 솔직한 한계

| 리스크 | 내용 | 대응 |
|---|---|---|
| Squad Template JSON에 예산 필드가 없다 | 템플릿은 에이전트 명단일 뿐이다. 예산 한도는 대시보드의 Budget Config에 있고 제출 JSON에 직렬화되지 않는다 | 예산 규칙을 **시스템 프롬프트와 트랙별 one-shot 프롬프트 안에** 넣어야 한다. 이건 제약이 아니라 설계 과제 |
| Treasurer 호출 자체가 비용 | 회계도 LLM이면 돈이 든다 | 출력 한 단어(`ok`/`stop`), `max_tokens` 5 내외. 자기 비용은 0에 수렴 |
| 견적이 틀리면 예산 규율이 무너진다 | Assessor의 예측이 부정확할 수 있다 | 연습 세트 364문항으로 실측 보정. 예측이 아니라 **트랙+kind별 실측 중앙값**을 기본으로 |
| 토큰 카운팅이 근사치 | AI:GO 공식 문서 경고: 시스템이 초과를 감지하기 전에 한도를 약간 넘길 수 있다 | 여유를 두고 한도 설정 |

## 6. 확인해야 할 것

- 모델별 **USD/Mtok 기준 단가.** 이게 없으면 "예산"의 단위를 정할 수 없다. 온보딩 세션 최우선 질문.
- `per_run_token_cap`과 `per_item_wallclock_seconds`의 실제 값.
- "AI:GO test run은 1/5로 과금"과 "dev key 사용량은 제출에 카운트되지 않는다"가 서로 안 맞는다. **무엇이 1/5로 계산되는 test run인지** 반드시 확인.

## 7. 추가 조사에서 나온 반박 증거 — 반드시 읽을 것

이 주제에 정면으로 불리한 실측 결과가 하나 있다. 숨기지 않고 적는다.

**s1: Simple test-time scaling** (arXiv:2501.19393, EMNLP 2025 본회의)이 예산 통제 방식을 세 가지로 비교했다.

| 통제 방식 | 결과 |
|---|---|
| **토큰 조건부** — "토큰 N개 안에 끝내라"고 지시 | **실패.** 모델은 학습을 시켜도 자기 토큰 수를 못 센다 |
| **단계 조건부** — "N단계 안에 끝내라"고 지시 | **해킹당함.** 모델이 "적은 단계 × 긴 토큰"에서 "많은 단계 × 짧은 토큰"으로 갈아타고, 총 토큰은 그대로 |
| **디코딩 레벨 하드 캡** — 종료 토큰을 강제 주입 | **유일하게 작동** |

**시사점: 예산을 프롬프트로 부탁하면 지켜지지 않는다.** "너에게 3,000 토큰이 배정됐다"라고 써 봐야 모델은 그걸 세지 못한다.

### 그래서 설계를 이렇게 고친다

예산은 **말이 아니라 기계로** 집행한다.

| 층 | 집행 수단 | LLM 관여 |
|---|---|---|
| 1 | `max_tokens` 하드 캡 (요청 파라미터) | 0 |
| 2 | AI:GO Budget Config — `Max agent turns`, `Max tokens per task`, `Max tokens per agent` | 0 |
| 3 | 러너 레벨 산수 — 잔액 < 견적이면 다음 시도를 **호출하지 않는다** | 0 |
| 4 | Treasurer 에이전트 | 있음 (최소) |

**1~3층이 실제 집행이고, Treasurer는 그 결정을 기록·설명하는 역할로 축소된다.** 이러면 주제의 서사는 살고("스쿼드가 예산을 쥐고 일한다") 통제는 실제로 작동한다. 오히려 시각화에는 유리하다 — 결정론적 규칙이라 화면에서 재현·검증이 가능하다.

`Max agent turns` 기본값이 20이라는 점도 중요하다. 공격적으로 4~8로 낮추는 것이 가장 직접적인 포기 장치다.

## 8. 이 주제를 피칭할 때 쓸 외부 숫자

"토큰 효율이 왜 독립된 실력인가"를 증명하는 공개 실측치들이다. 심사위원 앞에서 인용 가능하다.

| 사례 | 숫자 |
|---|---|
| **ARC Prize 공개 리더보드** | Gemini 3.7 Flash (High)와 Gemini 3 Deep Think이 **똑같이 84.6%**인데 과제당 비용은 **$0.249 vs $13.62 — 54.7배 차이** |
| **SWE-bench bash-only 리더보드** | MiniMax M2.5 **75.80% / 인스턴스당 $0.07** vs Claude 4.5 Opus **76.80% / $0.75**. 1.0%p 차이에 **10.7배** 비용 |
| **HAL (Princeton, arXiv:2510.11977)** | 첫 문장이 "에이전트는 1% 더 잘하려고 **100배** 더 비쌀 수 있다". 9개 벤치마크 중 **가장 비싼 모델이 파레토 경계에 오른 것은 1개뿐** |
| **Efficient Agents (arXiv:2508.02694)** | GAIA에서 성능 **96.7% 유지**하면서 과제당 비용 $0.398 → $0.228 (**42.7% 절감**). 단일 지표 이름이 **cost-of-pass** |
| **DARPA AIxCC 결승 (2025)** | LLM 크레딧 $50,000 하드 캡. **7팀 중 5팀이 예산의 25% 미만만 사용.** 우승팀 Team Atlanta는 LiteLLM을 예산 게이트웨이로 두고 챌린지별 API 키를 발급해 통제 |

**cost-of-pass**는 이 주제가 쓸 수 있는 가장 좋은 단일 지표 이름이다. 우리가 만든 말이 아니라 학계에서 쓰는 말이다.
