## 1. 전제

### 1-1. 채점 구조

| 항목 | 값 |
|---|---|
| 배점 | 벤치마크 40 + 시각화 30 + 토큰 효율 30 |
| 벤치마크 점수식 | `overall = 0.5 × acc(coding) + 0.25 × acc(generic) + 0.25 × acc(math)` |
| 40점 배분 방식 | **정확도 × 40이 아니라 팀 순위 순 배분** |
| 토큰 효율 30점 | `Σ [tokens(모델, 실행) × 단가(모델) × 실행배율]`이 낮은 순 |
| 실행 배율 | AI:GO test run **0.2** / submission run **1.0** |
| 동점 처리 | 1순위 총 토큰 적은 쪽, 2순위 wall-clock 짧은 쪽 |
| 채점자 | 항상 프로그램. LLM 심판 없음 |
| 제출 큐 | 대기 최대 3건, 동시 실행 1건. `check`는 무료·무제한 |
| 평가 중 도구 | **없다.** 저장소를 뒤질 수 없다. 문항 텍스트가 전부다 |

**토큰 효율은 두 번 작동한다.** 30점짜리 독립 축이면서 40점 축의 동점 처리 1순위다.

### 1-2. 트랙 성격 (연습 세트 121문항 실측)

| | coding | math | generic |
|---|---|---|---|
| 가중치 | **0.50** | 0.25 | 0.25 |
| hidden 문항 수 | 140~240 | 60~66 (**×2회 반복**) | 448~698 |
| 요청 크기 중앙값 | **63,812바이트** | 491바이트 | 918바이트 |
| 요청 크기 최대 | **70,310바이트 (토큰 미측정, §3-2 비율표 기준 약 17,900~20,300)** | 1,570바이트 | 2,926바이트 |

숫자는 `{coding,math,generic}/index.json`의 `request_bytes` 필드다. 유니코드 문자 수로 세면 coding 중앙값 63,809.5 / generic 918→917로 어긋난다. **바이트와 문자를 섞어 쓰지 않는다.**
| 출력 형식 | `*** PATCH START ***` + SEARCH/REPLACE | `FINAL ANSWER: \boxed{...}` | `ANSWER: <letter>` |
| 비용이 쏠리는 곳 | **입력** | 출력 | 출력 |

coding 요청은 두 봉우리로 갈린다. SWE-bench 13건은 62,935~70,310바이트, LiveCodeBench 7건은 1,999~3,066바이트다. **중앙값 하나로 설계하면 안 된다.**

**그리고 네 번째 자리를 비워 둔다.** 위 셋은 채점 벤치마크의 트랙이고, 하네스가 그 밖의 것을 보낼 수 있다. 세 트랙만 아는 스쿼드는 네 번째가 오는 순간 셋 중 하나의 형식을 억지로 씌워 **값이 맞아도 0점**을 받는다. 그래서 Router가 `other`를 포함해 넷으로 분류한다(§3-1).

세 트랙 공통 규칙 두 줄이 설계의 지렛대다.

> If more than one appears, **the last one is used**.
> Anything before it is **ignored, not penalised**.

답 블록 앞의 본문은 채점에서 무시된다. 추론을 앞에 써도 감점이 없다. 다만 **토큰은 그대로 든다.**

### 1-3. 이 플랫폼이 실제로 하는 일 (부록 A 요약)

설계를 강제하는 실측 사실 다섯 개다.

**① 채점기는 `finalResult` → 마지막 웨이브 역순으로 읽는다.**
`finalResult`가 `**Execution complete** — …` 상태 요약이면 무시하고, 태스크를 `(웨이브 번호, 배열 인덱스)` **내림차순**으로 훑어 첫 유효 출력을 답으로 삼는다. 실행 6건 전수 조사에서 `finalResult`는 **6/6 전부 상태 요약**이었다. 즉 실질적으로 언제나 마지막 웨이브의 배열 마지막 태스크가 답이 된다.

**② Planner 호출이 실패하면 요청 전문이 전 에이전트에게 뿌려진다.**
바이너리 문자열: *"The planner call failed (…), so the request was not decomposed. Each agent was given the whole request instead."* 실제로 발생했고, 63,475자 요청이 3명에게 각각 통째로 갔다. **에이전트 수 = 실패 시 낭비 배수다.**

**③ 워커는 원 요청이 아니라 Planner가 다시 쓴 설명을 본다(추정, 최우선 검증 대상).**
실측에서 Planner는 560자 투자 문제를 `"Calculate the number of bi-monthly periods in five years (5 years * 12 months/year / 2 months per period)."` 같은 요약으로 바꿨고, 원 지문은 어디에도 없었다. 요구 출력 형식도 `"in the required format"`으로 뭉개졌으며 최종 답이 32,328(정답 32,348)로 어긋났다.

**④ 호출당 고정 오버헤드가 1,400~3,000 토큰이다.**
요청 560자(약 160토큰)짜리 실행에서 5회 호출에 프롬프트 14,872토큰이 들었다(호출당 2,974). 150토큰짜리 수학 문항에 대해 **10~20배 증폭**이다. 태스크를 하나 더 만들면 이 오버헤드가 통째로 한 번 더 붙는다.

**⑤ 같은 웨이브 안에서도 직렬로 돈다.**
공식 문서는 병렬이라고 하지만 실측은 약 300밀리초 간격의 직렬이었다. 캐시 관점에서는 오히려 유리하다 — 동시 요청은 프리픽스 캐시를 깨뜨린다.

## 2. 명단 — 에이전트 5명

### 2-1. 구성

| # | 이름 | AI:GO `role` | 하는 일 | 도는 트랙 | 지문의 어느 질문에 답하나 |
|---|---|---|---|---|---|
| 1 | **Router** | `Planner` | **트랙 4분류**(coding / math / generic / other) + **60,000자를 재서 앵커와 원문 hunk만 하류로 내린다** + 분해 깊이 결정 | 전부 | *which agents read the code* |
| 2 | **Architect** | `Custom` → `Architect` | **무엇을 어디서 고칠지 정한다.** 경로 추적 → 공유 지점 특정 → 손대면 안 되는 것 지정 → 확신도 | coding (SWE-bench) | *which agents read the code* |
| 3 | **Editor** | `Developer` | SEARCH/REPLACE 블록 작성 | coding | *which ones modify it* |
| 4 | **Solver** | `Custom` → `Solver` | 수학·객관식 풀이 | math, generic | — |
| 5 | **Reviewer** | `Reviewer` | **내용 + 형식 두 층 검토** → 최종 답 블록 발행 → 못 고치면 중단 선언 | 전부 | *which ones verify the results* · *when to give up* |

**Architect는 60,000자를 읽지 않는다.** 그 일은 Router가 한다 — 이 앱에서 요청 전문을 보는 컴포넌트가 Planner 하나뿐이기 때문이다(부록 A-6). Architect가 받는 것은 앵커 2~3개, 약 2KB다. Architect가 들고 있는 것은 컨텍스트가 아니라 **판단 기준**이고, 그 기준은 `docs/resource/background_research/engineering_doctrine/`의 세 레포 분석에서 왔다.

### 2-1-1. *when to give up*에 답하는 방식

이 앱에서는 **"끊는 에이전트"를 만들 수 없다.** 플랜 그래프가 실행 전에 고정되고 조건 분기가 없어서, `give_up` 한 단어를 뱉는 에이전트를 둬도 **그 출력을 받아 다음 웨이브를 취소할 주체가 없다.** 공식 문서는 태스크 실패 시 뒤 웨이브를 건너뛴다고 하지만 실측에서는 그냥 실행됐다(부록 A-3-3).

그래서 포기를 네 층으로 나눈다.

| 층 | 누가 | 무엇을 끊나 |
|---|---|---|
| 1 | **Router** | 문항을 보고 태스크를 2개로 할지 3개로 할지 정한다. LiveCodeBench·math·generic에 Architect를 안 붙이면 호출 하나가 통째로 안 나간다 |
| 2 | **Architect** | 확신도 `none` — *"앵커 안에 실패를 설명하는 자리가 없다"*를 명시적으로 낸다. Editor는 그걸 받으면 정교한 오답 대신 최소 변경만 시도한다 |
| 3 | **Reviewer** | 판정 `stop` — 고칠 수 있으면 고치고, 못 고치면 **더 시도하지 않고** 지금 가진 것 중 형식이 유효한 최선을 낸다 |
| 4 | **BudgetConfig + 러너 잔액 산수**(§6-2) | 하드 스톱. 유일하게 LLM 판단이 아닌 층 |

2층이 실재하는 이유가 있다. 연습 문항 `coding-visible-0001`은 추가되는 테스트가 `astropy/io/ascii/tests/test_rst.py`인데 **발췌 11개 중 `rst.py`가 없다.** 고칠 파일이 요청에 안 들어온 문항이고, 무엇을 해도 못 푼다. 그런 문항에서 정교한 오답을 만드는 것보다 **최소 변경 + 낮은 확신도**가 싸다.

그리고 이 결정을 화면으로도 답한다 — §11-6의 포기 시점 곡선이다.

### 2-2. 컨텍스트 분배가 왜 Planner의 일인가

사용자가 요구한 "컨텍스트 제한에 맞춰서 입력을 나눠서 배분하는 에이전트"는 **Router**다. 이것을 별도 에이전트로 떼지 않고 Planner에 붙인 이유는 이 플랫폼의 구조 때문이다.

부록 A-6에서 확인한 것: **워커는 원 요청이 아니라 Planner가 쓴 태스크 설명을 본다.** 즉 이 앱에서

- 요청 전문을 **반드시** 보는 컴포넌트는 Planner 하나뿐이고,
- 워커에게 무언가를 전달하는 **유일한 통로**도 Planner의 태스크 설명이다.

컨텍스트 분배를 별도 에이전트로 떼면 이렇게 된다.

```
Router(20K 읽음) → 태스크 설명에 20K 전문 복사(20K 출력) → Steward(20K 읽음) → 앵커 2K
```

Router가 입력 20K + 출력 20K = 40K를 쓴다. **Qwen3-32B의 컨텍스트 한도 40,960토큰을 정확히 밟는다.** 넘기려면 128K 모델(배율 2)로 올려야 하고, 그러면 coding 문항 하나에 40K × 2 = 80K 비용 단위가 든다. hidden 190문항이면 15.2M이다.

Planner가 직접 분배하면 이렇게 된다.

```
Router(20K 읽음) → 앵커 + 원문 hunk 2K 출력 → Editor(3K 읽음)
```

입력 20K + 출력 2K = 22K. **배율 1 모델에 여유 있게 들어간다.** coding 문항당 총 비용이 약 38K로, 위 구성의 절반이다.

덤으로 에이전트가 한 명 줄어드는데, 이것이 §2-3의 폭발 반경을 직접 줄인다.

**대가도 정확히 적는다.** Planner에게는 앱이 자기 시스템 프롬프트를 주입한다(부록 A-3-1 원문). 그 안에는 *"Break requests into the smallest reasonable tasks"* 같은 우리 설계와 충돌하는 규칙이 들어 있고, 우리는 그 위에 우리 `systemPrompt`를 덧씌우는 방식으로만 통제할 수 있다. **분배 정확도가 Planner 프롬프트 경쟁에 노출된다는 뜻이다.** §10-E3에서 앵커 정확도를 별도로 측정한다.

### 2-3. 왜 5명인가 — 늘릴 근거와 줄일 근거

에이전트를 하나 더 두는 순간 비용이 붙고 정확도는 자동으로 따라오지 않는다. 정당한 분할 축은 문헌상 **두 개뿐**이다.

| 분할 축 | 측정된 효과 | 이 스쿼드의 대응 |
|---|---|---|
| **컨텍스트 격리** — 서브태스크가 큰 컨텍스트를 읽지만 본 작업에는 발췌만 필요할 때 | 파일 단위 컨텍스트 유무가 SWE-bench에서 **15~17배** 차이. 별도 localization 단계로 resolve **44.7% → 48.9~49.1%**(gold 52.4%), 게다가 **소요 시간도 줄었다** | Router → Editor |
| **출력 형식 생성 분리** — "무엇을 고칠까"와 "형식을 정확히 쓰기"가 다른 능력일 때 | SWE-Edit: 편집 성공률 93.4% → 96.9%, resolve 69.9% → 72.0%, 비용 −17.9% | Editor / Reviewer |

반대 방향 증거도 정확히 알고 간다.

- 멀티 에이전트는 같은 일에 토큰 **3~10배**를 쓴다. 에이전트는 채팅의 약 4배, 멀티 에이전트는 약 15배.
- 동일 thinking-token 예산에서는 단일 에이전트가 모든 비교에서 최고이거나 통계적으로 구분되지 않았다.
- MAST(트레이스 1,600건 이상): 실패의 **41.77%가 명세 문제, 36.94%가 에이전트 간 정렬 실패**. 모델 성능이 아니라 조직 설계가 실패 원인이다.
- 역할 페르소나 문장은 정확도를 올리지 않는다. 162개 역할 × 4개 모델 × 2,410문항에서 개선 없음, MMLU-Pro 300문항 × 6개 모델에서 **유의미한 악화 9건**.

그리고 이 플랫폼 고유의 제약이 상한을 눌러 준다. **Planner가 죽으면 요청 전문 × 에이전트 수만큼 토큰이 증발한다.** coding 문항 하나가 실패할 때 4명이면 약 80K, 5명이면 약 100K 토큰이 그대로 증발한다. **Architect를 되살린 대가가 정확히 이 20K다.** 막을 방법은 Planner를 죽이지 않는 것뿐이라, `requiresToolCalling`을 전부 `false`로 내리고 `minContextWindow`를 비웠다(§4-2).

**결론: Planner 강제 1명(= 컨텍스트 분배 겸임) + 근거 있는 분할 세 개(Architect, Editor, Solver) + 검토·발행 1명 = 5명. 그 이상은 없다.**

세 번째 분할 — **Architect / Editor** — 의 근거는 위 표의 "출력 형식 생성 분리" 축과 다른 것이다. 이쪽은 *"무엇을 어디서 고칠까"* 와 *"원문과 바이트 단위로 같은 SEARCH를 쓴다"* 를 나눈다. 근거는 두 갈래다.

- **측정된 것.** 리포트가 말한 경로만 고치고 형제 호출자를 남겨 두는 실패를, "네가 바꿀 함수의 호출자를 전부 훑어라"는 조작적 지시가 **Sonnet 1/6 → 6/6, Opus 1/6 → 6/6**으로 바꿨다. 같은 내용을 산문으로 쓴 대조군("흐름을 끝까지 따라가라")은 **0/3**이었다. 지시가 절차여야 효과가 난다는 뜻이고, 절차를 담을 자리가 필요하다 (`engineering_doctrine/01-ponytail.md` §4)
- **구조적인 것.** 그 절차는 SWE-bench 채점 구조 그 자체다. `fail_to_pass`만 보고 고치면 `pass_to_pass`가 깨진다

**대가도 정확히 적는다.** SWE-bench 경로에서 호출이 3회에서 4회로 는다. 문항 190건 기준 고정 오버헤드만 약 0.4M 토큰이 추가되고, Architect 자신의 입출력이 더 붙는다. §10-E3b가 이 분할을 재는 실험이다 — **분할 자체가 값을 하는지 아직 안 쟀다.**

`role` 필드는 스키마가 요구하니 채우되, **프롬프트에서 그 역할을 연기시키지 않는다.** `systemPrompt`는 전부 출력 계약으로 채운다.

### 2-4. `role` 문자열 주의

앱은 `role` 문자열을 **소문자로 바꾼 뒤 전체 일치**로 본다. 받는 값은 `planner` / `developer` / `reviewer` / `writer` / `custom` 다섯이고, 그 외는 전부 `{"type":"custom","value":"<원문>"}`이 된다. 즉 대소문자는 상관없고 **부분 일치가 안 된다** — `"Code Reviewer"`는 `custom`이다(부록 A-2-3, 바이너리 확인).

`custom`이어도 손해는 없다. `role`은 Planner에게 주는 팀 명단 줄에 그대로 찍힐 뿐이고, 알려진 역할에는 한 줄짜리 설명이 따라붙는다. 그래서 Solver는 `custom`으로 두되 이름이 곧 설명이 되게 지었다. 위 표의 `role` 값은 이 규칙에 맞춰 정한 것이다.

## 3. 에이전트별 계약

각 에이전트는 **받는 것 / 내는 것 / 절대 안 하는 것** 셋으로 정의된다. 이 세 줄이 `systemPrompt`의 **에이전트별 부분(Layer 3)** 전부여야 한다. 그 앞에 붙는 공통 계약(Layer 1)은 §7의 캐시 요구 때문에 길다 — 짧게 쓰는 것과 캐시가 걸리는 것 중 캐시를 택했고, 그 판단 근거는 §7에 있다.

### 3-1. Router (`Planner`)

| | |
|---|---|
| **받는 것** | 합성된 요청 전문 (one-shot 프롬프트 + 문항 payload + REQUIRED OUTPUT 블록) |
| **내는 것** | `create_task` 호출 2~3개. **마지막 웨이브는 반드시 태스크 1개** |
| **절대 안 하는 것** | 문제 풀이. **요약.** 4개 이상 태스크 생성. 자연어 설명 출력 |

**트랙 라벨이 요청에 없다.** Router가 트랙을 아는 유일한 방법은 요청 끝의 `=== REQUIRED OUTPUT ===` 블록이다. 이것을 프롬프트에 명시하지 않으면 Router는 지문 내용으로 추측하게 되고, MMLU-Pro의 수학 과목 문항이 math로 새는 식의 오분류가 난다.

#### 트랙은 넷이다

| 트랙 | 판별 | 비고 |
|---|---|---|
| `coding` | 블록에 `*** PATCH START ***` | |
| `math` | 블록에 `FINAL ANSWER:` + boxed 값 | |
| `generic` | 블록에 `ANSWER: <letter>` | |
| **`other`** | **셋 다 아니거나 블록 자체가 없다** | 실패가 아니라 분류다 |

앞의 셋은 이 스쿼드를 맞춰 놓은 벤치마크이고, **넷째는 그 밖의 것이 왔을 때를 위한 자리다.** 세 트랙만 아는 스쿼드는 네 번째가 오는 순간 셋 중 하나의 형식을 억지로 씌우고, **값이 맞아도 형식이 틀려서 0점**이 된다.

`other`의 규칙은 나머지 셋과 같은 규칙이다 — **요청이 자기 답의 형태를 말해 준다. 그 형태를 글자 그대로 지키고, 맨 뒤에 두고, 뒤에 아무것도 쓰지 않는다.** 다른 점은 그 형태를 우리가 미리 알지 못한다는 것뿐이고, 그래서 Router가 **요청의 그 문장을 그대로 하류로 옮긴다.**

#### 분류와 경로는 다른 축이다

트랙이 넷이라고 경로가 넷은 아니다. 경로를 정하는 것은 **코드를 읽어야 하는가**와 **코드를 써야 하는가** 둘이다.

| 조건 | 플랜 | 태스크 |
|---|---|---|
| `## Repository context` 있음 | **A** | Architect → Editor → Reviewer (3) |
| 없음 + 답이 코드다 | **B** | Editor → Reviewer (2) |
| 없음 + 답이 코드가 아니다 | **C** | Solver → Reviewer (2) |

**`other`가 저장소 발췌를 달고 오면 플랜 A로 간다.** 트랙 이름이 아니라 모양이 경로를 정한다. 셋은 배타적이고 합치면 빈틈이 없다 — 초안에서는 `other`+발췌없음이 B와 C 양쪽에 걸리는 겹침이 있었고, 그것을 이 표로 없앴다.

전달 규칙이 트랙마다 다르다. 기준은 하나다 — **하류 에이전트가 답을 내는 데 필요한 원문이 태스크 설명 안에 글자 그대로 있어야 한다.**

| 트랙 | 태스크 설명에 넣는 것 | 대략 출력 토큰 |
|---|---|---|
| math | 문제 지문 **전문 그대로** + REQUIRED OUTPUT 블록 그대로 | 약 300 |
| generic | 질문 + `Options:` 블록 **전문 그대로** | 약 400 |
| coding (발췌 있음) | **앵커 2~3개 + 각 앵커의 원문 hunk 그대로** (§3-2) | 약 2,000 |
| coding (발췌 없음) | **요청 전문 그대로.** LiveCodeBench 항목은 끝에 `## How your solution is run` 절이 붙어 있고 여기에 stdin/stdout 계약이 있다. "문제 지문만" 옮기면 이 절이 빠지고, 워커는 그것을 다른 데서 볼 방법이 없다 | 약 900 |

math·generic은 지문이 짧으니(중앙값 491자 / 917자) 통째로 옮기는 것이 가장 안전하고 가장 싸다. coding만 60,000자를 통째로 옮길 수 없으므로 §3-2의 분배 규칙이 필요하다.

앱이 Planner에게 주입하는 기본 프롬프트의 규칙 1번은 *"Break requests into the smallest reasonable tasks"*다(부록 A-3-1 원문). **이것이 우리 채점 구조와 정면으로 어긋난다.** 태스크를 잘게 쪼갤수록 호출당 1,400~3,000 토큰 오버헤드가 곱해지고, 마지막 웨이브에 태스크가 여러 개 생겨 채점기가 엉뚱한 것을 읽는다.

실측 사고 사례: Planner가 수학 문항 하나를 한 웨이브 3개 태스크로 쪼갰고, 정답 유도는 인덱스 0에 들어갔는데 채점기는 인덱스 2를 읽었다. 인덱스 1은 `Check status of max task` — 순수 낭비 호출이었다.

그래서 Router의 `systemPrompt`는 기본 규칙을 **명시적으로 덮어쓴다.**

```
Create the minimum number of tasks. Never more than three.
The final wave must contain exactly one task.
Whatever a downstream agent needs must appear inside its task description,
copied verbatim, byte for byte. Never summarise, paraphrase, reword, or reformat.
Do not solve anything yourself.
```

**원문 그대로 넘기라는 지시가 왜 필요한가.** 부록 A-6에서 워커가 원 요청 대신 Planner의 요약을 받는 정황이 나왔다. 요약은 두 가지를 죽인다. 첫째, SEARCH/REPLACE는 원문과 **공백 하나까지 같아야** 하므로 자연어를 한 번 거치면 그 순간 깨진다. 둘째, 요구 출력 형식 문장이 사라진다. 실측에서 정확히 그 일이 일어났다 — 요구 형식이 `"in the required format"`이라는 말로 뭉개졌고 최종 답도 어긋났다.

문헌도 같은 방향을 가리킨다. 위치 지정을 고정한 채 컨텍스트 표현만 바꾼 절제 실험에서 **원본 소스는 45문항 중 27건을 풀었고, 자연어 요약은 4건을 풀었다.** UML 스켈레톤(시그니처만 남긴 형태)은 주변 컨텍스트를 통째로 삭제한 것과 통계적으로 구분되지 않았다(70개 다중 파일 문항, p=0.75). **요약본 핸드오프는 성능을 6배 이상 깎는다.**

### 3-2. Router의 두 번째 일 — 컨텍스트 분배

Router는 태스크를 만드는 김에 **입력을 재서 나눈다.** 이것이 사용자가 요구한 "컨텍스트 제한에 맞춰서 입력을 나눠서 배분하는 에이전트"다.

| | |
|---|---|
| **받는 것** | coding 요청 전문 (이슈 + 발췌 최대 60,000자) |
| **내는 것** | 태스크 설명 안에 앵커 2~3개. 각 앵커는 `{경로, 줄 범위, 원문 hunk 그대로, why 한 줄}` |
| **절대 안 하는 것** | **요약.** 패치 작성. 코드 재작성. 발췌에 없는 경로 언급 |

발췌는 `--- path/to/file.py (lines A-B of N) ---` 헤더 줄과 그 아래 펜스 블록으로 들어온다. **앵커의 `path`와 줄 번호는 그 헤더에서 그대로 읽는다.** 펜스(` ``` `)는 요청의 서식이지 파일 내용이 아니므로 hunk에 포함하지 않는다.

#### 왜 문자 수가 아니라 토큰인가

문자당 토큰 비율은 내용에 따라 최대 5배 넘게 벌어진다. `tiktoken`으로 직접 측정한 값이다.

| 내용 | 문자/토큰 (`cl100k_base`) | 문자/토큰 (`o200k_base`) | 70,000자 → 토큰 |
|---|---|---|---|
| 영어 산문 | 5.34 | 5.34 | 13,097 |
| Python 코드 | 3.93 | 3.82 | 18,327 |
| C++ 코드 | 4.22 | 4.16 | 16,831 |
| JSON | 3.47 | 3.47 | 20,147 |
| 한국어 + 영어 혼합 | 1.93 | 2.80 | 25,019 |
| **한국어 산문** | **1.02** | **1.68** | **41,681** |

업계 관행인 "4자 ≈ 1토큰"은 한국어에서 용량을 **3~5배 과대평가**한다. 그리고 토크나이저가 바뀌면 같은 문장의 토큰 수가 달라진다. Anthropic 공식 문서: *"Claude 4.7 and later models … use a newer tokenizer. The same input text produces **approximately 30 percent more tokens** than on earlier models."*

> **규칙: 대상 모델의 실제 토크나이저로 세고, 안전 여유를 더한 뒤 판단한다. 문자 수 어림짐작 금지.**

#### 왜 한도에 닿기 전에 잘라야 하는가

컨텍스트 창은 광고값까지 안전하지 않다.

| 측정 | 내용 |
|---|---|
| RULER (17개 모델, 13개 태스크) | 실효 컨텍스트가 광고값의 **½ ~ ¼**. GPT-4 128K 주장 → 실효 64K (96.6@4K → 81.2@128K). Qwen2-72B 128K 주장 → 실효 **32K** (96.9@4K → 53.7@128K) |
| NoLiMa (ICML 2025) | 32K 토큰에서 **13개 모델 중 11개가 단문 기준선의 50% 아래**. GPT-4o 99.3%@1K → **69.7%@32K** |
| Lost in the Middle (TACL 2024) | 20문서 QA에서 정답 위치가 앞/중간/뒤일 때 GPT-3.5 **75.8% / 53.8% / 63.2%** — 중간에서 **22.0%p** 하락. **단 Chroma의 18개 모델 재측정에서 이 U자 곡선은 재현되지 않았다.** 2023년 모델·다문서 QA 결과이므로 앵커 배치 규칙을 이것 하나에 걸지 않는다 |
| FLenQA | 250토큰 0.92 → **3,000토큰 0.68**. 길이만 늘려도(내용 중복 패딩 포함) 떨어진다. **가장 작은 컨텍스트 한도보다 한 자릿수 아래에서 이미 측정된다** |
| Context Rot (18개 모델, 호출 194,480회) | 방해 정보(distractor) 1개만 넣어도 나빠지고 4개면 누적. 같은 조사에서 **Lost in the Middle의 U자 곡선은 재현되지 않았다** |

우리 조건이 정확히 최악에 해당한다. coding 컨텍스트는 후보 파일 53~811개에서 뽑은 발췌 5~22개이고, 그중 실제로 고칠 곳은 보통 1~2군데다. **나머지 대부분이 방해 정보다.**

#### 얼마나 남길 것인가

| 측정 | 함의 |
|---|---|
| 파일 단위 컨텍스트 절제 실험 (SWE-bench Verified 500문항, 61개 구성) | 파일 컨텍스트가 있고 없고가 **15~17배** 차이(무컨텍스트 3.6% → 파일 단위 56~63%). 같은 논문에서 버그가 실제로 있는 파일은 평균 **1.25개**(범위 1~21). *("최적 6~10개 파일", "줄 단위로 좁히면 나빠진다"는 앞선 초안의 서술인데 리서치 노트에서 확인되지 않았다 — 재확인 전까지 근거로 쓰지 않는다)* |
| Recall Trap | 파일당 1청크 중복 제거로 gold 파일 recall이 80.6% → 87.8%로 **올랐는데 resolve는 떨어졌다.** 끄니까 resolve **+7.6%p (39.2% → 46.8%, n=500, p=0.0003)**. **적은 파일을 깊게가 많은 파일을 얕게를 이긴다** |
| 컨텍스트 표현 절제 | 원본 소스 27/45 vs 자연어 요약 4/45 vs UML 스켈레톤 = 컨텍스트 삭제와 동급 |
| 압축 vs 절단 | LongLLMLingua는 NaturalQuestions 다문서 QA에서 **토큰 약 ¼로 성능 +21.4%**. 즉 무작정 자르는 것보다 골라내는 것이 낫다 |

> **규칙: 요약하지 말고 고른다. 넓게 얕게가 아니라 좁게 깊게 고른다. 앵커는 2~3개, 각 앵커는 원문 줄을 글자 그대로 싣는다.**

#### 무엇을 버렸는지 알린다

MAST 실패 모드 **FM-2.4 정보 은폐(information withholding)**가 실제 측정된 범주다(전체 실패의 1.66%). 분배 에이전트가 전제를 조용히 떨어뜨리면 하류 에이전트는 그것을 알 방법이 없다.

> **규칙: Router는 앵커와 함께 "버린 것 목록"을 한 줄로 낸다.** 예: `"dropped":{"excerpts":8,"chars":41203}`.

#### 출력 형식

```
{"anchors":[
  {"path":"django/core/files/storage.py","lines":[212,229],"why":"FILE_UPLOAD_PERMISSIONS default is read here"}
 ],"dropped":{"excerpts":8,"chars":41203}}
--- ANCHOR 1 VERBATIM (django/core/files/storage.py:212-229) ---
<원문 줄 그대로, 공백·들여쓰기 포함>
--- END ANCHOR 1 ---
```

JSON 한 줄은 계측용이고, `--- ANCHOR n VERBATIM ---` 블록이 Editor가 SEARCH를 복사해 갈 원본이다.

### 3-3. Architect (`Custom` → `Architect`)

| | |
|---|---|
| **받는 것** | 이슈 본문 + 앵커 2~3개 (각 앵커는 경로·줄 범위·원문 hunk). 약 2KB |
| **내는 것** | ledger 줄 → 다시 쓴 실패 명세 한 문장 → 홉 추적 → 고칠 지점 하나 → 손대면 안 되는 것 목록 → 확신도 |
| **절대 안 하는 것** | 패치 작성. 앵커 밖 코드 언급. 질문 |

이 에이전트의 판단 기준은 세 레포를 분석해서 뽑았다. 전문은 `docs/resource/background_research/engineering_doctrine/`에 있고, 여기에는 결론만 적는다.

#### 순서가 규율이다

```
1. 실패가 요구하는 것을 한 문장으로 다시 쓴다
2. 그 값이 앵커를 지나는 경로를 홉으로 따라간다        — 파일·줄, 성공 시, 부재 시, 에러 시
3. 바꿀 함수의 호출자를 앵커 안에서 전부 훑는다
4. 공유 지점 하나를 고른다. 못 고르면 확신도로 말한다
5. 손대면 안 되는 것을 이름으로 적는다
```

**3번이 이 계약의 이유다.** 리포트는 증상 하나를 말한다. 여러 경로가 같은 함수를 지나면 그 함수를 한 번 고쳐야 하고, 리포트가 말한 경로만 고치면 형제 호출자가 깨진 채로 남는다. **그리고 이미 통과하던 테스트가 그 형제를 검사하고 있다.** SWE-bench 채점이 `fail_to_pass` + `pass_to_pass`인 것과 정확히 같은 구조다.

이 지시의 효과가 측정돼 있다 — `transfer()`와 `withdraw()`가 공유 `_debit()`을 지나는 재현 과제에서, 리포트는 transfer만 말하고 채점기는 withdraw를 실행한다.

| 모델 | 근본 원인 수정률 (n=6) |
|---|---|
| Sonnet 4.6 | **1/6 → 6/6** |
| Opus 4.8 | **1/6 → 6/6** |
| Haiku 4.5 | 0/6 → 0~2/6 (잡음) |

**문구가 결정적이다.** 같은 내용을 "흐름을 끝까지 따라가라"는 산문으로 쓴 대조군은 Opus에서 **0/3**이었다. 조작적 지시("호출자를 전부 훑어라")만 6/6을 만들었다. 그래서 Architect 프롬프트는 조언이 아니라 절차로 쓰여 있다.

#### 발췌 경계 규칙 — 이것이 없으면 환각 원천이 된다

원 교리는 *"open every file it passes through"*라고 쓴다. **우리에겐 열 파일이 없다.**

> 경로는 앵커 경계에서 멈춘다. 앵커에 없는 홉은 **모른다**고 표시하고 추측하지 않는다.

같은 단서가 세 곳에 더 걸린다 — 심볼 삭제 제안(모든 참조가 앵커 안에 보일 때만), "계산했는데 안 읽음" 판정(모든 읽기 지점이 보일 때만), 그리고 시그니처 변경(보이지 않는 호출자가 있으므로 **금지**).

#### 발췌만 보고 확인 가능한 실패 패턴

| # | 찾는 것 | 왜 |
|---|---|---|
| 1 | `if x:` 에 `else`가 없다 | 부재가 무엇을 뜻하는지 아무도 정하지 않았다. 파서가 정했다 |
| 2 | 한 함수에서 falsy 반환이 둘, 뜻이 반대인 경로에서 | "확인했고 아니다"와 "확인할 수 없었다"가 같은 값이다 |
| 3 | URL·경로·셸 문자열 안 `${...}` | 미설정 변수가 `"undefined"`로 문자열화돼 **진짜 장애와 같은 catch에 떨어진다** |
| 4 | 여는 연산과 닫는 연산의 개수가 다르다 | 새는 쪽은 거의 항상 에러 경로다 |
| 5 | retry가 붙어 있다 | 멱등성을 몰래 주장한 것이다 |
| 6 | 벽시계로 구간을 잰다 | 시계가 뒤로 점프하면 음수가 된다 |
| 7 | 파생 클래스가 base와 같은 이름의 필드를 선언한다 | 오버라이드가 아니라 섀도잉이다 |

#### 부재 분기를 새로 쓸 때 — 방향을 유도한다

|  | 반경 좁음 | 반경 넓음 |
|---|---|---|
| **되돌릴 수 있음** | 낮춰서 계속 | 낮춰서 계속, 알린다 |
| **되돌릴 수 없음** | 거부, 이유를 호출자에게 | 거부, 알린다 |

**연산마다 새로 유도한다. 직전 답을 물려받지 않는다.** 같은 프로그램이 네 칸을 다 필요로 한다.

#### 구조를 더하는 라이선스

> 새 구조는 **앵커 안에 오늘 존재하는 두 번째 변이점**이 허가한다. 계획이 아니라, 가능성이 아니라, 지금. 두 인스턴스를 앵커 안 줄 번호로 인용하지 못하면 직접 코드를 쓴다.

앵커에 변이점이 둘 들어 있는 경우는 거의 없다. **그래서 이 라이선스는 사실상 추상 추가를 전부 거절한다 — 그게 목적이다.**

#### 확신도 — 첫 번째 컷오프

```
confident   앵커 안에서 실패를 설명하는 단일 지점을 찾았다
partial     후보가 여럿이고 하나를 못 고르겠다 → 최선 하나 + 차점 한 줄
none        앵커에 고칠 자리가 없다 → Editor는 최소 변경만 시도한다
```

`none`이 실제로 나온다. `coding-visible-0001`이 그 경우다(§2-1-1).

#### 이 에이전트가 안 가져온 것

`git log` 기반 판단 전부(히스토리가 없다), churn × complexity 타깃 선정(레포 전체를 못 본다), 결정 기록 작성(파일을 못 쓰고 채점되지도 않는다), "한 줄로 만들어라"(원 교리 자신의 측정에서 **줄 수를 가장 줄인 arm이 경로 탈출 가드를 잘랐다**), "삭제가 추가보다 낫다"(패치에서 삭제는 통과하던 테스트가 의존하는 코드를 없애는 것이다).

### 3-4. Editor (`Developer`)

| | |
|---|---|
| **받는 것** | Router의 앵커 블록 (원문 hunk 포함) 또는 발췌 없는 지문 전문 |
| **내는 것** | `*** PATCH START ***` … `*** PATCH END ***` 사이의 SEARCH/REPLACE 블록 |
| **절대 안 하는 것** | unified diff. 패치 뒤 설명. 마크다운 코드 펜스. 발췌 밖 경로 수정 |

편집 형식 자체가 점수를 좌우한다는 근거가 두 갈래로 있다.

- Aider 실측: 유연한 패치 적용을 끄면 **편집 오류가 9배로 늘었다**. 같은 글에서 GPT-4 Turbo가 편집 형식을 바꾸자 통과율 **20% → 61%**로 뛰었다.
- 형식별 성공률 비교(6개 태스크 평균): 최소 unified diff **19.34**, unified diff **30.28**, 전체 코드 **51.83**, **search/replace 45.89~56.69**, 함수 단위 diff 52.49~57.32. **unified diff가 압도적으로 나쁘다.**

우리 트랙은 SEARCH/REPLACE를 강제하므로 형식 선택의 여지는 없다. 대신 **원문 복사의 정확도**가 전부다. Editor의 `systemPrompt`에 SWE-Edit Editor 규칙 네 줄을 그대로 넣는다.

```
1. SEARCH must match the file content EXACTLY, including whitespace and indentation.
2. Multiple edits mean multiple SEARCH/REPLACE blocks.
3. An empty SEARCH block means the file is created new.
4. Each SEARCH block must be unique within the file. If the text occurs more than
   once, widen it with surrounding lines until it occurs exactly once.
```

4번은 실전에서 자주 빠뜨리는 규칙인데, 이것 없이는 채점기의 `parse_edit_blocks`가 통과해도 실제 적용에서 어긋난다.

여기에 이 채점기 고유의 함정 두 개를 더 넣는다.

**① 구분선 충돌.** `parse_edit_blocks`는 `=======`로 시작하는 줄에서 SEARCH 섹션을 끊는다. 그런데 발췌 안에 그런 줄이 실제로 있다 — `coding-visible-0024`의 `================================= test session starts =========================`. 이 줄을 SEARCH에 복사하면 **에러 없이 조용히** 거기서 잘린다. 규칙: 복사할 줄이 `=` `<` `>` 를 일곱 개 이상 연속으로 시작하면 다른 앵커를 고른다.

**② 빈 SEARCH는 프로그램이다.** LiveCodeBench에서 빈 SEARCH의 REPLACE 본문은 파일이 아니라 **실행되는 프로그램**이다. `grade.py`의 `run_livecodebench`는 `evaluation_mode`가 `functional`인 항목에서도 파일을 실행하고 stdin을 먹인다. 함수만 정의하고 출력하지 않으면 0점이다.

### 3-5. Solver (`Custom` → `Solver`)

| | |
|---|---|
| **받는 것** | math 또는 generic 요청 전문 |
| **내는 것** | math는 `FINAL ANSWER: \boxed{...}`, generic은 `ANSWER: <letter>` |
| **절대 안 하는 것** | 답 후보 여러 개 노출. 답 뒤 설명 |

#### generic에서 추론을 끄면 안 된다

가장 값비싼 함정이다. "객관식이니 답만 뽑자"는 MMLU 시대의 직관이고, MMLU-Pro에는 반대로 적용된다.

| 모델 | MMLU-Pro CoT | Direct | 차이 |
|---|---|---|---|
| GPT-4o | 72.6 | 53.5 | **+19.1** |
| GPT-4-Turbo | 63.7 | 48.4 | +15.3 |
| Llama-3-8B | 35.4 | 31.5 | +3.9 |

산수로 보면, generic 가중치 0.25 × 정확도 손실 10%p = **총점 2.5%p 손실**이다. 그 대가로 아끼는 것은 hidden 698문항 × 약 200토큰 = 약 14만 출력 토큰이다. 나쁜 거래다.

대신 **Chain-of-Draft**를 쓴다. 각 추론 단계를 다섯 단어 이하로 제한하면 CoT의 7.6~20% 토큰(논문 표현은 "as little as 7.6%")으로 정확도를 유지하거나 오히려 올린다(Sports 태스크: CoT 93.2%/189토큰 → CoD 97.3%/14토큰).

다만 반대 증거도 안다. **작은 모델에서는 CoD가 CoT보다 나빴다** — Qwen2.5-3B GSM8K에서 CoT 59.1% vs CoD 43.1%. 그래서 §10-E5에서 direct / CoD / full CoT 세 갈래를 실제로 재고 결정한다.

**측정 전 기본값은 CoD가 아니라 "짧은 단계, 개수 무제한"이다.** 초안 프롬프트는 `five words or fewer, three to six steps`로 한 문항당 최대 30단어를 강제했는데, 이것은 아직 재지 않은 가지를 가중치 0.25 트랙 전체에 하드코딩하는 것이다. 그리고 채점 규칙 2번(*답 블록 앞은 감점 없음*)과도 어긋난다. 그래서 템플릿은 **단계마다 한 절, 필요한 만큼**으로 두고, 상한은 E5가 정한다. 아끼는 대상은 단계 수가 아니라 문장 길이다.

#### 보기 문자를 하드코딩하지 않는다

연습 세트 42문항 실측: 보기 10개가 36건, 나머지는 3·4·7·8·9개다. **"A부터 J 중에 고르라"고 쓰면 보기 3개짜리 문항에서 존재하지 않는 보기를 고른다.** **`option_letters` 필드는 런타임에 안 보인다.** 그 필드는 `raw/generic.items.jsonl`에만 있고 합성된 요청 본문에는 없다. 요청에 실제로 들어오는 것은 `Options:` 블록의 `A.` `B.` … 접두사뿐이다. 그러니 "그 문항의 `Options:` 블록에 적힌 문자 중에서만 고르라"고 지시하고, 검사기도 그 블록을 파싱해서 문자 집합을 만든다.

#### self-consistency는 붓지 않는다

작은 모델 + 어려운 문항에서 다수결은 해로웠다. GPQA Diamond 198문항에서 Qwen2.5-7B는 문항의 **56.6%**, Llama-3-8B는 **65.7%**에서 다수결이 정확도를 낮췄다. 다수결 일치율 게이트도 토큰 엔트로피 게이트도 둘 다 실패했다(차이 0.002 미만).

### 3-6. Reviewer (`Reviewer`) — 내용 + 형식 두 층 검토, 그리고 발행

사용자가 요구한 것은 두 가지였다 — *"아웃풋 형태를 검토하는 에이전트"*, 그리고 *"내부에서 추론이랑 파일 생성만 하다가 아웃풋을 안 내놓는 경우도 감시하는 에이전트"*. 초안은 앞쪽만 구현했다(형식 파서). **이 판은 내용도 본다.**

| | |
|---|---|
| **받는 것** | 직전 태스크의 출력 전문 + 같은 앵커 |
| **내는 것** | ledger 줄 하나(§11-4) → **요구 형식 블록 하나. 그것으로 응답을 끝낸다.** |
| **절대 안 하는 것** | 새 추상 제안. 스타일·명명·길이 지적. 맞는 답을 지어낸 답으로 덮기 |

#### 두 층으로 본다

**층 1 — 내용.** 패치라면: 바꾼 줄이 실패가 요구하는 것에 하나씩 대응하나. 리포트가 말한 경로만 고치고 **형제 호출자를 남겨 두지** 않았나. 앵커 밖 심볼·경로·줄을 만들어 내지 않았나. 시그니처를 넓히지 않았나. 있던 가드를 지우지 않았나. 답이라면: 그 문항의 `Options:` 블록에 있는 문자인가, 값이 요구된 형태인가.

**층 2 — 형식.** §8의 검사 목록이 그대로 이 층이다.

**내용이 먼저다.** 형식만 보는 리뷰어는 *"형식은 완벽한데 형제 호출자를 깨뜨리는 패치"*를 통과시킨다. 그것이 `pass_to_pass` 실패이고, SWE-bench에서는 오답과 같은 0점이다.

#### 왜 이 에이전트가 마지막 웨이브를 혼자 차지하는가

두 가지가 겹친다.

첫째, **채점기가 마지막 웨이브부터 읽는다.** 마지막 웨이브가 리뷰만 하고 답을 다시 싣지 않으면 앞 웨이브의 정답을 못 읽어 간다. 그러니 마지막 웨이브 담당자는 반드시 답 블록을 낸다.

둘째, **실측에서 답이 안 나온 사례가 압도적이다.** 이 PC의 실행 6건 전수 조사에서 채점 가능한 출력은 **0건**이었다. `5e3813da`는 워크스페이스에 완결된 `solution.py`(908바이트)를 써 놓고 마크다운 코드 펜스로 코드를 출력했다. 패치 마커는 없었다. 파일은 만들고 답은 안 낸 것이다.

문헌에도 이름이 붙어 있는 실패다.

| 측정 | 값 |
|---|---|
| MAST FM-3.1 **조기 종료(premature termination)** | 전체 실패의 **7.82%** |
| MAST FM-1.1 **태스크 명세 불이행** | **10.98%** |
| MAST FM-3.2 **검증 없음 또는 불완전** | **6.82%** |
| 최종 답 없이 종료 직접 측정 | 출력 상한 2,048토큰에서 Qwen 수학 응답 **450건 중 49건(10.9%)**. DeepSeek 300건 중 5건(1.7%). 8,192토큰에서는 0건 |
| SWE 에이전트 실패 분해 | **"유효한 최종 diff 없이 종료"가 전체 실패의 13.2%** |

#### 검증은 판단이 아니라 파싱이다

Reviewer는 **판사가 아니라 파서**여야 한다. 근거가 양쪽으로 명확하다.

| 방식 | 측정 결과 |
|---|---|
| 외부 신호 없는 LLM 자기검증 | GSM8K GPT-4 **95.5% → 91.5% → 89.0%**. CommonSenseQA GPT-3.5 **75.8% → 38.1%**. 전 항목이 평평하거나 나빠졌다 |
| 자기 산출물을 읽는 LLM 심판 | 54회 평가 주기에서 에이전트는 **매번 개선을 주장했지만 56%는 실측 변화가 0 이하**였다. 심판을 붙였더니 **채택한 것의 44%가 퇴행**이었고 진짜 개선의 38%를 반려했다 |
| 검증 기준이 산출물 안에서 확인 가능할 때 | **심판의 오류율이 0으로 떨어졌다** |
| 결정론적 감시 + 조건부 조언 | SWE-bench Verified·Pro에서 resolve **평균 +9.9%, 최대 +15.2%**, 문항당 추가 비용 **$0.08** |
| 결정론적 검증 단독 | 실패의 **60% 탐지**(커버리지 검사 포함 시 96%), **오탐 63건 중 0건** |
| 실행 피드백 기반 자기 디버깅 | Spider +2~3%(최난도 +9%), TransCoder·MBPP 최대 +12%. **후보를 10배 더 뽑는 것보다 낫거나 같다** |

> **규칙: 형식은 파서가 보고, 내용은 경계가 그어진 판정으로 본다.** Reviewer 프롬프트의 층 2는 "이 정규식이 매칭되는지 확인하라"이고, 층 1은 "바꾼 줄이 실패에 대응하는가"다. 층 1이 자유 심판이 되지 않게 막는 것이 §3-6의 승인 허가 기준선(80% 확신, `pass`가 기대되는 결과)이다.

우리 채점기의 정규식은 공개돼 있다(`docs/resource/example_task/tools/grade.py:35-38`).

```python
LETTER_RE  = re.compile(r"^\s*ANSWER:\s*([A-Za-z])\s*$", re.MULTILINE)
BOXED_RE   = re.compile(r"FINAL ANSWER:\s*\\boxed\{")
PATCH_START = "*** PATCH START ***"
PATCH_END   = "*** PATCH END ***"
```

`LETTER_RE`가 **줄 전체에 고정**돼 있다는 점이 중요하다. `ANSWER: B — because…`는 매칭되지 않는다. Reviewer의 계약에 이 사실을 그대로 적는다.

#### Reviewer의 네 가지 판정

```
pass      두 층 다 통과              → 블록을 글자 그대로 다시 낸다. 아무것도 안 고친다
form      값은 맞고 형태가 틀렸다      → 형태만 고친다. 값은 안 건드린다
content   층 1이 틀렸고 앵커에 답이 보인다 → 한 번, 최소로 고친다. 재설계하지 않는다
stop      고칠 수 없다               → 지금 가진 것 중 형식이 유효한 최선을 내고 끝낸다.
                                      답이 아예 없으면 **아무것도 출력하지 않는다**
```

**`stop`이 이 스쿼드의 세 번째 컷오프다**(§2-1-1). 그리고 `stop`의 꼬리 — 아무것도 출력하지 않는 것 — 의 이유를 정확히 적는다.

`extract.py:58-75`는 태스크를 훑으면서 `status == "completed"`이고 상태 요약이 아닌 첫 출력을 답으로 삼는다. 그리고 `is_status_summary("")`는 **참**이다. 즉 **Reviewer가 빈 출력을 내면 채점기는 Reviewer를 건너뛰고 직전 태스크의 출력을 읽는다.** math·generic에서 직전 태스크는 Solver이고, Solver는 이미 유효한 답 블록으로 끝냈을 가능성이 높다.

그래서 "뽑을 것이 없으면 트랙 기본값(`ANSWER: A` / `\boxed{0}`)을 낸다"는 초안 규칙은 **기대값이 음수다.**

| | 기본값을 낸다 | 아무것도 안 낸다 |
|---|---|---|
| 직전 출력에 진짜 답이 없었다 | 0점 (`graded` 오답) | 0점 (`extraction_failed`) |
| 직전 출력에 답이 있었는데 Reviewer가 못 알아봤다 | **0점 — 맞는 답을 덮어썼다** | 직전 답이 그대로 채점된다 |

윗줄은 비긴다. 아랫줄에서만 갈리고, 아랫줄이 일어날 확률은 작지 않다. Reviewer는 gpt-oss-120b이고 IFBench 69.5다. 초안의 Qwen3-32B(IFBench 36.33, BFCL Max Delta 15.5)보다 낫지만 0은 아니다. 반대편에서 기본값이 맞을 확률은 보기 10개짜리가 36/42인 이 세트에서 약 0.10~0.14다. 그리고 연습 42문항의 정답 문자 분포는 `G 8, B 7, A 6, H 5, I 5, D 5, J 3, E 2, C 1` — **어느 글자를 고르든 의미 있는 차이가 없다.**

coding은 더 나쁘다. LiveCodeBench는 `created[-1][2]`, 즉 **마지막** 빈 SEARCH 블록만 실행하므로, 빈 기본 블록을 하나 더 내면 Editor가 쓴 프로그램 대신 빈 파일이 실행된다.

#### 승인 허가 — 이게 없으면 리뷰어가 정답을 반려한다

내용까지 보는 리뷰어를 두면 새 실패 모드가 생긴다. **맞는 답을 트집 잡아 망가뜨리는 것.** 그래서 기준선을 프롬프트에 박는다.

> 문제 제기는 그것이 진짜라고 확신할 때만 한다. **"고칠 것 없음"은 기대되는 결과다** — 반대 의견을 지어내지 말고 `pass`로 답하라. 스타일·명명·형식·함수 길이·"테스트를 추가하세요"는 여기서 문제가 아니다.

그리고 아첨 방지 한 줄이 붙는다. Reviewer가 받는 것은 **자신 있게 쓰인 패치**다.

> 확신은 근거가 아니다. 그것이 보이지 않는 코드에 대해 주장하는 바를 받아들이기 전에, 그 주장에 반대하는 가장 강한 논거를 먼저 세워라. 그 논거가 살아남으면 주장이 틀린 것이다.

두 문장 다 `engineering_doctrine/02-mark-pattern.md`에서 왔다.

**남는 것은 진단 가능성 하나인데**, 그것은 응답 본문 안 ledger 줄(§11-4)이 이미 담당한다. `{"a":"Reviewer","verdict":"stop",...}` 한 줄이 남으면 무엇이 일어났는지 알 수 있고, 맞는 답을 덮어쓰지도 않는다.

주최 측 문면 *"a silent zero hides a harness defect behind a team's score"*는 여전히 옳다. 다만 그 문장이 요구하는 것은 **구분 가능한 기록**이지 **지어낸 답**이 아니다.

#### Reviewer의 비용과 위험

Reviewer가 마지막 웨이브가 되면 **답 블록을 통째로 다시 실어야 한다.** coding 패치 재출력은 출력 토큰이 적지 않고, 재출력 과정에서 형식이 깨질 새 기회가 생긴다. 그래서 비용은 "호출 1회"가 아니라 **"호출 1회 + 답 재출력 + 재출력 실패 리스크"**다.

그럼에도 넣는 이유는 실측 6/6이 답을 못 냈기 때문이다. §10-E4에서 Reviewer 유/무를 A/B로 재고, `extraction_failed` 비율이 유의하게 줄지 않으면 뺀다.

#### 절단(truncation) 대응

출력 상한에 걸려 잘리면 그 자체가 `extraction_failed`다. 두 가지로 막는다.

**① 꼬리 예산을 미리 뗀다.** 답 블록이 차지할 토큰을 계산해 출력 상한에서 미리 빼 놓는다. `FINAL ANSWER: \boxed{...}`는 10~20토큰, `ANSWER: X`는 5토큰 안팎, SEARCH/REPLACE 블록은 훨씬 크다.

**② 잘림을 별도 신호로 다룬다.** `finish_reason: "length"`(OpenAI 계열) / `stop_reason: "max_tokens"`(Anthropic 계열)은 "끝났다"가 아니라 "잘렸다"다. 이때는 같은 요청을 반복하지 말고 **"이미 도출한 답의 형식 블록만 출력하라"는 짧은 재출력**을 시킨다.

출력 예산은 되는 대로 줄이면 안 된다. 예산 7단계(64~4,096토큰) × 4개 모델 × 3개 벤치마크, 총 **56,476회 추론** 실험에서 **문항의 3~19%가 예산을 늘렸는데 오히려 나빠졌고**(절단 효과를 통제한 뒤에도), **모델 순위가 예산에 따라 뒤집혔다**(McNemar p < 0.01). 즉 `max_tokens`는 자유롭게 만질 수 있는 손잡이가 아니라 **측정해서 정하는 값**이다(§10-E2).

### 3-7. 형식 제약이 추론을 해치는가 — 정면으로 다룬다

"형식을 강제하면 추론이 나빠진다"는 유명한 결과가 있다. 그대로 인용하면 이렇다.

| 모델 / 태스크 | 자유 형식 | JSON 강제 | 차이 |
|---|---|---|---|
| GPT-3.5-Turbo GSM8K | 76.6% | 49.3% | **−27.3%p** |
| Claude-3-Haiku GSM8K | 86.5% | 23.4% | **−63.1%p** |
| LLaMA-3-8B GSM8K | 74.7% | 48.9% | −25.8%p |
| Gemini-1.5-Flash GSM8K | 89.3% | 89.2% | −0.1%p |

그런데 이 결과에는 강한 반박이 있다. 동일 프롬프트로 다시 돌리면 GSM8K 0.77 → 0.78, Last Letter 0.73 → 0.77로 **오히려 구조화 쪽이 나았다**는 재현 실험이 있고, 원 실험의 방법론 결함 네 가지가 지적됐다(두 조건의 프롬프트가 달랐음, JSON 프롬프트에 스키마가 없었음, 파서로 LLM을 썼음, few-shot 예시가 테스트와 어긋남).

그리고 화해시키는 결과가 있다. 정보량을 맞춘 대조군과 4단계 스키마 복잡도로 다시 잰 실험에서:

- Sonnet은 MATH-Hard에서 **88.7 ± 4.0%(JSON) vs 89.3 ± 1.7%(CoT)** — 사실상 차이 없음
- 작은 모델에서는 손실이 컸고, Haiku의 −36.2%p는 **주로 절단 때문**이었다
- **"먼저 자유롭게 추론하고 나중에 형식을 붙이는" 지연 구조 절제 실험이 손실의 80~87%를 회복시켰다**

**우리 트랙의 형식은 정확히 이 안전한 쪽에 있다.** 응답 전체를 JSON으로 묶는 것이 아니라, 자유롭게 추론한 뒤 마지막 한 줄(또는 마지막 한 블록)만 형식을 지키면 된다. 그리고 채점 규칙이 *"Anything before it is ignored, not penalised"*이므로 앞부분은 형식 제약이 아예 없다.

> **규칙: 형식 제약은 마지막 블록에만 건다. 응답 전체를 구조화하지 않는다.**

한 가지 더. **의미를 보존한 재표현만으로도 형식이 무너진다.** 150개 질의 × 5개 소형 모델 × 4개 태스크(temperature 0) 실험에서, 단답을 요구하는 프롬프트를 내용 보존 방식으로 바꿔 쓰자 응답의 **약 78%가 답 공간을 벗어났고 약 22%만 정답 라벨을 어딘가에 남겼다.** 형식 지시 문구는 실험으로 고정해야지 손으로 다듬으면 안 된다.

| 128 | 8,192 | 16,384 | 8,192 |
| 256 | 4,096 | 8,192 | 1,024 |

**coding 요청은 약 17,900~20,300토큰이다(§1-2). Qwen3-32B는 배치 64에서 16,384로 떨어져, 이 범위 어느 값이든 요청이 안 들어간다.** 그리고 배치 크기는 우리가 아니라 **그 시각 그 엔드포인트를 함께 쓰는 모든 팀**이 정한다. 즉 우리 통제 밖이다.

gpt-oss-120b는 모든 배치 구간에서 **정확히 2배의 여유**를 가진다. 배치 64에서도 32,768이라 이 범위 전체가 들어간다.

그리고 Qwen3-32B FXB에는 **YaRN(컨텍스트 확장 기법)이 컴파일돼 있지 않다** (`rope_scaling=None`). 상류 모델 카드가 말하는 131,072은 이 배포본에 해당하지 않는다.

**low → high가 8~24배다.** 이 표가 §4-2의 강도 배정 근거다.

컨텍스트 한도는 **서빙 시점에 못 바꾼다.** `furiosa-llm serve`에는 `--max-seq-len` 같은 옵션이 없고, `fxb build --max-model-len`으로 빌드 때 굳는다. Furiosa 자체 운영 예시는 gpt-oss-120b를 `--max-model-len 32768`로 빌드한다. **주최 측이 실제로 어떤 값으로 빌드했는지는 `GET /v1/models`의 `max_prompt_len` / `max_context_len`을 한 번 찍어 보면 끝난다.** 온보딩에서 가장 먼저 할 일이다.

### 4-2. 배정

| 에이전트 | 모델 | 배율 | 원하는 추론 강도 | 템플릿으로 표현 가능한가 |
|---|---|---|---|---|
| **Router** | `furiosa-ai/gpt-oss-120b` | ×2 | low | **아니오** |
| **Architect** | `furiosa-ai/gpt-oss-120b` | ×2 | medium | **아니오** |
| **Editor** | `furiosa-ai/gpt-oss-120b` | ×2 | high | **아니오** |
| **Solver** | `furiosa-ai/K-EXAONE-236B-A23B-NVFP4A16` | ×3 | 켬(기본) | 기본값이라 그대로 |
| **Reviewer** | `furiosa-ai/gpt-oss-120b` | ×2 | medium | **아니오** — `/no_think`만 프롬프트에 남아 있다 |

**Reviewer가 Qwen3-32B(×1)에서 gpt-oss-120b(×2)로 올라갔다.** 이유를 적는다. 이 에이전트는 이제 형식만 보는 파서가 아니라 **가중치 0.5짜리 트랙의 내용을 판정하는 마지막 발화자**다. Qwen3-32B의 IFBench 36.33과 BFCL 형식 민감도 Max Delta 15.5(26개 순열에서 70.0~85.5%)는 정확히 이 자리에 나쁜 수치다. 부수 효과로 **다섯 자리 중 넷이 같은 모델이 되어 캐시 조건도 좋아진다**(§7의 4번).

대가는 정확히 이렇다 — Reviewer는 전 트랙 889회 실행 전부에서 돈다. ×1에서 ×2로 올리면 그 소계가 두 배다. §4-4의 절약 단계 S4가 이것을 되돌리는 손잡이다.

**추론 강도를 에이전트별로 지정할 수단이 이 템플릿에 없다.** 바이너리를 뜯어 확인한 것이다. `ModelPreferences`는 5개 필드(`preferredModelId`, `preferredProviderId`, `minContextWindow`, `requiresToolCalling`, `requiresVision`)뿐이고 `AgentSettingsOverrides` 6개 필드(`maxIterations`, `maxToolCalls`, `defaultTimeout`, `contextCompressionThreshold`, `maxTokens`, `allowedPaths`)에도 없다. 추론 강도는 **앱 전역 설정** `inference.defaultReasoningEffort` 하나이고, 이 PC의 현재 값은 **`none`**이다.

결과가 셋이다.

1. **Editor의 `high`는 지금 상태로는 적용되지 않는다.** §4-2가 "SWE-bench 62.4"를 근거로 산 것은 `high`인데, 실제로는 전역 기본값이 걸린다. 이 스펙에서 가장 큰 값을 주장하던 자리가 **표현 수단 없이 서 있었다.**
2. 남은 통로는 **프롬프트 본문**뿐이다. Reviewer의 `/no_think`는 Qwen3 채팅 템플릿이 프롬프트 문자열에서 읽는 소프트 스위치라 작동하고, gpt-oss의 `reasoning_effort`는 그런 소프트 스위치가 없다.
3. 그래서 **온보딩에서 확인할 것이 하나 더 늘었다** — 제출 러너가 모델 호출에 `reasoning_effort`를 어떻게 넣는지, 팀이 그것을 지정할 수 있는지(부록 A-13 #12). 지정할 수 없다면 §4-4의 비용 추정에서 gpt-oss 항목은 전역 기본값 기준으로 다시 계산해야 하고, §10-E6(강도 스윕)은 **실험이 아니라 확인 불가 항목**이 된다.

`minContextWindow`는 넷 다 `null`로 둔다. 이 필드를 읽는 코드가 바이너리에 없고(디스크의 실제 스쿼드 JSON도 전부 `null`), 앱의 `capabilities.db`는 이 세 모델에 대해 **행이 0개**이며, 라우터 카탈로그 `model-metadata.yaml`은 `gpt-oss-120b`의 컨텍스트를 **2048**로 적어 두었다. 즉 이 필터가 언젠가 실제로 동작하면 우리가 원하는 모델을 **배제**하는 쪽으로 동작한다. 그리고 Planner의 모델이 해석되지 않으면 바이너리는 `Planner agent has no usable model - falling back to a simple task split`으로 떨어지는데, 그것이 A-5의 요청 전문 브로드캐스트다. **얻을 것이 0이고 잃을 것이 최악인 필드라 비운다.**

배정 원칙은 하나다. **가중치가 큰 곳에 능력을 사고, 기계적인 일에서 아낀다.**

**먼저 이 배정을 위협하는 주최 측 경고 하나를 정면에 둔다.** 리더보드 Comparability 절 원문이다.

> every run on this page executed under a **per-item wall-clock cap** and a **per-run token cap**, identical for every team … **Two of the three evaluation models are reasoning models — one was measured spending 97% of its output budget on reasoning tokens before it answered — so a token cap bites roughly an order of magnitude harder on a squad built from reasoning models than on one built from an instruct model.**

우리 배정은 다섯 자리 전부가 추론 모델이고, Editor는 강도 `high`(GPQA에서 호출당 평균 약 19,300토큰)다. **캡 값이 공개되지 않았으므로 이 배정은 아직 검증되지 않은 도박이다.** 그래서 순서를 정한다.

1. §9-2 점검표 1번(`GET /v1/models`)과 함께 **첫 실행의 `PublishedCaps`(`per_run_token_cap`, `per_item_wallclock_seconds`)를 읽는다.**
2. 그 값이 나오기 전에는 Editor `high`를 확정하지 않는다. §10-E6이 강도 스윕이고, **캡 초과가 관측되면 E6의 결론과 무관하게 medium으로 내린다.** 잘린 답은 정확도가 아니라 `capped` 0점이다.

#### Router — gpt-oss-120b, low

이유는 능력이 아니라 **컨텍스트 여유**다.

coding 요청은 **약 17,900~20,300토큰**이다. Qwen3-32B는 배치 32에서 32,768, **배치 64에서 16,384로 떨어진다.** 추정 범위의 하한을 써도 안 들어간다. 배치 크기는 그 시각 엔드포인트를 함께 쓰는 전체 팀이 정하므로 우리 통제 밖이고, **배치 64면 coding 요청이 아예 안 들어간다.** gpt-oss-120b는 같은 배치 64에서 32,768이다.

여기에 문헌 근거가 겹친다. RULER 실측(17개 모델)에서 실효 컨텍스트는 광고값의 **½~¼**이고, 우리가 시키는 일 — 발췌 10~22개 중 실제 고칠 1~2군데 찾기 — 은 NoLiMa가 측정한 **비문자적 검색**이다. 32K에서 13개 모델 중 11개가 단문 기준선의 절반 아래로 떨어진 바로 그 태스크다.

**강도는 low다** *(단 §4-2 서두대로 이 값을 템플릿으로 지정할 수단이 없다 — 전역 `inference.defaultReasoningEffort`에 걸린다. 부록 A-13 #12)*. 위치를 짚는 일은 긴 사고가 필요 없고, low는 GPQA에서 평균 약 810토큰만 쓴다(high는 약 19,300). Artificial Analysis 표현으로 low는 *"very concise"*다.

#### Editor — gpt-oss-120b, high

**여기가 벤치마크 40점의 절반이 걸린 자리다.** 그리고 우리 두 코딩 과제에 정확히 대응하는 공개 수치가 있는 모델은 gpt-oss-120b 하나뿐이다.

| | 값 |
|---|---|
| SWE-bench Verified (high) | **62.4** — K-EXAONE 49.4, Qwen3-32B 미공개 |
| **Aider Polyglot (high)** | **44.4** — 다른 두 모델 모두 미공개. **이것이 편집 형식 준수를 재는 유일한 지표다** |
| LiveCodeBench v6 | 81.9 |
| Codeforces Elo (high) | 2463 |

Aider Polyglot이 중요한 이유는 이것이 **"지정된 편집 형식으로 기존 코드를 고치는" 능력**을 재는 벤치마크이기 때문이다. 우리 coding 트랙이 요구하는 것과 같다. 코드를 새로 쓰는 능력(LiveCodeBench)과는 다른 축이다.

**강도는 high다** *(같은 단서가 붙는다 — 부록 A-13 #12가 풀리기 전까지 이 값은 주장이지 설정이 아니다)*. low 47.9 → medium 52.6 → **high 62.4**. low에서 high로 **+14.5%p**다. 토큰은 8~24배 늘지만, 가중치 0.5짜리 트랙에서 SWE-bench 14.5%p는 **총점 7.25%p**다. 이만큼 확실한 거래는 이 스쿼드에 하나뿐이다.

#### Solver — K-EXAONE-236B, 추론 켬

math와 generic은 **합쳐서 벤치마크 가중치의 0.5**인데 **토큰 지출은 전체의 15% 미만**이다. 입력이 300~900자로 짧기 때문이다. 배율 3을 감당할 수 있는 유일한 자리다.

그리고 공개 수치가 K-EXAONE의 손을 들어 준다.

| | K-EXAONE | 차점 |
|---|---|---|
| **MMLU-Pro** (= generic 트랙) | **83.8** | gpt-oss high 80.7. Qwen3-32B는 사후학습 수치 미공개 |
| **AIME 2025** | **92.8** | gpt-oss high 92.5, Qwen3-32B 72.9 |
| LiveCodeBench v6 | 80.7 | — |
| IFEval (prompt-strict) | **89.7** | K-EXAONE이 최고 |
| MMMLU 한국어 | **85.7** | gpt-oss high 82.9 |

덤으로 **SuperBPE 토크나이저**가 있다. 같은 텍스트에 대해 한국어 **−29.0%**, 코드 **−26.7%**, 영어 **−19.6%** 토큰을 쓴다. **배율 3의 실질 부담이 그만큼 줄어든다.**

**추론은 반드시 켠 채로 쓴다.** 끄면 AIME 2025가 **92.8 → 44.6**, LiveCodeBench가 **80.7 → 44.6**으로 절반이 된다. "토큰 아끼려고 추론을 끈다"가 이 모델에서는 성립하지 않는다.

위험도 정확히 적는다.

- **기본으로 thinking이 켜져 있는데 파서는 꺼져 있다고 가정한다.** Furiosa 문서: `--default-chat-template-kwargs '{"enable_thinking": true}'`를 빠뜨리면 raw `<think>...</think>`가 응답에 그대로 실린다.
- **추론이 비표준 `message.reasoning` 필드로 온다.** *"accessing it on a response without reasoning content raises an AttributeError."* Backend.AI GO가 이 필드를 읽는지 **미확인**이다. 안 읽으면 `content`가 비어 나올 수 있다.
- Furiosa 검증 등급이 Performance **EXPERIMENTAL**이다.
- 컨텍스트 262,144은 **배치 1과 4에서만** 나온다. 배치 32면 32,768이다. 우리 math/generic 입력은 1K 미만이라 문제없다.

이 위험이 정확히 §3-6 Reviewer가 막는 것이고, §10-E7에서 검증한다.

#### Reviewer — gpt-oss-120b

**여기서 아끼지 않기로 했다.** 초안은 Reviewer를 Qwen3-32B(×1)에 두고 *"하는 일이 추론이 아니라 고정된 변환"*이라고 적었다. 그 전제가 §3-6에서 바뀌었다 — Reviewer는 이제 형식만 보는 변환기가 아니라 **가중치 0.5짜리 트랙의 내용을 판정하는 마지막 발화자**다.

Qwen3-32B가 이 자리에 나쁜 이유는 공개 수치로 명확하다.

| 지표 | Qwen3-32B | gpt-oss-120b |
|---|---|---|
| IFBench | **36.33** | 69.5 |
| BFCL V4 Max Delta (형식 민감도) | **15.5** | 미공개 |
| 26개 형식 순열에서의 정확도 범위 | **70.00 ~ 85.50%** | 미공개 |

BFCL의 Max Delta 15.5는 *같은 과제를 형식만 바꿔 26번 물었을 때 정확도가 15.5%p까지 벌어졌다*는 뜻이다. 형식을 판정하라고 앉힌 자리에서 형식에 흔들리는 모델을 쓰는 것이 초안의 문제였다.

**대가는 §4-4에 있다** — Reviewer 소계가 5.05M에서 10.10M으로 두 배가 된다. 되돌리는 손잡이가 절약 단계 S4이고, §10-E4가 그 손잡이를 재는 실험이다.

`/no_think`는 **템플릿에서 뺐다.** Qwen3 계열 채팅 템플릿이 읽는 소프트 스위치라서 gpt-oss-120b에서는 아무 일도 하지 않는 죽은 문자열이다. Qwen3-32B로 되돌리는 S4를 실행한다면 그때 Layer 3 첫 줄에 다시 넣는다 — Layer 1 앞에 두면 §7의 2번(다섯 프롬프트의 Layer 1이 바이트 단위로 같아야 한다)이 깨진다. 그리고 그 경우 `/no_think`를 붙여도 Qwen3-32B는 **빈 `<think></think>` 블록을 항상 낸다**(모델 카드 명시). **닫는 `</think>`가 빠지는 사례가 보고돼 있고**(QwenLM/Qwen3#1459) 그러면 서빙 계층이 응답 전체를 추론으로 분류해 `content`를 비운다. §8-X4가 이것을 잡는다.

### 4-3. 세 모델 전부가 빈 출력을 만들 수 있다 — 문서화된 메커니즘

Reviewer가 필요한 이유가 여기서 결정적으로 드러난다. **세 모델 모두, 채점 가능한 `content`가 비거나 오염되는 경로가 공개 이슈로 보고돼 있다.**

| 모델 | 메커니즘 | 출처 |
|---|---|---|
| Qwen3-32B | `enable_thinking=True`면 `/no_think`를 써도 **항상** `<think>…</think>` 블록을 낸다(내용은 빌 수 있음). 모델 카드 명시 | HF 모델 카드 |
| Qwen3-32B | **여는 `<think>`만 내고 닫는 `</think>`를 안 내는 사례** | [QwenLM/Qwen3#1459](https://github.com/QwenLM/Qwen3/issues/1459) |

### 4-4. 비용 추정과 절약 구성

hidden 1회 submission run 기준 개략치다. 문항 수는 목표 범위 중간값(coding 190, generic 573, math 63 × 2회 = 126 실행)을 썼고, 호출당 고정 오버헤드 2,000토큰(부록 A-6 실측 1,400~3,000의 중간)을 포함했다.

**기본 구성 (능력 우선)**

| 에이전트 | 모델·배율 | coding | generic | math | 소계 |
|---|---|---|---|---|---|
| Router | gpt-oss ×2 | 8.96M | 3.44M | 0.71M | **13.11M** |
| **Architect** | **gpt-oss ×2** | **2.28M** | — | — | **2.28M** |
| Editor | gpt-oss ×2 | 6.46M | — | — | **6.46M** |
| Solver | K-EXAONE ×3 | — | 5.80M | 2.25M | **8.05M** |

**4인 구성 대비 32.7M → 약 40.0M, 22% 증가다.** 늘어난 7.3M의 출처는 둘이다 — Architect 신설 2.28M, Reviewer 배율 ×1→×2로 5.05M 추가. Architect 소계는 (입력 약 3,500 + 출력 약 500 + 고정 오버헤드 2,000) × coding 문항 190건 × 배율 2 = 2.28M으로 잡았다. **LiveCodeBench 문항에는 Architect가 안 붙으므로 이 값은 상한이다.**

**절약 구성 (전 에이전트 Qwen3-32B ×1)**

|---|---|---|---|---|
| Router | 4.48M | 1.72M | 0.35M | 6.55M |
| Architect | 1.14M | — | — | 1.14M |
| Editor | 2.47M | — | — | 2.47M |

**기본 구성이 절약 구성의 2.2배다.** 그 2.2배로 사는 것을 정확히 적으면 이렇다.

| 사는 것 | 근거 수치 |
|---|---|
| coding 정확도 | SWE-bench Verified **62.4** (gpt-oss high). Qwen3-32B는 이 벤치마크 수치를 공개한 적이 없다. Aider Polyglot 44.4도 마찬가지 |

**중간 단계 세 개**를 미리 정해 둔다. 순위를 보고 내려간다.

| 단계 | 바꾸는 것 | 절감 | 잃는 것 |
|---|---|---|---|
| S1 | Editor 강도 high → **medium** *(A-13 #12가 풀려야 실행 가능)* | 약 2.9M | SWE-bench 62.4 → 52.6 |
| S2 | Router를 math·generic에서만 Qwen3-32B로… **불가능** (에이전트당 모델은 하나) → 대신 Router 전체를 Qwen3-32B로 | 약 6.6M | 배치 64에서 coding 요청 실패 위험 |
| S3 | Solver를 gpt-oss ×2로 | 약 2.7M | MMLU-Pro 83.8 → 80.7 |

| S5 | 플랜 A에서 Architect를 뺀다 (호출 4회 → 3회) | 약 2.28M (고정 오버헤드가 이미 이 안에 있다) | 형제 호출자를 남겨 두는 실패로 돌아간다. §10-E3b가 이 손잡이를 재는 실험이다 |

**S2가 왜 반쪽인가.** `preferredModelId`는 에이전트당 하나이고, Router는 트랙과 무관하게 전 문항에서 돈다. math·generic 699건에 대해서만 싼 모델을 쓸 방법이 없다. 이것이 "템플릿 하나" 제약이 만드는 실제 비용이고, math·generic에서 배율 2를 무는 **약 4.15M**이 그 값이다.

## 5. 웨이브 설계

웨이브는 `dependsOn` 의존성 그래프의 위상 층이다(부록 A-3-2 실측 확인). 우리가 통제하는 것은 Router가 만드는 `create_task(..., depends_on=[...])` 호출뿐이다.

### 5-1. 플랜 A — 저장소 발췌가 있다 (coding/SWE-bench, 그리고 발췌를 단 `other`)

```
[Router가 60,000자에서 앵커를 뽑아 태스크 설명에 싣는다 — 이것이 계획 단계 그 자체다]
웨이브 0:  T1  Architect   이슈 + 앵커 → 변경 설계 (지점·불변식·확신도)   약 500토큰 출력
웨이브 1:  T2  Editor      설계 + 원문 hunk → SEARCH/REPLACE 블록
웨이브 2:  T3  Reviewer    내용 + 형식 검토 → 최종 패치 블록 발행         ← 태스크 1개
```

**플랜 A만 태스크가 3개다.** `maxTasksPerPlan: 3`이 이 경로에 맞춰 잡힌 값이고, 플랜 B와 C는 2개다. 호출 수는 Planner 1 + 태스크 3 = **4회**.

### 5-2. 플랜 B — 발췌가 없고 답이 코드다 (coding/LiveCodeBench)

발췌 컨텍스트가 없다(요청이 1,999~3,066자뿐). Router는 지문을 통째로 옮긴다.

```
웨이브 0:  T1  Editor      빈 SEARCH 블록으로 새 파일 작성
웨이브 1:  T2  Reviewer    내용 + 형식 검토 → 재발행               ← 태스크 1개
```

**Architect를 붙이지 않는다.** 고칠 기존 코드가 없어서 "어디를 고칠까"라는 질문 자체가 없다. 대신 Architect가 들고 있는 판단 중 이 경로에 필요한 것 — 표준 라이브러리 우선, 서드파티 금지, 최소 구현 — 은 Editor 프롬프트 안에 직접 넣었다.

로컬 채점기는 LiveCodeBench 항목에서 **빈 SEARCH 블록(신규 파일 생성)만** 코드로 인정한다(`grade.py:234-241`). 없으면 `"no new-file block (empty SEARCH) — nothing for the judge to run"`으로 0점이다. 그리고 빈 SEARCH가 여럿이면 **마지막 것만 실행된다**(`grade.py:238`, `created[-1][2]`).

`run_livecodebench`는 `evaluation_mode`가 `functional`인 항목에서도 파일을 **프로그램으로 실행하고 stdin을 먹인다.** 함수만 정의하고 아무것도 출력하지 않는 답은 0점이다. 그래서 Router가 LiveCodeBench 지문을 넘길 때 `## How your solution is run` 절을 포함한 **요청 전문**을 그대로 옮겨야 한다.

### 5-3. 플랜 C — 발췌가 없고 답이 코드가 아니다 (math, generic, 그리고 대부분의 `other`)

```
웨이브 0:  T1  Solver      풀이 + 답 블록
웨이브 1:  T2  Reviewer    내용 + 형식 검토 → 재발행               ← 태스크 1개
```

**웨이브를 늘리지 않는다.** math는 `run_repeats: 2`라 실행이 두 배로 곱해지고, generic은 hidden 문항이 448~698개로 가장 많다. 호출당 1,400~3,000 토큰 고정 오버헤드가 여기서 가장 아프다.

**`other`도 여기로 온다.** 다른 점은 Solver가 답의 형태를 미리 모른다는 것뿐이고, 그래서 Router가 요청 전문을 그대로 옮긴다 — 요청이 자기 답의 형태를 말한 그 문장까지 포함해서. Solver 프롬프트의 `OTHER` 절이 *"다른 트랙의 형식을 갖다 쓰지 마라 — 숫자를 물은 문항에 `ANSWER:` 줄을 붙이면 맞는 값을 틀린 껍데기에 담은 것"*이라고 명시한다.

### 5-4. 조건부 재시도 웨이브는 만들 수 없다

제출 카피는 *"어긋난 지점을 알려준 뒤 다시 쓰게 한다"*고 말한다. 이 플랫폼에서 그 문장이 어디까지 참인지 정확히 적는다.

**플랜 그래프는 실행 전에 고정된다.** Router는 아직 아무 출력도 못 본 상태에서 태스크와 의존성을 정하고, 그 뒤로는 조건 분기가 없다. 따라서 "검사가 실패하면 Editor를 한 번 더 부른다"를 웨이브로 표현할 방법이 없다. 무조건 재시도 웨이브를 넣으면 성공한 문항에서도 호출 하나가 통째로 더 나가고, 그것은 §5-3에서 웨이브를 늘리지 않기로 한 이유와 정면으로 충돌한다.

그래서 "다시 쓰게 한다"는 두 자리로 쪼개진다.

| 자리 | 무엇이 도는가 | 언제 |
|---|---|---|
| **Reviewer 태스크 안** | `form`·`content` 재작성. `maxAgentTurns: 4` 안에서 자기 출력을 §8 체크리스트로 재고 고친다 | 제출 실행 포함 항상 |
| **로컬 러너** | §8 결정론적 검사 전체 + 구체 신호를 붙인 재호출 | 개발·측정 단계에서만 |

로컬 러너 쪽이 문헌이 말하는 +9.9%짜리 장치이고, 제출 실행에서 그것이 허용되는지는 아직 모른다(부록 A-13 #5). **허용되지 않으면 남는 것은 Reviewer 한 자리뿐이다.** 카피의 그 문장은 그 전제 위에서 읽어야 한다.

### 5-5. 실패 전파가 안 된다는 점

공식 문서는 "태스크가 실패하면 뒤 웨이브의 의존 태스크는 자동으로 건너뛴다"고 하지만, 실측에서는 그냥 실행됐다(부록 A-3-3). 즉 **앞 태스크가 실패해도 Reviewer는 돈다.** 이것은 우리에게 유리하다 — Reviewer의 `stop` 판정(답 블록이 아예 없을 때)가 바로 이 상황을 위한 것이다.

## 6. 예산 설정값

`BudgetConfig`는 Squad Template JSON에 들어가지 않는다(부록 A-7). `aigo squad budget set` 또는 대시보드 예산 패널로 따로 넣는다.

**예산은 트랙별로 나눌 수 없다.** 스쿼드 하나에 `BudgetConfig` 하나이고, 하나의 평가 실행이 세 트랙을 전부 돈다. 따라서 **가장 큰 트랙(coding)에 맞춰 한 벌만 정하고**, math·generic의 절약은 예산이 아니라 프롬프트와 웨이브 수로 한다.

### 6-1. 값과 이유

| 키 | AI:GO 기본 | 제안값 | 이유 |
|---|---|---|---|
| `maxTotalTokens` | 100,000 | **120,000** | SWE-bench 문항 하나가 최악일 때: Router 입력 약 20,300 + Architect 왕복 약 3,000 + Editor 12,000 출력 + Reviewer 왕복 약 25,000 + 고정 오버헤드 **4회**. 에이전트가 하나 늘어 90,000에서 올렸다 |
| `maxTokensPerAgent` | 30,000 | **50,000** | Router가 약 20,300을 읽고, Reviewer는 패치를 읽고 다시 쓴다 |
| `maxTokensPerTask` | 10,000 | **40,000** | 제약 `task ≤ agent ≤ total`을 지킨다 |
| `maxConcurrentAgents` | 3 | **1** | 캐시 엔트리는 첫 응답이 시작돼야 생긴다. 실측에서도 어차피 직렬이었다(부록 A-3-3) |
| `maxTasksPerPlan` | 20 | **3** | 플랜 A가 정확히 3개(Architect·Editor·Reviewer)이고 플랜 B·C는 2개다. Router가 그 이상으로 쪼개는 것을 구조적으로 막는다. 앱 기본 Planner 프롬프트의 규칙 1번이 "가장 작게 쪼개라"이므로 이 상한이 실제 방어선이다 |
| `maxPlanIterations` | 3 | **1** | 재계획은 요청 전문을 다시 읽는다. coding에서 2만 토큰가량이 한 번 더 나간다 |
| `maxAgentTurns` | 20 | **4** | 웨이브가 최대 셋이고 에이전트마다 한 턴이면 되므로 4면 여유가 있다. Reviewer가 자기 턴 안에서 형식을 다시 재는 여지도 여기서 나온다 |
| `executionTimeoutSecs` | 1,800 | **900** | 문항 wall-clock 캡 아래로. 실제 캡 값은 미공개 (부록 A-13 #4) |
| `taskTimeoutSecs` | 300 | **120** | |
| `agentIdleTimeoutSecs` | 60 | **45** | |
| `warningThresholdPercent` | 80 | **70** | 토큰 계수가 근사치라 여유가 필요하다 |

검증 제약이 있다(부록 A-7 오류 문자열): `max_tokens_per_task ≤ max_tokens_per_agent ≤ max_total_tokens`. 위 값들은 이 순서를 지킨다.

앱 공식 경고: *"Token counting is approximate and may slightly exceed configured limits before the system detects the overage."* 한도는 항상 여유를 두고 잡는다.

**`maxConcurrentAgents: 1`이 왜 중요한가.** 프리픽스 캐시(같은 앞부분을 다시 계산하지 않고 재사용하는 장치) 엔트리는 **첫 응답이 시작돼야 생긴다.** 같은 문항의 에이전트를 동시에 띄우면 둘 다 캐시 미스가 난다. 실측에서 어차피 직렬로 돌았으므로 잃는 것도 없다.

### 6-2. 포기의 나머지 절반 — 잔액 산수

§2-1-1이 포기를 네 층으로 나눴는데, 그중 4층(예산)을 위 표만으로 채우면 절반만 참이다. `BudgetConfig`는 **한도**이지 **계산**이 아니다. 한도는 초과한 뒤에 멈추고, 그때는 이미 토큰을 쓴 뒤다.

나머지 절반은 로컬 러너가 매 호출 직전에 하는 뺄셈 세 줄이다. LLM 호출 0회.

```
잔액   = maxTotalTokens − 지금까지 쓴 토큰
견적   = 고정 오버헤드(1,400~3,000) + 이 호출의 입력 토큰 + 이 호출의 출력 상한
꼬리   = 답 블록이 차지할 토큰 (generic 약 5, math 10~20, coding은 패치 크기)

if 잔액 < 견적 + 꼬리:  이 호출을 하지 않는다. 지금까지 나온 최선의 답을 형식에 넣어 낸다.
```

세 번째 줄이 핵심이다. **답 블록을 쓸 자리를 남겨 두고 멈춘다.** 예산을 다 쓰고 멈추면 `capped`(팀 책임 0점)이고, 꼬리를 남기고 멈추면 오답일지언정 채점은 된다. 출력 상한 2,048토큰에서 수학 응답 450건 중 49건(10.9%)이 최종 답 없이 끝났다는 측정이 정확히 이 자리를 가리킨다.

**AI:GO 안에서는 이 뺄셈을 표현할 수 없다.** 플랜 그래프는 실행 전에 고정되고 조건 분기가 없다. 그래서 이 층은 **로컬 러너에서만** 돈다 — 즉 개발·측정 단계에서는 작동하고, hidden 제출 실행에서는 `BudgetConfig` 한도와 Reviewer의 `stop` 판정만 남는다. **이 비대칭을 숨기지 않는다.** 제출 실행에서 잔액 산수에 해당하는 것은 §6 표의 `maxTokensPerTask 40,000`이 꼬리 예산을 미리 떼어 놓은 값이라는 사실 하나뿐이다.

## 7. 프롬프트 3층 배치

프리픽스 캐시는 **한 토큰만 달라도 그 뒤가 전부 재계산된다.** 그래서 순서가 전부다.

```
[Layer 1]  대회 컨텍스트 + 출력 계약 + 공통 금칙        ← 전 요청 동일. 캐시 히트 목표
[Layer 2]  이 문항 payload + 발췌                        ← 문항 안에서 공유
────────────────────────────── 캐시 경계 ──────────────
[Layer 3]  이 에이전트의 이번 턴 지시 (짧게)              ← 여기만 새로 계산
```

지켜야 할 것 여섯 가지.

1. **Layer 1을 1,024토큰 이상으로 만든다.** 최소 문턱 미달이면 캐시가 아예 안 걸린다. 짧게 쓰려는 본능과 반대 방향이다. 현재 템플릿의 Layer 1은 9,510자(영문 산문 기준 약 1,800토큰)이고 다섯 에이전트 전부 바이트 단위로 같다 — `sha256`으로 확인한다(§9-2 점검표 8).
2. **Layer 1은 다섯 에이전트의 `systemPrompt`에 바이트 단위로 똑같이 복제한다.** 한 글자만 달라도 깨진다.
3. **같은 문항의 에이전트를 병렬로 띄우지 않는다** (§6, `maxConcurrentAgents: 1`).
4. **모델이 다르면 캐시도 다르다.** KV 캐시는 모델 단위 자원이라 서로 다른 모델 사이에서는 공유되지 않는다. 이 스쿼드는 다섯 자리에 두 모델을 쓴다. gpt-oss-120b를 쓰는 **Router · Architect · Editor · Reviewer 넷 사이에서는** 문항 단위 공유가 성립할 수 있고, Solver(K-EXAONE)만 혼자다. 4인 구성에서 세 모델을 쓸 때보다 이쪽이 캐시에 유리하다 — Reviewer를 Qwen3-32B에서 gpt-oss로 올린 부수 효과다. 모델을 하나로 통일하면 다섯 자리가 전부 공유하지만, 그러면 배치 64에서 coding 요청이 안 들어간다(§12-1).
5. **Layer 1 안 worked example은 그 자체로 추출된다 — 알고 쓴다.** 정답 예시가 실제 마커를 보여 줘야 하므로 피할 수 없다. 모델이 시스템 프롬프트를 통째로 되뱉으면 `ANSWER: C`와 `\boxed{32349}`가 답으로 읽힌다. coding은 안전하다 — `extract_patch`가 `rindex`를 쓰는데 Layer 1의 **마지막** `*** PATCH START ***`는 들여쓴 오답 예시라 블록 0개로 파싱된다(§8 C8). math·generic은 그 방어가 없고, 방어할 방법도 없다. **§8-X5(첫 줄이 유효한 ledger인지)가 이것을 간접적으로 잡는 유일한 장치다.**
6. **문항 사이 캐시 재사용은 기대하지 않는다.** 연습 세트 실측에서 저장소 간 재사용률은 django 2.7%, 나머지 0%였다. 이득은 한 문항 안에서만 난다.

### 구조적 주의 — 이 앱에서는 순서가 뒤집힐 수 있다

AI:GO의 `systemPrompt`는 **에이전트별 필드**다. 실제 토큰 순서는 `[에이전트 systemPrompt][태스크 설명]`이 되므로, 우리가 의도한 `Layer 1 → Layer 2 → Layer 3`이 아니라 **`Layer 1 → Layer 3 → Layer 2`**가 될 가능성이 있다. 그러면 "문항 payload를 여러 에이전트가 캐시로 공유한다"는 계산이 성립하지 않는다.

대응 두 가지.

- Layer 3(에이전트별 지시)을 짧게 유지해 캐시 경계 뒤로 밀리는 양을 줄인다. 현재 길이는 Solver 1,538자 / Editor 2,606자 / Router 3,594자 / Reviewer 3,833자 / **Architect 4,483자**다. Architect가 가장 길고, 그것이 맞다 — 이 에이전트의 판단 절차 자체가 산출물이기 때문이다. 이 텍스트를 Layer 1로 올리면 나머지 넷이 읽지 않을 4,483자를 매 호출 싣게 된다.
- **캐시 절감을 예산에 미리 넣지 않는다.** `GET /api/teams/me/dev-usage`의 `cached_input_share`를 실측하기 전까지는 0으로 계산한다(§10-E8).

### `{{TASK}}`는 정확히 한 번, 맨 뒤에

one-shot 프롬프트의 합성 규칙은 이렇다(`tools/compose.py:31-33` 실측).

```python
body = normalise(one_shot_prompt).replace(PLACEHOLDER, normalise(task_content))
return body.rstrip() + "\n\n" + required_output.rstrip("\n") + "\n"
```

`{{TASK}}`를 두 번 쓰면 문항이 두 번 들어가 **입력 토큰이 2배**가 된다. REQUIRED OUTPUT 블록은 서버가 뒤에 붙이므로 프롬프트에 다시 적지 않는다.

| 14 | 임포트 검증 한도를 넘지 않는가 | 이름 ≤200자, 설명 ≤5,000자, 에이전트 ≤50명, `systemPrompt` ≤50,000자, 도구 목록 각 ≤100개, `category`는 다섯 값 중 하나. 현재 템플릿 최대치는 Architect 프롬프트 13,981자 |

## 10. 측정 계획

### 통계적 바닥

연습 세트가 작다는 것을 잊으면 안 된다.

- generic 개발 세트 28문항 → **1문항이 3.6%p**다(홀드아웃까지 합친 42문항 기준으로도 2.4%p). 두 프롬프트가 1문항 차이면 같은 프롬프트다.
- coding holdout 7문항 → **1문항이 14.3%p**다. coding 결과는 방향만 본다.
- 같은 프롬프트·같은 모델로 두 번 돌려도 답이 갈리는 것이 관측됐다(`run_repeats: 2`가 있는 이유이기도 하다). **크기는 아직 안 쟀다** — E0에서 같은 문항 10건을 2회씩 돌려 잡음 바닥부터 정한다. 그 값보다 작은 차이는 차이가 아니다.

### 필수 작업 — 실험이 아니다

**검사기 회귀 테스트.** §8의 결정론적 검사를 연습 세트 121문항 전부에 돌려 **정상 출력을 반려하는 비율을 0에 가깝게** 만든다. 결정론적이라는 말은 틀리면 항상 틀린다는 뜻이기도 하다. 이 검사기는 단일 실패점이다.

**로컬 coding 정확도를 그대로 믿지 않는다.** `grade.py`는 SWE-bench 항목에 대해 Docker를 안 돌리므로 `format_ok`(`correct = None`)를 내고, `grade.py:270`의 `if correct is not None`이 그 행들을 **정확도 분모에서 통째로 뺀다.** 즉 로컬 "coding 정확도"는 LiveCodeBench 7건과 추출 실패한 SWE-bench 항목만으로 계산된 숫자다. SWE-bench 쪽에서 로컬이 답할 수 있는 것은 **형식이 파싱되는가**까지이고, 그 이상은 제출해야 안다.

## 11. 시각화 산출물 계약 — 30점 축

이 장이 이 문서에 늦게 들어왔다. 그전까지 이 스펙은 100점 중 70점(벤치마크 40 + 토큰 효율 30)만 다뤘다.

### 11-1. 무엇이 채점되는가

주최 문면 그대로다.

> Scores will be awarded based on how effectively the **Trace, represented as log (text) data**, is visualized with consideration for **observability, interpretability, traceability, explainability, clarity, and insightfulness**.

그리고 산출물 목록에 이렇게 적혀 있다 — *"Interactive visualization (web, animation generator, etc.) of squad's problem-solving processes."* **선택 사항이 아니라 두 산출물 중 하나다.**

여섯 축 중 다섯(observability, traceability, interpretability, explainability, clarity)은 트레이스 뷰어를 제대로 만들면 채워진다. **점수가 갈리는 곳은 insightfulness 하나다.** AI:GO 앱에 이미 있는 화면 — 스윔레인, 칸반, 활동 피드, 예산 미터 — 을 다시 그리면 감점은 없고 가점도 없다.

### 11-2. 산출물 B는 이미 있다

`viz/trace-visualizer.html`. 단일 HTML 파일, 백엔드 없음, CDN 없음, 네트워크 요청 0. AI:GO **워크스페이스 폴더**를 고르면 실행 목록이 뜬다. `viz/src/app.html`이 원본이고 `viz/tools/build.sh`가 산출물을 만든다.

읽는 파일: `history.json`(필수 — 응답 본문 `tasks[].output`), `events.jsonl`(필수 — 웨이브 구조, `plannerWarning`, 토큰 시계열), `.squad.json`(스쿼드 구성·모델·시스템 프롬프트), `tasks/*.json`(`dependsOn`), `artifacts/*`.

**아직 안 된 것 하나 — generic 판정이 없다.** 뷰어가 아는 답 계약은 `patch`와 `boxed` 둘이고, `letter`는 *"계약을 몰라 판정 보류"*로 처리한다. generic은 hidden 448~698문항에 가중치 0.25다. §8의 G1~G3(줄 전체 고정, `Options:` 블록에서 파싱한 문자 집합, 한 글자)을 뷰어에 넣기 전까지는 **산출물 B가 완성됐다고 말하면 안 된다.**

**이 스펙과 뷰어 사이에 계약이 없었던 것이 문제였다.** 아래가 그 계약이다.

### 11-3. 플랫폼 로그가 비어 있다 — 실측

부록 A-10에서 확인한 것을 여기 다시 적는다. 시각화 관점에서는 이것이 전부이기 때문이다.

| 필드 | 실측 |
|---|---|
| `perAgentTokenUsage` | 8개 실행 전부 `{0, 0}` |
| 태스크 `tokenUsage` | 20건 전부 `0` |
| 태스크 `result` / `error` / `artifacts` | 20건 전부 `null` / `null` / `[]` (실패한 태스크 포함). 뷰어는 더 큰 스냅샷에서 25건 전부로 셌다 — 표본이 다르고 결론은 같다 |
| `plans/` | 항상 비어 있음 |
| **어느 모델이 이 태스크를 돌렸는가** | **로그에는 안 남는다.** `.squad.json`의 `preferredModelId`로 설정값만 유추할 수 있고, 그 태스크가 실제로 어느 모델에 갔는지는 알 수 없다 |
| Planner 호출의 토큰 | 집계에서 통째로 빠진다 (49초 작업, 토큰 이벤트 0건) |

그래서 뷰어가 **못 그리는 화면이 다섯 개**다 — 캐시 히트 곡선, 모델별 비용, 태스크별 토큰, 에이전트별 토큰(뷰어가 추정치로 대신 그린다), 확신도 캘리브레이션.

그리고 결정적인 것: **hidden 제출 실행의 워크스페이스는 우리 손에 없다.** 포털의 `breakdown`은 문항 단위로 쪼개 주지 않는다. 즉 채점되는 그 실행에 대해서는 `history.json`도 `events.jsonl`도 없다.

> **결론: 채점되는 실행의 per-item 트레이스는 스쿼드가 자기 응답 본문 안에 쓴 것만 남는다.** 이것이 ledger 줄이 장식이 아니라 유일한 채널인 이유다.

**단서를 정확히 단다.** "남는다"와 "우리가 읽을 수 있다"는 다르다. 포털 API에서 확인된 반환 스키마 어디에도 **스쿼드 출력 텍스트를 돌려주는 필드가 없다** — `ItemOutcomeView`는 `item_id`·`status`·`failure_kind`·`owner`·`question`까지고, `PublicItemLine`은 `item_id`·`track`·`outcome`·`score`·`subject`·`disclosure`다. 즉 hidden 실행의 응답 본문을 우리가 다시 읽을 경로는 **아직 확인되지 않았다**(부록 A-13 #11).

그러니 ledger 줄의 값은 두 단계로 갈린다. **확실한 것** — 개발·측정 실행(로컬 워크스페이스가 우리 손에 있는 실행)에서 모델명·확신도·분기 선택을 로그가 못 주는 자리에 채워 넣는다. 시각화의 재료 대부분이 여기서 나온다. **조건부인 것** — hidden 실행까지 커버하려면 A-13 #11이 열려야 한다. 열리지 않으면 hidden 실행에 대해 우리가 보여줄 수 있는 것은 포털이 주는 집계뿐이다. 비용이 총액의 0.24%라 어느 쪽이든 넣는 것이 맞지만, **피치에서 "채점된 실행의 트레이스"라고 말하려면 그 전에 #11을 확인해야 한다.**

### 11-4. ledger 줄 — 스쿼드가 시각화에 넘기는 것

세 트랙 공통 규칙 2번(*답 블록 앞은 무시되고 감점되지 않는다*)이 만드는 공짜 자리다. 모든 에이전트가 출력 **첫 줄**에 압축 JSON 한 줄을 쓴다.

| 에이전트 | 줄 | 채우는 구멍 |
|---|---|---|
| Router | `{"a":"Router","track":"coding|math|generic|other","excerpts":true,"tasks":3}` | **4분류 결과**, 발췌 유무, **분해 깊이**(첫 번째 컷오프). `other`가 얼마나 오는지가 이 필드 하나로 집계된다 |
| Router (coding) | 태스크 설명의 `{"anchors":[...],"dropped":{...}}` | 무엇을 버렸는지 |
| Architect | `{"a":"Architect","confidence":"partial","site":"django/core/files/storage.py:212"}` | **확신도**(두 번째 컷오프)와 고른 지점 |
| Editor | `{"a":"Editor","kind":"swebench","edits":2,"site":"..."}` | 편집 규모, 실제로 손댄 경로 |
| Solver | `{"a":"Solver","track":"math","conf":0.72}` | **확신도 — 캘리브레이션 곡선의 유일한 입력** |
| Reviewer | `{"a":"Reviewer","verdict":"form","track":"generic","fix":"stripped trailing text"}` | **판정**(세 번째 컷오프)과 무엇을 고쳤는지 |

이 여섯 줄이 모이면 **포기 사슬 네 층 중 셋이 문항마다 기록된다.** §11-6의 포기 시점 곡선이 그 위에서 그려진다.

비용은 에이전트당 출력 토큰 약 30개다. SWE-bench 문항은 호출 4회, 나머지는 3회이므로 889회 실행 기준 약 0.09M — §4-4 총액의 0.3% 미만이다.

지켜야 할 것 세 가지. **① 한 줄이다** — 줄바꿈이 들어가면 파싱이 깨진다. **② 답 마커를 그 안에 쓰지 않는다** — `ANSWER:`가 줄머리에 오거나 `FINAL ANSWER: \boxed{`가 나오면 채점기가 그것을 답으로 읽을 수 있다. **③ `**Execution`으로 시작하지 않는다** — `extract.py`가 출력 전체를 상태 요약으로 분류한다.

세 트랙 전부에서 ledger 줄이 추출을 깨지 않는 것은 `grade.py` 함수로 직접 확인했다.

### 11-5. 주최 측 용어를 그대로 쓴다

`Outcome`(`graded` / `extraction_failed` / `capped` / `grader_error` / `infrastructure_failed`), `ItemStatus`(`ok` / `capped_tokens` / `capped_wallclock` / `error`), `FailureKind`(`infrastructure` / `upstream_error` / `token_cap` / `wallclock_cap` / `runner`), `FailureOwner`(`team` / `policy` / `configuration` / `organizer`).

심사위원이 화면을 읽는 데 드는 학습 비용이 0이 된다. 그리고 **`grader_error`와 `infrastructure_failed`는 순위 분모에서 빠진다** — 우리 잘못이 아닌 0과 우리 잘못인 0을 화면에서 갈라 보이는 것 자체가 이 트랙을 읽었다는 증거다.

주의 두 가지.

**① 로컬 `grade.py`는 이 다섯 중 `graded`와 `extraction_failed` 둘만 내고, 여기 없는 `format_ok`를 하나 더 낸다**(§10 참고). 화면에서 로컬 판정과 포털 판정을 같은 색으로 칠하면 안 된다.

**② 현재 뷰어가 이 어휘를 아직 안 따른다.** `viz/src/app.html`이 쓰는 실패 분류에 `context_overflow`, `rate_limit`, `unclassified`가 있고 소유자에 `—`가 있다. 넷 다 주최 열거형에 없는 값이다. 뷰어 문서는 열거형을 따른다고 적어 놨으니 **문서와 화면이 어긋나 있다.** 주최 값으로 매핑하거나(예: `context_overflow` → `configuration` + `upstream_error`), 화면에 "로컬 확장"이라고 명시해야 한다.

### 11-6. insightfulness — 여기서만 점수가 갈린다

넷이면 충분하다. 전부 이 스펙이 이미 만드는 데이터로 그려진다.

| 화면 | 입력 | 무엇을 보여주나 |
|---|---|---|
| **토큰 대 정답 산점도** | 문항별 (총 토큰, 정오) | 오른쪽 아래 사분면 = 많이 쓰고 틀린 문항. 비용의 대부분이 거기 있다 |
| **포기 시점 곡선** | §10-E2 / E6 스윕 결과 | 지문이 물은 *which ones determine when it is time to give up*에 대한 우리 답. 에이전트가 아니라 곡선으로 답한다 |
| **실패 소유권 흐름도** | 위 어휘 4종 | 팀 책임 0과 주최 책임 0을 갈라 보인다 |
| **웨이브별 한계 수익** | 웨이브 추가 전/후 정확도와 토큰 | Reviewer 웨이브가 값을 하는지를 화면이 스스로 말한다 (§10-E4) |

**반사실 재생**(counterfactual replay — 실제로 일어나지 않은 조건을 가정해 기록 위에 다시 그리는 것)**에는 정직한 이름을 붙인다.** 트레이스에서 Reviewer 구간을 지우고 다시 그리는 것은 ablation이 **아니다.** 화면에는 셋 중 무엇인지 라벨을 단다 — **`Observed replay`**(실제로 일어난 것을 그대로 다시 보여 준다), **`Prefix stop simulation`**(기록된 실행을 중간에서 끊었다고 가정한다. 끊은 뒤는 실제로 안 돌았다), **`Assumption-bound policy simulation`**(정책을 바꿨다고 가정하고 남은 부분을 추정으로 채운다. 추정한 부분을 화면에 표시한다). 진짜 A/B는 재실행이고 그것은 §10-E4다.

중간 태스크 출력도 `docs/resource/example_task/tools/grade.py`로 미리 채점해 둔다. 그러면 슬라이더를 움직일 때 모델을 다시 부르지 않고 정확도가 다시 계산된다. LLM 호출 0회, CPU만 쓴다.

### 12-1. 검토했고 버린 것 — 이유를 남긴다

위 표가 "하면 안 되는 것"이라면, 이쪽은 "해볼 만했는데 이 플랫폼에서 안 되는 것"이다. 나중에 누가 다시 제안할 때 같은 조사를 반복하지 않도록 적어 둔다.

| 버린 것 | 무엇이었나 | 왜 버렸나 |
|---|---|---|
| **적응적 조기 종료** (Beta 사후분포 정지, 엔트로피 게이트, Adaptive-Consistency) | 샘플을 하나씩 뽑다가 확신이 서면 멈춘다. 문헌상 연산 64% 절감, 샘플 7.9배 감소에 정확도 손실 0.1% 미만 | **멈출 샘플 스트림이 없다.** `preferredModelId`는 에이전트당 하나이고 문항당 1샘플이다. 멈출 대상 자체가 존재하지 않는다 |
| **결정론적 Hunk Slicer** | Router가 `{path, 줄 범위}`만 내고, **프로그램**이 60,000자에서 ±50줄을 잘라 Editor에게 준다. LLM이 hunk를 다시 타이핑할 필요가 없어져 coding 문항당 출력 약 2,000토큰이 사라진다 | 태스크 설명과 워커 사이에 **러너가 끼어들 수 있는지 미확인**(부록 A-13 #5). 허용되면 이것이 §3-2보다 낫다. **허용 여부가 확인되면 즉시 재검토할 것** |
| **Metamorphic 검사** (보기 순서 셔플 불변성, 변수명 치환) | 정답 라벨 없이 자기모순을 잡는다. generic에서 보기 순서만 바꿔 두 번 물어 답이 흔들리면 낮은 확신도 | 문항당 호출이 2배가 된다. hidden generic이 448~698문항이라 가장 비싼 자리다. **로컬 검사기에서 무료로 할 수 있는 형태가 있으면(같은 응답 안의 자기모순) §8에 넣는다** |
| **분류 전용 에이전트** | 문항을 coding / math / generic / other 넷으로 나누는 일만 하는 에이전트 | **정보 이득이 0이다.** 이 앱에서 요청 전문을 보는 컴포넌트는 Planner 하나뿐이라(부록 A-6), 분류기를 따로 두면 **Router가 먼저 읽고 분류해야 그 분류기에게 무엇을 복사할지 정할 수 있다.** 게다가 플랜 그래프가 정적이라 분류 결과로 분기를 바꿀 주체도 Router뿐이다. 비용은 호출 1회 × 889실행 × 오버헤드 2,000 × 배율 2 ≈ **3.6M**, 그리고 Planner 실패 시 증발 토큰이 20K 더 늘어난다 |
| **Blind Jury** (독립 solver 둘, 불일치할 때만 승급) | 값싼 확신도 신호 | 두 번째 solver가 문항당 호출 하나다. 그리고 §3-5의 다수결 반증(GPQA에서 56.6~65.7% 문항의 정확도를 낮춤)이 같은 방향으로 작용한다 |
| **전 에이전트 동일 모델** | 모델이 하나면 문항 안에서 다섯 에이전트가 KV 캐시를 공유할 수 있다 | 배치 64에서 Qwen3-32B 컨텍스트가 16,384으로 떨어져 coding 요청이 안 들어간다(§4-1). **캐시 이득보다 무응답 위험이 크다.** 대신 그 대가를 §7의 4번에 명시했다 |

### 13-5. 컨텍스트 선택과 분배

- [Agentless](https://arxiv.org/abs/2407.01489) — 계층적 위치 지정(파일 → 클래스/함수 → 편집 지점) + 수리 + 검증. SWE-bench Lite 32.00%, 문항당 $0.70
- [Loc2Repair](https://arxiv.org/abs/2606.30963) — 파일 단위 위치 지정을 분리했을 때 resolve **44.7% → 48.9/49.1%** (gold 52.4%), **소요 시간도 감소**

- [The Recall Trap](https://arxiv.org/abs/2608.14838) — 중복 제거로 recall 80.6 → 87.8%인데 **resolve는 하락**. 끄니 **+7.6%p (39.2 → 46.8, n=500, p=0.0003)**
- [What context does an agent actually need](https://arxiv.org/abs/2607.09691) — 원본 소스 **27/45** vs 자연어 요약 **4/45**. UML 스켈레톤은 컨텍스트 삭제와 구분 안 됨(p=0.75). 압축 컨텍스트 약 19K 토큰 vs 전체 파일 약 94K
- [Self-Route](https://arxiv.org/abs/2407.16833) — RAG와 긴 컨텍스트 사이 라우팅. Gemini-1.5-Pro **LC 49.70 → Self-Route 46.41을 LC 토큰의 38.39%로**
- [LongLLMLingua](https://arxiv.org/abs/2310.06839) — NaturalQuestions 다문서 QA에서 **토큰 약 ¼로 성능 +21.4%**
- [Chunking strategies for repository-level code completion](https://arxiv.org/abs/2605.04763) — 864회 실험. **교차 파일 컨텍스트 길이가 지배 변수**(2,048 → 8,192에서 +4.2%p). 함수 단위 청킹은 전 전략 중 최하

### 13-13. 표기 규칙

이 문서에서 **미공개**로 적은 것은 찾아봤는데 공개된 수치가 없는 것이고, **미확인**으로 적은 것은 확인할 수 있는데 아직 안 한 것이다. 후자는 전부 부록 A-13에 확인 방법과 함께 정리해 두었다.

2026년 발행 arXiv 프리프린트(2601~2608 번호대)는 동료 심사를 거치지 않았다. **그리고 이 목록의 상당수가 이 저장소의 리서치 노트(`docs/resource/background_research/`)에 흔적이 없다** — 즉 노트를 거치지 않고 이 문서에서 처음 등장한 인용이다. 해당하는 것은 15건 정도이고, 컨텍스트 선택(§3-2)·형식(§3-6)·검증(§3-5)·절단(§3-5) 네 곳에 걸쳐 있다. 이 문서의 주요 설계 규칙 넷이 여기에 닿는다.

**두 가지를 지킨다.** 첫째, §0의 30초 요약처럼 문서 전체를 지탱하는 자리에는 재확인되지 않은 인용을 단독 근거로 두지 않는다. 둘째, 재확인 전까지는 그 숫자를 방향 지시로만 쓰고 절대값으로 인용하지 않는다.

한 가지 더 — §13-6의 문자/토큰 표는 `tiktoken`(`cl100k_base` / `o200k_base`)으로 잰 것이다. **이 둘 중 어느 것도 우리가 쓰는 모델의 토크나이저가 아니다.** §3-2가 "대상 모델의 실제 토크나이저로 세라"고 해 놓고 정작 그 표는 OpenAI 토크나이저로 쟀다. 표는 **언어별 상대 비교**로만 읽고, 절대 토큰 수는 Qwen3 / gpt-oss / K-EXAONE(SuperBPE) 토크나이저로 다시 재야 한다.
