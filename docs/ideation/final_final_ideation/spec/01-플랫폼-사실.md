# 부록 A — Backend.AI GO 스쿼드 플랫폼 실측 사실

이 문서는 스펙 본문(`00-스쿼드-스펙.md`)이 딛고 선 **바닥**이다. 여기 적힌 것은 추론이 아니라 이 PC에 설치된 Backend.AI GO 1.12.1의 실제 파일, 실제 바이너리, 실제 실행 기록에서 직접 확인한 것이다.

각 항목에는 상태 표시가 붙는다.

- **확인** — 실제 파일이나 바이너리 문자열을 직접 읽었다. 경로와 줄 번호를 적는다.
- **측정** — 실제 실행 기록에서 숫자를 뽑았다.
- **추론** — 직접 못 봤지만 구조상 그렇게밖에 될 수 없다. 근거를 적는다.
- **미확인** — 모른다. 확인 방법을 적는다.

조사 대상 경로는 셋이다.

| 대상 | 경로 |
|---|---|
| 앱 번들 | `/Applications/Backend.AI GO.app/Contents/` |

## A-1. 파일이 세 종류다. 어느 것이 무엇인지부터 정리한다

여기서 가장 흔한 오해가 생긴다. `.squad.json`이라는 이름 때문에 "이 파일을 손으로 쓰면 스쿼드가 만들어진다"고 생각하기 쉬운데, **아니다.**

| 파일 | 정체 | 손으로 쓸 수 있나 |
|---|---|---|
| `<워크스페이스>/.squad.json` | 앱이 워크스페이스를 초기화할 때 **써 놓는** 메타데이터 스냅샷 | 아니다 (앱이 만든다) |
| `~/Library/Application Support/ai.backend.go/squads/<uuid>.json` | 앱이 시작할 때 읽는 **진짜 원본** | 가능하지만 `index.json`도 같이 고쳐야 한다 |
| **Squad Template JSON** | `aigo squad template import <파일>` 또는 UI에서 가져오는 **이식용 포맷**. **해커톤 제출물이 이것이다** | **그렇다. 이게 정답 경로다** |

**확인** — 스쿼드 저장소 위치는 앱 로그에 직접 찍혀 있다.

```
~/Library/Application Support/ai.backend.go/logs/backend-ai-go.2026-08-22:75
INFO backend_ai_go_lib::squad::storage: SquadStorage initialized at ".../ai.backend.go/squads"
```

**확인** — 실제 `.squad.json`은 4줄짜리 메타데이터다. `squad/test/.squad.json` 전문(180바이트):

```json
{
  "squadId": "36e6827e-4143-43fc-8815-329b243944bf",
  "squadName": "Full-Stack Dev Squad-test",
  "initializedAt": "2026-08-22T12:01:32.137549+00:00",
  "appVersion": "1.12.1"
}
```

네 번째 파일 이름도 하나 더 있다. `.squad-config.json`은 `aigo squad restore <워크스페이스경로>` 전용 이식 매니페스트이고, `schemaVersion`이 `"1.0"`이어야 한다. **확인** — 바이너리 문자열: `Manifest is missing required 'schemaVersion' field`, `Unsupported manifest schema version 'X'. This application supports version 'Y'`. 이 PC의 두 워크스페이스에는 이 파일이 없다.

## A-2. 제출물의 실체 — Squad Template JSON 스키마

**확인** — 앱 번들에 내장 템플릿 5개가 들어 있다.

```
/Applications/Backend.AI GO.app/Contents/Resources/squad-templates/builtin/
  code-review-team.json       4.6K
  content-team.json           4.4K
  documentation-team.json     4.7K
  fullstack-dev-team.json     4.6K
  research-team.json          4.4K
```

이 5개 파일의 키를 전부 뽑아 합집합을 냈다. **측정** 결과:

```
최상위 키 10개: agents, category, description, i18nKey, icon, id, isBuiltin, name, schemaVersion, suggestedModels
에이전트 키 9개: i18nKey, icon, memoryEnabled, modelPreferences, name, role, systemPrompt, toolConfig, tools
```

**확인** — 바이너리 안의 serde(러스트 직렬화 라이브러리) 구조체 크기 문자열이 이 개수를 뒷받침한다.

```
struct SquadTemplate with 12 elements
struct AgentTemplate with 9 elements
struct ModelPreferences with 5 elements
```

`AgentTemplate`이 정확히 9개이고 실제 파일에서 뽑은 것도 9개다. **즉 에이전트 필드 목록은 완전하다.**

### A-2-1. 최상위 필드

| 필드 | 타입 | 필수 | 값·주의 |
|---|---|---|---|
| `schemaVersion` | number | 아니오 | `1`. 없으면 1로 간주 |
| `id` | string | 예 | 내장은 `builtin-…`, 사용자는 `user-…` |
| `name` | string | 예 | |
| `description` | string | 예 | |
| `icon` | string | 예 | 이모지 |
| `category` | string | 예 | `development` / `content` / `research` / `review` / `custom` 중 하나 |
| `isBuiltin` | boolean | 예 | **가져오기(import) 시 무조건 `false`로 덮어써진다** |
| `suggestedModels` | string[] | 예 | **정보성일 뿐 동작에 영향 없다.** 여기에 모델을 적어도 배정되지 않는다 |
| `i18nKey` | object | 아니오 | 번역 키 |
| `agents` | array | 예 | |

`suggestedModels`가 동작에 영향을 주지 않는다는 것이 실전에서 중요하다. **모델 배정은 오직 `agents[].modelPreferences.preferredModelId`로만 된다.**

### A-2-2. 에이전트 필드 (9개, 완전 목록)

| 필드 | 타입 | 필수 | 값·주의 |
|---|---|---|---|
| `name` | string | 예 | 표시 이름 |
| `role` | **plain string** | 예 | 아래 매핑 규칙 참조 |
| `systemPrompt` | string | 예 | |
| `tools` | string[] | 예 | 레거시 편의 목록 |
| `toolConfig` | object | 아니오 | **있으면 `tools`를 이긴다** |
| `modelPreferences` | object | 아니오 | 아래 5개 키 |
| `memoryEnabled` | boolean | 예 | |
| `icon` | string | 예 | 이모지 |
| `i18nKey` | object | 아니오 | |

**템플릿에는 `settingsOverrides`도 `executionMode`도 없다.** **측정** — 내장 템플릿 5개 전부에서 두 키 모두 부재. 이것이 스펙 본문의 제약 하나를 만든다: 에이전트별 출력 토큰 상한(`maxTokens`)과 컨텍스트 압축 문턱(`contextCompressionThreshold`)은 **템플릿으로 실을 수 없고, 가져온 뒤에 따로 설정해야 한다.**

### A-2-3. `role` 문자열 매핑 규칙

**확인** — 바이너리의 `AgentRole` 열거형은 adjacently tagged(태그 필드와 값 필드가 나란히 붙는 형태)다. 변형 이름 블록 원문:

```
…provisioning AgentRole plannerdeveloperwriter SquadStatus sourceProfileId Squad workspacePath…
```

`reviewer`는 다른 문자열 풀에 따로 저장돼 있다(`…ask_once assigned exceeded sequence toolCall sections hostPath reviewer filePath modelRef…`).

**확인** — 매핑은 **라벨 전체가 정확히 일치할 때만** 알려진 역할이 된다. `fullstack-dev-team.json`을 가져온 실제 결과(`squads/36e6827e-….json`)를 보면:

| 템플릿의 `role` | 변환된 결과 |
|---|---|
| `"Planner"` | `{"type": "planner"}` |
| `"Frontend Developer"` | `{"type": "custom", "value": "Frontend Developer"}` |
| `"Backend Developer"` | `{"type": "custom", "value": "Backend Developer"}` |
| `"Code Reviewer"` | `{"type": "custom", "value": "Code Reviewer"}` |

`"Code Reviewer"`가 `reviewer`로 안 가고 `custom`이 됐다. **부분 문자열 일치가 아니다.** 알려진 역할로 넣으려면 정확히 `Planner`, `Developer`, `Reviewer`, `Writer` 넷 중 하나여야 한다.

### A-2-4. `modelPreferences` — 모델 배정이 실제로 일어나는 곳

**확인** — 바이너리는 `struct ModelPreferences with 5 elements`이고, 필드 이름들이 연속으로 박혀 있다.

```
…disabledTools toolPermissionOverrides customToolConfigs preferredProviderId requiresToolCalling requiresVision systemPrompt instructions…
…preferredModelId minContextWindow modelPreferences tool…
```

| 키 | 타입 | 기본값 | 의미 |
|---|---|---|---|
| `preferredModelId` | string \| null | `null` | **에이전트별 모델 지정.** 실제 값 예: `"unsloth/gpt-oss-20b"` |
| `preferredProviderId` | string \| 생략 | 생략 | 제공자 고정 |
| `minContextWindow` | int \| null | `null` | **이 값보다 작은 컨텍스트 창을 가진 모델은 선택되지 않는다** |
| `requiresToolCalling` | bool | `true` | |
| `requiresVision` | bool | `false` | |

내장 템플릿 5개는 `modelPreferences`에 `requiresToolCalling`과 `requiresVision`만 적어 놨지만, 역직렬화기는 5개 키를 전부 받는다. **따라서 제출용 템플릿에 `preferredModelId`와 `minContextWindow`를 실을 수 있다.**

`preferredModelId`가 `null`이면 `settings.json`의 `defaultModels.agentDefaultModelId`로 떨어진다. **확인** — 이 PC의 `settings.json`에서 그 값은 현재 `null`이다.

### A-2-5. 사용 가능한 도구

**확인** — 앱이 스쿼드 에이전트에게 강제하는 규칙이 바이너리에 문장 그대로 있다.

```
All file tool paths (read_file, write_file, list_files, list_directory, search_files, diff_files)
must be RELATIVE to the workspace root. Do NOT use absolute paths.
```

그리고 차단 규칙:

```
Tool '<이름>' is not available to squad agents: it operates on the host outside the squad workspace
and is blocked for safety. Use the workspace-scoped file tools instead, all relative to the squad
workspace root: 'list_files' to list a directory, 'read_file' to read a file, and 'write_file' to
write a file.
```

**주의 — 위 문구는 차단 안내문이지 도구 목록이 아니다.** 실제로 등록된 워크스페이스 도구는 아홉 개다: `read_file`, `write_file`, `list_files`, `list_directory`, `search_files`, `diff_files`, `read_memory`, `write_memory`, `search_memory`.

차단되는 것은 따로 있다. 호스트로 새는 도구 14개를 이름으로 막는다: `delete_file`, `run_command`, `audio_transcribe`, `create_directory`, `move_file`, `run_shell`, `execute_python`, `search_content`, `pdf_reader`, `csv_reader`, `json_query`, `image_info`, `run_python`, `image_to_base64`.

**`web_search`, `fetch_url`, `http_request`는 이 목록에 없다** — 즉 차단되지 않는다. `enabledTools`에 적으면 제공될 수 있다. 평가 중에는 어차피 쓰지 않지만, "네트워크 도구는 앱이 막아 준다"는 가정은 틀렸다.

**그리고 `disabledTools`를 읽는 코드가 스쿼드 실행 경로(파일 경로가 아니라 코드 경로다)에 없다.** 도구 구성은 `enabledTools`를 받아 호스트 탈출 이름만 걸러 내는 함수 하나가 결정하고, 결과가 비면 아예 도구 없이 모델을 부른다. 그래서 우리 템플릿은 **`enabledTools: []`로 도구를 0개로 만든다.** `disabledTools`에 이름을 나열하는 것은 아무 효과가 없다.

Planner는 이 필터의 영향을 받지 않는다. `create_task` 같은 플래너 도구는 별도 경로에서 만들어지므로 **`enabledTools: []`인 Context Router도 태스크를 만들 수 있다.** 대신 Patcher는 `write_file`을 못 쓴다 — 이것은 의도한 것이다. 실측 6건 중 하나가 답을 내는 대신 워크스페이스에 `solution.py`를 쓰고 끝냈다.

**측정** — 내장 템플릿 5개가 실제로 쓰는 도구는 4개뿐이다: `brave_search`, `list_directory`, `read_file`, `write_file`. 그리고 내장 에이전트 20명 전원이 `memoryEnabled: true`다.

### A-2-6. 임포트 검증 한도 (바이너리 확인)

`validate_template_content`가 강제하는 값이다. 넘으면 임포트가 거부된다.

| 대상 | 한도 |
|---|---|
| `name` | 200자 |
| `description` | 5,000자 |
| `agents` | 50명 |
| 에이전트당 `systemPrompt` | **50,000자** |
| `enabledTools` / `disabledTools` / 그 외 도구 목록 각각 | 100개 |
| `id` | 비어 있지 않고 200자 이하, 제한된 문자셋 |
| `category` | `development` / `content` / `research` / `review` / `custom` **닫힌 열거형.** 다른 값은 파싱 자체가 실패한다 |

`SquadTemplate`의 실제 필드는 12개다 — A-2-1이 적은 10개에 `sourceUrl`, `installedAt`이 더 있다(파서 내부의 `__ignore`는 필드가 아니라 미지 키를 버리는 자리다). **모르는 키는 거부되지 않고 조용히 무시된다** — 최상위와 에이전트 양쪽 다. 즉 스키마에 없는 필드를 넣어도 오류가 안 나고 그냥 사라진다.

## A-3. 실행 모델 — 웨이브는 의존성 그래프의 위상 층이다

### A-3-1. Planner가 태스크를 만들고, 앱이 층으로 나눈다

**확인** — 앱이 Planner에게 주입하는 시스템 프롬프트 원문이 바이너리에 통째로 있다.

```
You are the Planner for squad "<이름>". Your job is to coordinate the team.
## Your Team
## Your Tools
- create_task(title, description, assigned_to, depends_on, priority)  Create and assign a task
- check_task_status(task_id)   Check if a task is complete
- read_task_result(task_id)    Read a completed task's output
- update_plan(plan_id, changes)  Modify the execution plan
- aggregate_results(task_ids)  Combine outputs from multiple tasks
- send_feedback(agent_id, message)  Send feedback to an agent
## Rules
1. Break requests into the smallest reasonable tasks
2. Specify dependencies explicitly (task B depends on task A)
3. Assign tasks matching agent expertise
4. Always create all tasks before execution begins
5. If a task fails, decide: retry, reassign, or modify the plan
6. After all tasks complete, produce a unified final response using aggregate_results
7. Re-planning is limited to <N> attempts per task
## Workspace
The squad workspace is at <경로>
- plans/     Task plans
- tasks/     Task tracking
- artifacts/ Output files
- logs/      Execution logs
## Memory
You can read and write to your memory bank at <경로>/memory/.
Always update your memory with important decisions, patterns, and context.
```

**주목할 점: 이 프롬프트 어디에도 "출력 형식을 지켜라"는 말이 없다.** "가장 작은 태스크로 쪼개라"가 규칙 1번이다. 해커톤 채점 형식과 정면으로 어긋나는 기본값이고, 우리 `systemPrompt`가 이걸 덮어써야 한다.

일반 에이전트에게 주입되는 프롬프트도 있다. **확인**:

```
## Squad Context
You are "<이름>" in squad "<스쿼드명>"
Your role: <역할>
Workspace: <경로>
Available tools: <목록>
## Workspace
You share a workspace with other agents.
- plans/ … tasks/ … artifacts/ … logs/ …
## Important: File Tool Paths
(위 A-2-5의 상대 경로 규칙)
```

의존 태스크의 결과는 고정 제목 아래 붙는다. **확인** — 바이너리 문자열 `## Context from previous tasks:`

### A-3-2. 웨이브는 실제로 위상 정렬 층이다

**측정** — `squad/test_2/logs/events.jsonl` 154번 이벤트:

```json
{"id": 154, "eventType": "squad:plan-ready",
 "payload": {"autoApprove": true, "taskCount": 4,
  "waves": [["ce6a5c3b…", "ec51c1cf…"], ["e7d9920f…"], ["3e5d7a55…"]]}}
```

그리고 `squad/test_2/tasks/3e5d7a55-….json`:

```json
{"title": "Aggregate and produce final answer",
 "dependsOn": ["ec51c1cf…", "e7d9920f…"]}
```

그래프를 그리면 정확히 맞아떨어진다.

```
웨이브 0:  ce6a5c3b  dependsOn []
           ec51c1cf  dependsOn []
웨이브 1:  e7d9920f  dependsOn [ec51c1cf]
웨이브 2:  3e5d7a55  dependsOn [ec51c1cf, e7d9920f]
```

깊이 0 / 1 / max(부모)+1 = 2. **웨이브 = 의존성 DAG(방향 있고 순환 없는 그래프)의 위상 층이다.**

### A-3-3. 문서와 실측이 어긋나는 두 곳

공식 매뉴얼(`https://go.backend.ai/ko/manual/squad/execution/`)은 두 가지를 말하는데 실측은 다르다.

**① "같은 웨이브의 태스크는 병렬 실행된다" — 실측에서는 직렬이었다.**

**측정** — `squad/test_2/logs/6c802677-….jsonl`. 한 웨이브 안 5개 태스크가 배정→완료→배정 순으로 약 300밀리초 간격을 두고 이어진다.

```
11:50:23.441 assigned … 11:50:34.094 completed / 11:50:34.397 assigned …
```

`squad/test/logs/76bb50f0-….jsonl`에서는 웨이브 1의 3개 태스크가 **서로 다른 3명의 에이전트**에게 갔는데도 직렬이었다(09:20:09.18 → 09:20:10.91).

의미: 웨이브는 **순서**를 사는 장치이지 **동시성**을 사는 장치가 아니다. 이는 캐시 관점에서는 오히려 유리하다(동시 요청은 프리픽스 캐시를 깨뜨린다).

**② "태스크가 실패하면 뒤 웨이브의 의존 태스크는 자동으로 건너뛴다" — 실측에서는 그냥 실행됐다.**

**측정** — `squad/test`에서 태스크 `a529b345`가 실패했는데 그 의존 태스크 `e0b4c4cf`가 그대로 실행됐고(그리고 같이 실패했고), `squad:execution-completed`는 여전히 `status: "completed"`, `taskCounts.skipped: 0`으로 보고했다.

의미: **실패가 전파되지 않는다.** 앞 태스크가 실패해도 뒤 태스크는 빈 컨텍스트를 받고 돌아간다. 이 동작이 아래 A-5의 "실패를 컨텍스트로 넘긴다" 문제와 이어진다.

## A-4. 채점기가 답을 찾는 순서 — 이것이 설계를 결정한다

로컬 추출기 `docs/resource/example_task/tools/extract.py`의 `extract()`(58-75행)를 직접 읽었다. 로직은 두 단계다.

```python
def extract(execution, order):
    final = execution.get("finalResult") or ""
    if not is_status_summary(final):
        return final, "aggregated_result"

    tasks = execution.get("tasks", [])
    ranked = sorted(
        enumerate(tasks),
        key=lambda pair: (order.get(pair[1].get("taskId"), 0), pair[0]),
        reverse=True,
    )
    for _, task in ranked:
        out = task.get("output") or ""
        if task.get("status") == "completed" and not is_status_summary(out):
            return out, f"task_output(wave={...}, title={...})"
    return "", "nothing_extractable"
```

그리고 상태 요약 판정(`extract.py:29-35`):

```python
STATUS_SUMMARY = re.compile(r"^\s*\*\*Execution (complete|failed)\*\*\s*—", re.MULTILINE)
def is_status_summary(text):
    if not text or not text.strip(): return True
    return bool(STATUS_SUMMARY.search(text[:200]))
```

읽는 순서를 말로 풀면 이렇다.

1. `finalResult`를 먼저 본다. 이게 `**Execution complete** — …`로 시작하는 상태 요약이 아니면 **그것이 답이다.**
2. 상태 요약이면 태스크들을 `(웨이브 번호, 배열 인덱스)` **내림차순**으로 정렬한다. 즉 **마지막 웨이브의, 배열에서 가장 뒤에 있는** 태스크부터 본다.
3. 그중 `status == "completed"`이고 상태 요약이 아닌 첫 출력을 답으로 삼는다.
4. 아무것도 못 찾으면 `nothing_extractable`.

### `finalResult`는 실측 6건 전부 상태 요약이었다

**측정** — `squad/test/logs/history.json`의 실행 6건 전수 조사:

| 실행 ID | 상태 | 태스크 수 | `finalResult`가 `**Execution`으로 시작? | 길이 |
|---|---|---|---|---|
| `6498a8b2` | completed | 1 | **예** | 133 |
| `a9c80d0a` | completed | 3 | **예** | 264 |
| `561f1cbd` | completed | 1 | **예** | 117 |
| `5e3813da` | completed | 1 | **예** | 118 |
| `51c68753` | completed | 3 | **예** | 536 |
| `76bb50f0` | completed | 3 | **예** | 536 |

`a9c80d0a`의 `finalResult` 전문:

```
**Execution complete** — 3 task(s) processed in 1 wave(s).

1. ✅ **Compute maximum of quadratic**
   Agent: `Backend Developer`
2. ✅ **Check status of max task**
   Agent: `Backend Developer`
3. ✅ **Expand quadratic expression**
   Agent: `Backend Developer`
```

**6건 중 6건.** Planner 프롬프트에 `aggregate_results`가 있는데도 `finalResult`에는 한 번도 LLM 집계 결과가 들어가지 않았다. 앱이 결정론적 템플릿으로 채운다.

**따라서 실질적으로 추출은 언제나 2단계로 떨어진다: 마지막 웨이브의 배열 마지막 태스크.**

### 그래서 나온 두 개의 하드 룰

> **룰 1. 마지막 웨이브에는 태스크가 정확히 하나여야 한다.**
> 여러 개면 배열 인덱스가 큰 쪽이 이기는데, 어느 태스크가 배열 뒤에 놓일지는 Planner가 정하고 우리가 통제할 수 없다.

**측정** — 이 함정이 실제로 발생했다. `a9c80d0a`에서 Planner가 수학 문항 하나를 한 웨이브 3개 태스크로 쪼갰고, 정답 유도는 인덱스 0(`Compute maximum of quadratic`, 909자)에 들어갔는데, 추출기는 인덱스 2(`Expand quadratic expression`, 414자)를 골랐다. 인덱스 1은 `Check status of max task` — 순수하게 낭비된 LLM 호출이다.

> **룰 2. 그 마지막 태스크의 출력이 요구 형식 블록으로 끝나야 한다.**

**측정** — 6건 중 답 블록을 가진 것은 0건이었다. `5e3813da`는 워크스페이스에 `solution.py`(908바이트, 정상적으로 보이는 완결된 프로그램)를 써 놓고 마크다운 코드 펜스로 코드를 출력했다. `*** PATCH START ***` 마커는 없었다. **파일은 만들었는데 채점되는 출력은 없었다** — 사용자가 지목한 바로 그 실패 유형이다.

## A-6. 워커는 원문을 못 본다. Planner가 다시 쓴 설명만 본다

이것이 수학 오답과 형식 소실의 진짜 원인이다.

**먼저 확정된 절반부터.** Planner에게 가는 사용자 메시지는 바이너리에 문자열로 있다 — *"Decompose this request into tasks and assign them to the appropriate agents using the create_task tool. … \nRequest: <text>"*. 즉 **Planner는 요청 전문을 본다.** 이것은 추정이 아니다. 미확인으로 남은 것은 워커 쪽뿐이고, 아래가 그 정황이다.

**측정** — 실행 `13a35667`의 원 요청은 560자짜리 투자 문제였다. Planner가 만든 태스크 4개의 `description`을 실제 태스크 파일에서 읽었다.

```
Calculate periods
  → "Calculate the number of bi-monthly periods in five years (5 years * 12 months/year / 2 months per period)."
Calculate final amount
  → "Calculate the final investment amount using the formula: final = 24000 * (1 + 0.01)^n, where n is the number of bi-monthly periods calculated earlier."
Check periods status
  → "Check status of 'Calculate periods' task"
Aggregate and produce final answer
  → "Aggregate the results from 'Calculate periods' and 'Calculate final amount' and produce the final answer in the required format."
```

**원 문제 지문이 어디에도 없다.** Planner가 숫자를 뽑아 자기 말로 다시 썼다. 그래서 요구 출력 형식(`FINAL ANSWER: \boxed{...}`)도 "in the required format"이라는 말로 뭉개졌고, 최종 답은 32,328(정답 32,348)로 어긋났다.

**추론** — 토큰 산수도 같은 결론을 가리킨다.

| 실행 | 요청 길이 | 호출 수(태스크+Planner) | promptTokens 합 | 호출당 평균 |
|---|---|---|---|---|
| `13a35667` | 560자 (≈160토큰) | 5 | 14,872 | **2,974** |
| `6c802677` | 424자 (≈121토큰) | 6 | 8,237 | **1,373** |

요청이 160토큰인데 호출당 프롬프트가 2,974토큰이다. 요청 원문이 실려 있었다면 이 숫자가 나올 수 없고, 실려 있지 않았다면 나머지는 전부 시스템 프롬프트 + 스쿼드 컨텍스트 헤더 + 메모리 재참조 + 태스크 틀이다.

> **호출당 고정 오버헤드가 1,400~3,000 토큰이다.**
> 150토큰짜리 수학 문항에 대해 이는 **10~20배 증폭**이다. 태스크를 하나 더 만들 때마다 이 오버헤드가 통째로 한 번 더 붙는다.

그리고 폴백 메시지 문장 자체가 반증이 된다. *"Each agent was given the whole request instead"* — **평소에는 주지 않는다**는 뜻이다.

**미확인** — 주최 측 평가 스택에서도 동일한지. 확인 방법: 연습 문항 하나를 실제 스쿼드로 돌리고 `history.json`의 `tasks[].description`에 원문이 그대로 있는지 본다.

## A-9. 메모리는 켜면 호출마다 토큰을 먹는다

**확인** — `~/Library/Application Support/ai.backend.go/settings.json`:

```
memory.maxTokens                = 2000
memory.perAgentReadbackMode     = multiplier
memory.perAgentReadbackMultiplier = 1.0
memory.perAgentReadbackTokens   = 2000
memory.extractionContextWindow  = 10
memory.autoExtractionEnabled    = false        ← 초안이 놓친 값
memory.extractionTriggerInterval = 5
```

공식 매뉴얼(`https://go.backend.ai/ko/manual/squad/workspace-memory/`)에 따르면 `memoryEnabled`가 켜진 에이전트는 태스크 시작 때 메모리 파일을 컨텍스트에 싣고, **N번의 턴마다 앱이 별도 LLM 추출 패스를 돌린다.** 에이전트가 도구를 부르지 않아도 돈다.

**단 이 PC에서는 `autoExtractionEnabled`가 `false`다.** 즉 추출 패스는 지금 꺼져 있고, 켜면 5턴마다 돈다. 그래서 `memoryEnabled: true`의 실제 비용은 **입력 토큰 쪽 한 갈래**이고, 추출 호출은 설정 하나로 되살아나는 잠재 비용이다. 메모리를 끄는 결정 자체는 바뀌지 않는다 — 벤치마크 문항은 서로 독립이라 실을 것이 없다.

정리하면 비용 갈래는 둘인데 지금 살아 있는 것은 하나다.

1. **지금 드는 비용** — 호출마다 최대 2,000토큰의 메모리 재참조 입력
2. **잠재 비용** — `autoExtractionEnabled`를 켜면 `trigger_interval`(기본 5)마다 추가 LLM 호출 1회

벤치마크 문항은 서로 독립이라 누적 학습의 이득이 거의 없다. **기본은 끈다.**

내장 템플릿 5개는 전부 `memoryEnabled: true`다. 이걸 그대로 쓰면 안 된다.

## A-10. 실행 결과가 디스크에 남는 곳

```
squad:planning-started    squad:plan-ready            squad:execution-started
squad:task-wave-started   squad:task-status-changed   squad:agent-state-changed
squad:task-completed      squad:execution-token-usage squad:token-usage-update
squad:aggregation-started squad:execution-completed   squad:workspace-file-changed
```

**웨이브 종료 이벤트는 없다.** 웨이브 완료는 실행 `.jsonl`의 `Wave 1/3 completed` 텍스트로만 확인된다.

### 믿으면 안 되는 필드들

**측정** — 실측에서 항상 비어 있거나 0인 필드:

| 필드 | 관측값 | 진짜 값이 있는 곳 |
|---|---|---|
| `perAgentTokenUsage` | 8건 전부 `{promptTokens: 0, completionTokens: 0}` | 없음. `totalTokenUsage`만 정확하다 |
| 태스크의 `result` | 20개 전부 `null` | `history.json`의 `tasks[].output` |
| 태스크의 `error` | 20개 전부 `null` (실패 태스크 포함) | `history.json`의 `tasks[].error` |
| 태스크의 `artifacts` | 20개 전부 `[]` (파일을 쓴 태스크 포함) | 워크스페이스 파일 직접 확인 |
| 태스크의 `tokenUsage` | 20개 전부 `0` | 이벤트 스트림 |
| `retryCount` | 20개 전부 `1` (실패 3건에도 안 올라감) | 없음 |
| `plans/` 디렉터리 | 항상 비어 있음 | `squad:plan-ready` 이벤트 페이로드 |

**`history.json`의 `tasks[].output`이 에이전트의 실제 답 텍스트가 남는 유일한 곳이다.** 시각화와 로컬 채점의 입력은 여기다.

**측정** — 태스크 실행에 어떤 모델이 쓰였는지는 디스크에 남지 않는다. `sessions/*/*.json`에 `modelId`가 있지만 그것은 태스크 실행과 별개인 직접 채팅 채널이다.

## A-11. CLI로 할 수 있는 것

`aigo` 1.12.1이 `~/.local/bin/aigo`에 설치돼 있다. `aigo squad`의 하위 명령 전체(**확인**, `docs/resource/example_task/reference/aigo-cli-1.12.1-help.txt`):

```
list  create  show  update  delete  restore  workspace  task  memory  session
message  conversation  execute  approve  reject  execution  cancel  files  cat
search  activity  history  analytics  budget  emergency-stop  template  discussion
```

스펙과 직결되는 것들:

```
aigo squad template import <FILE>              템플릿 가져오기
aigo squad template export <ID> [-o FILE]      템플릿 내보내기 — GUI 없이 제출 JSON을 뽑는 경로
aigo squad budget set <SQUAD_ID> <BODY_JSON>   BudgetConfig 설정
aigo squad execute [--auto-approve] [--wait] <SQUAD_ID> <REQUEST>
aigo squad task graph <SQUAD_ID>               의존성 그래프 출력
aigo squad activity [--persisted] <SQUAD_ID>   활동 로그
aigo squad analytics <SQUAD_ID>                토큰·비용·처리량
```

`--persisted` 설명 원문: *"Force reload the persisted `logs/events.jsonl` file from the workspace. Without this flag, only the in-memory buffer is returned, which may be empty after a server restart"* — 서버를 재시작했으면 이 플래그가 없으면 빈 결과가 나온다.

**측정** — 현재 이 PC에서 CLI는 인증에 막혀 있다.

```
$ aigo squad list
Error: Authentication failed: Invalid or missing API key authentication
```

**측정** — 그리고 1.12.1에서 헤드리스(desktop 앱 없이) 실행 시 Planner가 돌지 않는다. `docs/resource/example_task/tools/run_agent_batch.py:4-8`에 기록된 내용: 헤드리스 Management API가 실행을 접수하고 빈 플랜을 쓴 뒤 `executing` 상태에서 `taskCounts.total = 0`으로 영원히 머문다. 라우터 요청 카운터가 움직이지 않으므로 **LLM 호출이 아예 일어나지 않는다.**

**결론: 실제 실행 검증은 데스크톱 앱에서 해야 한다.**
