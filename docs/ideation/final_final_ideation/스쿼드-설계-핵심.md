## 1. 채점 구조 (이것만 알면 된다)

| 항목 | 값 |
|---|---|
| 배점 | 벤치마크 40 + 시각화 30 + 토큰 효율 30 |
| 총점 식 | `0.5×coding + 0.25×generic + 0.25×math` (가중치는 문항 수가 아니라 정확도 계수) |
| 동점 처리 | 1순위 총 토큰이 적은 쪽, 2순위 wall-clock이 짧은 쪽 |
| 채점자 | 항상 프로그램. LLM 심판 없음 |
| 제출물 | Squad Template JSON **1개** + 트랙별 one-shot 프롬프트 3개 |
| 제출 비용 | submit 1회 = 전액, AI:GO test run = 1/5. check는 무료 무제한 |
| 평가 중 도구 | **없음.** 저장소를 뒤지지 않는다. judge가 60,000자로 잘라 넣어준다 |

**토큰 효율은 두 번 작동한다.** 30점짜리 독립 축이면서 40점짜리 축의 동점 처리 1순위다.

### 트랙 성격

| | coding | math | generic |
|---|---|---|---|
| 가중치 | **0.50** | 0.25 | 0.25 |
| hidden 문항 | 140~240 | 60~66 (**×2회 반복**) | **448~698** |
| 문항당 입력 | 60,000자 ≈ 16~20k 토큰 | ~150 토큰 | ~300 토큰 |
| 출력 형식 | `*** PATCH START ***` + SEARCH/REPLACE 블록 | `FINAL ANSWER: \boxed{...}` | `ANSWER: <letter>` |
| 우리 모델 단일 호출 기준선 | LiveCodeBench v6 43.2 / Aider-Polyglot **35.6** | AIME25 61.3 / MATH-500 97.5 | MMLU-Pro 78.4 |
| 어디에 돈을 쓰나 | 입력(캐시로 흡수) | 출력 | 출력 |

**coding 출력은 unified diff가 아니다.** `git diff`를 내면 전 문항 `extraction_failed`가 된다.

### 세 트랙 공통 규칙 두 줄 (설계의 지렛대)

> If more than one appears, **the last one is used**.
> Anything before it is **ignored, not penalised**.

답 블록 앞의 본문은 채점에서 무시된다. 즉 **추론도, 실행 기록도 앞에 써도 감점이 없다.** 다만 토큰은 그대로 든다.

### judge가 답을 읽는 방식 (여기서 사고가 난다)

judge는 AI:GO가 만드는 `**Execution complete** — N task(s)...` 상태 요약을 답으로 인정하지 않고, **마지막 웨이브부터 거꾸로** 태스크 출력을 훑는다.

> **마지막 웨이브의 태스크 출력이 답 블록으로 끝나야 한다.**

마지막 웨이브가 리뷰만 하고 답을 다시 싣지 않으면, 앞 웨이브가 정답을 냈어도 못 읽어간다. 이 한 줄이 "리뷰어를 마지막에 두는 설계"를 사실상 금지한다.

그리고 요청 합성 규칙: `{{TASK}}`를 **정확히 한 번, 프롬프트 맨 뒤에** 둔다. 두 번 쓰면 문항이 두 번 들어가 입력 토큰이 2배가 된다. REQUIRED OUTPUT 블록은 서버가 뒤에 붙이므로 프롬프트에 다시 적지 않는다.

## 2. 효율적인 스쿼드에 필요한 것 다섯 가지

연구가 서로 다른 방향에서 같은 지점을 가리키는 것만 모았다.

### (1) 에이전트를 늘릴 근거는 두 개뿐이다

에이전트를 하나 더 두는 순간 비용이 붙고, 정확도는 자동으로 안 따라온다. 정당한 이유는 두 가지다.

| 분할 축 | 조건 | 측정된 효과 |
|---|---|---|
| **컨텍스트 격리** | 서브태스크가 큰 컨텍스트를 읽지만 본 작업에는 요약본만 필요할 때 | 파일 컨텍스트 유무가 SWE-bench resolve 3.6% ↔ 56~63% (15~17배). 명시적 localization 추가로 44.7% → 48.9% |
| **출력 형식 생성 분리** | "무엇을 고칠까"와 "형식을 정확히 쓰기"가 다른 능력일 때 | SWE-Edit: 편집 성공률 +2.7~18.3%p, resolve +1.4~2.1%p, 비용 −17.9% |

그 외 이유(역할이 있어 보인다, 팀처럼 보인다, 검증자가 있어야 할 것 같다)는 근거가 아니다.

반대 방향 증거도 정확히 알고 있어야 한다.

- Nature Machine Intelligence 2026: SWE-bench Verified에서 단일 에이전트 0.488 vs hybrid 0.481. 예산을 맞추면 hybrid가 턴을 6.2배 썼다. 에이전트가 3~4명을 넘으면 통신 비용이 지배하는 천장이 관측됐다.
- 동일 thinking-token 예산 비교: 정상 컨텍스트에서 단일 에이전트가 모든 비교에서 최고이거나 통계적으로 구분되지 않았다.
- BenchAgent: 단일 74.12%, 최고 MAS 75.56%. 차이 +1.44pp는 1회 실행 노이즈보다 작다.
- MAST(트레이스 1,642개): 실패의 41.77%가 명세 문제, 36.94%가 에이전트 간 정렬 실패. **모델 성능이 아니라 조직 설계가 실패 원인이다.**

### (2) 역할 프롬프트는 정확도를 올리지 않는다

`"You are an expert Python developer."` 같은 문장은 토큰만 쓴다.

- 162개 역할 × 4개 모델 × 2,410문항: persona 추가로 성능이 오르지 않았고 일부는 떨어졌다.
- MMLU-Pro 300문항 × 6개 모델: 6개 중 5개에서 유의미한 개선 없음, **유의미한 악화 9건**. 도메인이 안 맞는 전문가 persona를 주면 한 모델이 문항당 25회 중 10.56회 답변을 거부했다.

**대신 시스템 프롬프트를 출력 계약으로 채운다.** 무엇을 출력하고 무엇을 출력하지 않는지, 그리고 이번 턴에 넘길 것이 정확히 무엇인지.
AI:GO 스키마가 `role` 필드를 요구하므로 라벨은 채우되, 프롬프트에서 그 역할을 연기시키지 않는다.

### (3) 검증자는 LLM이 아니어도 된다

문제 지문이 "which ones verify the results"를 물었다. 우리 답은 "프로그램이 한다"다.

| 방식 | 근거 |
|---|---|
| LLM 자기검증 | 외부 신호 없이 하면 성능이 떨어진다. GSM8K GPT-4 95.5% → 89.0%, CommonSenseQA GPT-3.5 75.8% → 38.1%. 특히 **프롬프트가 이미 정밀하고 명시적일 때 더 나빠진다** |
| 별도 LLM 검증자(GenRM) | 단순 다수결을 따라잡는 데만 최대 8배 연산. 그리고 우리는 검증자를 학습시킬 수도 없다 |
| **결정론적 형식 검증** | SWE-Edit 실측으로 편집 성공률 +2.7~18.3%p. LLM 호출 0회 |

단 재시도할 때 "다시 해봐"는 소용없다. **어느 블록의 몇 번째 줄이 왜 안 맞는지 + 가장 가까운 후보 줄**을 돌려줘야 한다(Aider의 `ApplyError` 되먹임 패턴). 외부 결정론적 신호가 붙으므로 이건 위에서 배제한 자기검증이 아니다.

### (4) 포기는 세 층의 산수로 만든다

s1 논문이 실측했다. 모델은 자기 토큰을 못 세고, 단계 수로 지시하면 "많은 단계 × 짧은 토큰"으로 갈아탄다. 강제 종료만 작동했다.

| 층 | 수단 | LLM 관여 |
|---|---|---|
| 1 | 요청 파라미터 `max_tokens` 하드 캡 | 0 |
| 2 | AI:GO Budget Config (`Max agent turns`, `Max tokens per task`, `Max plan iterations`) | 0 |
| 3 | 러너 산수: `잔액 < 다음 시도 견적`이면 다음 호출을 하지 않는다 | 0 |

**모델의 확신도를 포기 근거로 쓰지 않는다.** 언어로 표현한 확신도는 정답 여부와 거의 무관하게 부풀고, GPQA 실험에서는 다수결 일치율 게이트와 토큰 엔트로피 게이트가 둘 다 실패했다(차이 0.002 미만).

조기 종료는 비용 장치로는 확실하다. 답이 수렴하면 중단하는 방식으로 샘플 수를 최대 7.9배 줄이면서 정확도 손실은 0.1% 미만이었다.

### (5) 캐시는 프롬프트 순서가 전부다

```
[Layer 1] 대회 컨텍스트 + 출력 계약 + few-shot      ← 전 요청 동일. 캐시 히트
[Layer 2] 이 문항 payload + 60,000자 컨텍스트        ← 문항 안 전 에이전트 공유
──────────────────────────────────── 캐시 경계 ────
[Layer 3] 이 에이전트의 지시 (짧게)                  ← 여기만 새로 계산
```

지켜야 할 것:

- Layer 1을 **1,024토큰 이상**으로 만든다. 최소 문턱 미달이면 캐시가 아예 안 걸린다. 짧게 쓰려는 본능과 반대 방향이다.
- Layer 1은 모든 에이전트의 `systemPrompt`에 **바이트 단위로 똑같이** 복제한다. 한 글자만 달라도 깨진다.
- 같은 문항의 에이전트를 **병렬로 띄우지 않는다.** 캐시 엔트리는 첫 응답이 시작돼야 생긴다. `Max concurrent agents`는 2 이하.
- 문항 사이 캐시 재사용은 기대하지 않는다(실측 django 2.7%, 나머지 0%). 이득은 **한 문항 안**에서만 난다.

**주의할 구조적 단서.** AI:GO의 `systemPrompt`는 에이전트별 필드라서 실제 토큰 순서가 `Layer 1 → Layer 3 → Layer 2`가 될 가능성이 있다. 그러면 "문항 안 4에이전트 공유로 입력 1/4" 계산이 성립하지 않는다. Layer 3을 한두 줄로 줄이고, `cached_input_share`를 실측해서 확인해야 한다.

그리고 반대 방향의 힘이 있다. 캐시가 비용을 흡수해도 **길이는 정확도를 깎는다**(context rot, 18개 모델 194,480회 호출). 발췌 10개 중 8~9개가 distractor인 우리 조건이 가장 나쁜 조건이다. 16~20k 구간은 아직 안전하지만(RULER 16k 96.9), 대화 이력이 쌓여 32k, 64k로 밀려가면 곡선이 꺾인다.

## 3. 권장 구조

### 3-1. 단계적으로 올린다

**감으로 5명을 고정하지 말고, 이긴 것만 남긴다.**

| 단계 | 구성 | 상태 |
|---|---|---|
| B1 | Router(Planner) + 트랙별 Solver 3명, 문항당 2 call | **권장 baseline** |
| C1 | B1 + coding에만 Architect / Editor 분리 | 1순위 A/B 후보 |
| C2 | B1 + coding 조건부 Reviewer | 별도 A/B (마지막 웨이브 규칙 주의) |
| C3 | math AIME 문항만 2번째 샘플 | 불일치와 오답의 상관을 확인한 뒤에만 |
| C4 | generic 다중 샘플 / 토론 | 기본 기각 |

C1은 근거가 가장 강하지만 그래도 A/B다. 승급 조건 네 개를 미리 못 박아 둔다.

1. Architect가 파일 경로, **원문 그대로의 줄**, 의도한 변경, 지켜야 할 불변 조건을 손실 없이 넘긴다.
2. Editor가 60,000자를 다시 받지 않아 입력 비용이 실제로 준다.
3. holdout에서 패치 파싱률과 정확도가 합친 solver보다 낮아지지 않는다.
4. 두 번째 호출 비용까지 포함해 파레토 경계가 개선된다.

### 3-2. C1까지 갔을 때의 전체 그림

```
one-shot prompt + item payload
            │
            ▼
      ┌───────────┐  role: Planner (AI:GO가 정확히 1명 강제)
      │  Router   │  출력: JSON 한 줄. max_tokens 소량
      └─────┬─────┘
            │ payload.kind
   ┌────────┼────────────────────┐
   ▼        ▼                    ▼
 CODE      MATH               GENERIC
   │        │                    │
Architect  Solver               Solver
(앵커 2~3개  (단계별 풀이        (Chain-of-Draft
 + why 한 줄) + \boxed{})        3~6줄 + ANSWER: X)
   │        │                    │
Editor   [Preflight M1~M3]   [Preflight G1~G3]
(SEARCH/REPLACE)  │                │
   │             종료             종료
[Preflight C1~C8]
   │
   실패 → 구체 신호 붙여 Editor 재호출 (최대 1회)
   │
   2회 실패 → 포기
   │
[잔액 산수] 잔액 < 견적이면 다음 호출 안 함
```

livecodebench 문항은 컨텍스트가 없으므로 Architect를 건너뛴다.

### 3-3. 에이전트별 계약

| 에이전트 | AI:GO role | 받는 것 | 내는 것 | 절대 안 하는 것 |
|---|---|---|---|---|
| Router | `Planner` | 요청 전체, `payload.kind` | 라우팅 봉투 JSON 한 줄 | 문제 풀이, 요약, fan-out |
| Architect | `Custom` | coding 요청 전체 | 앵커 2~3개(발췌 인덱스, 줄 범위, `why` 한 줄) | **요약.** 원문을 자연어로 바꾸는 순간 SEARCH가 죽는다 |
| Editor | `Developer` | 앵커 주변 발췌 + 원문 hunk | SEARCH/REPLACE 블록 | unified diff, 패치 뒤 설명 |
| Solver | `Custom` | math·generic 요청 전체 | `\boxed{}` 또는 `ANSWER: X` | 여러 답 후보 노출, 답 뒤 설명 |
| Preflight | 에이전트 아님 | 직전 출력 + 원문 발췌 | 통과 / 구체적 실패 지점 | LLM 호출 |

**핸드오프는 요약이 아니라 좌표와 원문을 나른다.** SEARCH 블록은 공백 하나까지 원문과 같아야 하므로 중간에 자연어를 거치면 그 순간 깨진다.

### 3-4. 트랙별 정책 한 장

| 항목 | coding | math | generic |
|---|---|---|---|
| 웨이브 | 2~3 | **1** | **1** |
| 샘플 수 | 1 (재시도 최대 1회) | 1, AIME만 실험 | 1 |
| 추론 | 켬 | 켬 | **켬 (Chain-of-Draft)** |
| `max_tokens` | 2,048~4,096 + 꼬리 예산 | 1,024~2,048 | 512~1,024 |
| `Max agent turns` | 4~6 | 3 | 2 |
| 검증 | Preflight C1~C8 + 1회 재시도 | Preflight M1~M3 | Preflight G1~G3 |
| 아끼는 법 | 캐시로 흡수 | 웨이브를 안 늘림(2회 반복이라 2배) | 짧은 CoT |

`max_tokens`를 4나 32로 내리는 극단 절약은 하지 않는다. 잘리면 `extraction_failed`이고, 그건 **팀 책임**으로 분류돼 점수에 그대로 들어간다. 절약은 `max_tokens`가 아니라 프롬프트("설명 금지, 서두 금지")와 Chain-of-Draft로 한다.

### 3-5. Preflight 검사 목록 (전부 LLM 호출 0회)

**coding**

| # | 검사 |
|---|---|
| C1 | `*** PATCH START ***` / `*** PATCH END ***` 짝. 마지막 것만 유효 |
| C2 | `<<<<<<< SEARCH` / `=======` / `>>>>>>> REPLACE` 세 마커 짝 |
| C3 | 모든 SEARCH 앞에 path 줄. path가 컨텍스트 발췌 집합 안에 있음 |
| C4 | **SEARCH 문자열이 발췌 안에 공백·들여쓰기까지 글자 그대로 존재** |
| C5 | **SEARCH 블록이 파일 안에서 유일함** (여러 곳에 걸리면 반려) |
| C6 | SEARCH가 온전한 줄 단위 (줄 중간에서 시작·끝나지 않음) |
| C7 | 빈 SEARCH가 신규 파일 생성 의도인지 |
| C8 | 마지막 블록이 잘리지 않았는지, 마크다운 펜스가 섞이지 않았는지 |

**math**: `\boxed{}` 존재(마지막 것 사용) / `answer_format: integer`인데 수식·단위·쉼표가 들어갔는지 / 닫는 중괄호 존재.
**generic**: 답 문자가 **그 문항의 `option_letters` 안**에 있는지(보기 수가 3~10개로 들쭉날쭉하다) / 정확히 1개인지.

C4 실패 시 돌려주는 형식:

```
SEARCH block #2, line 3 not found verbatim in excerpt.
Closest line in excerpt (path/to/file.py:127):
    <원문 줄>
Your line:
    <모델이 쓴 줄>
Difference: leading whitespace (4 spaces vs 8 spaces)
```

**Preflight는 단일 실패점이다.** 결정론적이라는 말은 틀리면 항상 틀린다는 뜻이기도 하다. 연습 세트 121문항으로 회귀 테스트를 돌려 **정상 출력을 반려하는 비율을 0에 가깝게** 만들어야 한다.

### 3-6. 예산 초기값

| 설정 | AI:GO 기본 | 제안 |
|---|---|---|
| Max total tokens | 100,000 | coding 80k / math 8k / generic 6k |
| Max tokens per agent | 30,000 | coding 30k, 그 외 3k |
| Max tokens per task | 10,000 | coding 20k / math 2k / generic 1.5k |
| Max concurrent agents | 3 | **2** (캐시 때문에도 낮춰야 함) |
| Max tasks per plan | 20 | 6 |
| Max plan iterations | 3 | **1** |
| Max agent turns | 20 | coding 4~6 / math 3 / generic 2 |
| Task timeout | 300초 | 120초 |
| Warning threshold | 80% | 70% |

AI:GO 공식 경고: 토큰 카운팅은 근사치이고 시스템이 초과를 감지하기 전에 한도를 조금 넘길 수 있다. 여유를 두고 잡는다.

메모리(`memoryEnabled`)는 **기본 끈다.** 태스크마다 메모리 파일이 로드되고 추출 패스가 추가 호출을 만든다. Planner에만 켜서 A/B로 확인한다.
Discussion Room을 쓴다면 `Autonomous` 전략은 금지다. 매 턴 참가자 수만큼 LLM 호출이 추가된다.

## 4. 적용하면 좋은 참신한 구조 일곱 개

전부 근거가 있고, 대부분 다른 팀이 안 할 것들이다.

### (1) 실행 기록을 채점되는 응답 본문 안에 쓴다

"마지막 블록만 채점, 앞은 무시"라는 규칙이 답 블록 앞을 **감점 없는 공간**으로 만든다. 거기에 한 줄 JSON으로 실행 기록을 남긴다.

```
{"a":"Router","lane":"code","budget":18000}
{"a":"Architect","anchors":["astropy/io/ascii/rst.py:27-45"],"conf":0.72}
{"a":"Editor","try":1}
*** PATCH START ***  … 1차 시도 (버려질 예정)  *** PATCH END ***
{"a":"Preflight","fail":"SEARCH_NOT_VERBATIM","block":2}
{"a":"Editor","try":2}
*** PATCH START ***  … 마지막 것 = 실제로 채점되는 것  *** PATCH END ***
```

얻는 것 두 가지.

- **계측 비용 0.** 별도 로거도, 요약 호출도 없다. 재시도가 덧붙이기라 앞 시도가 프리픽스로 남아 캐시도 걸린다.
- **"이 화면이 렌더링하는 바이트가 채점기가 읽은 그 바이트다."** 옆에서 수집한 트레이스는 실제 채점 실행과 어긋날 수 있고 심사위원은 확인할 방법이 없다. 이 방식은 어긋남이 구조적으로 불가능하다.

통제 두 개를 같이 건다. 기록 줄은 JSON 한 줄(약 30토큰)로 제한하고, **꼬리 예산을 예약**해 마지막 블록이 잘리지 않게 한다.

### (2) 무료 반사실 재생기

한 번 녹화하고, 재생은 무한히 한다. 중간 시도마다 로컬 채점기로 점수를 미리 붙여 두면 "n번째에서 멈췄다면 몇 점이었나"가 **모델 호출 없이** 조회된다.

심사위원이 직접 끄는 슬라이더: 최대 시도 횟수, 승급 문턱, 트랙별 예산, 그리고 **에이전트 한 명 제거(무료 ablation)**.

마지막 것이 핵심이다. 설계를 자랑하는 팀은 많고, **자기 설계가 밥값을 하는지 반증 가능한 형태로 보여주는 팀은 드물다.**

정직하게 표시할 한계도 있다. 시도 2가 시도 1의 실패 신호를 보고 쓰였다면, 시도 1을 지운 세계에서 시도 2가 그대로 나온다는 보장은 없다. 학계도 같은 지적을 한다. 재생 기반 개입은 이상적인 개입의 근사이지 정확한 재현이 아니다. **화면에 그대로 적는다.** 한계를 표시한 화면이 표시 안 한 화면보다 심사에서 낫다. 그리고 진짜 ablation은 재실행으로 따로 한 번 확인한다.

### (3) 전 에이전트 같은 모델 고정 (2026년 1월 발견, 잘 안 알려짐)

`Rethinking the Value of Multi-Agent Workflow`(arXiv 2601.12307)의 결론은 두 갈래다.

- 모든 에이전트가 같은 base LLM을 쓰는 **동종(homogeneous) 워크플로**는 단일 에이전트의 멀티턴으로 그대로 재현되고, 그때 이득은 **KV 캐시 재사용**에서 나온다.
- 그리고 결정적으로: **서로 다른 LLM 사이에서는 KV 캐시 공유가 안 된다.**

이 트랙에 옮기면 이렇게 된다. 우리 스쿼드가 노리는 "문항 안 60,000자 캐시 공유"는 **전 에이전트가 같은 모델을 쓸 때만** 성립한다. 어려운 문항만 reasoning 모델로 올리는 cascade는 정확도에는 도움이 될 수 있지만, **그 문항의 캐시 공유를 통째로 날린다.**

그래서 정책은 이렇다. **기본은 instruct 단일 모델 고정.** cascade를 쓴다면 coding처럼 입력이 큰 트랙이 아니라, 입력이 짧아 캐시 이득이 애초에 작은 math AIME 문항에서만 시도한다.

### (4) 분해 깊이 자체를 Router의 결정 변수로 둔다

보통은 "3단 파이프라인으로 간다"를 사람이 미리 정한다. Uno-Orchestra(arXiv 2605.05007)는 **얼마나 쪼갤지, 누구에게 줄지, 예산을 얼마 줄지를 하나의 목적함수로 같이 정한다.** 13개 벤치마크에서 77.0% macro pass@1로 최강 workflow baseline보다 약 16% 높으면서 문항당 비용은 대략 한 자릿수 낮았다.

우리 버전은 학습 없이 간다. Router가 문항 하나를 보고 **깊이를 고른다.**

| 신호 | 배정 |
|---|---|
| `payload.kind`가 generic이거나 math인데 지문이 짧다 | 깊이 1 (Solver 한 번) |
| coding이고 `problem_statement`가 짧고 발췌가 적다 | 깊이 2 (Editor 직행) |
| coding이고 발췌가 많거나 지문이 길다 | 깊이 3 (Architect → Editor) |

**핵심은 깊이가 문항마다 다르다는 것 자체가 시각화 재료라는 점이다.** "우리 스쿼드는 문항 종류에 따라 다른 깊이로 돈다"를 한 화면에 보여주면, 그 화면이 곧 토큰 효율 30점의 논거가 된다.

### (5) Preflight 되먹임 재시도로 LLM 검증자를 대체한다

```
Editor 출력 → Preflight
  ├─ 통과 → 종료
  └─ 실패 → 실패 사유(블록 번호, 안 맞는 줄, 가장 가까운 후보)를 붙여 Editor 재호출 (최대 1회)
             └─ 재실패 → 포기
```

이건 위에서 배제한 자기검증이 아니다. 외부 결정론적 신호가 붙기 때문이다. Aider가 실제로 이렇게 돌고 있고, GenRM보다 훨씬 싸다.

**요구사항 대응.** 문제 지문이 "검증"을 물었으므로 템플릿에는 Reviewer를 남기되, 호출 조건을 "Preflight 2회 실패, coding 한정"으로 좁힌다. 그리고 **Auditor 호출률과 Auditor를 제거했을 때의 점수를 나란히 보여준다.** 요구사항도 만족하고, "검증자를 뒀지만 밥값을 하는지도 측정했다"는 서사가 된다.

주의. Auditor가 마지막 웨이브가 되면 답 블록을 통째로 다시 실어야 하고, 그 과정에서 형식이 깨질 새 기회가 생긴다. Auditor의 비용은 호출 1회가 아니라 **호출 1회 + 답 재출력 + 재출력 실패 리스크**다.

### (6) generic은 Chain-of-Draft로 간다

가장 값비싼 발견이다. "객관식이니 답만 뽑자"는 MMLU 시대의 직관이고 MMLU-Pro에는 반대로 적용된다.

| 모델 | MMLU-Pro CoT | Direct | 차이 |
|---|---|---|---|
| GPT-4o | 72.6 | 53.5 | **+19.1** |
| GPT-4-Turbo | 63.7 | 48.4 | +15.3 |
| Llama-3-8B | 35.4 | 31.5 | +3.9 |

CoT 이득은 모델이 강할수록 크다. 우리 모델의 MMLU-Pro 78.4는 GPT-4o(72.6)보다 높으니 이득 구간의 위쪽에 있을 가능성이 크다.

산수로 보면 이렇다. generic 가중치 0.25 × 정확도 손실 10%p = **총점 2.5%p 손실**. 그 대가로 아끼는 건 hidden 698문항 × 약 200토큰 = 약 14만 출력 토큰이다. 나쁜 거래다.

대안은 Chain-of-Draft다. **각 추론 단계를 다섯 단어 이하로 제한**하면 CoT의 7.6~20% 토큰으로 정확도를 유지하거나 오히려 올린다(Sports 태스크에서 CoT 93.2%/189토큰 → CoD 97.3%/14토큰).

```
<5단어 이하 단계 3~6줄>
ANSWER: X
```

그리고 self-consistency는 generic에 붓지 않는다. 작은 모델 + 어려운 문항에서는 다수결이 문항의 절반 이상에서 해로웠고(GPQA에서 56.6~65.7%), 답 공간이 3~10개로 작아 최빈 오답으로 수렴하기가 특히 쉽다.

### (7) 실패 소유권을 우리가 먼저 분리해서 보여준다

평가 엔드포인트는 간헐적으로 죽는다(한 오후에 5회 관측). 그리고 AI:GO는 실패를 컨텍스트로 넘기는 의미론을 쓰기 때문에, **재시도되지 않은 connect timeout이 "실행 완료, 전 태스크 실패"로 보고된다.** 채점은 그걸 팀의 0점으로 읽는다.

그래서 러너 레벨에서 네트워크 오류와 모델 실패를 분리해 기록하고, 시각화에서 주최 열거형을 그대로 써서 보여준다.

| 어휘 | 값 |
|---|---|
| `Outcome` | `graded` / `extraction_failed` / `capped` / `grader_error` / `infrastructure_failed` |
| `FailureOwner` | `team` / `policy` / `configuration` / `organizer` |
| `FailureKind` | `infrastructure` / `upstream_error` / `token_cap` / `wallclock_cap` / `runner` |

앞의 두 개(`extraction_failed`, `capped`)는 팀 책임이고, 뒤의 두 개는 주최 책임이라 순위 계산 분모에서 빠진다. **이 구분을 화면에 그리는 것 자체가 점수다.**

## 6. 시각화 30점 요약

채점 6축 중 다섯(observability, interpretability, traceability, explainability, clarity)은 잘 만든 트레이스 뷰어면 채워진다. **승부는 insightfulness에서 난다.**

그리고 빈틈이 문서화돼 있다. 5개 관측 도구(LangSmith, Phoenix, Langfuse, LangGraph Studio 등)를 같은 질문으로 비교한 공개 테스트에서 **단일 트레이스 근본원인 규명에 60~90분**이 걸렸다. 진단은 한 줄이다.

> They record the "when," not the "why."

학계 쪽 숫자도 같은 방향이다. 완전한 트레이스를 줬을 때 실패 귀인 정확도가 에이전트 수준 65.9%, 스텝 수준 30.3%였고(TraceElephant, ACL 2026), **입력까지 포함한 완전 관측과 동적 재생이 둘 다 귀인을 개선**했다. 우리가 입력과 출력을 함께 남기고 재생기를 붙이는 이유가 이것이다.

만들 화면:

| 화면 | 무엇을 답하나 |
|---|---|
| 장부 대조 뷰 (좌 `request.txt` 원문 / 우 우리 응답) | 채점된 바이트가 화면의 바이트와 같은가 |
| 앵커 정확도 띠 | Architect가 실제 수정 위치를 짚었나 |
| 패치 해부도 | SEARCH 불일치를 글자 단위로 |
| 낭비 사분면 (x=문항당 토큰, y=정답 여부) | 어디서 토큰을 버렸나. 수직 절단선이 슬라이더 |
| 포기 최적 곡선 | 몇 턴에서 끊는 게 최적인가 |
| 실패 소유권 Sankey | 이 0점이 우리 탓인가 인프라 탓인가 |
| 캐시 히트 곡선 | 프롬프트 순서를 바꿀 때마다 `cached_input_share`가 어떻게 움직였나 |

어휘는 OpenTelemetry GenAI Semantic Conventions 위에 `jxc.*`를 얹는다(`jxc.track`, `jxc.outcome`, `jxc.failure_owner`, `jxc.preflight.check`, `jxc.anchor.hit`, `jxc.graded`). 주최 열거형을 그대로 쓰면 심사위원의 학습 비용이 0이다.

**오프라인 재생이 기본이다.** 데모 중 네트워크가 죽어도 살아남고, 타임라인 스크러빙이 공짜로 따라온다.

## 7. 검증 순서

연습 세트 121문항, test run은 1/5 과금이다. 측정에 투자하는 게 옳다.

| 우선 | 실험 | 변수 | 판정 |
|---|---|---|---|
| 1 | E1 | generic: direct / CoD / full CoT | CoD가 direct보다 유의하게 정확하면 "답만 뽑기" 폐기 확정 |
| 1 | E2 | `max_tokens` 스윕 | 잘림 0%가 되는 최소값 + 여유 |
| 2 | E3 | Architect 유/무 | coding 정확도, 총 토큰, `cached_input_share` |
| 2 | E4 | Preflight 유/무 | `extraction_failed` 비율, 재시도 횟수 |
| 3 | E5 | 프롬프트 순서, Layer 1 길이 | `cached_input_share` (캐시 최소 문턱 확인) |
| 3 | E6 | 동시 실행 1 / 2 / 3 | 병렬이 캐시를 깨는지 |
| 4 | E7 | AIME만 n=1 / 3 | 이득 vs 4배 비용 (`run_repeats: 2` 포함) |

**모든 실험의 공통 판정 기준 하나.**

> 같은 예산의 baseline보다 나을 때만 채택한다.

"정확도가 올랐다"로는 부족하다. 같은 토큰을 다른 데 썼을 때보다 나은지를 봐야 한다. 이 트랙은 토큰 효율이 30점이고 동점 처리 기준이므로, 이 기준이 곧 채점 구조다.

그리고 Preflight 회귀 테스트는 실험이 아니라 필수 작업이다. 정상 출력을 반려하는 비율을 먼저 0에 가깝게 만든다.
