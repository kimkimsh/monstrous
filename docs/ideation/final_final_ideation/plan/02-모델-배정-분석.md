## 1. 배정을 강제하는 세 가지 사실

능력 비교표보다 이 셋이 먼저다. 능력은 순위를 바꾸지만, 이 셋은 **선택지를 없앤다.**

### 1-1. 컨텍스트는 고정값이 아니라 배치 크기의 함수다

컴파일된 FXB 번들의 커널 버킷을 읽은 값이다.

| 배치 | Qwen3-32B-FP8 | gpt-oss-120b | K-EXAONE-236B |
|---|---|---|---|
| ≤16 | 40,960 | **131,072** | 262,144 (배치 1·4에서만) |
| 32 | 32,768 | 65,536 | 32,768 |
| **64** | **16,384** | **32,768** | **16,384** |
| 128 | 8,192 | 16,384 | 8,192 |
| 256 | 4,096 | 8,192 | 1,024 |

coding 요청은 **63,812바이트(중앙값) ~ 70,310바이트(최대)**, 토큰으로 약 **17,900~20,300**이다. 배치 64에서 Qwen3-32B와 K-EXAONE은 16,384로 떨어져 **요청 자체가 들어가지 않는다.** gpt-oss-120b만 32,768로 전 구간에서 정확히 2배의 여유를 가진다.

**그리고 배치 크기는 우리가 정하지 않는다.** 그 시각 같은 엔드포인트를 쓰는 모든 팀이 정한다.

이것이 이론이 아니라는 증거가 이 PC에 있다. `squad/test/logs/events.jsonl`, 실행 `76bb50f0`:

```
"request (14082 tokens) exceeds the available context size (4096 tokens)"   ← Planner
"request (13887 tokens) exceeds ..."   ← Code Reviewer,      360 ms
"request (15715 tokens) exceeds ..."   ← Backend Developer,  386 ms
"request (13941 tokens) exceeds ..."   ← Frontend Developer, 370 ms
```

**coding 문항 100%가 이렇게 죽는다.** 그리고 Planner가 죽으면 요청 전문이 전 에이전트에 뿌려져 낭비가 에이전트 수만큼 곱해진다.

> 규칙 1: **요청 전문을 읽는 자리(Router)는 gpt-oss-120b여야 한다.** 다른 선택은 배치 64에서 coding 트랙 전체(가중치 0.5)를 잃는다.

### 1-2. 추론 강도를 에이전트별로 지정할 수단이 없다 — 그리고 이것이 배정을 바꾼다

**[바이너리]** `ModelPreferences` 5개 필드에도, `AgentSettingsOverrides` 6개 필드에도 추론 강도가 없다. 강도는 **앱 전역 설정** `inference.defaultReasoningEffort` 하나이고, **[디스크]** 이 PC의 현재 값은 **`none`**이다.

이것이 능력 비교를 통째로 다시 읽게 만든다.

| 모델 | 강도를 못 정할 때 실제로 얻는 것 |
|---|---|
| **gpt-oss-120b** | `reasoning_effort`가 low/medium/high 셋이고 **기본값은 medium**이다. 파라미터를 안 보내면 medium이 걸린다. **즉 SWE-bench 62.4가 아니라 52.6이 기대값이다** — 그리고 이 52.6은 모델 카드가 `Reasoning: medium`이라고 명시해 둔 바로 그 값이다 |
| **K-EXAONE-236B** | 추론이 **기본으로 켜져 있다.** 92.8 / 83.8 / 80.7이 기본 상태의 수치다. 우리가 아무것도 안 해도 그 값이다 |
| **Qwen3-32B** | 하이브리드, 기본 켜짐. `/think` `/no_think`가 **프롬프트 문자열에서 읽는 소프트 스위치**다 |

> 규칙 2: **설정으로 사야 하는 능력은 못 산다.** gpt-oss-120b의 최고 수치는 전부 `high`에서 나오고, 템플릿에는 `high`를 지정할 통로가 없다. K-EXAONE의 최고 수치는 기본 상태에서 나온다.

이것이 §4-4에서 Solver를 K-EXAONE으로 고정하는 결정적 근거다. 초안이 "MMLU-Pro 83.8 대 80.7, 3.1점 차이에 배율 1.5배"라고 계산했을 때 그 80.7은 **살 수 없는 값이었다.**

#### 다만 gpt-oss에는 프롬프트 통로가 있을 수 있다 — 검증할 가치가 가장 큰 항목

스펙 초안은 *"gpt-oss의 `reasoning_effort`는 소프트 스위치가 없다"*고 적었다. **그 문장은 재검토가 필요하다.** OpenAI 자신의 설명은 이렇다.

> developers can easily set the reasoning effort **with one sentence in the system message**

harmony 형식에서 강도는 시스템 메시지의 `Reasoning: high` 한 줄로 표현된다. 문제는 **우리 `systemPrompt`가 harmony의 어느 자리로 들어가느냐**다. harmony는 `system`과 `developer`를 구분하고, *"the developer message represents what is commonly considered the 'system prompt'"*이므로, 우리 프롬프트는 `developer`로 갈 가능성이 높다. 그러면 `Reasoning:` 줄은 위치를 벗어난다.

**그래도 이것이 이 스쿼드에서 값이 가장 큰 실험이다.** 성공하면 Editor의 SWE-bench 기대값이 **52.6 → 62.4(+9.8%p)**로 오르고, coding 가중치 0.5를 곱하면 **총점 +4.9%p**다. 실패해도 잃는 것은 프롬프트 한 줄이다.

**실험 방법.** Editor의 **Layer 3 첫 줄**(`=== END SQUAD CONTRACT ===` 바로 뒤)에 `Reasoning: high`를 넣는다. Layer 1 앞에 두면 다섯 프롬프트의 바이트 동일성이 깨지므로 그 자리는 안 된다. 개발 세트 coding 13문항을 유/무로 돌려 출력 토큰 수를 본다 — **강도가 실제로 바뀌면 응답 토큰이 8~24배로 늘어나므로**(§2-4) 정확도를 기다릴 것 없이 토큰만 봐도 즉시 판정된다.

**토큰 캡을 먼저 확인해야 한다**(§3). `high`는 GPQA에서 호출당 평균 약 19,300토큰이다. 캡이 낮으면 성공이 곧 `capped` 0점이다.

### 1-3. 모델이 다르면 프리픽스 캐시가 다르다

KV 캐시는 모델 단위 자원이라 서로 다른 모델 사이에서 공유되지 않는다. 다섯 `systemPrompt`의 Layer 1이 바이트 단위로 같게(9,510자, `sha256 126b9dab…`) 설계된 이유가 그것이다.

**gpt-oss-120b를 쓰는 Router · Architect · Editor · Reviewer 넷 사이에서는** 문항 단위 공유가 성립할 수 있다. Solver만 혼자다. 다섯을 한 모델로 통일하면 전부 공유하지만, 그러면 §1-1에 걸린다.

**대가도 적는다.** Furiosa 공식 문서는 하이브리드 어텐션 모델에서 *"cache hits … may be shorter than raw token overlap"*이라고 경고하고, gpt-oss-120b와 K-EXAONE 둘 다 하이브리드다. **깨끗한 radix 경로를 가진 것은 Qwen3-32B 하나뿐이다.** 그래서 캐시 절감을 예산에 미리 넣지 않는다 — `cached_input_share`를 실측하기 전까지 0으로 계산한다.

## 2. 세 모델의 성질

### 2-1. 구조

| | `Qwen3-32B-FP8` | `gpt-oss-120b` | `K-EXAONE-236B-A23B-NVFP4A16` |
|---|---|---|---|
| 비용 배율 *(구두 전달, 기록 없음)* | ×1 | ×2 | ×3 |
| 파라미터 | 32.8B dense | 116.8B 총 / **5.13B 활성** | 236B 총 / **23B 활성** |
| 어텐션 | dense | hybrid (sliding 128 + global, YaRN ×32) | 3:1 hybrid (sliding 36 + global 12) |
| 양자화 | FP8 e4m3 + KV 16-bit | **MXFP4** 전문가층 | **NVFP4** 가중치, 활성·KV 16-bit |
| 프리픽스 캐시 | **깨끗한 radix** | 하이브리드 — 히트가 짧아질 수 있음 | 하이브리드 — 동일 |
| Furiosa 검증 등급 | **Function/Correctness/Performance 전부 PASS** | Performance **EXPERIMENTAL** | Performance **EXPERIMENTAL** |
| 추론 기본 상태 | 켜짐 (`/no_think`로 끌 수 있음) | `reasoning_effort` 기본 medium | 켜짐 |
| 토크나이저 | — | — | **SuperBPE 153,600** |

Qwen3-32B FXB에는 **YaRN이 컴파일돼 있지 않다**(`rope_scaling=None`). 상류 모델 카드의 131,072은 이 배포본에 해당하지 않는다.

### 2-2. 트랙별 능력 — 공개된 수치만

**미공개**로 적은 것은 찾아봤는데 공개된 수치가 없는 것이다. 비슷한 모델의 숫자로 대신 채우지 않았다.

**coding** — SWE-bench Verified가 hidden coding의 다수(150/190), LiveCodeBench가 나머지(40/190)

| | Qwen3-32B | gpt-oss-120b (low / med / **high**) | K-EXAONE |
|---|---|---|---|
| SWE-bench Verified | **미공개** | 47.9 / **52.6** / 62.4 | **49.4** |
| LiveCodeBench | v5 65.7 (thinking) / 31.3 | v6 **81.9** | v6 **80.7** / 44.6 |
| **Aider Polyglot** | **약 40.0** (Aider 자체 하네스) | 24.0 / **34.2** / 44.4 *(출처 충돌, 아래)* | **미공개** |
| Codeforces Elo | 1977 / 1353 | 1595 / **2205** / 2463 | 미공개 |

**Aider Polyglot 항목을 초안에서 두 군데 고쳤다.**

**① Qwen3-32B는 미공개가 아니다.** 초안은 이 칸을 "미공개"로 적고 *"편집 형식 준수를 재는 유일한 공개 지표"*라며 gpt-oss의 근거로 삼았는데, **Aider 자체 리더보드에 Qwen3-32B가 약 40.0으로 올라 있다.** 그러면 gpt-oss가 `medium`(34.2)일 때는 **오히려 Qwen3-32B가 앞선다.** §4-3의 논거를 다시 세워야 했고, 아래에서 그렇게 했다.

**② gpt-oss의 값 자체에도 출처 충돌이 있다.** 24.0 / 34.2 / 44.4는 스펙 초안이 인용한 값이고, HuggingFace 모델 페이지의 커뮤니티 측정([discussions/116](https://huggingface.co/openai/gpt-oss-120b/discussions/116))은 `reasoning_effort: high`에서 **68.4**를 보고한다. 하네스와 설정이 다르므로 **한 표에 섞어 쓰지 않는다.**

> **결론: Aider Polyglot은 이 배정의 근거로 쓸 수 없다.** 세 수치가 서로 다른 하네스에서 나왔고, 우리가 얻는 강도의 값이 상대를 이긴다는 보장이 없다.

**math** — hidden은 MATH-500 level-5 + AIME 2024, `run_repeats: 2`

| | Qwen3-32B | gpt-oss-120b (low / med / high) | K-EXAONE |
|---|---|---|---|
| MATH-500 | **97.2** / 88.6 | 미공개 | 미공개 |
| AIME 2025 | 72.9 / 20.2 | 50.4 / **80.0** / 92.5 | **92.8** (BF16) / 44.6 — **NVFP4에서 88.6, §2-5** |
| GPQA-Diamond | 68.4 / 54.6 | 67.1 / **73.1** / 80.1 | **79.1** / 70.6 |

**generic** — MMLU-Pro. hidden 448~698문항으로 가장 많다

| | Qwen3-32B | gpt-oss-120b (high) | K-EXAONE |
|---|---|---|---|
| MMLU-Pro | **미공개** (base 65.54뿐) | 80.7 | **83.8** / 81.0 |
| MMMLU 한국어 | 70.6 / 51.8 | 82.9 | **85.7** / 83.8 |
| KMMLU-Pro | 미공개 | 62.4 | **67.3** |

**형식 준수** — 이 트랙의 점수가 실제로 갈리는 축

| | Qwen3-32B | gpt-oss-120b | K-EXAONE |
|---|---|---|---|
| IFEval (prompt-strict) | 85.0 / 83.2 | 89.5 | **89.7** / 85.5 |
| **IFBench** | **36.33** | **69.5** | 67.3 |
| BFCL V4 Max Delta (형식 민감도) | **15.5** (26개 순열에서 70.00~85.50%) | 미공개 | 미공개 |

**IFEval은 포화됐다** — 셋이 83~90 안에 몰려 구분이 안 된다. **IFBench가 갈라놓는다: 36 vs 69 vs 67.** IFBench 논문은 *"Qwen3-32B 같은 선도 모델이 50% 미만"*이라며 이 모델을 개선 여지 사례로 직접 지목한다.

### 2-3. 추론을 끄면 벌어지는 일

| 모델 | 끄면 |
|---|---|
| K-EXAONE | AIME 2025 **92.8 → 44.6**, LiveCodeBench v6 **80.7 → 44.6**. 절반 |
| Qwen3-32B | AIME 2025 **72.9 → 20.2**, LiveCodeBench v5 **65.7 → 31.3**. 절반 이하 |
| gpt-oss-120b | 끄는 것이 아니라 강도를 낮추는 것이고, 값이 측정돼 있다 (§2-4) |

**"토큰 아끼려고 추론을 끈다"는 이 세 모델 어디서도 성립하지 않는다.**

### 2-4. gpt-oss-120b의 강도별 토큰 지출

| 평균 CoT+답변 토큰 | low | medium | **high** |
|---|---|---|---|
| AIME 2025 (도구 포함) | 약 1,580 | 약 4,340 | **약 13,260** |
| GPQA Diamond (도구 포함) | 약 810 | 약 3,850 | **약 19,300** |

**low → high가 8~24배다.** 그리고 §1-2대로 우리는 이 손잡이를 못 잡는다.

### 2-5. 공개 수치가 서빙되는 모델의 수치가 아니다 — 그리고 세 모델이 서로 다르다

**이것이 이번 조사에서 나온 가장 중요한 수정이다.** 위 표의 숫자들은 각 모델의 **원본 가중치**에서 측정된 값이고, 우리가 부르는 것은 **양자화된 배포본**이다. 그 격차가 모델마다 다르다.

| 모델 | 공개 수치를 측정한 가중치 | 우리가 부르는 가중치 | 격차 |
|---|---|---|---|
| gpt-oss-120b | **MXFP4** — 전문가층이 처음부터 4.25 bit로 학습된 릴리스 | 같은 MXFP4 | **없음** |
| Qwen3-32B | BF16 | FP8 e4m3 (KV 16-bit) | 미측정 |
| K-EXAONE-236B | **BF16** | **NVFP4 (활성·KV 16-bit)** | **측정됨 — 아래** |

Nota AI가 같은 베이스 모델을 NVFP4로 양자화해 독립 측정한 결과다([blog](https://blog.nota.ai/insights/netspresso-k-exaone-236b-nvfp4)).

| | BF16 (공개 수치) | NVFP4 | 차이 |
|---|---|---|---|
| GPQA-Diamond | 79.1 | 79.80 | +0.7 |
| IFBench | 67.3 | 68.98 | +1.7 |
| **AIME 2025** | **92.8** | **88.57** | **−4.2** |

*"99.2% 정확도 유지"*라고 발표됐지만 그것은 **평균의 비율이지 비율의 평균이 아니고**, 손실이 AIME 하나에 몰려 있다.

**단서 둘을 정확히 단다.** ① 이것은 **NetsPresso**의 NVFP4 양자화이지 FuriosaAI의 것이 아니다. 툴체인이 다르므로 **"NVFP4라는 형식의 비용"을 가리키는 지표이지 Furiosa 빌드의 측정값이 아니다.** ② Furiosa의 레시피는 어텐션·라우터·공유 전문가·MTP·임베딩·layer-0 MLP를 양자화에서 제외하므로 일부를 회복할 수 있다.

> **규칙 3: K-EXAONE의 math 수치는 할인해서 읽는다. gpt-oss의 수치는 할인하지 않는다.** 이것이 §4-4에서 margin이 좁아지는 이유이고, 초안이 "AIME 92.8 대 92.5, 사실상 동률"이라고 적었을 때 실제로는 **88.6 대 92.5**였을 수 있다는 뜻이다.

**FuriosaAI의 1차 자료는 없다.** NVFP4A16 정확도 회복 표를 Furiosa가 공개한 적이 없다. 이것이 이 배정에서 가장 큰 미확인 항목이다.

### 2-6. SuperBPE — 배율 ×3의 실질 부담을 깎는다

K-EXAONE의 토크나이저는 어휘 153,600의 SuperBPE이고, 같은 텍스트에 대해 다른 토크나이저보다 적은 토큰을 쓴다.

| | 절감 |
|---|---|
| 한국어 | **−29.0%** |
| 코드 | **−26.7%** |
| 영어 | **−19.6%** |

우리 math·generic 입력은 영어이므로 **−19.6%**가 적용된다. 명목 배율 ×3이 실효 약 **×2.4**로 내려온다.

## 3. 주최 측 경고 — 배정 전체를 위협한다

리더보드 Comparability 절 원문이다.

> every run on this page executed under a **per-item wall-clock cap** and a **per-run token cap**, identical for every team … **Two of the three evaluation models are reasoning models — one was measured spending 97% of its output budget on reasoning tokens before it answered — so a token cap bites roughly an order of magnitude harder on a squad built from reasoning models than on one built from an instruct model.**

**우리 배정은 다섯 자리 전부가 추론 모델이다.** 캡 값이 공개되지 않았으므로 이 배정은 아직 검증되지 않았다. 그래서 순서를 정한다.

1. 첫 실행의 `PublishedCaps`(`per_run_token_cap`, `per_item_wallclock_seconds`)를 읽는다.
2. 캡 초과가 관측되면 §7의 절약 단계를 위에서부터 실행한다. **잘린 답은 정확도가 아니라 `capped` 0점이다.**

## 4. 자리별 분석

각 자리마다 세 모델을 전부 놓고, 채택 이유가 아니라 **탈락 이유**를 먼저 적는다.

### 4-1. Router (Planner)

| | Qwen3-32B ×1 | gpt-oss-120b ×2 | K-EXAONE ×3 |
|---|---|---|---|
| 배치 64 컨텍스트 | **16,384 — coding 요청이 안 들어감** | 32,768 — 들어감 | **16,384 — 안 들어감** |
| 하는 일과의 적합 | 위치 지정. 긴 사고 불필요 | 같음 | 같음 |
| 소계 (§7) | 6.55M | **13.11M** | 약 19.7M |
| 판정 | **탈락 — 적재 실패** | **채택** | **탈락 — 적재 실패 + 최고가** |

**두 모델이 능력이 아니라 적재로 탈락한다.** Router는 요청 전문을 보는 유일한 컴포넌트이고, 그 자리에서 컨텍스트가 모자라면 문항이 0점이 아니라 **스쿼드 전체가 브로드캐스트로 무너진다.**

**대가는 정확히 이것이다.** Router는 전 트랙 889회 실행에서 전부 돌고, ×2를 무는 소계 13.11M은 총액 40.0M의 **33%**로 다섯 자리 중 최대다. math·generic 699건에 대해서만 싼 모델을 쓸 방법은 없다 — `preferredModelId`가 에이전트당 하나이기 때문이다. 그 대가가 약 **4.15M**이고, 이것이 "템플릿 하나" 제약의 실제 가격이다.

여기에 문헌 근거가 겹친다. RULER(17개 모델) 실측에서 실효 컨텍스트는 광고값의 **½~¼**이고, Router가 하는 일 — 발췌 10~22개 중 실제로 고칠 1~2군데 찾기 — 은 NoLiMa가 측정한 **비문자적 검색**이다. 32K에서 13개 모델 중 11개가 단문 기준선의 절반 아래로 떨어진 바로 그 태스크다. **즉 32,768은 넉넉한 값이 아니라 최소한이다.**

### 4-2. Architect

| | Qwen3-32B ×1 | gpt-oss-120b ×2 | K-EXAONE ×3 |
|---|---|---|---|
| 필요 컨텍스트 | 약 3.5K — 셋 다 충분 | 충분 | 충분 |
| SWE-bench Verified | **미공개** | **52.6** (medium 기대값) | 49.4 |
| 캐시 | 혼자 다른 모델이 됨 | **Router·Editor·Reviewer와 공유** | 혼자 |
| 소계 | 1.14M | **2.28M** | 약 3.4M |
| 판정 | 탈락 — 능력 미상 + 캐시 분열 | **채택** | 탈락 — 능력이 낮고 값이 비쌈 |

Architect가 받는 것은 앵커 2~3개, 약 2KB다. **컨텍스트는 제약이 아니다.** 그러니 이 자리는 순수하게 능력과 캐시로 정해진다.

능력 쪽은 **gpt-oss 52.6 대 K-EXAONE 49.4**로 3.2점 차이인데, K-EXAONE은 배율이 1.5배다. 그리고 Qwen3-32B는 이 벤치마크 수치를 공개한 적이 없어 **비교 자체가 불가능하다** — 미공개를 "아마 비슷할 것"으로 읽지 않는다.

캐시 쪽이 결정적이다. Architect를 다른 모델로 두면 Layer 1(약 1,800토큰)을 그 모델에서 **혼자 다시 계산**한다. 셋 중 어느 쪽으로 바꿔도 gpt-oss 세 자리와의 공유가 깨진다.

**이 자리 자체가 아직 값을 증명하지 못했다는 것도 적는다.** Architect / Editor 분할의 근거인 SWE-Edit 실험은 **도구를 쓰는 Viewer**가 있던 구성에서 나왔고, 우리는 도구가 없다. §10-E3b가 "분할이 값을 하는가"를 재는 실험이고, 절약 단계 S5가 이 자리를 통째로 빼는 손잡이다.

### 4-3. Editor

| | Qwen3-32B ×1 | gpt-oss-120b ×2 | K-EXAONE ×3 |
|---|---|---|---|
| **SWE-bench Verified** (coding의 150/190) | **미공개** | **52.6** (medium) | 49.4 (BF16) |
| Aider Polyglot | 약 40.0 | 34.2 (medium) / 44.4 (high) | 미공개 |
| LiveCodeBench (신규 작성, 40/190) | v5 65.7 | v6 **81.9** | v6 80.7 |
| **IFBench** (형식 지시 준수) | **36.33** | **69.5** | 67.3 |
| 필요 컨텍스트 | 앵커 약 3K 또는 지문 3K — 셋 다 충분 | 충분 | 충분 |
| 캐시 | 혼자 다른 모델 | **Router·Architect·Reviewer와 공유** | 혼자 |
| 소계 | 2.47M | **6.46M** | 약 9.7M |
| 판정 | 탈락 | **채택** | 탈락 |

**여기가 벤치마크 40점의 절반이 걸린 자리다.** 그리고 **컨텍스트가 제약이 아닌 자리**이기도 하다 — Editor는 플랜 A에서 앵커 약 3KB를, 플랜 B에서 LiveCodeBench 지문 1,999~3,066바이트를 받는다. 셋 다 들어간다. **그래서 §1-1의 적재 논거가 여기서는 안 통하고, 순수하게 능력으로 정해야 한다.**

**초안의 논거는 무너졌다.** 초안은 *"Aider Polyglot 44.4 — 편집 형식 준수를 재는 유일한 공개 지표"*로 이 자리를 샀는데, 둘 다 틀렸다. Qwen3-32B에도 값이 있고(약 40.0), 44.4는 우리가 못 사는 `high`의 값이다. **medium의 34.2는 Qwen3-32B의 40.0보다 낮다.**

**그래도 gpt-oss-120b가 맞다. 근거를 세 개로 다시 세운다.**

**① SWE-bench Verified가 이 트랙의 다수다.** hidden coding 약 190건 중 SWE-bench가 150건, LiveCodeBench가 40건이다. gpt-oss는 medium에서 **52.6**을 공개했고 — 모델 카드가 `Reasoning: medium`이라고 명시해 둔 값이다 — **Qwen3-32B는 이 벤치마크 수치를 공개한 적이 없다.** 78%를 차지하는 하위 트랙에서 비교가 아예 불가능한 모델을 고를 수 없다.

**② IFBench 36.33 대 69.5.** Editor의 실제 작업은 "발췌의 줄을 공백 하나까지 그대로 복사해 세 마커 사이에 넣고, 마커를 0열에서 시작한다"이다. **이것은 추론이 아니라 형식 지시 준수다.** 그리고 그 능력을 재는 지표에서 Qwen3-32B는 **세 모델 중 압도적 최하위**이고, BFCL V4 Max Delta 15.5는 형식만 바꿔도 정확도가 15.5점 흔들린다는 뜻이다. IFBench 논문이 *"Qwen3-32B 같은 선도 모델이 50% 미만"*이라며 이 모델을 개선 여지 사례로 직접 지목한다.

**③ 캐시.** Editor를 다른 모델로 두면 Layer 1(약 1,800토큰)을 혼자 다시 계산하고, gpt-oss 세 자리와의 문항 내 공유가 깨진다.

형식이 능력보다 먼저인 이유는 측정돼 있다. Aider 실측에서 유연한 패치 적용을 끄면 **편집 오류가 9배**로 늘었고, 같은 글에서 GPT-4 Turbo가 편집 형식만 바꾸자 통과율이 **20% → 61%**로 뛰었다. 형식별 성공률 비교(6개 태스크 평균)에서도 unified diff 19.34~30.28 대 search/replace **45.89~56.69**로 갈린다.

> **"SWE-bench 62.4를 산다"고 말하지 않는다. 사는 것은 52.6이고, 그 위에 IFBench 69.5와 캐시 공유가 얹힌다.** 62.4는 §1-2의 실험이 성공했을 때만 되살아난다.

### 4-4. Solver

| | Qwen3-32B ×1 | gpt-oss-120b ×2 | K-EXAONE ×3 |
|---|---|---|---|
| MMLU-Pro (= generic, 지출 72%) | **미공개** (base 65.54) | 80.7 (**high에서만**) | **83.8** |
| AIME 2025 | 72.9 | 80.0 (medium) / 92.5 (high) | 92.8 BF16 → **약 88.6 NVFP4** |
| MATH-500 | **97.2** | 미공개 | 미공개 |
| IFEval prompt-strict | 85.0 | 89.5 | **89.7** |
| 강도 의존성 | 켜짐이 기본 | **최고 수치가 전부 high** | **기본 상태가 최고 수치** |
| 공개 수치 = 서빙 수치? | 미측정 (BF16→FP8) | **예** (MXFP4 네이티브) | **아니오** (BF16→NVFP4, §2-5) |
| 토크나이저 절감 | — | — | **영어 −19.6%** |
| 소계 | 3.17M | 약 5.4M | **8.05M** |
| 판정 | 탈락 — generic 능력 미상 | 탈락 — 살 수 없는 수치 | **채택, 단 margin이 좁다** |

math와 generic은 **합쳐서 벤치마크 가중치의 0.5**인데 **토큰 지출은 전체의 15% 미만**이다. 입력이 300~900자로 짧기 때문이다. **배율 3을 감당할 수 있는 유일한 자리다.**

**gpt-oss-120b가 탈락하는 이유가 §1-2다.** 표의 80.7은 `high`에서만 나오는 값이고, medium에서의 MMLU-Pro는 공개돼 있지 않다. AIME도 92.5(high) 대 80.0(medium)으로 12.5점이 강도에 걸려 있다. **우리가 못 만지는 설정에 걸린 수치로 3.1점 차이를 계산하는 것은 계산이 아니다.**

**Qwen3-32B는 MATH-500 97.2로 math 하나만 보면 매력적이다.** 그런데 이 자리는 math와 generic을 둘 다 맡고, generic 쪽 사후학습 수치가 **미공개**다(base 65.54는 사후학습 전 값이라 비교에 쓸 수 없다). 그리고 지출은 generic 쪽이 크다 — Solver 소계 8.05M 중 generic이 5.80M, math가 2.25M이다. **큰 쪽이 미상인 모델을 고를 수 없다.**

#### 이 결정에 대한 가장 강한 반론 — 그리고 왜 그래도 K-EXAONE인가

**반론:** K-EXAONE이 세 모델 중 확실히 이기는 축은 **한국어**다 — KMMLU-Pro 67.3 대 62.4, MMMLU-ko 85.7 대 82.9, 그리고 SuperBPE의 한국어 −29.0%. **그런데 우리 세 트랙에 한국어가 없다.** MMLU-Pro도 MATH-500도 AIME도 SWE-bench도 전부 영어다. 게다가 §2-5대로 math 수치를 할인하면 AIME는 88.6이 되어 gpt-oss high 92.5에 진다. 그리고 이 모델은 이미 세대가 지났다 — 후속 모델 K-EXAONE 2.0(750B)이 같은 SWE-bench에서 **68.2 대 49.4**를 낸다.

**답:** 세 가지가 반론을 넘긴다.

1. **비교 대상이 `high`가 아니다.** AIME 92.5도 MMLU-Pro 80.7도 gpt-oss `high`의 값이고, 우리는 그 강도를 지정할 수 없다(§1-2). 우리가 실제로 얻는 medium에서는 AIME **80.0**이고, MMLU-Pro의 medium 값은 **공개돼 있지 않다.** 88.6 대 80.0이면 K-EXAONE이 여전히 앞선다.
2. **지출이 큰 쪽은 generic이고, 거기서는 NVFP4 손실이 관측되지 않았다.** Solver 소계 8.05M 중 generic이 5.80M(72%)이다. §2-5의 측정에서 GPQA-Diamond(+0.7)와 IFBench(+1.7)는 오히려 올랐고, 손실은 AIME 하나에 몰렸다. **MMLU-Pro 83.8은 할인 대상이 아닐 가능성이 높다** — 다만 이것은 추론이고, MMLU-Pro의 NVFP4 측정값은 없다.
3. **세대가 지났다는 것은 배정 결정이 아니다.** 후속 750B는 FuriosaAI가 빌드를 공개하지 않았다. **선택지는 셋뿐이다.**

**이 반론이 뒤집히는 조건은 하나다** — `reasoning_effort`를 지정할 수 있게 되는 것(§1-2의 실험). 그렇게 되면 gpt-oss `high`가 AIME 92.5·MMLU-Pro 80.7을 배율 ×2에 내놓으므로, math 트랙은 gpt-oss로 넘어가고 generic만 다시 계산해야 한다.

#### 이 자리에 붙는 위험

**① `<think>` 태그가 응답에 그대로 실린다 — 메커니즘이 끝까지 추적됐다.**

채팅 템플릿이 프롬프트 끝에 **여는 태그를 미리 넣는다.**

| `enable_thinking` | 프롬프트 끝 |
|---|---|
| `True` 또는 생략 | `<\|assistant\|>\n<think>\n` — **여는 태그가 프롬프트에 있다** |
| `False` | `<\|assistant\|>\n<think>\n\n</think>\n\n` — 빈 블록으로 미리 닫는다 |

그래서 모델은 `추론 → </think> → 답변` 순으로 내고 **여는 태그를 절대 생성하지 않는다.** 그런데 vLLM의 `deepseek_v3` 파서는 `chat_kwargs.get("enable_thinking", False)` — **기본값이 False**라 `IdentityReasoningParser`로 떨어지고, 완성문 전체를 `content`로 돌려준다. **템플릿의 기본값과 파서의 기본값이 서로 어긋나는 것이 버그의 전부다.**

그리고 `<think>`(id 54)와 `</think>`(id 55)가 `tokenizer_config.json`에 **`"special": false`로 등록**돼 있어서 `skip_special_tokens=True`로도 안 걷힌다. 재현이 두 번 보고됐다 — [HF discussion #5](https://huggingface.co/LGAI-EXAONE/K-EXAONE-236B-A23B/discussions/5)(LG 인정)와 Elice Cloud의 [운영 장애](https://forum.elice.io/t/k-exaone-236b-a23b-api-think/109).

**우리에게 이것이 얼마나 나쁜가 — 정확히 적는다.** 채점기는 **마지막** 매치를 쓰고 답 블록 앞은 무시되므로, `</think>`가 본문에 섞여도 **답 블록이 마지막에 있으면 점수는 살아남는다.** 그리고 추론 토큰은 `reasoning` 필드에 있든 `content`에 있든 **똑같이 과금된다.** 즉 이 누출은 토큰 비용을 늘리지 않고, 형식 위험만 늘린다. **그 형식 위험을 막는 것이 정확히 Reviewer의 일이다**(§4-5).

**② Furiosa 검증 등급이 Performance EXPERIMENTAL이다.**

**③ Furiosa 모델 카드의 이식성 주장이 의심스럽다.** 카드는 이 가중치가 *"vLLM, SGLang, Transformers에서도 바로 돈다"*고 적지만, `config.json`이 **옛 표기 `ExaoneMoEForCausalLM`**을 선언하고(vLLM 레지스트리에는 새 표기만 있다) `sliding_windows` 등 vLLM이 **fallback 없이 읽는 키 셋이 빠져 있다.** **Furiosa-LLM 위에서는 문제없다**(FXB가 그 경로를 안 탄다). 못 믿을 것은 이식성 주장 쪽이다.

**④ 컨텍스트 262,144은 배치 1·4에서만 나온다.** 배치 32면 32,768이다. **우리 math/generic 입력은 1K 미만이라 문제없다.**

### 4-5. Reviewer

| | Qwen3-32B ×1 | gpt-oss-120b ×2 | K-EXAONE ×3 |
|---|---|---|---|
| **IFBench** (형식 지시 준수) | **36.33** | **69.5** | 67.3 |
| BFCL Max Delta (형식 민감도) | **15.5 — 나쁨** | 미공개 | 미공개 |
| 내용 판정 (coding) | 미공개 | 52.6 | 49.4 |
| 캐시 | 혼자 다른 모델 | **셋과 공유** | 혼자 |
| 소계 | **5.05M** | **10.10M** | 약 15.1M |
| 판정 | 탈락 — 이 자리에 가장 나쁜 지표 | **채택** | 탈락 — 값이 비싸고 IFBench가 더 낮음 |

Reviewer는 전 트랙 889회 실행 전부에서 돌고, 소계 10.10M은 총액의 **25%**다. **가장 크게 아낄 수 있는 자리이고, 그래서 가장 신중하게 봐야 하는 자리다.**

싼 쪽으로 내리면 5.05M을 아낀다. 총액의 12.6%다. 그 대가가 이것이다.

- **IFBench 36.33 대 69.5.** 이 자리가 하는 일이 정확히 "요구된 형식을 지켰는지 판정하고, 그 형식으로 다시 발행하는 것"이다.
- **BFCL V4 Max Delta 15.5** — 같은 과제를 형식만 바꿔 26번 물었을 때 정확도가 70.00~85.50%로 **15.5점 벌어졌다**는 뜻이다. 형식을 판정하라고 앉힌 자리에서 형식에 흔들리는 모델을 쓰는 셈이다.
- **`<think>` 태그 누출.** Qwen3-32B는 `enable_thinking=True`면 `/no_think`를 써도 항상 `<think>…</think>` 블록을 낸다(모델 카드 명시). 닫는 태그가 빠지는 사례가 보고돼 있고([QwenLM/Qwen3#1459](https://github.com/QwenLM/Qwen3/issues/1459)), 그러면 서빙 계층이 응답 전체를 추론으로 분류해 **`content`를 비운다.** `<think>` 블록을 안 걷어내면 IFEval prompt-strict가 **83.2 → 63.40**으로 20점 떨어진 것도 보고돼 있다([#1563](https://github.com/QwenLM/Qwen3/issues/1563)).

**마지막 항목이 결정적이다.** Reviewer는 마지막 웨이브를 혼자 차지하고, 그 출력이 채점되는 바이트다. 그 자리에서 `content`가 비면 그 문항은 `extraction_failed`다.

**K-EXAONE이 탈락하는 이유는 단순하다.** IFBench가 67.3으로 gpt-oss보다 낮고 배율은 1.5배 높다. 그리고 캐시를 혼자 쓰게 된다.

**`/no_think`는 템플릿에서 뺐다.** Qwen3 계열 채팅 템플릿이 읽는 소프트 스위치라 gpt-oss-120b에서는 아무 일도 하지 않는 죽은 문자열이다. 절약 단계 S4로 Qwen3-32B에 되돌릴 때만 Layer 3 첫 줄에 다시 넣는다 — Layer 1 앞에 두면 다섯 프롬프트의 바이트 동일성이 깨진다.

## 5. Qwen3-32B가 한 자리도 못 받은 것을 정면으로 본다

배율 ×1로 가장 싼 모델이고, **세 모델 중 유일하게 Furiosa 검증 등급이 전 항목 PASS**이며, **유일하게 깨끗한 radix 프리픽스 캐시 경로**를 가진다. 그런데 한 자리도 못 받았다. 근거를 자리별로 다시 모으면 이렇다.

| 자리 | 탈락 사유 | 이 사유를 뒤집을 관측 |
|---|---|---|
| Router | 배치 64에서 컨텍스트 16,384 < 요청 17,900~20,300 | `GET /v1/models`가 실제 `max_context_len`을 크게 보고하고, 배치가 32 이하로 유지된다는 확인 |
| Architect | SWE-bench Verified **미공개** — 비교 불가 | 우리 개발 세트 13문항에서 직접 측정 (§10-E3b와 같이) |
| Editor | SWE-bench Verified **미공개**(coding의 78%), IFBench **36.33** | 개발 세트에서 `format_ok` 비율과 SWE-bench 통과율 직접 측정. **Aider Polyglot은 약 40.0으로 오히려 gpt-oss medium(34.2)보다 높다** — 이 자리의 근거는 Aider가 아니다 |
| Solver | MMLU-Pro 사후학습 수치 **미공개**, generic이 Solver 지출의 72% | 개발 세트 28문항 측정. 단 1문항이 3.6%p라 방향만 본다 |
| Reviewer | IFBench **36.33**, BFCL Max Delta 15.5, `<think>` 누출 경로 셋 | 없음 — 이 자리에 대해서는 공개 수치가 명확히 반대 방향이다 |

**핵심 사유가 대부분 "미공개"다.** 이것은 "Qwen3-32B가 나쁘다"가 아니라 **"근거 없이 배율 1을 고를 수 없다"**는 뜻이다. 그리고 절약 단계 S1~S5(§7)가 전부 이 모델로 내려가는 계단이다. **순위를 보고 내려간다.**

**내려갈 때 알아야 할 것 둘.** ① Qwen3-32B의 강점인 **깨끗한 프리픽스 캐시는 thinking 모드에서만 성립한다** — non-thinking 모드가 캐시를 깨뜨리는 이슈가 보고돼 있다([QwenLM/Qwen3#1826](https://github.com/QwenLM/Qwen3/issues/1826)). 즉 `/no_think`로 토큰을 아끼려는 순간 캐시 이득이 사라진다. **두 장점이 서로 배타적이다.** ② 같은 모드에서 structured output도 깨진다([vllm#18819](https://github.com/vllm-project/vllm/issues/18819)) — 우리는 structured output을 안 쓰므로 해당 없음이다(§5-2).

### 5-1. 내려가기 전에 — 세 모델 모두에 걸린 지뢰 하나. structured output은 쓰지 않는다

Furiosa-LLM은 정규식·JSON Schema·CFG로 출력을 강제하는 structured output을 지원한다. 답 형식이 정규식으로 정의된 이 트랙에서 매력적으로 보이지만, **쓰지 않는다.**

- Furiosa의 기본 백엔드 llguidance와 `openai_gptoss` 조합이 알려진 실패다([vllm#37359](https://github.com/vllm-project/vllm/issues/37359))
- gpt-oss를 `json_schema` strict로 돌리면 응답 앞에 쓰레기가 붙는 비율이 약 **27%**로 보고됐다([vllm#43338](https://github.com/vllm-project/vllm/issues/43338))
- Furiosa는 **추론이 켜져 있으면 `--structured-outputs-backend xgrammar` 지정을 조용히 무시한다.** 우리 다섯 자리는 전부 추론 모델이다

그리고 설계 쪽 근거가 이미 있다 — 응답 전체를 구조화하면 추론이 깎이고, 우리 계약은 **마지막 블록에만 형식을 건다.**

## 6. 이 배정이 사는 것과 그 값

hidden 1회 submission run 기준 개략치다. 문항 수는 coding 190, generic 573, math 63×2=126 실행, 호출당 고정 오버헤드 2,000토큰을 포함했다.

| 에이전트 | 모델·배율 | coding | generic | math | 소계 |
|---|---|---|---|---|---|
| Router | gpt-oss ×2 | 8.96M | 3.44M | 0.71M | **13.11M** |
| Architect | gpt-oss ×2 | 2.28M | — | — | **2.28M** |
| Editor | gpt-oss ×2 | 6.46M | — | — | **6.46M** |
| Solver | K-EXAONE ×3 | — | 5.80M | 2.25M | **8.05M** |
| Reviewer | gpt-oss ×2 | 4.18M | 4.12M | 1.80M | **10.10M** |
| | | | | **합계** | **약 40.0M** |

Solver 소계는 SuperBPE의 영어 −19.6%를 반영해 낮춰 잡았다. 전 에이전트 Qwen3-32B ×1 구성은 약 **18.4M**이므로 **이 배정은 그것의 2.2배다.**

그 2.2배로 사는 것을 정확히 적으면 이렇다.

| 사는 것 | 근거 수치 |
|---|---|
| **coding이 아예 실행된다** | 배치 64에서 Qwen3-32B 컨텍스트 16,384 < 요청 17,900~20,300. 이것은 정확도가 아니라 **가부**의 문제다 |
| coding 정확도 | SWE-bench Verified **52.6**(medium, coding의 78%). Qwen3-32B는 이 벤치마크 수치를 공개한 적이 없다 |
| generic 정확도 | MMLU-Pro **83.8**. Qwen3-32B 사후학습 수치 미공개 |
| math 정확도 | AIME 2025 **약 88.6**(NVFP4 할인 후) 대 72.9 — **+15.7%p** |
| **형식 준수** | IFBench **69.5 / 67.3** 대 **36.33**. Editor와 Reviewer 두 자리가 여기에 걸려 있다 |

**사지 못하는 것도 적는다** — Aider Polyglot은 근거가 아니다(§2-2). gpt-oss의 `high` 수치(SWE-bench 62.4, AIME 92.5, MMLU-Pro 80.7)도 §1-2의 실험이 성공하기 전에는 사는 것이 아니다.

**판단 기준.** 벤치마크 40점도 토큰 효율 30점도 **둘 다 순위 기반**이고, 토큰은 벤치마크 동점 처리의 1순위이기도 하다. 그래서 절대 목표치가 없고, "얼마 썼나"가 아니라 **"쓴 만큼 순위가 올라갔나"**만이 옳은 질문이다.

## 7. 절약 계단 — 순위를 보고 내려간다

| 단계 | 바꾸는 것 | 절감 | 잃는 것 |
|---|---|---|---|
| **S1** | Reviewer를 Qwen3-32B ×1로 | **약 5.05M** (12.6%) | IFBench 36.33, BFCL Max Delta 15.5, `<think>` 누출 경로. §10-E4가 재는 손잡이 |
| **S2** | Solver를 gpt-oss ×2로 | 약 2.7M | MMLU-Pro 83.8 → 80.7 — **단 그 80.7은 `high`에서만 나온다**(§1-2). 실제로는 더 잃을 수 있다 |
| **S3** | 플랜 A에서 Architect를 뺀다 (호출 4회 → 3회) | 약 2.28M | 형제 호출자를 남겨 두는 실패로 돌아간다. §10-E3b가 재는 손잡이 |
| **S4** | Router를 Qwen3-32B ×1로 | 약 6.6M | **배치 64에서 coding 요청 실패.** 배치가 32 이하로 유지된다는 관측이 있을 때만 |
| **S5** | 전 에이전트 Qwen3-32B ×1 | 약 21.6M | 위 전부 |

**S1을 맨 위에 둔 이유:** 절감이 가장 크고(12.6%), 그것을 재는 실험(E4)이 가장 싸고(연습 세트 재실행), 잃는 것이 `extraction_failed` 비율이라는 **하나의 숫자로 측정된다.**

**S4를 아래에 둔 이유:** 절감은 두 번째로 크지만, 잃는 것이 정확도가 아니라 **가부**다. 배치 크기는 우리 통제 밖이므로 이 단계는 실측 없이 실행하지 않는다.
