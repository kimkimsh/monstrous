## 0. 이 기획안이 하는 일

`docs/ideation/final_final_ideation/spec/`가 **무엇을 만들지**를 정했다. 이 기획안은 그 위에서 **JSON 설정 계층을 다시 정한다.**

기존 템플릿에서 비어 있던 자리는 이랬다.

```json
"tools": [],
"toolConfig": { "enabledTools": [], "disabledTools": [],
                "toolPermissionOverrides": {}, "customToolConfigs": {} },
"modelPreferences": { "preferredModelId": "furiosa-ai/gpt-oss-120b",
                      "minContextWindow": null,
                      "requiresToolCalling": false, "requiresVision": false },
"memoryEnabled": false
```

이 값들이 **맞는 값인지, 게으른 기본값인지**를 가르는 것이 이번 작업의 전부였다. 조사 결과 셋으로 갈렸다.

| 판정 | 필드 | 근거의 성격 |
|---|---|---|
| **채운다** | `disabledTools`(22개), `toolPermissionOverrides`(22개) | 비용 0. 다만 스쿼드 실행 경로에서 **무효**임을 확인했다 — 기록이지 방어선이 아니다 |
| **비운 채로 두되 근거를 바꾼다** | `minContextWindow`, `requiresToolCalling`, `requiresVision` | 초안은 "이 필터가 우리 모델을 배제한다"였다. 실제로는 **애초에 아무 일도 하지 않는다.** 값은 같고 이유가 다르다 |
| **비운 것이 옳다 — 근거가 더 세졌다** | `enabledTools`, `memoryEnabled`, `customToolConfigs` | 실행 로그에서 **도구가 답을 죽인 사례 2건**, 메모리가 환각을 영구화한 사례 2건을 찾았다 |

전부 `01-JSON-필드-결정표.md`에 필드 단위로 있다.

그리고 사용자가 따로 지목한 것 하나 — **에이전트별 모델 선택**은 `02-모델-배정-분석.md` 한 문서 전체가 다룬다. 자리 5개 × 모델 3개를 전부 놓고, 채택 이유가 아니라 **탈락 이유**부터 적었다.

## 1. 조사 방법 — 무엇을 근거로 삼았나

이 기획안의 결론 대부분은 **문서가 아니라 이 PC의 실물**에서 나왔다. 문서만 근거인 주장은 그렇게 표시했다.

| 출처 | 무엇을 얻었나 |
|---|---|
| **앱 바이너리 디스어셈블리** (`backend-ai-go`, 77.8MB, arm64, 심볼 9만 개) | 도구 결정 경로 전문, 모델 배정 경로 전문, 임포트 한도 상수, serde 필드 목록 |
| **이 PC의 앱 데이터** | `providers.json`(모델 3종), `model-metadata.yaml`(컨텍스트·capabilities), `capabilities.db`(행 0개), `settings.json`(메모리 설정), 빌트인 템플릿 5개, 빌트인 에이전트 프로필 4개 |
| **실제 실행 로그** (`squad/test`, `squad/test_2`, `squad/ikkim`) | 실행 21건, 태스크 50개, 토큰 실측, 실패 사례 |
| **Lablup 공식 매뉴얼** (`go.backend.ai/ko/manual/`) | 템플릿 스키마, 도구 레지스트리 31개, 예산 문서 |
| **공개 JSON Schema** (`lablup/agent-catalog`) | `ToolPermission` 열거형 4종, `customToolConfigs` 정의 |
| 이 저장소의 트랙 자료·리서치 노트 | 채점 규칙, 벤치마크 수치, 문헌 근거 |

**초안 스펙의 방법론 결함 하나를 고쳤다.** `spec/01-플랫폼-사실.md`는 여러 필드 목록을 "바이너리에서 이름들이 붙어 있다"는 관찰로 유도했다. 그 추론은 성립하지 않는다 — Rust/LLVM은 문자열 리터럴을 **구조체 순서가 아니라 길이별로** 묶는다. 실제로 오프셋 49953100에는 `create_directory`, `audio_transcribe`, `get_current_time`, `Unexpected Crash`, `--repeat-penalty`가 나란히 있다. 전부 정확히 16자이고 서로 아무 관계가 없다.

그래서 필드 목록은 전부 **serde field visitor 함수**에서 다시 뽑았다. 결과적으로 초안이 주장한 개수는 전부 맞았지만, **이제는 추측이 아니라 증명이다.**

## 3. 가장 크게 바뀐 판단 — 도구

### 3-1. 초안의 근거는 "평가 중에는 도구가 없다"였다

맞는 말이지만 **약한 근거다.** 평가에 도구가 없다면 도구를 선언해도 손해가 없다는 반론이 성립한다.

### 3-2. 실제 근거는 로그에 있었다

이 PC의 실행 21건 중 **9건이 채점 가능한 답을 내지 못했다.** 그중 둘의 원인이 도구다.

```
squad/test_2  실행 13a35667
  artifacts/final_answer.txt  →  "Final amount: **≈ $32,328**"     ← 정답
  응답 본문                    →  \boxed{} 없음. extraction_failed

squad/test    실행 5e3813da
  워크스페이스                 →  완결된 solution.py (908바이트)
  응답 본문                    →  마크다운 코드 펜스. 패치 마커 없음
```

> **채점기는 응답 본문을 읽지, 워크스페이스를 열지 않는다.** `write_file`이 열려 있으면 모델은 "산출물을 만들었다"고 판단하고 응답에는 요약만 쓴다.

**그리고 도구 호출은 로그에 전혀 안 남는다.** 전 워크스페이스에서 `tool_use` / `tool_calls` / `toolName` 키가 **0건**인데, `squad:workspace-file-changed` 이벤트와 실제 파일은 남아 있다. **`write_file`은 가장 많이 쓰인 도구이면서 호출 기록이 하나도 없는 도구다.**

### 3-3. 그리고 `enabledTools: []`가 실제로 도구를 0개로 만든다

**[바이너리]** `squad::agent_turn::build_tools_for_agent`(`0x101d920fc`)는 `effective_enabled_tools`의 결과가 비면 **곧장 반환한다.** 도구 목록 없이 모델을 부른다. 추측이 아니라 분기 하나다.

같은 조사에서 `disabledTools`가 **읽히지 않는다는 것**도 확인했다(`effective_enabled_tools`는 문자열 슬라이스 하나만 받는다). 그래서 22개를 채우되 **그것이 방어선이 아니라 기록이라고 적었다.**

## 4. 두 번째로 크게 바뀐 판단 — `modelPreferences`의 세 필드

초안의 논리는 이랬다. *"`minContextWindow`를 채우면 앱 카탈로그가 gpt-oss-120b를 2048로 알고 있으므로 우리 모델이 배제되고, Planner가 모델을 잃으면 요청 전문이 브로드캐스트된다."*

**결론은 맞고 전제는 틀렸다.** 모델 배정 경로 전체가 함수 둘이고, 둘 다 컨텍스트도 capabilities도 읽지 않는다.

```
resolve_agent_readiness (0x101da3db4)
  → Option 판별자 한 번 검사. preferredModelId가 있으면 그대로 반환
  → 없으면 앱 기본 모델. 그것도 없으면 "No model is configured for …" 에러

resolve_model_id_with_source (0x101cfa88c)
  → 후보 문자열 둘을 trim, 빈 것과 리터럴 "default"를 걸러 첫 번째 반환
```

**그러니 `minContextWindow` · `requiresToolCalling` · `requiresVision` · `preferredProviderId` 넷 다 1.12.1에서 무효다.**

이것이 값을 바꿀 이유가 되지는 않는다. 무효인 필드에 값을 넣는 것은 둘 중 하나다 — 아무 일도 안 하거나, **앱이 업데이트되어 배선되는 순간 그 값대로 작동하거나.** 그래서 기준을 "배선되면 어떻게 되는가"로 바꿔 다시 골랐고, 답은 같았다.

- `minContextWindow: null` — 배선되면 카탈로그의 `gpt-oss-120b: context_window 2048`이 우리 모델 넷을 탈락시킨다
- `requiresToolCalling: false` — 배선되면 카탈로그의 `gpt-oss-120b: ["chat","code"]`(tool 없음)가 세 모델 중 둘을 탈락시킨다. **스키마 기본값이 `true`라 반드시 명시한다**
- `requiresVision: false` — 배선되면 `true`는 세 모델 전부를 탈락시킨다

**바뀐 것은 문장이 아니라 확신의 근거다.** 초안은 "그럴 것이다"였고 지금은 "지금은 아니고, 되면 이렇게 된다"다.

## 5. 새로 찾은 사실 하나 — `role`이 Planner 프롬프트를 바꾼다

**[바이너리]** 팀 명단 빌더 근처에 role 설명 네 줄이 리터럴로 박혀 있다. 바로 옆이 `No description`과 `No agents available.`이라 같은 함수가 쓴다는 것이 드러난다.

```
Coordinator — decomposes and distributes tasks
Developer   — writes and modifies code
Reviewer    — reviews code and ensures quality
Writer      — creates documentation and content
```

**즉 `role: "Reviewer"`는 Planner의 팀 명단에 "reviews code and ensures quality"를 싣는다.** 우리 Reviewer는 math·generic 문항에서도 마지막 웨이브를 혼자 맡는데, 그 문항들에는 코드가 없다. **"코드를 리뷰한다"는 설명이 math 문항에서 Planner를 헷갈리게 할 수 있다.**

**그럼에도 바꾸지 않았다.** custom으로 바꿔도 그 자리에 우리 문장이 들어가지는 않는다 — 위 리터럴 넷 밖의 값을 넣을 통로가 없고, custom은 `No description`이 된다. **"틀린 한 줄"과 "설명 없음"의 교환이므로, 먼저 재고 나서 바꾸는 것이 옳다.** `03-검증과-배포.md` 점검표 9번이 그 측정이다.

## 6. 프롬프트에 대한 제안 — 이번 판에서는 실행하지 않았다

이 기획안의 작업 범위는 JSON 설정 계층이고, 프롬프트는 스펙의 산출물이다. **바꾸지 않았다.** 다만 조사 중에 나온 제안 셋을 남긴다. 실행 전에 §10의 측정이 먼저다.

**[2026-08-23 갱신]** 아래 표의 1·2·3·4번과, 이후 검토에서 새로 나온 결함 다섯을 `squad-template.json`에 반영했다. Layer 1은 9,510자 → **10,292자**(`sha256 c5fec0a204c33189`)가 됐고 다섯 프롬프트의 바이트 동일성은 유지된다.

| # | 실행한 것 | 무엇이 문제였나 |
|---|---|---|
| **K** | **Solver MATH 절에서 간결 압박 제거 + 2차 검산 절차** | hidden 실측이 math **13문항**이다. 1문항이 총점 **1.92%p**로 generic 1문항의 7.4배, coding 1문항의 1.46배인데, 프롬프트는 그 트랙에 *"shortest chain of steps"*를 걸고 generic에는 *"as many as needed"*를 주고 있었다. 초안의 126 대 573 가정에서는 맞았고 13 대 96에서는 반대다. 게다가 출처가 **HMMT Feb 2026 + AIME 2026**이고 토큰 캡은 `null`이다 |
| A | Layer 1 첫 줄 *"exactly three tracks"* → *"three named tracks, and has to survive a fourth thing the harness has not named"* | 아홉 줄 뒤의 *"There are four answers"*와 정면 충돌. `other` 트랙 전체가 그 한 문장에 눌린다 |
| B | Layer 1의 math worked example 교체 (`\boxed{32349}` → `\boxed{204800}`) | 그 예시는 연습 문항 `math-visible-0017` 그대로였고 **답이 틀렸다.** 24000 × 1.01³⁰ = 32348.37이고 gold는 `\$32,\!348`인데, 예시는 존재하지 않는 중간값 32348.67을 거쳐 32349로 반올림한다. 추출 가능한 자리에 실제 문항의 오답이 있었다 |
| C | Layer 1 *"There are no tools during evaluation"* → Planner의 태스크 도구를 예외로 명시 | Router가 곧 Planner다. "도구가 없다"는 단언이 `create_task` 호출을 억제하면 그것이 요청 전문 브로드캐스트(문항당 약 100K 토큰)다 |
| D | Layer 1 ledger 규칙에 예외 한 줄 + `\boxed{` 경고 | Reviewer의 `stop` 판정은 **아무것도 안 내야** 채점기가 앞 웨이브로 떨어진다. 그런데 ledger 줄은 필수였다 — ledger만 있는 응답은 빈 응답이 아니라서 그것이 답으로 채점된다. `BOXED_RE`가 줄 고정이 아니라는 사실도 같이 적었다 |
| E | Router: 4,000자 상한 → 앵커 예산 약 8,000자, 지문은 상한 밖 | 실측 `coding-visible-0055`의 합성 요청이 4,512자라 플랜 B가 성립하지 않았고, SWE-bench 3건은 **앵커를 붙이기 전에** 이슈 본문만으로 상한을 넘었다. 유일한 탈출구가 "지문을 줄이는 것"이었는데 그게 이 설계가 막으려는 바로 그 실패다 |
| F | Router: 발췌 헤더의 `not shown in this file:` 절을 앵커와 함께 넘기게 함 | 실제 헤더 132개 중 109개가 그 절을 단다. 그 이름들이 Architect의 "보이지 않는 호출자" 판정의 유일한 무료 단서다 |
| G | Architect: 앵커 블록을 **원문 그대로 다시 실어** 끝내게 함 · Router: `T3 -> Reviewer, depends_on [T1, T2]` | 플랜 A에서 앵커가 실리는 곳은 T1(Architect) 설명뿐인데 Architect는 원문 재출력이 금지돼 있었다. **Editor가 SEARCH를 복사할 원본을 못 받는다** — SWE-bench 전 문항이 여기서 죽는다. Reviewer도 같은 이유로 "앵커에 없는 심볼인가"를 판정할 수 없었다 |
| H | Editor: LiveCodeBench 실행 방식을 **두 형태**로 분기 | 연습 7건 중 3건이 *"The judge imports your file and calls the entry point … read nothing from standard input"*인데, 프롬프트는 "stdin을 읽어라"만 알고 있었다. 정확히 반대 지시다 |
| I | Solver: ledger `track` 열거에 `other` 추가, 표기 보존 문장 추가 | 열거가 `math\|generic` 둘뿐이라 `other` 문항에서 모델이 스스로를 generic이라 적고 `ANSWER:` 형식을 끌어 쓴다. 그리고 gold 24건이 통화·구간·대분수 표기를 그대로 요구한다 |
| J | Reviewer: `stop`에서 ledger까지 억제, `fix`를 인용이 아닌 범주로 | D와 짝이다. `fix`에 `FINAL ANSWER: \boxed{`를 인용하면 그 ledger가 답이 된다 |

아래는 원래의 제안 표다. 4번은 여전히 실험이고 실행하지 않았다.

| # | 제안 | 근거 | 왜 지금 안 하나 |
|---|---|---|---|
| 1 | ~~Layer 1의 *"exactly three tracks"*~~ | | **실행함 (A).** "동시에 고쳐야 한다"는 사유가 애초에 약했다 — Layer 1은 어차피 다섯 곳에 같은 문자열이고, 그 동일성은 `validate_template.py`가 매번 `sha256`으로 검사한다 |
| 2 | Layer 1의 worked example이 그 자체로 추출된다 — `ANSWER: C`와 `\boxed{32349}` | 모델이 시스템 프롬프트를 되뱉으면 채점기가 그것을 답으로 읽는다 | **방어할 방법이 없다.** 정답 예시가 실제 마커를 보여 줘야 하기 때문이다. 다만 채점기는 **마지막** 매치를 쓰고 Reviewer 계약이 "블록 뒤에 아무것도 쓰지 마라"이므로 노출이 작다. §8-X5가 간접적으로 잡는다 |
| 3 | Reviewer 프롬프트에 `<think>` 누출 대응을 한 줄 넣는다 | 세 모델 모두 `content`가 비는 경로가 공개 이슈로 보고돼 있다 | 프롬프트로 막을 수 있는 실패인지 미확인. §9-2 점검표 12가 먼저다 |
| 4 | **Editor의 Layer 3 첫 줄에 `Reasoning: high`를 넣는다** | OpenAI 원문: *"developers can easily set the reasoning effort with one sentence in the system message."* 성공하면 Editor SWE-bench 기대값 **52.6 → 62.4**, coding 가중치 0.5를 곱해 **총점 +4.9%p** | harmony가 `system`과 `developer`를 구분하고 우리 프롬프트는 `developer`로 갈 가능성이 높다. **그래도 이 스쿼드에서 값이 가장 큰 실험이다** — 판정이 싸다(응답 토큰이 8~24배로 늘면 성공). 단 `PublishedCaps`를 먼저 읽어야 한다. `high`는 호출당 약 19,300토큰이라 캡이 낮으면 성공이 곧 `capped` 0점이다. 자세히는 `02-모델-배정-분석.md` §1-2 |
