**Monstrous Squad** answers AI:GO benchmark items with three agents, and ships a single-file viewer that says which runs would have scored.

## The squad

```
item ──► Router ──create_task──► Coder   patches, from-scratch programs
                             └─► Solver  math, multiple choice, anything else
                                           └─► this output is graded
```

Three agents, one model (`furiosa-ai/gpt-oss-120b`), one wave, two model calls per item.

**Why one wave.** The grader reads one thing: the output of the last task. The runtime's `finalResult` is a status summary and gets rejected, 28 times out of 28. So the task that writes the answer must be the last task, and every hop we put after it was measured losing the answer. An agent holding tools saved its answer to a workspace file and replied "done"; the grader never opens the workspace. A reviewer placed last rewrote an answer for a question it never received.

**Why not one agent.** Only the planner sees the request body, so that seat stays. Router and Solver split over prompt length: the patch-format rules take 7,698 characters, which a merged agent would carry through all 109 non-coding items of a 147-item hidden set. Head count is also a blast radius: when the planner call fails the app hands the whole request, median 63,812 bytes on coding, to every seat.

## The brief's four questions

**Who reads the code.** Router, copying the request into the task character for character. A coding item's 60,000-character excerpt bundle will not fit, so it ranks excerpts by how directly the issue reaches them and copies about 32,000 characters. It drops a whole excerpt instead of trimming one.

**Who modifies it.** Coder, holding no tools. A path or line number not in the text it received is invented, and invented patches do not apply.

**Who verifies.** Nobody as a separate hop. Verification moved into the same response, so it costs no extra call: Solver re-derives its value a second way, Coder checks the sibling callers of what it touched. And into the build, as a program. `tools/validate_template.py` runs the grader's own extractors (`extract_letter`, `extract_boxed`, `extract_patch`) against all six prompt files, and refuses to emit if any of them pulls an answer out of our instructions. That check exists because v1 failed it: those prompts hand the extractors `letter=C` and `boxed=204800`.

**When to give up.** No agent can decide it: the plan graph is fixed before execution and has no conditional branch. So it is four rules. Router creates exactly one task, never replans, and stops copying at 32,000 characters. The worker cuts a long derivation off and writes its best current value, since a truncated response carries no answer line. And empty responses are banned, because with one wave there is no earlier wave to fall back to.

## What v1 cost us

v1 placed 23rd of 24, overall 0.0925. The leaderboard API gave us the autopsy. 1,192 requests, 8.1 per item. 5,368,135 input tokens, the most of any team. Five system prompts averaging about 3,670 tokens, 81% of that input. Of 76 task files on disk, the 63 the planner actually wrote mention the answer format zero times.

v2 answers those line by line: three agents, one model, no shared preamble, `enabledTools: []` everywhere, memory off. Running the practice set through the new prompts gives about 294 requests and 2.12M tokens. That is an estimate, not a result; we have no score for v2 yet.

## The viewer

One HTML file. No install, no server, zero external requests. Drop a workspace folder on it.

The top gauge is the question it was built for: **AI:GO success against gradable.** The app calls a run finished when its tasks finish; the submission server calls it scored when the response body carries the required answer format. The gap is where the score goes.

Zero is not one thing either. The viewer splits it four ways and names the fixer in words, not color alone: call rejected (config), undecided (checker), no answer format (prompt), not an item (nothing to fix). The first three leave the denominator.

It draws nothing that is not in the logs, so there is no cache-hit rate and no per-task token chart: those fields come back empty. Estimates are labeled, and the cut-line figure is stated on screen as an upper bound on loss.

It also corrected us. A fifth zero class, "contract not sent", had been blaming the runner for 8 runs. On screen those requests ran 83 to 499 bytes, and the contract clause alone is about 250, so it was never there to send. We deleted the class and gradable went from 6/15 to 12/22. Nothing improved; we had been counting wrong.

The redesign replaced every screen and changed no data. The 1,105 lines that parse, judge, aggregate, load and export were copied byte for byte from the old viewer, and the build refuses to emit if one of them differs. Same folder in, same JSON export out, byte identical.
