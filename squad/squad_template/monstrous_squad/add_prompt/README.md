# add_prompt — 트랙별 one-shot 프롬프트 3개

제출물의 나머지 절반이다. 포털은 **Squad Template JSON 1개 + 트랙별 one-shot 프롬프트 3개**를 받는다.

| 파일 | 붙는 트랙 | 크기 |
|---|---|---|
| `coding.txt` | SWE-bench Lite + LiveCodeBench v6 (hidden 38문항) | 5,938자 |
| `math.txt` | HMMT Feb 2026 + AIME 2026 (hidden 13문항) | 2,902자 |
| `generic.txt` | MMLU-Pro + GPQA (hidden 96문항) | 2,609자 |

**이 폴더가 원본이다.** `docs/resource/example_task/prompts/`에 같은 파일이 있는 것은 로컬 하네스(`compose.py`)의 기본 경로이기 때문이고, `validate_template.py`가 두 벌이 어긋나면 실패한다. 고칠 자리는 여기 하나다.

## 합성되는 방식

세 파일 모두 **맨 끝에 `{{TASK}}`가 정확히 한 번** 있다. 서버는 이렇게 조립한다(`compose.py:31-33` 실측).

```
[이 파일 전문, {{TASK}}는 문항 본문으로 치환]
                                          ← 서버가 빈 줄 하나
=== REQUIRED OUTPUT ===
<트랙별 형식 지시>
```

그래서 실제 순서는 **우리 프롬프트 → 문항 → REQUIRED OUTPUT 블록**이다. 두 가지가 여기서 따라온다.

- **`{{TASK}}`를 두 번 쓰면 문항이 두 번 들어간다.** 입력 토큰이 그대로 2배다. 검사기가 개수를 센다.
- **`{{TASK}}`가 맨 끝이라 우리 프롬프트가 통째로 안정 프리픽스다.** 한 트랙 안에서 바이트가 완전히 같으므로 프리픽스 캐시가 걸릴 수 있는 유일한 구간이고, 순서를 바꾸면 그 성질이 사라진다.
- REQUIRED OUTPUT 블록은 서버가 붙이므로 여기 다시 적지 않는다. 세 파일이 형식을 한 번씩 되짚는 것은 중복이 아니라 **모델이 문항을 읽기 전에 계약을 먼저 보게 하려는 것**이고, 서버 블록이 맨 뒤에서 그것을 다시 못 박는다.

## 되뱉기 안전성 — 실측

모델이 프롬프트를 응답에 그대로 복사하면 그 안의 예시가 답으로 추출될 수 있다. 실제 채점기 함수에 세 파일을 그대로 먹여 확인했다.

| 파일 | `extract_letter` | `extract_boxed` | `parse_edit_blocks` |
|---|---|---|---|
| `coding.txt` | None | None | **0 blocks** |
| `math.txt` | None | `<answer>` | 마커 없음 |
| `generic.txt` | None | None | 마커 없음 |

`coding.txt`의 패치 예시 두 개는 **일부러 4칸 들여썼다.** `extract_patch`는 들여쓴 `*** PATCH START ***`도 찾지만 `parse_edit_blocks`는 세 내부 마커를 `startswith`로 재기 때문에, 되뱉어도 0블록으로 파싱된다. 순서를 바꾸거나 들여쓰기를 펴면 이 성질이 깨진다.

`math.txt`의 `<answer>`는 없앨 수 없다 — 계약을 보여주려면 `FINAL ANSWER: \boxed{` 리터럴을 써야 하고, `BOXED_RE`는 줄 고정이 아니다. 다만 **서버가 뒤에 붙이는 REQUIRED OUTPUT 블록에 같은 리터럴이 있고 그쪽이 더 뒤**라 우리가 늘리는 위험은 0이다. 추출되더라도 `<answer>`는 값이 아니라 오답이 된다.

`generic.txt`는 초안에서 계약 예시를 `ANSWER: X`로 썼다가 그것이 `LETTER_RE`에 걸리는 것을 발견해 `<letter>`로 바꿨다. 서버 블록도 `<letter>`라 매칭되지 않는다.

## 세 파일이 공통으로 하는 것

- **무엇이 채점되는지 먼저 말한다.** 프로그램이 정규식으로 뽑고, 추론은 안 읽고, LLM 심판은 없다.
- **0점이 되는 경로를 이름으로 나열한다.** "형식을 지켜라"가 아니라 *"굵게 쓰면 매칭이 안 된다"*처럼 실패를 구체적으로 적는다.
- **답 블록 앞은 감점이 없다고 명시한다.** 캡이 없으므로(실측 `per_run_token_cap: null`) 추론을 아낄 이유가 없고, 아끼는 대상은 서두·자기소개·문제 재진술이다.
- **도구가 없다고 못 박는다.** 실행해서 확인하겠다는 계획을 세우는 것 자체가 낭비다.

## 트랙별로 다르게 한 것과 그 근거

**`coding.txt`가 가장 길다.** hidden 38문항에 가중치 0.5이고, 리더보드 10개 실행에서 **아무도 정확도 0.263을 못 넘었다.** 그 분포는 "고칠 줄 모른다"보다 "패치가 적용이 안 된다"에 가깝다. 그래서 파서가 실제로 강제하는 것 — 세 내부 마커의 0열, SEARCH 바이트 일치, 파일 내 유일성, 블록 사이 산문이 조용히 path로 읽히는 것, `=` 7개 이상으로 시작하는 줄이 섹션을 끊는 것 — 을 전부 이름으로 적었다. 요청이 63KB라 이 길이는 잡음 수준이다.

**LiveCodeBench 실행 방식 두 가지를 다 싣는다.** 연습 7건 중 4건은 *"runs your file as a program"*(stdin을 읽는다), 3건은 *"imports your file and calls the entry point"*(**stdin을 읽지 않는다**)다. 정반대이고, 틀리면 알고리즘이 맞아도 0점이다.

**`math.txt`는 간결 압박을 걸지 않는다.** hidden math는 **13문항**뿐인데 1문항이 총점 **1.92%p**로 generic 1문항(0.26%p)의 7.4배, coding 1문항(1.32%p)의 1.46배다. 게다가 2026년 대회 문제라 어느 모델의 학습 데이터에도 없다(1위 팀도 0.538). 그래서 2단계로 **다른 경로의 검산**을 시키고, 답 형태 제약은 "형식 문제가 아니라 값이 틀린 것"으로 읽게 했다. 13문항에 추론을 더 쓰는 비용은 총액의 2% 미만이다.

**`generic.txt`는 추론을 반드시 켠다.** 객관식이라 답만 뽑고 싶어지지만 MMLU-Pro에서 direct answering은 CoT 대비 큰 폭으로 진다. 다만 96문항이라 프롬프트 길이가 여기서 가장 비싸므로, 절차를 다섯 줄로 눌렀다. 보기 개수를 **하드코딩하지 않는다** — 연습 42문항에서 3·4·7·8·9·10개가 섞여 있었고 항상 A~J도 아니다.

## 고칠 때

```bash
python3 ../tools/validate_template.py ../squad-template.json
```

`{{TASK}}` 개수·위치, 하네스 사본과의 동기화를 검사한다. 세 파일을 고치면 하네스 쪽(`docs/resource/example_task/prompts/`)에도 같은 내용을 복사해야 검사를 통과한다.
