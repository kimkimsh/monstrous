# auto_test — 설계

AI:GO 스쿼드에 연습 문항을 자동으로 넣고, 토큰과 정확도를 보는 데스크톱 도구.

## 왜 이게 필요한가

지금 `example_task/tools/run_agent_batch.py`로 터미널에서 돌릴 수는 있다. 그런데 프롬프트를 깎아가며 반복하는 작업에서는
① 어떤 문항을 돌릴지 매번 플래그로 지정해야 하고 ② 결과를 보려면 별도로 `grade.py`를 돌려야 하고 ③ 실행 중에는 아무것도 안 보인다.
문항 고르기 · 실행 · 채점 · 토큰 집계를 한 화면에서 하면 그 순환이 짧아진다.

## 구성

```
auto_test/
├── app.py                  진입점 + 창 전체 (PySide6)
├── core/
│   ├── samples.py          test_sample 로드·검증
│   ├── runner.py           aigo CLI 래퍼 (세션 격리, 취소 가능)
│   ├── grading.py          grade.py 어댑터
│   └── session.py          실행 오케스트레이션 + 집계
├── tools/
│   ├── build_samples.py    example_task → test_sample 생성기
│   └── smoke_runner.py     runner 실동작 확인
├── test_sample/{coding,math,generic}/*.json
├── runs/                   실행 결과 자동 저장
├── SAMPLE_SPEC.md          샘플 규격
└── pyproject.toml          uv 관리 (PySide6, math-verify)
```

## 동작

### 검사 (Check) — LLM을 부르지 않는다

무료이고 원하는 만큼 반복할 수 있어야 한다. 확인 항목:

| 항목 | 실패 시 |
|---|---|
| `aigo` 실행 파일 존재 | 경로를 알려주고 중단 |
| 서버 health | `router`/`pool` 중 무엇이 죽었는지 표시 |
| 스쿼드·에이전트 선택됨 | 어느 쪽이 비었는지 표시 |
| 에이전트 모델이 서빙 중인가 | 모델 id와 `loaded list` 대조 |
| 샘플 로드·스키마·sha256 | 깨진 파일 경로와 사유 나열 |
| 선택 항목 중 채점 불가 개수 | 개수와 사유 표시 (막지는 않음) |

### 실행 (Run)

선택 항목을 **순차** 실행한다. 병렬은 안 한다 — 로컬 모델 서버가 하나고, 동시 요청은 슬롯 경합으로 지연만 늘린다.

문항마다: `squad session new` → `squad message` → `squad conversation` 폴링 → 채점 → 행 갱신.

세션을 문항마다 새로 파는 것이 핵심이다. 재사용하면 앞 문항의 질문과 답이 다음 프롬프트에 그대로 남는다.
math 3문항 실측: 세션 공유 7,635 tok, 세션 격리 2,940 tok. 토큰만 부푸는 게 아니라 앞 답이 새서 연습 점수가 무의미해진다.

중지 버튼은 폴링 사이에서 걸린다. 이미 끝난 문항 결과는 남긴다.

### 결과 분류 — 여기가 제일 틀리기 쉽다

정확도의 분모를 뭘로 잡느냐가 측정 전체를 좌우한다.

| 결과 | 뜻 | 정확도 분모 | 표시 |
|---|---|---|---|
| `graded` correct | 맞음 | 포함 | PASS |
| `graded` incorrect | 틀림 | 포함 | FAIL |
| `extraction_failed` | 형식을 못 맞춰서 답을 못 뽑음 | **포함** | FAIL (형식) |
| `format_ok` | swebench — 패치 형식은 맞지만 로컬에서 채점 불가 | **제외** | 채점 불가 |
| `error` / `no_reply` | CLI 실패, 타임아웃, 서버 장애 | **제외** | 실행 실패 |

`extraction_failed`를 분모에 넣는 이유: 포털이 그걸 0점으로 센다. 형식을 못 맞추는 것은 실제 실점이다.
`error`를 분모에서 빼는 이유: 인프라 장애는 오답이 아니다. 섞으면 서버가 흔들린 날의 점수가 프롬프트 품질처럼 보인다.

두 숫자를 따로 보여준다. 하나로 합치면 어느 쪽이 나빠졌는지 알 수 없다.

### 저장

실행이 끝나면 `runs/<타임스탬프>.jsonl`에 자동 저장한다. 각 줄은 `grade.py`가 그대로 먹는 형태
(`item_id`, `track`, `output`, `status`, `prompt_tokens`, `completion_tokens`, `wallclock_seconds`)로 쓴다.
GUI가 죽어도 결과가 남고, 터미널 채점기와 대조할 수 있다.

## 스레딩

Qt 위젯은 메인 스레드에서만 만진다. 실행은 `QThread` 워커 하나가 문항을 순차로 돌고,
`itemStarted` / `itemFinished` / `runFinished` 시그널로만 UI에 닿는다. 취소는 `threading.Event`.

워커가 위젯을 직접 건드리면 그 자리에서 안 죽고 나중에 엉뚱한 곳에서 죽는다. 그래서 워커는 순수 데이터만 내보낸다.

## 안 만드는 것

- 플러그인 구조, 전략 등록기, 설정 레이어 — 구현이 하나뿐인 자리에 인터페이스를 두지 않는다
- 재시도 로직 — 기록되지 않는 재시도는 인프라 장애를 정확도 하락으로 둔갑시킨다. 실패는 실패로 남기고 사람이 다시 돌린다
- 병렬 실행 — 위 이유
- 원격 모델 전환 UI — 과금 대상이라 실수로 누를 수 있는 자리에 두지 않는다

## 리뷰에서 나온 수정 사항

### UI를 파일 하나로 합친다

원래 `ui/main_window.py` · `ui/models.py` · `ui/theme.py`로 나눠 두었다. 되돌린다.
`theme.py`는 색상 상수 몇 개뿐이고, `models.py`의 테이블 모델은 창 하나만 쓴다.
구현이 하나뿐인 자리에 경계를 그으면 파일만 늘고 얻는 게 없다. `app.py` 하나로 간다.

`core/`의 네 모듈은 유지한다. 각각 Qt 없이 단독으로 테스트할 수 있고, 실제로 테스트가 붙는다.

### 결과는 끝날 때가 아니라 문항마다 쓴다

원래 "실행이 끝나면 `runs/<타임스탬프>.jsonl`에 저장"이었다. 121문항이 20~40분 걸리는데,
그동안 GUI가 죽거나 사람이 창을 닫으면 전부 날아간다. 문항이 끝날 때마다 한 줄씩 append하고 flush한다.

### 취소가 걸리는 최대 지연을 계산해 둔다

중지 버튼은 폴링 사이에서만 걸린다. 그런데 진행 중인 `aigo` 서브프로세스는 그 자체의 타임아웃까지 안 끝난다.
그래서 CLI 호출 하나의 타임아웃을 문항 타임아웃보다 훨씬 짧게 잡는다.

```
문항 타임아웃 300s
 ├ session new     CLI 타임아웃 30s
 ├ message         CLI 타임아웃 60s
 └ conversation    CLI 타임아웃 30s, 5s 간격 폴링
최악의 취소 지연 = 진행 중인 CLI 호출 하나 = 60s
```

이 숫자를 코드에 상수로 두고, 화면에도 "중지 요청됨 — 현재 문항 끝나면 멈춤"으로 표시한다.
버튼을 눌렀는데 아무 일도 안 일어나는 것처럼 보이는 게 제일 나쁘다.

### 결과 행마다 스쿼드·에이전트·모델을 박는다

실행 중간에 스쿼드나 에이전트를 바꾸면, 이미 나온 행의 숫자는 다른 조건에서 나온 것이다.
그런데 화면에는 똑같이 남아 있어서 한 표처럼 보인다. 행마다 어느 조건에서 나온 결과인지 기록하고,
한 화면에 조건이 섞이면 요약줄에 표시한다.

### 토큰과 정확도의 모수가 다르다는 것을 화면에 쓴다

토큰은 **시도한 모든 문항**의 합이다. 실패한 문항도 토큰은 썼다.
정확도는 **채점된 문항**만의 비율이다. 두 숫자의 모수가 다르므로 요약줄에 그렇게 적는다.

```
채점 2/3 · 정확도 66.7%   ← 분모 = graded + extraction_failed
채점 불가 1               ← swebench
실행 실패 0               ← 타임아웃·CLI 오류
토큰 2,940               ← 분모 = 시도한 전부
```

### 확인한 것 — 70KB 프롬프트를 CLI 인자로 넘기는 게 되는가

`aigo squad message <squad> <agent> <TEXT>`에 프롬프트를 인자로 넘긴다.
가장 큰 샘플은 `coding-visible-0017.swebench.txt`로 **70,310 bytes**다.

실측: 이 크기를 그대로 넘겼을 때 exec는 통과하고, 오류는 API 계층에서만 났다
(`Model not found: No active session for agent ...`). macOS `ARG_MAX`는 1,048,576이라 14배 여유가 있다.

한계에 부딪히면 증상이 "인자 목록이 너무 깁니다"라 원인을 찾기 쉽다. 지금은 문제 없다.

### 테스트에 하나 추가

집계 로직 자체를 테스트한다. `graded` / `extraction_failed` / `format_ok` / `error`를 섞은
가짜 결과를 넣어서 정확도 분모, 채점 불가 개수, 실행 실패 개수, 토큰 합계가 맞는지 본다.
여기가 조용히 틀리기 가장 쉬운 자리다 — 숫자가 그럴듯하게 나오면 아무도 의심하지 않는다.
